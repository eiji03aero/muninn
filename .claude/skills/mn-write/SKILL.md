# mn-write: お題 → 執筆 → 講評 → 改稿 → 作品

CLAUDE.md の規約（命名・タグ・**コミット運用**）に必ず従うこと。
目的は **ユーザー自身の文章力を伸ばす** こと。作品を仕上げることではなく、**書く人が上手くなること**が成果物。

## 絶対原則（これを破ると仕組みごと無価値になる）

1. **代筆しない。** 書き換えた完成文・修正案の全文を出さない。出すのは**観点**と、必要なら**使える素材（部品）**まで。
   ユーザーが「書き直して」と言っても、まず「観点だけ渡す」を提案する。それでも明確に頼まれたら従うが、
   その稿は `rounds` に**採点を記録しない**（自分の実力の記録ではないため）。
   **例外は確定後の「別解」だけ**——`status: done` にした作品について書き手から
   「同じ題材をどう書くか」を明示的に頼まれた場合に限り、比較教材として別解を書いてよい。
   確定前には絶対に出さない（書き手が自分で出すはずの答えを潰すため）。
   別解は完成稿の下に `## 参考: 別解（Claude 版・採点対象外）` として置き、**`rounds` には記録しない**。
   優劣を競うのではなく「切り取りの違いとその代償」を示すのが目的なので、
   **確定稿より良いと思ったら正直にそう書き、悪いと思ったらその理由も書く**。
2. **毎回、固定の5軸で採点する。** `writings/rubric.md` が軸の正本。軸を勝手に増減しない。
   軸が動くと「上達したか」が測れなくなる——これがこの仕組みを作った最大の理由。
3. **重点は毎回1つだけ。** 観点は複数書いてよいが、「次の1稿で直すのはこれ」は必ず1つに絞る。
4. **お世辞を書かない。** 点が上がっていないのに「良くなりました」と書かない。褒めるのは実際に機能している箇所だけ。
5. **過去の稿と点を書き換えない。** 版は追記のみ。推敲の軌跡そのものが資産。
   **あとで採点が誤りだったと分かっても、点は書き換えず、訂正を追記で示す**（訂正の履歴も資産）。
6. **自分の読みを実測より信用しない。** 文脈を持った側の「読める」は、読者の「読めた」ではない。
   毎稿コールドリードを回し、**食い違ったら実測を採る**（→「講評の3役」）。

## これは何concernか（間違えないこと）

- **writings（このskill）** = **自分が書いたものを推敲して上手くなる**。1作品＝1ファイルに版を積む。
- **follows（mn-follow）** = 1対象を定点観測して変遷を追う。**似ているが単位が違う**——follows は日付が単位、
  writings は**作品が単位**（同じ作品の3稿が3ファイルに散らないこと自体が要件）。
- **logs（mn-log）** = 多数の別々の項目を同じスキーマで貯める台帳。作品は「1回で終わらない」ので logs では受けられない。
- **notes（mn-research）** = 講評で出た**汎用の作法**の蒸留先。作品固有の話は piece に留める。

## データ構造

```
writings/
  rubric.md              # kind: rubric。評価軸の正本（5軸・各1〜5点）
  prompts.md             # kind: prompts。お題ストック（在庫と進行中）
  pieces/<slug>.md       # kind: piece。1作品1ファイル。お題＋全版＋各版の講評
```

- `<slug>` は kebab-case（例: `oyachumi-no-jikan`）。作品名が決まっていなければお題の特徴で仮置きし、完成時に見直す。
- piece は `templates/writing-piece.md` に従う。`kind: piece`（`srs` は付けない＝クイズ対象外）。
- **画像・音声はコミットしない**（follows / atlas と同じ）。

## 6つのモード（文脈で判断する）

### A. お題を出す（「お題ちょうだい」）

1. `writings/prompts.md` の在庫から、**鍛えたい軸**に合うものを1つ選んで提示する。
   ユーザーが軸を指定しなければ、直近の piece の低い軸を狙って選ぶ（弱点から潰す）。
2. お題には必ず **狙う軸・縛り・目安の字数** を付ける。「なんでもいいから書いて」は上達が遅い。
3. 着手が決まったら `prompts.md` の表を `active` にし、piece を作る（Mode B へ）。
4. **在庫が3本を切ったら補充を提案する**（お題を考える手間で書く気が萎えるのを防ぐ）。

### B. 初稿を受け取る（メインループの入口）

1. **最新化と日付確認**: `git fetch origin` → ローカル `main` を最新化。**`date` を実行して今日の日付を確認する**
   （セッションは日をまたいで再開されるので、会話の最初に見た日付を使い回すと必ずずれる）。
2. `writings/pieces/<slug>.md` を `templates/writing-piece.md` から作成。お題・`target_axes` を埋める。
3. **設定と前提を先に聞く（重要）**: その作品の設定・狙い・この先の展開を確認し、`## 作品メモ（設定）` に書く。
   **一節に書かれていない設定は、こちらからは絶対に分からない。**推測で講評すると重点を丸ごと外す
   （実際に外した——書き手は「娘が逆再生で戻ってくる」つもりだったのに、こちらは「娘が失われた」と読んで
   1稿ぶん見当違いの重点を渡した）。書き手が言語化していなければ「どういう話にするつもり？」と一言聞く。
   聞くのは設定と狙いだけで、**どう書くかは聞かない**（それは書き手の領分）。
   あわせて **「これは改稿する前提か、すでに公開・提出済みか」** を確認する。
   公開済みならモードE（改稿しない講評）に切り替える。
4. 初稿を **`## v1` に原文のまま**貼る。誤字も直さない（軌跡が資産）。
   誤字・表記ゆれ・一人称の揺れは**本文は直さず、講評で指摘する**（文体・声の軸に効く事故なので、黙って直すと採点が嘘になる）。
5. **コールドリードを回す**（上記「講評の3役」）。Agent を2人以上並列で、**本文だけ**を渡す。
   結果を `## 読者テスト` に記録する。**採点より先にこれをやる**——先に自分で採点すると、
   その点を守る方向にコールドリードを解釈してしまう。
6. **講評を書く**（下記「講評の書き方」）→ `rounds` に採点を追記。
   コールドリードで出た「詰まった箇所」は、**自分が気づいていなくても観点に入れる**。
7. commit & push。

### C. 改稿を受け取る（ループを回す）

1. 日付確認 → `## v2`（v3, v4...）として本文を追記。
2. **前回の重点が実際に効いたかを最初に判定する**。効いていなければ「効いていない」と正直に書く。
   ここを曖昧にすると、毎回違う場所を殴るだけの講評になる。
3. **コールドリードを回す**（モードB手順5と同じ。毎稿やる——前稿で読めたものが今稿で読めなくなることがある）。
4. 5軸を再採点し、**前回との差分を必ず表で示す**（どこが伸びてどこが落ちたか）。
   1つ直すと別の軸が落ちることは普通に起きる。それを見えるようにするのが固定軸の効能。
5. 次の1稿の重点を1つ渡す。**もう十分なら「これで完成でいいと思う」と言う**——延々と推敲させない。
6. commit & push。

### D. 作品として確定する（「これで完成」）

1. `status: done` にし、確定稿を `## 完成稿` に置く（版の履歴は上に残す）。
2. **総括を書く**: 初稿から何が変わったか、どの軸が何点伸びたか、次の作品に持ち越す課題。
3. `writings/prompts.md` の該当行を `done` にし、piece へリンクを張る。
4. **汎用の作法を `notes/` に蒸留する**（下記「蒸留」）。
5. `moc/home.md` の作品一覧に載っているか確認 → commit & push。

### E. 既発表・改稿しない作品の講評（「もう公開済みなので直さない」）

書き手が**すでに公開・提出した作品**を持ち込むことがある。この場合は改稿ループを回さない。

1. piece を作り、**`status: done`・1稿のみ**で記録する（作品メモに「既発表・改稿なし」と明記）。
2. 5軸で採点し、講評は通常どおり書く。**採点を省かない**——上達の記録としての価値は改稿の有無と無関係。
3. **「次の1稿の重点」は渡さない。** 代わりに `### 次の作品に持ち越す観点` として書く。
   直せない作品に直し方を渡すのは、書き手にとってただの後悔製造機なので、
   **必ず「次に書くときに効く観点」の形に変換する**。
4. 総括で、**過去作との比較**を必ず入れる。既発表作品は「今の素の実力」のサンプルなので、
   前作で潰した癖が出ていないかを見るのに最も価値がある。
5. 蒸留 → commit & push。

**注意**: 持ち込まれた時点で公開済みと分かっていないことがある（改稿の重点を渡したあとに
「実はもう公開済み」と判明する）。**初稿を受け取るとき、モードBの設定確認と一緒に
「これは改稿する前提か、もう出したものか」を聞く**と空振りが減る。

### F. 振り返り（「今どれくらい伸びてる？」）

1. `writings/pieces/*.md` の `rounds` を読み、軸ごとの推移を出す。
2. **伸びていない軸を名指しする**。全体平均で誤魔化さない。
3. 次に取るべきお題を提案（弱い軸を狙ったもの）。記録更新が無ければ commit しない（閲覧のみ）。

## 講評の3役（コンテキスト汚染を避ける）

**この skill の最大の弱点は、講評する側が文脈を持ちすぎることだった。**
お題・設定・過去の稿・自分が渡した重点を全部知った状態で読むと、**書かれていないものまで読めてしまう**。
実際に事故が起きた（2026-09-18、『静寂の中の実演』）——確定稿に構成5・声5を出したあとで、
**本文だけを渡した独立の読者2人が、構成と声の問題を別々に見つけた**。知っているから見えなかった。

そこで講評を**3役に分ける**。役ごとに**渡す情報を変える**のが肝で、これは手間ではなく**測定の設計**。

| 役 | 渡すもの | 出すもの |
|---|---|---|
| **コールドリーダー**（Agent・**毎稿・2人以上並列**） | **本文だけ** | 何が読めたか／詰まった箇所／跳ね返りはあったか |
| **意図検証**（Agent・狙いが明確なときだけ） | 本文＋**作者の狙い** | 狙いが本文だけで成立するかの機構分析 |
| **本セッション**（履歴を持つ側） | 全履歴 | 前回の重点は効いたか／通時的な癖／**次の重点1つ**／採点 |

### コールドリーダーの回し方（必須・毎稿）

1. **Agent を2人以上、並列で**投げる（`general-purpose`）。
2. プロンプトには**確定した本文だけ**を貼る。**お題・設定・過去稿・意図は一切渡さない。**
3. **ファイルアクセスを明示的に禁止する**——`writings/pieces/*.md` には講評も意図も全部書いてあるので、
   読まれた瞬間に実験が壊れる。「Read / Glob / Grep / Bash でリポジトリを調べるな」と書く。
4. 聞くこと: 何が起きているか／最後の一文の意味／語り手と対象の関係／読後感／**詰まった箇所**／1文要約。
5. **2人が独立に同じ箇所を挙げたら本物**。1人だけならその読者の癖と区別がつかない。**n=1で判断しない。**

### 意図検証の回し方（作者が狙いを明言しているときだけ）

- 本文＋狙いを渡し、**「意図を知らない読者が本文だけからそう読めるか」だけを問題にしろ**と指示する。
  「意図を知っていれば読める」は根拠にならない、と明示する。
- **判定は信用しすぎない。機構の説明を採用する。**
  意図を知った状態で「読めるか」を推論させると**悲観に振れる**（同日の実験で、
  意図検証は「不成立」と判定したが、実際のコールドリーダー2人は自力で読み取っていた）。
  **判定＝実測（コールドリード）／説明＝検証（意図検証）**と役割を分ける。

### 本セッションが手放してはいけない判断

履歴がないと出せないものは**新規 Agent には原理的に無理**なので、こちらでやる。

- 前回の重点は効いたか
- **通時的な癖**（「文体が3作連続で最低軸」「これは前作の自己模倣」）
- 5軸の採点と、次の重点1つ
- 作者の決定の尊重（伏せると決めた情報、却下された観点）

### 結果の記録

コールドリードの結果は **piece の `## 読者テスト` に残す**（`templates/writing-piece.md` 参照）。
**「読者はここで詰まった」は一次データで、こちらの講評より価値が高いことがある。**
採点との食い違いが出たら、**食い違いごと残す**（点は書き換えない。訂正は追記で示す）。

## 講評の書き方

順番を守る。**効いている点 → 軸ごとの所見 → 重点1つ → 観点**。

- **採点は本文の語に紐づける**。「具体2点」ではなく「山場が『時間』『未来永劫』と抽象語だけなので具体2点」。
  紐づけない点数は、ユーザーが次に何を見ればいいか分からず、ただの通知簿になる。
- **軸ごとに1〜3行**。5軸すべて書く（点が高い軸も書く。なぜ機能しているかを言語化するのは再現性のため）。
- **重点は「どう直すか」ではなく「何を見るか」**で書く。手順を渡すと、次回も手順待ちになる。
- **観点が抽象的すぎて動けない場合だけ、素材（部品）のリストを添える**。
  例: 「逆再生を症状で見せる」→ 使える素材として「足音・湯気・こぼれた水・カーテンの揺れ」までは出してよい。
  **それを文にした完成形は出さない**。
- **クリシェの指摘は具体的に**。「陳腐」ではなく「その現象は既存作品で頻出なので、
  現象の名前を呼ばずに描くと新品に見える」まで書く（→ [[cliche-overused-not-necessarily-old]]）。

## 蒸留（作品を作法に変える）

講評で出た知見のうち、**他の作品にも使い回せる客観的な作法**だけを `notes/`（`kind: knowledge`・`srs` 初期化）に原子ノート化する。

- **作品固有の話は piece に留める**（「この一節では『とことこ』が効いた」は notes にしない）。
- 蒸留するのは「サスペンスは情報を与えることで生まれる（ヒッチコック）」のような、**裏が取れる作法**。
  自分の意見を「知識」として登録しない。確証がないものは piece 側に `insight` として書くか、明示的に仮説と書く。
- ノートができたら piece の `## Links` から張り、`rubric.md` の該当軸からも参照する。
  こうして **書く → 講評 → 作法が知識になる → クイズで定着（`/mn-review`）** が閉じる。
- タグは既存を Grep してから付ける（`writing/craft` が既存。新タグを作るならコミットメッセージに明記）。

## /mn（統一入口）との関係

`/mn`（mn-capture）は「自分が書いた作品らしい入力」「お題への回答らしい入力」を判定したらこの skill に振り分ける。
mn-capture 経由でも上記フロー（特に**固定5軸での採点**と**代筆しない**）を守る。

## サイト（web/）との関係

**作品（pieces）はサイトで読める**（2026-09-11、PBI-04 完了）。`一覧 → 作品`、または `探す` から辿れる。
`rubric.md` と `prompts.md` は**サイトに出さない運用**（軸は講評の道具、お題は運営の楽屋であって読み物ではない）。

`web/scripts/build-data.mjs` が piece のスキーマを検証する。**rubric に無い軸の点・`status` 不正・
`total` と `scores` の合計の不一致はビルドが落ちる**（軸が固定されていることに意味があるので、砦を置いてある）。
piece を書いたら `npm --prefix web run build:data` を走らせ、`pieces N` が出ることを確認してから commit する。

## コミット運用（CLAUDE.md 準拠）

- push 前に必ず `git fetch origin` → ローカル `main` を最新化 → `main` にコミット → **remote `main` に push**。
  session で別ブランチが指定されていても、最終 push は必ずローカル `main` 経由で remote `main` へ。
- コミットは意味のある単位で分ける（作品新規 / 改稿追加 / 完成確定 / お題補充）。
- コミットメッセージ例:
  - `write(oyachumi-no-jikan): 初稿を記録し講評（13/25・重点=山場を症状で書く）`
  - `write(oyachumi-no-jikan): v2 を追記（具体 2→4・引き 3→4）`
  - `write(oyachumi-no-jikan): 作品として確定（19/25）＋サスペンスの作法を notes に蒸留`

## 注意

- **上達させるのが目的で、良い作品を出すのが目的ではない**。ここを取り違えると全部代筆したほうが早くなる。
- **点が下がることを恐れて甘く付けない**。下がった事実こそが情報（1つ直すと別が落ちるのは正常）。
- **推敲を無限に続けさせない**。伸びが止まったら「これで確定していい」と言うのも講評の仕事。
