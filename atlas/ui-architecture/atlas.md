## このアトラスについて

画面を作るという仕事は、突き詰めれば **「時間とともに変わる状態を、画面という表現に矛盾なく写し続ける」** ことだ。この一文に、UI開発のバグのほとんどが詰まっている——押されたボタン、返ってきたレスポンス、切り替わったタブ。そのたびに状態が動き、画面が追随しなければならない。

このアトラスは、その問題に対して現代のフロントエンドが出した答えを、**設計思想のレベルで**読み解くための地図だ。フレームワークの使い方（API の暗記）ではなく、「なぜその形になったのか」「何を捨てて何を守ったのか」を扱う。

最初に置いたのは **React のモデル** と **The Elm Architecture（TEA）** の二つ。どちらも「UI は状態の関数である」という同じ出発点に立ちながら、**状態をどこに置くか**・**副作用をどこまで言語で縛るか** で正反対の方向に歩いた、対照実験のような一対だからだ。片方だけを知っていると、それが唯一の自然な形に見えてしまう。並べると初めて、両方が「選択」だったことが分かる。

## 読み方

2つの見方を用意している。

- **マップ**: グラフ全体を俯瞰して、興味のある概念から自由に飛べる。今どこを理解していて、次に何が繋がるかが見える。
- **ルート**: 「理解しやすい順路」に沿って一本道で読み進める。前提を踏んでから次へ進むよう組んである。

まずはルート **「二つの答えを比べる」** を頭から読むのがおすすめだ。共通の問題設定を押さえてから React → Elm と読み、最後の比較で指標ごとに突き合わせる、という組み方になっている。**比較を先に読んでも意味は取れない**——優劣は「何を守るために何を諦めたか」を知って初めて評価できるからだ。

マップにはまだ本文のない概念（仮想DOMと照合、フックと局所状態、Flux/Redux、細粒度リアクティビティ、副作用をデータとして扱う、React Server Components）が置いてある。これは順路の先に何が繋がるかを先に見せるためで、読みたくなった枝から順に書き足していく。
