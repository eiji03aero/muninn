[[react-model|React]] と [[the-elm-architecture|TEA]] は、[[ui-as-state-projection|同じ問題]]に対する二つの答えだった。ではどちらが優れているのか。

この問いは、指標を決めない限り答えが出ない。しかも指標ごとに勝者が入れ替わる。以下、10の軸で突き合わせる。**「◎ / ○ / △」は絶対評価ではなく、この一対の中での相対評価**だと読んでほしい。

### 1. 学習の立ち上がり — React ○ / TEA △

React は最初の一歩が極端に軽い。JSXと `useState` を覚えれば動くものが作れる。既存のJavaScript知識がそのまま資産になる。

TEA は言語ごと新しい。直和型、パターンマッチ、カリー化、`Maybe` / `Result` による例外の不在——関数型の語彙を通らないとカウンタすら書けない。ただしこれは **前借りの学習コスト**であり、Elm 側の反論は「React は最初が軽い代わりに、後から `useEffect` の依存配列や再レンダリングの罠を学び直す」というものになる。**立ち上がりの傾きは React が緩く、後半の追加学習は Elm が少ない。**

### 2. 記述量・ボイラープレート — React ◎ / TEA △

小さな部品では差は出ないが、**部品を組み合わせ始めた瞬間に差が開く**。React は状態を必要な場所に `useState` 一行で置ける。TEA は子の `Model` を親に埋め、`Msg` をラップし、`Html.map` と `Cmd.map` で配線する。

これは TEA の設計上の代償であって、書き方の下手さではない。「アプリの状態はひとつの値である」を守るなら、部品の状態は必ず親の型に現れなければならない。**局所性を捨てて一望性を買った**分の請求書がここに来る。

### 3. 大規模での状態の見通し — React △ / TEA ◎

「いま、このアプリはどういう状態か」に一箇所で答えられるか。TEA は答えられる。`Model` を見ればいい。React は答えられない——状態は `useState` として散在し、Context にも外部ストアにもある。

React 側でこれを埋めようとしたのが [[flux-and-redux|Redux]] であり、そのRedux が Elm から着想を得ているのは示唆的だ。**ただし Redux を入れると React は「TEA のボイラープレートを、型の保証なしで払う」状態に近づく**。近年 Zustand や Jotai のような軽量ストアが好まれるのは、この請求書を値切る動きだと読める。

### 4. 型安全性・実行時エラー — React △ / TEA ◎

ここが最大の差だ。Elm は「コンパイルが通れば実行時例外が出ない」を実用上ほぼ達成している。`null` / `undefined` が言語に無く、例外機構が無く、パターンマッチが網羅を強制されるからだ。**「本番で undefined is not a function」という体験が構造的に起きない。**

TypeScript は大きく効くが、質が違う。型は後付けの層であり、`any` で抜けられ、外部データの境界（JSONパース）で嘘をつける。**Elm は境界に `Decoder` を書かせて型を強制するが、TypeScript は書かなくても通ってしまう。** 保証の強さは Elm、適用範囲の広さは TypeScript。

### 5. 副作用の扱いとテスタビリティ — React △ / TEA ◎

TEA の `update` は純粋関数なので、テストは値の比較で終わる。HTTPのモックも時間の凍結もいらない。ロジックのテストが**書きやすいのではなく、書くしかない形に**なっている。

React は `useEffect` に任意のJavaScriptを書ける。書けるということは、書き方が人と場所で揺れるということだ。依存配列の漏れ、後始末忘れ、二重発火は React 実務の定番バグで、テストにはレンダリング環境とモックが要る。**これは「Reactが下手」なのではなく、逃がし弁を用意した設計の必然的な帰結だ。**

### 6. リファクタリング耐性 — React △ / TEA ◎

Elm では「型を変えて、コンパイラが赤くする箇所を全部直す」が有効な作業手順として成立する。エラーメッセージの質も高い。**大きな構造変更を、網羅性を担保しながら機械的に進められる。**

React + TypeScript でも近いことはできるが、`useEffect` の中身・実行時の分岐・型が付いていない外部データ境界に抜けが残る。テストの網に頼る部分が大きい。

### 7. パフォーマンスと最適化の手当 — React ○ / TEA ○（性格が違う）

素の描画性能はどちらも同程度で、実アプリで差が問題になることは稀だ。違うのは**最適化の作法**である。

React は再レンダリングの範囲が広くなりがちで、伝統的に `useMemo` / `useCallback` / `memo` を人間が手で当てていた。2025年10月に **React Compiler が 1.0** になり、この層はビルド時に自動化された——「宣言的に書き、最適化はツールがやる」という当初の理想に近づいた形だ。

Elm はコンパイル時最適化とデッドコード削除が強く、生成物が小さいことで知られる。一方でランタイム側の逃げ道（手動での細かい制御）は少ない。**React は「詰まったら手で殴れる」、Elm は「そもそも詰まりにくいが殴る手段も少ない」。**

### 8. エコシステム・既存資産との相互運用 — React ◎ / TEA △

決定的な差。React には事実上あらゆる領域のライブラリ（UIキット、フォーム、テーブル、地図、決済SDK）がある。npm がそのまま使える。

Elm から JS を呼ぶ手段は ports だけで、非同期メッセージパッシングに限られる。決済SDKやリッチエディタを組み込むには、毎回この境界を自分で敷設することになる。**「必要なものが無ければ自分で書く」が前提の言語**だと理解しておくべきだ。これは安全性を買った代金であって、修正可能な欠点ではない。

### 9. 採用・チームでの調達 — React ◎ / TEA △

React 経験者は市場に大量にいる。教材・記事・LLMの学習量も桁違いだ。Elm 経験者は稀少で、採用時は「未経験者に学ばせる」前提になる。**チームの人数が増えるほど、この差は技術的優劣を押し流す。**

もっとも、Elm 側には「言語が小さく規約が強いので、未経験者でも書けるコードのばらつきが小さい」という反論がある。**調達しやすいのは React、揃えやすいのは Elm。**

### 10. 将来性・変化への追随 — React ○ / TEA △（ただし読み方が割れる）

React は動き続けている。Server Components、Actions、Compiler。**進化が速いことは、追随コストがかかることでもある**——クラス→フック→Server Components と、数年ごとに書き方の常識が更新されてきた。

Elm は 0.19.1（2019年10月）から長く止まり、2026年7月6日の 0.19.2 でようやく動いた。言語変更なし、コンパイラ性能改善のみで、1.0 に向けた小さな非破壊リリースの連続が予告されている。**この事実を「完成して安定している」と読むか「本番を預けるには動きが乏しい」と読むかで、評価は正反対になる。** どちらの読みも同じ事実に立っているので、ここは事実で決着しない——リスク許容度の問題だ。

### 総合 — 順位は付かない。恐れているものが違う

10軸のうち React が明確に勝つのが 2・8・9（合成の軽さ、エコシステム、人の調達）、TEA が明確に勝つのが 3・4・5・6（状態の一望性、型安全性、副作用管理、リファクタリング耐性）だ。**この分布自体が答えを示している。**

React が守っているのは **変化への適応力**だ。何が必要になるか分からない世界で、逃げ道を全部開けておく。だから壊れ方も自由で、規律はチームが供給しなければならない。

TEA が守っているのは **壊れなさ**だ。書ける形を狭めることで、書けないバグを作る。だから自由度と接続性を失い、その代金をボイラープレートとエコシステムの薄さで払っている。

実務的な選び方はこうなる。**外部サービスとの結合が多く、要件が動き、人が入れ替わるプロダクトなら React**（＋ TypeScript ＋ 状態管理の規約を明文化する）。**要件が自分たちで決められ、長期に保守し、少人数で書き、バグの実行時発現を最も恐れるなら Elm** は今でも強い選択肢だ。

そしてもうひとつ。**Elm を採らなくても TEA は学ぶ価値がある。** Redux、Vuex、Bloc（Flutter）、Composable Architecture（Swift）——「状態をひとつに畳み、出来事を列挙し、遷移を純粋関数で書き、副作用をデータとして返す」という型は、あらゆるプラットフォームに輸出されている。**Elm が発明したのは言語ではなく、この語彙のほうだ**と言ってもいい。
