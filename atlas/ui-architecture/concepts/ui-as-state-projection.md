チェックボックスがひとつある画面を想像してほしい。チェックすると下にフォームが開き、送信ボタンが有効になり、ヘッダーのバッジが増える。難しくない。では、その状態を「サーバーから復元する」機能が加わったら？ 「取り消し」が加わったら？ タブを切り替えても保持されるようになったら？

**個々の変化は簡単なのに、組み合わさった途端に難しくなる。** これがUI開発の性格だ。

### 命令的UIが抱えていた二重帳簿

かつての書き方——jQuery に代表される命令的DOM操作——では、こう書いた。「チェックボックスが変わったら、フォームを `show()` して、ボタンの `disabled` を外して、バッジのテキストを書き換える」。イベントごとに、**画面をいまの状態から次の状態へ動かす手順**を人間が書く。

ここで何が起きているかというと、状態が**二箇所**にある。JavaScript 側の変数と、DOM に描かれている見た目だ。二重帳簿である。そして帳簿の同期は、開発者が書いたイベントハンドラの網に完全に依存している。イベントの種類が n 個、影響を受ける画面要素が m 個あれば、考えるべき組み合わせは n×m に近づく。**「この経路を通ってきたときだけバッジが更新されない」**——UIのバグの大半は、この網の穴だ。

もうひとつ厄介なのは、**画面が「どうやってそこに来たか」を記憶してしまう**ことだ。同じ状態でも、辿った経路が違えば見た目が違う。再現できないバグはたいていここから来る。

### 宣言的UIという転回

そこで発想が反転する。**差分の当て方を書くのをやめて、「その状態のときの画面はこうだ」という完成形だけを書く。** 状態が変わったら、また完成形を作り直す。差分をどう当てるかはランタイムに任せる。

式にすればこうなる。

```
view = f(state)
```

`f` は純粋関数だ。同じ状態を入れれば必ず同じ画面が出る。経路の記憶は消える。開発者が守るべき不変条件は「状態と表示が一致していること」から「`f` が正しいこと」に縮む——これが宣言的UIの本当の利得で、パフォーマンスの話ではない。

「毎回全部作り直すなんて遅いのでは」という疑問は正しい。だからこそ各実装は、作り直しの結果を実DOMへ最小コストで反映する仕組み（React の照合＝reconciliation、あるいは細粒度な購読）を用意している。**その仕組みは、宣言的な書き味を現実的な速度で成立させるための代償であって、目的ではない。**

### 分岐点は二つある

`view = f(state)` に合意した後、まだ二つの大きな問いが残っている。ここから設計思想が分かれる。

**ひとつ、状態をどこに置くか。** アプリ全体でひとつの `state` にまとめるのか、画面の部品ごとに小さく分散して持つのか。まとめれば全体が見通せるが、部品は自己完結しなくなる。分散すれば部品は再利用しやすいが、「いまアプリ全体はどういう状態か」を一箇所で答えられなくなる。

**ふたつ、副作用をどう扱うか。** 現実のアプリは画面を描くだけでは終わらない。HTTP を叩き、localStorage に書き、タイマーを回す。`f` を純粋に保つと言っても、これらはどこかで実行されなければならない。純粋な世界のすぐ外側に置いて「必要なら好きに書いていい」とするのか、副作用すら**データとして記述**させてランタイムだけが実行するのか。

[[react-model|React のモデル]]と [[the-elm-architecture|The Elm Architecture]] は、この二つの問いに正反対の答えを出した。前者は「開発者の裁量に委ねる」、後者は「言語とランタイムで縛る」。どちらが正しいという話ではなく、**何を守るために何を諦めたか**が違う。次はその中身を見ていく。
