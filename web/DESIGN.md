# muninn 閲覧サイト — 設計思想

このディレクトリ（`web/`）にある閲覧サイトが**何のためにどう組まれているか**を書いた文書。
実装の細部ではなく、**判断が割れたときに立ち返る上位の思想**を残すのが目的。

> **この文書は、サイトを変更するたびに更新する。**
> 実装だけ変わって思想が古びると、次の変更で原則が失われる。更新規約は末尾「この文書の運用」を参照。

作成: 2026-07-31（C案「日報」への刷新時）/ 前提資料: `../docs/web-renewal/`

---

## 1. このサイトの位置づけ

muninn には**3つの非対称**があり、設計はすべてここから出ている。

| # | 非対称 | 帰結 |
|---|--------|------|
| 1 | **正本は markdown、サイトは派生** | サイトはいつ捨てても再生成できる。markdown のスキーマを増やすのは正当だが、サイトの都合で正本を汚さない |
| 2 | **読むのはサイト、書くのは Claude Code** | サイトに書き込み UI は作れない。作れるのは「Claude に渡す依頼」まで |
| 3 | **読むのはスマホ、書くのは Mac** | 読んでいる最中に思いついた依頼を、その場で実行させない。**溜めて後でまとめて渡す** |

この3つ目が「伝票（slip）」という仕組みの理由。サイトは書き込めないが、**書き込みの"意図"は溜められる**。

## 2. なぜ刷新したか

オーナーの訴えは5つあった（機能が把握しにくい／何ができるか分からない／情報があるのに辿り着けない／繋がりが見えない／各機能が見やすい形に落ちていない）。分析の結果、根本は4つだった。

```
根本1: IA が「ファイルの置き場所」の写像だった
       → 画面が concern 名（notes/follows/atlas/logs/moc）で割れ、ユーザーの目的で割れていない
根本2: 横断のインフラが無かった
       → 全文検索なし・バックリンク未計算・タグは押せない装飾。データはあるが辿る手段だけが欠けていた
根本3: 想起と定着が Web に存在しなかった
       → 5 concern のうち1つがビューアに欠落。「蓄積を回収して楽しむ」が見る面で完結しない
根本4: データ構造のリッチさに表示が追いついていなかった
       → 数値は静止、markdown は素通し、比較機能は空回り
```

**症状ではなく根本を直すこと。** 画面を綺麗にするだけでは1つも解決しない。

## 3. 設計原則

判断が割れたら、この順で優先する。

### 原則1: 探させない、差し出す
検索は最後の手段であって最初の手段ではない。既定の動詞は「めくる」。
開いた時点で今日読むものが決まっている状態を作る。
— ただし**差し出すだけでは「あれ何だっけ」と「何があるんだっけ」に答えられない**。だから面は4タブの1枚にすぎない（原則7）。

### 原則2: 紙面は閲覧日で組む
ビルド時にやるのは素材の下ごしらえまで。**「今日どれを載せるか」はクライアントが `new Date()` で決める**。
これにより push が2週間止まっても面は毎日入れ替わる。更新頻度が低い（数日〜週単位）という現実への直接の回答。
→ ビルド日で固定される派生値（かつての `due` フラグ）は作らない。

### 原則3: 数えるのは「やった量」であって借金ではない
未消化の件数をバッジで出さない。
かつての「復習期限 59」は knowledge 59件すべてが該当していて**常時点灯＝情報量ゼロの壁紙**だった。減らない借金の額は行動を止める。
出してよいのは「今週12件 再読した」のような**増えるカウンタ**だけ。

### 原則4: 主燃料は「新着」ではなく「忘却」
一番豊かな在庫は、すでに書いて忘れた90本のほう。新着は面の一部にすぎない。
だから在庫が枯れない。**新規投入がゼロでも編集が成立する**ことが、この設計の生命線。

### 原則5: 空にならないことを構造で保証する
「在庫が無ければ次の型に落ちる」というカスケードを持ち、**最後は必ず常時在庫のカード型に着地する**（→ §5）。
空状態は「ありません」と書かず、**次の一手（依頼ボタン）に変換する**。
コンテンツ量が極端に不均一（notes の47%がゴルフ、記録帖は1件）でも面が死なないための唯一の方法。

### 原則6: 行き止まりを1つも作らない
すべての詳細ページに「ここへ来る道」（バックリンク）を**例外なく**置く。
型によって有無が分かれる実装を禁止する——まだらに残った行き止まりは、根本2の再発そのもの。

### 原則7: 面が答えられないジョブには、面が答えようとしない
編集された紙面は「読む姿勢」だけを担う。
ピンポイント想起は**探す**、網羅把握は**棚**、システムの把握は**デスク**。役割を混ぜない。

### 原則8: 手入力の索引をゲートにしない
タグが第一階層。MOC の束は**上乗せであってゲートではない**。
宣言し忘れた関心事が不可視になる構造は、「情報があるのに辿り着けない」を形を変えて再生産する。
（コンペで敗れたA案の急所がここで、両審査員が独立に同じ指摘をした。**ここを崩すと採択理由が消える**。）

### 原則9: 数字に嘘をつかせない
指標の良し悪しは**正本が宣言する**（`metric_goals`）。宣言のない指標は中立に扱い、良し悪しを判定しない。
実例: フェース角は大きくなるほど悪い。最大値を機械的に「自己ベスト」と表示したとき、
**profile 自身が「最重要ウォッチ」と警告している悪化を、成果として見せていた**。
定点観測ツールが数字の解釈を間違えるのは、機能が無いことより悪い。

### 原則10: 決定的であること
日替わりは乱数ではなく**日付シードのハッシュ**で作る。同じ日は何度開いても同じ紙面。
リロードで引き直せると賭博になり、「今日はこれを読んだ」という記憶が成立しない。
グラフのレイアウトも同様（決定的配置。force-directed を使わない）——同じ場所に描かれることが記憶の手がかりになる。

### 原則11: 一度に見せるノードは12点まで
俯瞰の単位を上げて畳む。超える画面を作らない。図は必ずリストで代替可能にする（図は近道であって UI の本体ではない）。

## 4. 情報構造（IA）

**concern（ファイルの置き場所）ではなく、読む姿勢で割る。**
タブ名がそのまま「muninn でできること」の要約になっているのが要点で、これが「何ができるんだっけ」への構造的な回答になっている。

```
▣ 面     /            めくる     — 今日の紙面。既定の入口
▤ 棚     /shelf       俯瞰する   — 在庫マップ（面積比例）。タグが第一階層
⌕ 探す   /search      当てる     — 全concern横断・本文込みの全文検索
✎ デスク /desk        頼む       — できること／在庫の健康／未送信の伝票

葉: /note/:slug · /follow/:name（+/player/:slug）· /atlas/:slug（+/concept/:cslug）· /log/:topic（+/entry/:slug）
```

**廃止したもの**: `/notes`（90件フラットリスト）・`/moc/:slug`（生 markdown）・`/logs`（トピック索引）。
いずれも「置き場所の写像」であり、棚と検索に吸収された。旧 URL は棚へリダイレクトする（PWA のホーム追加やブックマークから踏まれるため）。

**画面に内部語彙を出さない。** ノート→記事、フォロー→定点、アトラス→連載/章、ログ→記録帖、MOC→束。
concern 名はコードとこの文書の中だけで使う。

## 5. 面の組版モデル

面は**スコア順のフィードではない**。固定の段があり、各段に適格なカード型が優先順で落ちる。

```
題字   常時
リード  speed → milestone → chapter-new → brief → feature → revival
袖     countdown → slip（伝票3件以上のときだけ）
再読   recall ×3
連載   chapter → chapter-request
特集   feature（MOC束 → タグ束）
記録   series → compare
在庫   常時
```

**リード段が空にならないことが構造的に保証されている**のが肝。
下2つ（`feature` = 束の日替わりローテーション、`revival` = 最終更新が最も古い群からの日替わり）は
**記事が1件でもあれば必ず出る**ため、上5つが全滅してもリードは埋まる。

各段は在庫が無ければ**段ごと消える**（「ありません」と書かない）。

## 6. 想起の二層モデル

静的サイトなので `srs` を markdown に書き戻せない。この制約を二層で解く。

```
層1 影SRS（localStorage）    判定が即座に効く。明日はもう出ない、次は6日後
                             → サーバに何も送っていないのに、体験としてはSRSが回っている
層2 伝票（デスクで束ねる）    溜まった判定を1つのプロンプトで /mn-review に流し込む
                             → 正本が追いついたら影を捨てる（自己修復同期）
```

**両側が同一の SM-2 式を使うこと。** 式が同じなので値が必ず一致し、送信を忘れても乖離しない。
`/mn-review` の式を変えるときは、必ずサイト側も同時に変える。

**想起はクイズではなく読み物として出す。** muninn のノートはタイトルが言い切り形＝答えそのものなので、
タイトルを伏せて問い（`recall`）だけを見せる。「クイズを始める」というモード切替が無いので起動コストがゼロ。
`recall` が無いノートはタグと文脈で degrade する——**劣化するが壊れない**。

**自己申告の甘さを設計で補正する。** 一言を書いたかで q を分岐（書いて わかった=5 / 書かず=4 / あやしい=2）し、
サイト由来の ease 成長は skill 由来より 30% 抑える。伝票が20件たまったら
「本気の1問を `/mn-review` で受けないか」と提案する（校正チェックポイント）。
——摩擦の低さは強みだが、それが定着の質を静かに下げるのを放置しない。

## 7. データの流れと責務分担

```
markdown（正本）
   ↓  build-data.mjs        ── ビルド時にしかできないことだけをやる
site.json                       ・git 履歴からの最終更新日
   ↓  （復号してメモリへ）        ・スキーマ検証（logs の必須/enum/範囲。壊れていたらビルドを落とす）
lib/graph.js                 ── 全concernを1つのノード集合として見る
   ・被リンク（理由つき）          ※ route を ID にしているので wiki.js のリンク解決とそのまま噛み合う
   ・タグ横断索引
   ・MOC束のタグ自動割当
lib/edition.js               ── 閲覧日 × 在庫 で今日の紙面を組む
lib/recall.js                ── 影SRS・伝票・閲覧履歴（localStorage 一切合切）
```

**判断の基準**: ビルド時にやるのは「git が要る」「検証で落としたい」ものだけ。
横断計算・検索・グラフ構築は**全部クライアントでよい**（全データが復号済みでメモリ上にあり、90記事規模なら数ミリ秒）。
専用の検索インデックスを作らないのは過剰設計を避けるため。

**正本のスキーマを増やすとき**は、それが「サイトのための都合」ではなく
「記録として正しい情報」かを問う。`metrics` は観測値そのものなので正当。`metric_goals` は
指標の意味の宣言なので正当。表示の都合だけの項目は入れない。

## 8. 意図的にやらないこと

| やらない | 理由 |
|---|---|
| 90ノードの force-directed グラフ | 7〜8個の団子が浮かぶだけで情報量ゼロ。モバイルでは毛玉になる |
| 全ノート一覧ページ | 「置き場所の写像」そのもの。棚と検索が代替する |
| 未消化件数のバッジ | 行動を止める。原則3 |
| ビルド日基準の派生フラグ | push が止まると面が古びる。原則2 |
| サイト上での書き込み UI | 正本は markdown。作れるのは依頼まで |
| 号数・発行部数のような演出 | 新聞メタファーの装飾的な部分。中身がないのに様式だけ真似ない |
| 自動生成リンクを人力リンクと同じ見た目で出す | 「本人がそう言った」と「機械がそう推測した」を混ぜるとナレッジベースの信頼が壊れる |

## 9. 既知の未達

- **`brief`（予習）カードの素材が無い。** `follows/*/briefs/` を作るか、`/mn-brief` の出力を
  正本に落とす運用を決める必要がある。現状は snapshot で代替している。
- **記録帖の比較テーブルが実データで検証できていない。** entries が1件しかないため。2件目が入ってから確認する。
- **degrade 表示（`recall` 無し）の経路が実データで踏まれなくなった。** 既存分は全件埋めたが、
  今後 `/mn-research` 等で新規ノートを作るときに `recall` を付け忘れると再び degrade する。
  デスクの「想起の問いが無い記事」がゼロでない状態は、放置せず埋める。

### 解消済み
- ~~`recall` が全 knowledge ノートに無く、想起カードの大半が degrade 表示~~
  → 2026-07-31、既存 knowledge 59件すべてに `recall` を付与して解消。
  伏せ記事が本来の姿（タイトルを伏せて問いだけを見せる）で動くようになった。

## 10. この文書の運用

- **サイトを変更したら、この文書を同じコミットで更新する。**
  更新するのは「思想が変わったとき」と「未達が解消/追加されたとき」。
  ボタンの色を変えた程度では更新しない——**ここは実装の写しではなく、判断の拠り所**である。
- 新しい原則を足すときは、**なぜそれが必要になったか（どの失敗から学んだか）を必ず書く**。
  理由のない原則は次の担当者に無視される。
- 原則どうしが衝突したら、番号の小さいほうを優先する。衝突が繰り返されるなら原則の側を直す。
- 刷新の経緯・比較検討の記録は `../docs/web-renewal/` にある（現状分析・3案・両審査・ワイヤーフレーム）。
  この文書はその**結論だけ**を持ち、経緯は持たない。
