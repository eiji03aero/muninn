# muninn 閲覧サイト — 設計思想

このディレクトリ（`web/`）にある閲覧サイトが**何のためにどう組まれているか**を書いた文書。
実装の細部ではなく、**判断が割れたときに立ち返る上位の思想**を残すのが目的。

> **この文書は、サイトを変更するたびに更新する。**
> 実装だけ変わって思想が古びると、次の変更で原則が失われる。更新規約は末尾「この文書の運用」を参照。

## 1. このサイトの位置づけ

muninn には**3つの非対称**があり、設計はすべてここから出ている。

| # | 非対称 | 帰結 |
|---|--------|------|
| 1 | **正本は markdown、サイトは派生** | サイトはいつ捨てても再生成できる。markdown のスキーマを増やすのは正当だが、サイトの都合で正本を汚さない |
| 2 | **読むのはサイト、書くのは Claude Code** | サイトに書き込み UI は作れない。作れるのは「Claude に渡す依頼」まで |
| 3 | **読むのはスマホ、書くのは Mac** | 読んでいる最中に思いついた依頼を、その場で実行させない。**溜めて後でまとめて渡す** |

この3つ目が「伝票（slip）」という仕組みの理由。サイトは書き込めないが、**書き込みの"意図"は溜められる**。

## 2. なぜ刷新したか

オーナーの訴えは5つあった（機能が把握しにくい／何ができるか分からない／情報があるのに辿り着けない／繋がりが見えない／各機能が見やすい形に落ちていない）。分析の結果、根本は4つだった。

```
根本1: IA が「ファイルの置き場所」の写像だった
       → 画面が concern 名（notes/follows/atlas/logs/moc）で割れ、ユーザーの目的で割れていない
根本2: 横断のインフラが無かった
       → 全文検索なし・バックリンク未計算・タグは押せない装飾。データはあるが辿る手段だけが欠けていた
根本3: 想起と定着が Web に存在しなかった
       → 5 concern のうち1つがビューアに欠落。「蓄積を回収して楽しむ」が見る面で完結しない
根本4: データ構造のリッチさに表示が追いついていなかった
       → 数値は静止、markdown は素通し、比較機能は空回り
```

**症状ではなく根本を直すこと。** 画面を綺麗にするだけでは1つも解決しない。

## 3. 設計原則

判断が割れたら、この順で優先する。

### 原則1: 探させない、差し出す
検索は最後の手段であって最初の手段ではない。既定の動詞は「めくる」。
開いた時点で今日読むものが決まっている状態を作る。
— ただし**差し出すだけでは「あれ何だっけ」と「何があるんだっけ」に答えられない**。だから今日の紙面は5タブの1枚にすぎない（原則7）。

### 原則2: 紙面は閲覧日で組む
ビルド時にやるのは素材の下ごしらえまで。**「今日どれを載せるか」はクライアントが `new Date()` で決める**。
これにより push が2週間止まっても面は毎日入れ替わる。更新頻度が低い（数日〜週単位）という現実への直接の回答。
→ ビルド日で固定される派生値（かつての `due` フラグ）は作らない。

### 原則3: 数えるのは「やった量」であって借金ではない
未消化の件数をバッジで出さない。
かつての「復習期限 59」は knowledge 59件すべてが該当していて**常時点灯＝情報量ゼロの壁紙**だった。減らない借金の額は行動を止める。
出してよいのは「今週12件 再読した」のような**増えるカウンタ**だけ。

### 原則4: 主燃料は「新着」ではなく「忘却」
一番豊かな在庫は、すでに書いて忘れた90本のほう。新着は面の一部にすぎない。
だから在庫が枯れない。**新規投入がゼロでも編集が成立する**ことが、この設計の生命線。

### 原則5: 空にならないことを構造で保証する
「在庫が無ければ次の型に落ちる」というカスケードを持ち、**最後は必ず常時在庫のカード型に着地する**（→ §5）。
空状態は「ありません」と書かず、**次の一手（依頼ボタン）に変換する**。
コンテンツ量が極端に不均一（notes の47%がゴルフ、記録帖は1件）でも面が死なないための唯一の方法。

### 原則6: 行き止まりを1つも作らない
すべての詳細ページに「ここへ来る道」（バックリンク）を**例外なく**置く。
型によって有無が分かれる実装を禁止する——まだらに残った行き止まりは、根本2の再発そのもの。

### 原則7: 面が答えられないジョブには、面が答えようとしない
編集された紙面は「読む姿勢」だけを担う。
ピンポイント想起は**探す**、網羅把握は**テーマ**、続きの把握は**続きもの**、システムの把握は**依頼**。役割を混ぜない。

### 原則8: 手入力の索引をゲートにしない
タグが第一階層。MOC の束は**上乗せであってゲートではない**。
宣言し忘れた関心事が不可視になる構造は、「情報があるのに辿り着けない」を形を変えて再生産する。
（コンペで敗れたA案の急所がここで、両審査員が独立に同じ指摘をした。**ここを崩すと採択理由が消える**。）

### 原則9: 数字に嘘をつかせない
指標の良し悪しは**正本が宣言する**（`metric_goals`）。宣言のない指標は中立に扱い、良し悪しを判定しない。
実例: フェース角は大きくなるほど悪い。最大値を機械的に「自己ベスト」と表示したとき、
**profile 自身が「最重要ウォッチ」と警告している悪化を、成果として見せていた**。
定点観測ツールが数字の解釈を間違えるのは、機能が無いことより悪い。

### 原則10: 決定的であること
日替わりは乱数ではなく**日付シードのハッシュ**で作る。同じ日は何度開いても同じ紙面。
リロードで引き直せると賭博になり、「今日はこれを読んだ」という記憶が成立しない。
グラフのレイアウトも同様（決定的配置。force-directed を使わない）——同じ場所に描かれることが記憶の手がかりになる。

### 原則11: 一度に見せるノードは12点まで
俯瞰の単位を上げて畳む。超える画面を作らない。図は必ずリストで代替可能にする（図は近道であって UI の本体ではない）。

### 原則12: 積み上げは面ではなく muninn に属する
読んだ記録・影SRS・伝票・章の読了は、**どの面で操作しても同じ1つの状態**を触る（`localStorage` のキーを面ごとに切らない）。
日替わりの種（`dayIndex`/`hash32`）も全面で共有し、同じ日は**どの面で開いても同じ顔ぶれ・同じ順序**にする。
— なぜ必要か: 面を選べるようにした瞬間、面ごとに状態を持つのが実装上いちばん自然な形になる。
だがそれをやると**面を切り替えた瞬間に積み上げが消え、「面を試す」こと自体に罰が付く**。
罰があると人は試さないので、比べるために作った仕組みが比べられなくなる。
面が変えてよいのは**見せ方と操作**だけで、**何が真実か**は変えてはいけない。

### 原則13: 比べるのは構造であって書体ではない
**書体（font-family）は比較対象の設計変数から外し、全面共通で1つに固定する**（`index.css` の `--font-base`）。
面ごとの `*.css` で書体を宣言しない。等幅を使ってよいのは「意味として等幅であるもの」——
コード・伝票のプリフォーマット・キーヒント・桁を揃える数値——だけで、そこは共通の `--font-mono` を使う。
面が作ってよい差は**情報密度・余白・操作**であり、それは `font-size` / `line-height` / レイアウトで作る。
— なぜ必要か: この原則が無いあいだ、**`index.css` にベースフォントはどこにも宣言されていなかった**。
面の間にあった書体差は**設計判断の差ではなく、宣言漏れという抜けの差**だった。

> ⚠️ **ここで一度事故を起こしている。原則を足すとき、値の根拠を取り違えた。**
> 「宣言が無い＝ブラウザ既定＝明朝が元の姿」と読んで `--font-base` に Times／明朝を焼き込み、
> **3面すべてを明朝にしてしまった**（日報は見出しだけ Chakra 由来のサンセリフが残り、混在した）。
> 事実は逆で、刷新前は `main.jsx` で **`ChakraProvider` がアプリ全体を包んでいて、Chakra のリセットが
> サンセリフを供給していた**。だから `index.css` に宣言が要らなかっただけである。
> Chakra を日報の中に閉じた瞬間にその供給が切れたのが、本当の原因だった。
> **ベースはゴシック（サンセリフ）が正**——モック（`mock-a` / `mock-b`）も両方ヒラギノ角ゴ系を指定している。
> 教訓: **「宣言が無い」は「既定でよい」の証拠ではない。** 誰がその値を供給していたかを先に確かめる。
それに気づかないまま3案を見比べると、「未指定というバグ」を「案の個性」として評価してしまう。
比較実験の土台は揃えておかないと、比較そのものが汚れる。
なお原則3〜12と衝突した場合は番号の小さいほうを優先する（この原則は最も譲れる）。

### 原則14: 画面の名前は、押す前に中身が分かる言葉にする
タブ名・画面名に**比喩を使わない**。名前は「そこに何があるか」を言い、覚えないと使えない語を作らない。
比喩を使ってよいのは**画面のかたちの呼び名**（`日報`・`親指ひとつ`・`一本の欄`）だけで、
これは選ぶときに説明文と並んで出るので、名前だけで意味が通る必要がない。
— なぜ必要か: 最初の4タブは `面 / 棚 / 探す / デスク` で、**押してみるまで中身が分からないのが3つ**だった。
「タブ名がそのまま "muninn でできること" の要約になる」という狙いは、要約が読者の語彙で書かれて初めて成立する。
さらに `面` は**タブ名（今日の紙面）と、画面のかたちそのもの**の二重の意味で同時に画面に出ていて、
設定側が「いまは『日報』」と添えて誤読を防ぐ応急処置まで必要になっていた（旧 §9）。
比喩を1つ残らず追い出すと、この衝突は名前の付け替えだけで自然に消える。

### 原則15: 図はテキストで、正本の側に持つ
図版は **SVG ファイル**として `atlas/<topic>/assets/` に置き、本文からは `![説明](assets/x.svg)` で参照する。
build が `public/atlas-media/<topic>/` へ複写し、本文中の参照を公開URLへ書き換える。
**SVG 以外の拡張子は build が弾く**（＝「バイナリはコミットしない」を機械で担保する）。
参照先が無い図はビルドを落とす——logs のスキーマ検証と同じ「砦」の考え方。
— なぜ必要か: 最初、机まわりの配置図を**コードフェンス内のASCIIアート**で書いた。
等幅文字では寸法も角度も表現できず、読み手に「分かりにくい」と言われた。代案を3つ検討した結果:
**mermaid** は関係グラフ・フローの道具で、「机上25cm・視線17°下」のような幾何を描けない（箱と矢印に落ちて情報が減る）。
**インラインSVG（`rehype-raw`）** は幾何を描けるが、正本の `.md` に40行の実装が埋まって本文が読めなくなる——
**「正本は markdown」という muninn の根幹に反する**。だから別ファイルのSVGに倒した。
ベクタはテキストで diff が取れるので写真・動画とは扱いを分けてよく、正本の `.md` は1行の参照で済む。
— 同時に判明したこと: `index.css` には `.md table` のスタイルが**あった**のに `remark-gfm` が入っておらず、
正本側で表を使っている16ファイルが**パイプ記号の生テキストとして出ていた**。
**スタイルが存在することは、描画されている証拠にならない。**

### 原則16: 入口の鍵は端末に置く。ただし非常口を必ず1本残す
本文は**コンテンツ鍵 CK 1本**で暗号化し（`CK = PBKDF2(MN_SITE_PASSWORD, 固定salt)`）、
CK を開ける手段を**鍵スロット**として複数持つ（`web/keyslots.json`）。既定は
**パスキー（WebAuthn PRF）で CK を包んだスロット**——Face ID をかざすだけで開き、打鍵はゼロ。
パスワードは**非常口として残すが、画面では畳んでおく**。
— なぜ必要か: 入口が「パスワード欄1つ」だった頃、iPhone でソフトキーボードを開くのが面倒で、
入口そのものが読む頻度のボトルネックになっていた。だが**単に入力を短くする（PINにする）のは誤り**である。
`site.enc.json` は Pages 上で誰でもダウンロードでき、**オフラインで総当たりし放題**だからだ
（PBKDF2 200k でも、GPU 1枚あれば6桁PINは数十秒、12桁の数字で1年のオーダー）。
**公開される暗号文の鍵は強いまま据え置き、楽な解錠は端末に閉じた層で作る**——これが分割の理由。
— なぜ「パスキーだけ」にしないか: PRF 拡張は WebAuthn Level 3（Candidate Recommendation）で、
Chromium / WebKit 実装済みだが段差が残る。**iOS は外部セキュリティキーに拡張データを渡さない**（予備鍵が作れない）。
**QR のクロスデバイス認証ではオンデバイスと異なる PRF 値を返す実装がある**（他人の PC から開けない）。
非対応ブラウザに当たれば詰む。**「開かない日」は必ず来る**ので、非常口を消してはならない。
— 支えている事実: 仮に全端末のパスキーを失っても、**失うのはサイトであって知識ではない**
（正本は markdown、CK の素は GitHub Secrets）。この非対称があるから、既定を大胆にできる。
— 制約: `CK` の salt は `web/keyslots.json` に**固定**する。ビルドごとにランダム生成すると
CK が毎回変わり、既存のパスキースロットが次の push で全部無効になる。ここは動かさない。
— 置き場所の教訓: 端末の登録画面は、最初 `public/enroll.html` という**独立したページ**にした。
「アプリが壊れていても動く非常口」のつもりだったが、**PWA のサービスワーカーが
`navigateFallback` で index.html を返すため、古いSWを掴んでいる端末では登録ページに永久に辿り着けなかった**
（サーバは 200 を返しているのに、画面はパスワードゲートのまま）。
SW が生きている限り、**アプリの外に置いた .html はいつでも飲まれる**。
だから登録はゲートの中（`shell/Enroll.jsx`）に移した——**「index.html が返ってきても目的地」である場所**が、
SW と同居できる唯一の置き場所。ついでに `lib/crypto.js` の重複実装も消えた。
そもそも非常口はパスワードであって登録ではないので、独立させる利益は最初から小さかった。
— 導線の教訓（原則6との衝突）: 登録リンクを「鍵スロットが1本も無いとき」に出す条件で書いたところ、
**1台目を登録した瞬間に、全端末で2台目の登録導線が消えた**。
`keyslots.json` の状態は**サイト全体のもの**で、「この端末が登録済みか」ではないからだ。
しかも WebAuthn には**この端末に鍵があるかを事前に問い合わせる手段が無い**（プライバシー上わざと無い）。
結果、未登録の端末には「押しても無言で何も起きない Face ID ボタン」だけが残った。
**判定できない条件で導線を隠すな**——導線は出しておいて、押した人に試させるほうが安い。
併せて、WebAuthn が「中断」と「鍵が無い」を同じ `NotAllowedError` で返すことを踏まえ、
**失敗時は必ず何か言い、非常口を開く**。無言で元の画面に戻すのは、壊れているのと区別がつかない。

## 4. 情報構造（IA）

**読む面のかたちは1つではない。** 読者はいま3つの「面」から1つを選ぶ（§10。画面に出す呼び名は `画面のかたち`）。
下の5タブ構成は、そのうち **`日報` という1つの面の中の IA** であって、サイト全体の IA ではない。
——2026-08-01 以前はこの2つが同じものだった。分けたのは、`親指ひとつ` と `一本の欄` が
**そもそもタブもページ遷移も持たない**（＝この IA が原理的に載らない）ためである。

サイト全体として固定なのは、**面の外側（shell）が握る2つの URL だけ**:

```
#/settings   画面のかたちを選ぶ。どの面が選ばれていても開ける非常口
#/note/:slug · #/follow/:name（+/player/:slug）· #/atlas/:slug（+/concept/:cslug）· #/log/:topic（+/entry/:slug）
             対象へのディープリンク。面が変わっても生き続ける契約（面ごとの流儀で表示してよいが 404 にしない）
```

これ以外の画面内の移動は**各面の自由**（URL に出す/出さないも面が決める）。
共通のルータを全面に強制していないのは、面Bが**ページ遷移そのものを廃止**する設計だからで、
ここで共通ルータを強制すると比べたかった案が最初から成立しない。

### `日報` の面の中の IA

**concern（ファイルの置き場所）ではなく、読む姿勢で割る。**
タブ名がそのまま「muninn でできること」の要約になっているのが要点で、これが「何ができるんだっけ」への構造的な回答になっている。
そして**その要約は読者の語彙で書く**（原則14）——比喩のタブ名は、要約ではなく暗号になる。

```
▣ 今日     /            めくる     — 今日の紙面。既定の入口
▤ 続きもの /series      続きを見る — 中身が増える入れ物（連載・記録帖・定点）の一覧と分類
▦ テーマ   /shelf       俯瞰する   — 在庫マップ（面積比例）。タグが第一階層
⌕ 探す     /search      当てる     — 全concern横断・本文込みの全文検索
✎ 依頼     /desk        頼む       — できること／在庫の健康／未送信の伝票／画面のかたち
```

（2026-08-12 以前は `面 / 棚 / 探す / デスク` の4つ。改名の理由は原則14、`続きもの` の新設理由は次項）

**なぜ `続きもの` が要るか**: muninn には、単体で完結する記事とは別に**中身が増え続ける入れ物**が3種類ある
（連載＝章が増える／記録帖＝件数が増える／定点＝回数が増える）。
これらはテーマの在庫マップでは**中の1ノードとして散らばる**だけで、束ねて見せる場所がどこにも無かった。
結果、「そもそもどんな連載があるんだっけ」に**サイトが一度も答えられていなかった**——
検索は名前を覚えている人にしか効かないが、覚えていないから探している。
この面は**その1問だけ**に答える（原則7）。分け方は`かたち別 / テーマ別 / 動いた順`の3つに固定し、増やさない。
先頭には**読みかけの連載の「続きから」**を差し出す（原則1）。読みかけが1本も無いときだけ、
最新の1本を「まずはここから」として出す——未読を全部並べると下の一覧と丸ごと重複して嵩むだけになる。

**廃止したもの**: `/notes`（90件フラットリスト）・`/moc/:slug`（生 markdown）・`/logs`（トピック索引）。
いずれも「置き場所の写像」であり、テーマと検索に吸収された。旧 URL はリダイレクトする（PWA のホーム追加やブックマークから踏まれるため）。
`/logs` だけは**トピックの索引という役目を `続きもの` が継いだ**ので、そちらへ送る。

**どの面も、設定への導線を必ず1つ持つ**（日報は `依頼` の末尾）。
面ごとに操作体系がまったく違うので、ここが塞がると「試したら二度と戻せない」が普通に起きる。
`#/settings` を直打ちできるのはその保険であって、代わりではない。

**画面に内部語彙を出さない。** ノート→記事、フォロー→定点、アトラス→連載/章、ログ→記録帖、MOC→束、
タグ→テーマ、連載・記録帖・定点の総称→続きもの。concern 名はコードとこの文書の中だけで使う。
**`面` も内部語彙に降格した**（コードの `face` / `faces/` はそのまま）。画面に出す呼び名は **`画面のかたち`**。
`日報`・`親指ひとつ`・`一本の欄` という個々のかたちの名前は、選ぶときに説明文と並んで出るので画面に出してよい。
`モードA`・`案B`・`thumb`・`field` のような開発上の呼び名は出さない。
タグの表示名（`lib/graph.js` の `TAG_JA`）も同じ話で、**未登録のタグは英語 slug のまま画面に出る**。
テーマ名は読者が選ぶための名前なので、使われているタグには日本語を用意しておく。

## 5. `日報` の組版モデル

面は**スコア順のフィードではない**。固定の段があり、各段に適格なカード型が優先順で落ちる。

```
題字   常時
リード  speed → milestone → chapter-new → brief → feature → revival
袖     countdown → slip（伝票3件以上のときだけ）
再読   recall ×3
連載   chapter → chapter-request
特集   feature（MOC束 → タグ束）
記録   series → compare
在庫   常時
```

**リード段が空にならないことが構造的に保証されている**のが肝。
下2つ（`feature` = 束の日替わりローテーション、`revival` = 最終更新が最も古い群からの日替わり）は
**記事が1件でもあれば必ず出る**ため、上5つが全滅してもリードは埋まる。

各段は在庫が無ければ**段ごと消える**（「ありません」と書かない）。

## 6. 想起の二層モデル

静的サイトなので `srs` を markdown に書き戻せない。この制約を二層で解く。

```
層1 影SRS（localStorage）    判定が即座に効く。明日はもう出ない、次は6日後
                             → サーバに何も送っていないのに、体験としてはSRSが回っている
層2 伝票（`依頼` で束ねる）   溜まった判定を1つのプロンプトで /mn-review に流し込む
                             → 正本が追いついたら影を捨てる（自己修復同期）
```

**両側が同一の SM-2 式を使うこと。** 式が同じなので値が必ず一致し、送信を忘れても乖離しない。
`/mn-review` の式を変えるときは、必ずサイト側も同時に変える。

**想起はクイズではなく読み物として出す。** muninn のノートはタイトルが言い切り形＝答えそのものなので、
タイトルを伏せて問い（`recall`）だけを見せる。「クイズを始める」というモード切替が無いので起動コストがゼロ。
`recall` が無いノートはタグと文脈で degrade する——**劣化するが壊れない**。

**自己申告の甘さを設計で補正する。** 一言を書いたかで q を分岐（書いて わかった=5 / 書かず=4 / あやしい=2）し、
サイト由来の ease 成長は skill 由来より 30% 抑える。伝票が20件たまったら
「本気の1問を `/mn-review` で受けないか」と提案する（校正チェックポイント）。
——摩擦の低さは強みだが、それが定着の質を静かに下げるのを放置しない。

## 7. データの流れと責務分担

```
markdown（正本）
   ↓  build-data.mjs        ── ビルド時にしかできないことだけをやる
site.json                       ・git 履歴からの最終更新日
   ↓  （復号してメモリへ）        ・スキーマ検証（logs の必須/enum/範囲。壊れていたらビルドを落とす）
                                ・図版の複写（atlas/*/assets/*.svg → public/atlas-media/。原則15）
lib/crypto.js · webauthn.js  ── 解錠。CK を中心に据え、開ける手段だけを差し替える（原則16）
   ・パスキー: HKDF(PRF出力) で slot.wrapped を解いて CK を得る
   ・パスワード: PBKDF2 で CK を直接導く（非常口）
   ※ 端末の登録は shell/Enroll.jsx（ゲートの中。SW に飲まれない場所を選んだ＝原則16）
lib/graph.js                 ── 全concernを1つのノード集合として見る
   ・被リンク（理由つき）          ※ route を ID にしているので wiki.js のリンク解決とそのまま噛み合う
   ・タグ横断索引
   ・MOC束のタグ自動割当
lib/series.js                ── 「続きもの」（連載・記録帖・定点）を同じ形に揃える
   ・件数／読了／最終更新          ※ 読了は localStorage 由来なので呼び出し側から reads を渡す
   ・続きから（順路上の最初の未読）  ※ 一覧の説明文は本文の書き出しから作る（正本に説明用の項目を足さない）
lib/edition.js               ── 閲覧日 × 在庫 で今日の紙面を組む
lib/recall.js                ── 影SRS・伝票・閲覧履歴（localStorage 一切合切）
```

**コードの層は3つ。判断の基準は「面によって答えが変わるか」**:

```
lib/       どの面でも同じ答えを返すもの（復号・索引・被リンク・紙面編成・影SRS・伝票）
           → 面の名前を知ってはいけない。ここに面の分岐が入った時点で、面ごとに真実が割れる
shared/    どの面でも意味が同じ部品（本文の描画・数値と前回比・相対日・コピー）
           → UI ライブラリに依存させない。依存させると、それを使わない面が道連れになる
shell/     面の外側（復号ゲート・面の登録簿・設定・ディープリンクの受け口）
faces/<面>/ 何をどう並べるか・どう操作するか。**揃えないのが目的**
```

面ごとの CSS は `[data-face="<id>"]` の下に閉じる。UI ライブラリの Provider も面の中で立てる
（`日報` の Chakra は `faces/daily` の持ち物）——負けた面を消すとき、依存ごと落とせる状態を保つため。

**判断の基準**: ビルド時にやるのは「git が要る」「検証で落としたい」ものだけ。
横断計算・検索・グラフ構築は**全部クライアントでよい**（全データが復号済みでメモリ上にあり、90記事規模なら数ミリ秒）。
専用の検索インデックスを作らないのは過剰設計を避けるため。

**正本のスキーマを増やすとき**は、それが「サイトのための都合」ではなく
「記録として正しい情報」かを問う。`metrics` は観測値そのものなので正当。`metric_goals` は
指標の意味の宣言なので正当。表示の都合だけの項目は入れない。

## 8. 意図的にやらないこと

| やらない | 理由 |
|---|---|
| 90ノードの force-directed グラフ | 7〜8個の団子が浮かぶだけで情報量ゼロ。モバイルでは毛玉になる |
| 全ノート一覧ページ | 「置き場所の写像」そのもの。テーマと検索が代替する（`続きもの` が一覧するのは**入れ物**だけで、記事は一覧しない） |
| 未消化件数のバッジ | 行動を止める。原則3 |
| ビルド日基準の派生フラグ | push が止まると面が古びる。原則2 |
| サイト上での書き込み UI | 正本は markdown。作れるのは依頼まで |
| 号数・発行部数のような演出 | 新聞メタファーの装飾的な部分。中身がないのに様式だけ真似ない |
| 自動生成リンクを人力リンクと同じ見た目で出す | 「本人がそう言った」と「機械がそう推測した」を混ぜるとナレッジベースの信頼が壊れる |
| **面の自動切り替え**（時間帯・端末・場面で勝手に変える） | 選ぶのは人。勝手に変わると「どの面が良かったか」を本人が判断できなくなり、比べるために作った仕組みが壊れる。UI が予測不能になる代償も大きい |
| **3つの面のデザインを揃えること**（ただし書体を除く） | 揃えないのが目的。揃えた時点で比べる意味が消える。**書体だけは例外**で、全面共通に固定する（原則13）——面の間の書体差は設計判断ではなく宣言漏れだったため、比較の土台として揃える側に倒した |
| 面ごとに `localStorage` のキーを切ること | 原則12。面を試すことに罰が付く |

## 9. 既知の未達

- **`brief`（予習）カードの素材が無い。** `follows/*/briefs/` を作るか、`/mn-brief` の出力を
  正本に落とす運用を決める必要がある。現状は snapshot で代替している。
- **記録帖の比較テーブルが実データで検証できていない。** entries が1件しかないため。2件目が入ってから確認する。
- **degrade 表示（`recall` 無し）の経路が実データで踏まれなくなった。** これは2度目で、
  1度目（2026-07-31）は「付け忘れたら埋める」という運用の約束で締めたが、**約束は守られず再発した**
  （2026-08-15、22件）。2度目はテンプレート側を直して塞いだので、次に再発したら
  **運用でも型でもなく、ビルドで落とすべきサイン**と考える（`kind: knowledge` に `recall` 必須の検証）。
  `依頼` の「想起の問いが無い記事」がゼロでない状態は、放置せず埋める。
- **面が3つある間、保守は3倍になる。** 原則もこの文書も、面ごとに解釈が割れていく。
  これは承知のうえの一時的な負債で、**返済期限は 2026-08-29**（§10）。期限を延ばす判断をするなら、
  延ばす理由をこの節に書くこと。書けないなら延ばさない。
- **`親指ひとつ` と `一本の欄` は登録されているだけで中身が無い**（PBI-02 / PBI-03）。
  いまはどちらも「まだ作られていない」旨と、ディープリンクで来た対象の素朴な表示、

  **使われないのが当たり前になり、比較の材料にならない**ので、中身が入るまで期限の起点は動かさない。

  束ねて見る道はまだ無い（素材は `lib/series.js` にあるので、面ごとの組版を足せば載る）。
  面を1本に絞るとき（§10）に、残った面が日報でないならここを移植する。
- **`日報` の「できること」に `/mn ... notes に記録して` のような依頼文が出ている。**
  内部語彙を画面に出さない原則（§4）と厳密には衝突するが、これは
  「Claude にそのまま渡す文字列」なので正確さが優先される。
  依頼文と表示テキストの線引きは、まだ明文化できていない。

- **鍵スロットの失効手段が無い。** 端末を失くしたときスロットを消しても、
  **CK が変わらない限り、以前公開された `keyslots.json` と暗号文の組があれば開けてしまう**。
  正しい失効は「`MN_SITE_PASSWORD` を変える → CK が変わる → 全スロットを作り直す」で、
  いまはこれを手作業でやるしかない。失効が現実に必要になったら手順を書く。
- **図版パイプラインは `atlas/` にしかない。** `notes/` から図を貼る道は無く、参照しても

## 10. 3つの面は実験である（終わらせ方を先に決める）

2026-08-01 から、読む面を **`日報` / `親指ひとつ` / `一本の欄`** の3つから選べるようにした。
`docs/web-uiux-experiment/` で3案を実データのモックまで作って審査したが、
**両案の最大の賭けは、数日使ってみないと答えが出ない種類の問い**だった——
案A（親指ひとつ）の「方向の記憶が1日数分の利用頻度で育つか」も、
案B（一本の欄）の「上向きの組版に体が馴染むか」も、紙の上では判定できない。
だから実地で比べる。

> ⚠️ **これは恒久構成ではない。** 読者1人のプロダクトで3つの面を維持し続けるのは、単純に保守が3倍になる。
> 実験は始め方より**終わらせ方**を先に決めておかないと、ただの負債になる。

### 観測期間

**4週間（2026-08-01 〜 2026-08-29）。** ただし起点は「3つの面に中身が入った日」であって、
土台ができた日ではない（§9）。中身の無い面を数えても比較にならない。

### 判断に使う材料（これ以外は使わない）

設定画面に出している2つ。どちらも**増えるカウンタ**であって、未消化の借金ではない（原則3）。

| 材料 | 出どころ | 何を見るか |
|---|---|---|
| 面ごとの**使った日数** | `mn.face.usage`（面を開いた日を1日1回だけ数える） | どれを選び続けたか |
| 面ごとの**再読の枚数** | `mn.recall.log` の `via`（どの面で判定したかのラベル） | どれが実際に読ませたか |

**「気に入った」と言ったかどうかは材料にしない。** 好みの申告と、実際に開いて読んだ量は一致しない。
この2つは自己申告を挟まずに取れるから選んでいる。

### 絞ったあと何をするか

1. 残す面を1つ決める。
2. **負けた面のコードを消す**（`shell/face.js` の登録簿から1行、`faces/<id>/` を丸ごと）。
   残す面が `日報` でないなら、Chakra への依存も一緒に落とす。
3. この §10 を「何を選び、なぜそうしたか」の記録に書き換える。**節ごと消さない。**
4. §4 の「面のかたちは1つではない」を、選ばれた面の IA に戻す。

**面を1つに絞ったあとも設定画面は残す。** 面の選択肢は消えるが、`#/settings` という非常口の
契約自体は他の設定（文字の大きさなど）が入る器として生きる。

## 11. この文書の運用

- **サイトを変更したら、この文書を同じコミットで更新する。**
  更新するのは「思想が変わったとき」と「未達が解消/追加されたとき」。
  ボタンの色を変えた程度では更新しない——**ここは実装の写しではなく、判断の拠り所**である。
- 新しい原則を足すときは、**なぜそれが必要になったか（どの失敗から学んだか）を必ず書く**。
  理由のない原則は次の担当者に無視される。
- 原則どうしが衝突したら、番号の小さいほうを優先する。衝突が繰り返されるなら原則の側を直す。
- 刷新の経緯・比較検討の記録は `../docs/web-renewal/` にある（現状分析・3案・両審査・ワイヤーフレーム）。
  この文書はその**結論だけ**を持ち、経緯は持たない。
