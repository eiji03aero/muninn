# RATIONALE — 設計判断の記録

FSPEC をこの形にした理由と、**入れなかったもの** の理由。
判断が割れうる箇所はすべてここに残す。

---

## 0. 出発点

要求は「DRY であることと網羅的であることの両立」だった。この 2 つは普通は緊張関係にある。
DRY を突き詰めると記述が分散して全体像が見えなくなり、網羅性を求めると同じことを
複数の視点から書き直すことになる。

FSPEC はこれを次の分業で解く。

- **人間（と AI）が書くのは、事実の唯一の定義だけ。**（DRY 側）
- **全体像・一覧・網羅性チェックは、コンパイラが導出する。**（網羅性側）

したがって言語設計の中心的な問いは常に「これは書かせるべきか、導出すべきか」だった。
以下の判断はほぼすべてこの問いから出ている。

---

## 1. カバレッジ要件への対応方針

指示にあった 6 つの関心事の扱い。

| 関心事 | 扱い | 判断 |
|-------|------|------|
| 利用者の種別と権限 | **一級市民に分解**（`actor` / `capability` / `scope` / `grant` の 4 つ） | §2 |
| ドメイン上の概念とその関係 | 概念は一級市民（`entity`）、**関係は畳んだ**（フィールドの型） | §3 |
| 常に成り立つべき制約と、その違反時の扱い | **一級市民**（`rule`）。違反時の扱いは `rule` の属性に畳んだ | §4 |
| 利用者から見た振る舞いの単位 | **一級市民**（`feature`） | §5 |
| 時間軸を持つ状態の変化 | **2 つに分けた**：状態機械は `lifecycle`、時刻起動は `job` | §6 |
| 機能間の依存・影響関係 | **書かせない。全面的に導出**（参照グラフ + `event` + `after`） | §7 |

### 1.1 なぜ権限を 4 つに割ったのか

「ロール × 機能」の表を直接書かせる案（`feature` に `roles: [DeptAdmin, SysAdmin]`）は却下した。
業務系 Web アプリの権限が壊れる原因は、ほぼ常に **範囲（scope）** の扱いだからである。
「部門管理者は予約を取り消せる」は正しくない。正しくは「自部門の予約を取り消せる」であり、
この "自部門の" が機能ごとに散らばると必ず矛盾する。

そこで:

- `capability` … 何ができるか（範囲を持たない原子単位）
- `scope` … どの範囲か（エンティティ非依存の述語として 1 度だけ書く）
- `grant` … 誰が・何を・どの範囲で（唯一の対応表）
- `actor` … ロールと、その包含関係

`feature` 側には `capability` を 1 つ書くだけにした。範囲の判定が feature に散らばらない。

実証課題では、この分割が `F_view_reservations` を **1 本で 3 ロール分まかなう** 形に落とした。
一般利用者には自分の予約、部門管理者には部門の予約、システム管理者には全部が返る。
機能を 3 本書き分けていれば、いずれ 3 本の間に差分が生まれていた。

`scope.where` が参照できるパスを `self.owner` と `self.scope_key` の 2 つに固定したのは、
scope をエンティティごとに書き分けさせないため。代償として、
所有者・区画のどちらでもない軸（例: プロジェクト単位）で切りたくなったとき表現できない。
そのときは軸を増やす（`scope_by2:`）のではなく、**scope 述語に entity 固有の条件を書けるようにする**
拡張（`scope S_x on E { where: ... }`）を 1.1 で検討する。今はスコープ軸を 2 本に絞る判断をした。

### 1.2 ロール用 `enum` を禁止した理由

`actor` を宣言すると同時に、それは組込み型 `Actor` の値になる。
`enum Role { Member, DeptAdmin, SysAdmin }` を別に書くと、ロールの定義が 2 箇所になり、
片方だけ更新される事故が起きる。検査 C-10 で禁止した。同じ理由で
状態を表す `enum` も禁止（C-14）し、`State<L>` を使わせている。

## 2. 制約を `rule` に閉じ込めた（最重要の判断）

### 2.1 述語を書ける場所を構文的に制限した

`feature` に `precondition:` を書ける言語にすると、必ず同じ条件が複数の feature に写経される。
「重複予約は禁止」は作成にも変更にも管理者操作にも関わるからだ。

そこで **述語（Bool を返す式）を書ける位置を `rule.assert` / `rule.when` / `scope.where` /
`derive` 本体 / `effect` の条件 / `scenario.then` に限定した**（検査 C-19）。
`feature` に制約を書く構文が存在しない。

代わりに `rule` が自分の適用先を宣言し（`on:`）、どの feature に効くかはコンパイラが計算する
（§9.1.1 の束縛アルゴリズム）。**「制約 → 機能」の向きに書き、「機能 → 制約」の向きは導出する。**
これが「同一の制約が 2 箇所以上に書かれていない」の構造的な保証である。

さらに念のため、正規化した `assert` の AST ハッシュが一致する rule が 2 本あればエラーにした
（C-DUP）。言い換えを含む重複はさすがに検出できないが、コピペ由来の重複は機械的に潰せる。

### 2.2 違反時の扱いを「文脈別」にした

ここは設計中もっとも迷った点。

「役務提供終了後にかかる予約は保持しない」は、新規作成のときは **拒否**、
既存予約に対しては **自動取消** である。素直に書くと制約が 2 本に割れる。
2 本に割れた瞬間、片方だけ条件が変わって矛盾する — これがまさに解決したかった問題だった。

そこで `on_violation` をブロックにして、文脈別の処分を書けるようにした。

```fspec
on_violation {
  when ctx.op.kind == create : reject(E_BEYOND_SERVICE_END, blames: input.period)
  default: compensate(E_RESERVATION_ENDED_BY_CANCELLATION) { effect { ... } }
}
```

述語は 1 つ、扱いが 2 つ。記述順で最初にマッチしたものを採るので決定的。

処分を 4 種（`reject` / `warn` / `allow` / `compensate`）に限ったのも判断で、
とくに `compensate` を入れたことが実証課題の質を決めた。
「キャンセル期限を跨いだ場合の課金」は、**「期限までに取り消すこと」という制約の違反に対する
是正処置** として書ける。期限も違約金も rule 1 本にしか現れない。
`compensate` がなければ、これを feature の分岐として書くことになり、
「期限」という概念が制約側と機能側の 2 箇所に現れていた。

### 2.3 上書き（override）を rule 側に置いた

「管理者による強制上書き」を別 feature にする案（`F_force_create_reservation`）は却下。
上書き可能な操作が増えるたびに feature が倍になり、本体側の変更が二重に必要になる。

`rule.override` に「どの権限で」「どの入力フラグで要求され」「上書き時に何をするか」を書く。
上書きされる制約は 1 つなので、記述も 1 箇所で済む。
`R_no_double_booking.override` の effect が、競合する既存予約を取り消す部分まで含んでいる。

副次的な利点として、`checkRule()` が `overridableBy: <capability>` を返せるので、
UI 側は「あなたには上書きボタンが出せる／出せない」を仕様から直接判定できる。

同じ仕組みで「システム管理者による違約金免除」も書けた（`R_cancel_before_deadline.override`）。
免除のための feature も、免除フラグを見る分岐も、どこにも書いていない。

### 2.4 `recheck` を自動推論しなかった

不変条件が `self` 以外のエンティティを参照するとき、そのエンティティが変わっても条件は破れうる。
「契約を解約したら、期間外の既存予約が違反になる」がまさにそれ。

理屈のうえでは述語から逆方向の到達集合を推論できそうに見えるが、一般には決定不能で、
できるように制限すると述語の表現力が実務に耐えなくなる。近似で自動化すると
「たまに漏れる」という最悪の性質になる。

そこで **明示させる**判断をした。`recheck { on write E as x : <再評価対象の集合> }`。
そのかわり、外部エンティティを参照する不変条件に `recheck` がなければ **エラー**にした（C-21）。
書き忘れは静的に検出される。「片方向しか考えていない制約」という、自然言語仕様で
もっとも見つけにくい欠陥が、機械的に潰れる。

`recheck` は §3.12 の副産物ももたらす。`recheck` を持つ rule はそのまま
「同時実行制御が必要な箇所」の一覧になる。

### 2.5 是正処置の後に再評価しない

`compensate` / `override` の effect が別の制約を破る可能性はある。不動点まで反復する案は
却下した。停止性が保証できず、評価順によって結果が変わる余地が生まれ、決定論が壊れる。
1 回だけ適用して終わりにし、是正処置が別の制約を破るケースは `scenario` で検出する方針にした。

## 3. ドメイン — 関係を一級市民にしなかった

`relation Reservation -> Room { cardinality: many_to_one }` のような独立宣言は入れなかった。
フィールドの型（`Ref<E>` / `List<Ref<E>>` / `?`）が多重度をすべて表現できるので、
独立宣言を置くと同じ関係が 2 箇所に書かれることになる。逆方向が必要なときだけ
`inverse:` を 1 行足す。

### 3.1 値オブジェクト（record）を入れなかった

`record Money { amount, currency }` のような構造体を入れる案は却下した。理由は 2 つ。

1. 業務系 Web アプリで本当に必要な複合値（金額・期間・区間）は、組込み型として提供したほうが
   演算子・丸め・比較の意味論を仕様として固定できる。ユーザ定義 record にすると
   `overlaps` のような演算を各仕様が再定義することになり、決定性の保証が難しくなる。
2. それ以外の複合値（請求明細など）は、実際には主キーを持ちたくなる。
   最初から `entity` にしておくほうが後で困らない。

代償: 「主キーを持たせたくないが構造化したい値」が表現できない。
実証課題では `InvoiceLine` を主キー付き `entity` にした。実害はなかった。

### 3.2 エンティティの継承・サブタイピングを入れなかった

型階層はドメインモデルとしては自然だが、仕様レイヤーに入れると
「どの制約がどのサブタイプに効くか」の解決規則が必要になり、束縛アルゴリズム（§9.1.1）が
一意でなくなる。決定論を優先して外した。表現したい場合は
列挙 + 省略可能フィールド、または別エンティティ + `rule` で書く。

## 4. 振る舞い — 書かせないものを最大化した

`feature` から意図的に取り除いたもの:

| 取り除いたもの | 導出方法 | 理由 |
|--------------|---------|------|
| `reads` / `writes` | `effect` / `value` / 束縛された rule から解析 | 手書きすると実装とずれる。ずれた瞬間、影響追跡が嘘になる |
| エラー一覧 | 束縛された rule の `on_violation` から | 仕様書のエラー一覧が実態と食い違うのは典型的な事故 |
| 前提条件・事後条件 | `applies(F)` から | §2.1 |
| 状態遷移のトリガ | `effect` の `transition` 文から | 遷移表と実装の二重管理を避ける |
| 発行イベント | `emit` 文から | 同上 |

書かせているのは「その機能が何をするか」（`effect`）と「誰が実行できるか」（`actor` / `capability`）
と「何を受け取るか」（`input`）だけ。それ以外はすべて計算で出る。

### 4.1 query を feature に含めた

参照系を仕様から外す案もあったが、含めた。理由は権限である。
「誰に何が見えるか」は業務系アプリでは立派な仕様であり、しかも
`grant` の scope をそのまま返却リストのフィルタとして再利用できる。
一覧画面の可視範囲が権限表から自動的に決まるのは、実装事故を実際に減らす。

ただし、返却型が `Ref<E>` でない query（値の射影）には scope フィルタを適用しない。
「空き時間帯は全員に見せるが、誰の予約かは見せない」という要求を素直に書くためである。
`F_view_room_availability` がその例。

### 4.2 `effect` を宣言的（pre-state 評価）にした

手続き的にすると、文の順序が結果を変える＝順序が仕様の一部になる。
`effect` は状態差分の宣言であり、すべての式は操作前の状態に対して評価され、
差分は原子的に適用される。同一フィールドへの二重代入は実行時エラーにした。

代償: `update self { plan: X }` の後に `self.plan` と書いても旧値になる、という
直感に反する挙動がある。これは `effect` の冒頭に注記を書く運用でカバーする
（実証課題の `F_change_plan` にコメントを入れてある）。
手続き的にして順序依存を導入するより、こちらのほうが害が小さいと判断した。

### 4.3 `draft` / `commit` を入れた

生成系の機能では、不変条件を「まだ存在しないインスタンス」に対して評価する必要がある。
`draft E as self { ... }` で候補を作り、rule はそれを `self` として見る。
これがないと、生成時の制約を「入力に対する制約」として書き直す羽目になり、
更新時の制約と重複する。

## 5. 時間軸 — 2 つに分けた

「時間軸を持つ状態の変化」は 2 種類ある。

1. **状態機械としての変化**（予約が Confirmed → Cancelled）→ `lifecycle`
2. **時刻そのものが引き金になる変化**（毎月 1 日に請求を締める）→ `job`

1 つの構文にまとめる案（遷移に時刻トリガを書ける）は却下した。
状態機械の遷移は「誰かの操作の結果」であり、時刻起動は「操作なしに起きること」で、
認可・入力・エラーの扱いがまったく違う。混ぜると両方が歪む。

### 5.1 `lifecycle` にガードもトリガも書かない

- **トリガ**は `effect` の `transition` 文から導出する（二重管理を避ける）。
- **ガード**は `rule { kind: guard, on: [transition T] }` として書く。
  遷移条件も他の制約と同じ場所に集約されるので、「遷移条件だけ別の場所にある」状態にならない。

結果として `lifecycle` は状態と辺だけの、非常に薄い宣言になった。
そのぶん検査（到達可能性・出遷移・デッド遷移・初期状態）が単純明快に書ける。

### 5.2 「キャンセル期限」を timer にしなかった

期限を「時刻になったら発火するタイマー」として設計する案があったが、却下。
期限は状態ではなく **述語** であり、取消が試みられた瞬間に評価すれば足りる。
タイマーにすると、期限到来時に何も起きないのに状態遷移やジョブが必要になり、
仕様が実装都合で汚れる。`ctx.now <= self.period.start - P_cancel_free_window` で十分。

### 5.3 ISO 8601 duration の年・月を禁止した

`P1M` は 28〜31 日と長さが変わる。決定論を掲げる以上、長さが文脈依存のリテラルは置けない。
暦月の加算は `add_months(date, n)`（月末クランプ）として関数にし、
タイムゾーンを明示的に受け取らせた。実証課題の `D_next_period` がこれを使っている。

## 6. 数値 — 浮動小数点を言語から消した

日割り計算がある以上、ここは妥協できない。

- 浮動小数点型は存在しない。
- `/` の結果は常に厳密有理数（`Rational`）。
- `Rational` はエンティティのフィールドに格納できない（C-05）。
- `Money` / `Decimal(s)` に落とすには `round_money` / `round` の明示呼び出しが必須（C-06）。
- 丸めモードは `param` に固定する（実証課題では `P_money_rounding = HALF_UP`）。

これにより「日割りの端数処理が実装ごとに違う」が構文レベルで起きない。
サーバとクライアントで同じ `derive` を評価しても必ず同じ値になるので、
プラン変更画面の差額プレビューをクライアント計算にできる。

代償: `(to_price - from_price) * ratio` のような式で、どこで丸めるかを毎回書く必要がある。
冗長だが、丸め位置は日割り計算の仕様そのものなので、明示させるのが正しいと判断した。

`derive` から `ctx` とエンティティ外延の参照を禁止した（C-07）のも同じ動機で、
計算が完全に引数だけの関数になり、単体テストとクライアント実行が保証される。

## 7. 機能間の依存 — 3 つの経路に分けた

「機能間の依存・影響関係」を書かせる構文（`depends_on:`）を主役にする案は却下した。
人が書いた依存関係は必ず実態からずれる。

FSPEC では依存が 3 つの経路で現れる。

1. **データ依存**（導出）— 同じエンティティを読む／書く。参照グラフの `reads` / `writes` 辺。
2. **通知依存**（明示）— `event` の `emit` と `trigger: on`。疎結合な連携はこれで書く。
3. **順序依存**（明示）— `after:`。「A が成立していないと B は意味を持たない」を書く唯一の場所。

そして影響追跡は §11 の辺定義（20 種、これで閉じている）に対するグラフ演算として定義した。
辺の作られ方が閉じた表になっているので、`impact()` の結果は一意に定まる。

`policy` モジュールを設けたのも、この依存関係を構造として見せるためである。
`reservation` は `billing` を import せず、`billing` も `reservation` を import しない。
両者にまたがる制約は必ず `policy` を通る。結果として
「契約側の変更が予約側のどこに効くか」がモジュール構造の時点で読める。

## 8. 言語形式について

### 8.1 なぜ YAML / JSON ではなく独自構文か

AI が書き AI が読むなら YAML でよい、という判断もありうる。しかし却下した。

1. **式言語が必要**。`exists r in Reservation where ...` を YAML に埋めると、
   結局その文字列に対する独自パーサが必要になる。だったら全体を一貫した文法にしたほうがよい。
2. **人間がレビューする**。制約の可読性は YAML のネストより中置記法のほうが圧倒的に高い。
   レビューが成立しない仕様言語は要件を満たさない。
3. **静的検査の質**。位置情報つきのエラーを出すには専用パーサが要る。

そのかわり、パーサが素直に書ける文法にした（`grammar.ebnf`）。
改行区切り・ブロックはブレース・式は標準的な優先順位の中置記法・宣言種別ごとに
サブ宣言キーワードが有限集合なので LL(2) で決定的に解析できる。
インデント有意にしなかったのは、LLM が生成するときの事故（インデント崩れ）を避けるため。

### 8.2 `doc:` を非規範にした

自然言語の但し書きへ逃げないことが要件だった。そこで `doc:` は
**いかなる導出にも使われない** と規定した（P6）。`doc:` に制約を書いても効果がない。
制約を効かせたければ `rule` にするしかない。

### 8.3 `scenario` / `world` を言語に入れた

テストは設計レイヤーの成果物、という整理もありうるが、入れた。
AI が書いた仕様を人間がレビューするとき、「この仕様はこう解釈される」を具体例で
確認できることの価値が大きい。しかも `scenario` は IR に載って機械実行できるので、
仕様自身の回帰テストになり、`derive` のテストベクタにもなり、E2E テストの原型にもなる。

`world` を別宣言にしたのは、fixture の重複を避けるため。制約の重複だけでなく、
具体例のデータ重複も避けたかった。

### 8.4 `requirement` を薄いアンカーにした

要件そのものを FSPEC で表現する案は却下した。要件は上流の成果物であり、
仕様言語が要件の書式まで規定すると越権になる。
`requirement` は ID・出典・優先度だけを持つアンカーで、
価値は「`traces` されていない要件を検出できる」（C-COV-1）ことに尽きる。

## 9. 扱わないと決めたもの

| 対象外 | 理由 |
|-------|------|
| 画面・レイアウト・画面遷移 | 設計判断。ただし画面制御の**根拠**（可視性・活性・項目エラー・確認ダイアログ）はランタイム API で提供する（SPEC §13.2）。仕様は「何が許されるか」を持ち、「どう見せるか」は持たない |
| API エンドポイント / HTTP / GraphQL | プロトコル選択は基本設計の決定。`error.class` をプロトコル中立にし、写像は WORKFLOW §3.6 の表で行う |
| DB スキーマ・索引・正規化 | 同上。ただし WORKFLOW §3.13 で候補は機械的に出す |
| トランザクション境界・ロック戦略 | 実装戦略。ただし WORKFLOW §3.12 で「直列化が必要な箇所」は機械的に特定できるようにした。ここは「扱わないが、必要性は指し示す」という中間の立場をとった |
| 非機能要件（性能・可用性・SLA） | 述語として表現できない。無理に入れると `doc:` に書くのと変わらない飾りになる |
| メッセージの多言語カタログ | `error.message` は既定文言のみ。翻訳は実装の関心事 |
| ループ・再帰・任意計算 | 全域性と決定論のため。`derive` は非再帰の DAG（C-23） |
| ワークフロー／BPMN 的な長期プロセス記述 | `lifecycle` + `job` + `event` の 3 つで表現できる範囲に留めた。専用のプロセス記述を足すと、状態の定義場所が 2 つになる |
| バージョニング付きのエンティティ履歴・監査ログ | 監査要件は横断的で、仕様に書くと全エンティティに同じ記述が増える（DRY 違反）。`event` を購読して実装する設計事項とした |
| 承認フロー・多段階ワークフロー | 実証課題に不要。必要なら `lifecycle` の状態と `capability` で表現できるため、専用構文は入れない |

## 10. 実証課題における個別の仕様判断

言語ではなく「会議室予約システムの仕様」として決めた事項。要件に明記がなかったため、
下記のとおり決めて仕様に書き下した。実運用では要件側に確認すべき論点である。

| # | 論点 | 決めたこと | 理由 |
|---|------|-----------|------|
| 1 | 契約の単位 | 部門ごとに 1 件（`Subscription.department`） | 3 ロールのうち部門管理者に契約操作を割り当てるなら部門単位が自然 |
| 2 | プラン変更の反映時期 | 上位・下位とも**即時反映** | 「即時反映＋日割り精算」が最も単純で、日割り計算の実証にもなる |
| 3 | 下位変更の差額 | 返金せず、**負値の控除明細**を当期請求に計上 | 返金は決済手段に依存する実装事項。仕様レイヤーでは請求への反映に留めた |
| 4 | 下位変更の制限 | 既存予約が変更後プランの上限を超えるなら**拒否** | 「変更したら既存予約が消える」より予測可能。`R_plan_quota_*` / `R_plan_advance_limit` の `on_violation` 文脈分岐で表現 |
| 5 | 解約の効力 | 当期末で役務提供終了（`service_end = current_period.end`）。日割り返金なし | 一般的なサブスクリプションの慣行 |
| 6 | 解約後の予約 | `service_end` **より後に終わる**予約を解約時点で自動取消。それ以前は保持 | 「解約したのに来月の予約が生きている」を防ぐ。かつ期間内の利用権は守る |
| 7 | 自動取消時の違約金 | **課さない**（`R_cancel_before_deadline` は `F_cancel_reservation` にのみ束縛） | 利用者の意思による取消ではないため |
| 8 | 強制上書き時の違約金 | 上書きされた側に**課さない**（同上、かつ理由は `OverriddenByAdmin`） | 同上 |
| 9 | 会議室の利用料 | 通常利用は**課金しない**（プラン料金に含む）。`hourly_rate` は違約金算定にのみ使う | 従量課金を入れると論点が増え、実証の焦点がぼやける |
| 10 | キャンセル期限 | 開始 24 時間前。違約金 = 時間単価 × 利用時間 × 50% | いずれも `param`。テナント設定可 |
| 11 | 予約の変更 | 変更機能を設けず、**取消 + 再作成**（`period` は `immutable`） | 変更を入れると期限・違約金・重複判定が変更にも波及し、制約が増える。仕様を小さく保つ判断 |
| 12 | 予約の承認フロー | なし（作成即 Confirmed） | 要件になく、入れると状態と権限が倍増する |
| 13 | 支払・督促 | 例から**除外**（`PastDue` 状態を置かなかった） | 決済連携は実証課題の焦点ではない。言語側の制約ではなく例の範囲の判断 |
| 14 | 重複判定の対象 | `status == Confirmed` のみ。取消済み・利用終了は対象外 | 自明だが、明示しないと実装がぶれる |
| 15 | 空き状況の可視範囲 | 予約者情報を返さない照会（`F_view_room_availability`）を分離し、全員に開放 | 「自分の予約しか見えない」と空き確認ができない矛盾を、権限モデルの中で解いた |
| 16 | 締め処理の起動 | 毎日 03:00 に走り、期間終了済みの契約だけを処理 | 月次 cron より冪等で、タイムゾーンと月末クランプの影響を受けにくい |

## 11. 既知の限界

正直に書いておく。

1. **`recheck` は手書き**。書き忘れは C-21 が検出するが、`recheck` の
   *対象集合が間違っている* ことは検出できない。`scenario` で担保するしかない。
2. **意味的な重複は検出できない**。C-DUP は正規化 AST の一致しか見ない。
   `a < b` と `not (a >= b)` は別物として通る。正規化を強めれば拾えるが、
   完全にはできない。
3. **`the()` の実行時失敗**。`the([...])` は要素数が 1 でなければ実行時エラーになる。
   「部門には契約が必ず 1 件」を静的に保証する手段が言語にない
   （`entity` に基数制約を書く構文を入れる案は、`rule` との重複になるため見送った）。
   実証課題では `R_one_open_invoice_per_department` のように不変条件で守っているが、
   保証は実行時のものになる。
4. **scope 軸が 2 本固定**（§1.1）。
5. **クエリの表現力**。集計・ソート・ページングを持たない。一覧画面の並び順は
   設計レイヤーの関心事という整理だが、「デフォルトの並び順」が業務要件であるケースは実在する。
6. **是正処置の連鎖を扱わない**（§2.5）。
7. **性能**。集合に対する `assert` を素直に評価すると全件走査になる。
   `QueryPort` が述語をストレージへプッシュダウンする前提で設計しているが、
   プッシュダウンの正しさは実装側の責任になる。
