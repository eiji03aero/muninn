# RATIONALE — 設計判断の記録

## 1. 全体方針

**テキスト DSL + コンパイル済み JSON IR の二層**にした。

- YAML / JSON を表面構文にしなかった理由: (a) 構造の正しさを文法で強制できず、
  検査がスキーマバリデーションに退化する。(b) 式(制約・計算)を文字列として
  埋め込むことになり、「文字列の中に別言語」という最悪の機械可読性になる。
  (c) 人間レビューの単位として冗長すぎる。JSON は決定論的な機械処理・ランタイム
  組み込みに向くので、そちらは IR(SpecIR)が担う。
- 自然言語は `doc` / `trace` の文字列にのみ許した。文法上、式や制約の位置に
  文字列リテラルを書けない。「但し書きへの逃げ」をレビュー規約ではなく
  **文法で**禁止するためである。
- AI が書く前提なので、人間の書き味(省略記法・構文糖衣)より
  **一意に解析・一意に導出できること**を優先した。節の順序を文法で固定したのも
  同じ理由(同じ内容は常に同じ形になり、diff レビューが安定する)。

## 2. カバレッジ要件 6 項目の扱い

| 関心事 | 扱い | 形 |
|---|---|---|
| 利用者の種別と権限 | 種別は一級 / 権限は畳む | `actors` 宣言(一級)。権限は behavior の `allow` 属性に畳んだ。中央の権限マトリクスは**導出物**(WORKFLOW D-02) |
| ドメイン概念と関係 | 一級 | `entity` / `enum` / `ref` フィールド |
| 常に成り立つ制約と違反時の扱い | 一級 | `rule`。違反時の扱いは `on violation reject error CODE` + `overridable by` |
| 利用者から見た振る舞いの単位 | 一級 | `behavior` |
| 時間軸を持つ状態の変化 | 準一級(entity に畳む) | `lifecycle`(状態機械)+ `at` タイマー遷移 |
| 機能間の依存・影響関係 | **扱わない(書かせない)** | 参照グラフから**導出**する(SPEC §8) |

畳んだ/外した判断の理由:

- **権限を behavior の属性に畳んだ**: 権限の実体は「誰が・どの操作を・どの範囲で」
  であり、操作(behavior)から切り離した中央マトリクスを一級にすると、behavior 追加の
  たびに 2 箇所の同期が必要になる(散らばりの再発明)。単一定義点は behavior 側に置き、
  マトリクスは常に導出で得る。スコープ条件(`where`)が式で書けるため、
  「自部門のみ」等の行レベル権限も但し書きなしで表現できる。
- **状態機械を entity 内に畳んだ**: 状態はエンティティの属性であり、独立した
  state machine 宣言を一級にすると「どのエンティティの状態か」の結線が別途必要になる。
  lifecycle フィールドは `transition` 文でしか変更できないという強い保証も、
  entity 内に置くことで自然に定義できる。1 エンティティ 1 lifecycle の制限は
  中規模業務アプリでは十分で、複数必要になったら状態を持つ子エンティティに分ける。
- **依存関係を書かせない**: 手書きの依存宣言は必ず腐る(書き忘れ・消し忘れを
  検査できない)。fspec では参照がすべて名前解決されるため、依存グラフは AST から
  完全に再構成できる。「ある機能を変えたとき影響を受ける仕様」は `impact()` の
  逆推移閉包で常に正確に得られる。**書いた依存より導出した依存のほうが信頼できる**。

## 3. 主要な設計判断

### 3.1 制約の単一定義: rule の自動適用

不変条件(rule)は「どの behavior が検査するか」を書かない。コンパイラが各 behavior の
effect から書き込み集合を求め、掛かる rule を導出する(SPEC §5.6, §7 C-04)。

- 採らなかった案: behavior 側に `checks no_double_booking` と列挙させる。
  → 列挙漏れが静的に検出できず、「同じ制約が複数箇所に散らばる」問題が
  参照の形で再発する。自動適用なら behavior を追加しただけで既存の全制約が掛かる。
- 帰結として、`create_reservation` と `force_reserve` のどちらにも重複禁止の記述が
  一切現れない(受け入れ基準 2 の構造的達成)。

### 3.2 invariant(rule)と precondition(require)の使い分け基準

**「すべての状態で常に真であるべきもの」だけを rule にする。「その操作を許すかどうかの
ゲート」は behavior の require にする。** 実証課題での適用例がプラン上限
(`max_future_reservations`):

- これを rule にすると、下位プランへの変更(更新時適用)で既存予約が新上限を超えた
  瞬間に不変条件が壊れ、`renew` タイマーが実行不能になる。業務的には「既存予約は
  尊重し、新規作成だけを止める」が正しい。ゆえに `create_reservation` の require。
- 逆に重複禁止・契約有効性は、どの経路(通常予約・強制上書き・解約)から書き込んでも
  成り立つべきなので rule。

この基準を明文化しておくことで、AI が仕様を書くときの置き場所判断が決定的になる。

### 3.3 依存・影響を導出にした(再掲、判断として記録)

受け入れ基準 4(影響追跡)を「宣言」ではなく「導出」で満たした。§2 参照。

### 3.4 違反時の扱いを reject 1 種に絞った

`on violation` の選択肢として warn(警告して続行)や defer(後で修復)も検討したが外した。

- warn は「常に成り立つべき制約」の定義と矛盾する(成り立たなくてよいなら
  それは制約ではなくレポート要件)。
- defer(結果整合)は修復プロセスの仕様が別途必要になり、仕様レイヤーの範囲を超える。
  修復が業務上必要なもの(解約時の予約整理)は、**遷移の effect による即時解消**として
  明示的にモデル化させる(`Subscription.cancel` がその実例)。
- 「違反しうるが特権者は例外」は rule の緩和ではなく `overridable by` +
  override behavior で表す(§3.5)。

### 3.5 管理者の強制上書きは「rule の例外」ではなく「衝突を解消する behavior」

`force_reserve` は no_double_booking を止めない。**先に衝突予約を `force_release` で
解放し、不変条件が保たれる状態にしてから**予約を作る。rule は常に検査される(多重防御)。

- 採らなかった案: rule 側に「system_admin なら違反を許す」という緩和分岐を書く。
  → 不変条件が実行主体依存になり、「データがこの条件を満たす」というモデル上の
  保証が消える。また rule から behavior への逆参照(解消手順)が循環参照を生む。
- `overrides` 節は意味論上メタデータだが、(a) rule と上書き behavior の対応を
  機械検査可能にし(W-07: アクター整合 + audit 必須)、(b) レビューアと導出物に
  「この操作はこの禁止の例外経路」と明示するために一級の節にした。

### 3.6 グローバル名前空間・import なし

モジュールをドキュメント用グルーピングに留め、名前は仕様セット全体で一意とした。
数十機能規模なら名前衝突は命名規約で回避でき、import 解決・可視性の仕様が丸ごと不要に
なる。参照は常に「その名前の定義は仕様セット内にちょうど 1 つ」なので、AI にとっても
影響分析にとっても解決が自明。数百機能規模で破綻したらそのとき名前空間を足す。

### 3.7 ロール継承なし

`dept_admin extends member` 型の継承は、3〜5 ロール規模では「暗黙に許可が増える」
リスクが節約できる行数を上回る。allow の明示列挙は冗長だが、権限レビュー
(誰が何をできるか)が宣言を読むだけで完結する。ロールが 10 を超える規模になったら
再考する。

### 3.8 時刻の扱い

- `now` は評価文脈から注入される(仕様内で「現在時刻を取得する」操作はない)。
  タイマー遷移は**予約された発火時刻を now として**評価するので、実行遅延が
  結果に影響しない。これで「期限を跨いだらどうなるか」が壁時計に依存せず一意になる。
- Date 型は置かず DateTime に統一した(§4.11)。「日割り」は `days_between` の
  床関数として明示的に定義され、タイムゾーン・日境界の暗黙解釈が入り込まない
  (仕様セットは UTC 固定。表示時のタイムゾーンは設計層の関心事)。

### 3.9 数値の決定論

浮動小数点を言語から排除し、厳密有理数 + 明示 `round` のみとした。丸めが起こる場所と
モードが構文上可視なので、日割り計算の結果は実装言語・実行環境によらず一意。
`Money` の未丸め値をフィールドに格納できないことは型検査で保証される(SPEC §3.2)。

### 3.10 「定義の重複」と「参照の再出現」の区別

DRY(受け入れ基準 2)の判定基準を次のように定めた:
**制約・計算の「意味(述語・式)」が 2 箇所に書かれたら重複。単一定義への「参照」が
複数箇所に現れるのは重複ではない。** 例えば `exists(active_subscriptions(caller))`
という require は複数の behavior に現れるが、「有効な契約」の意味は
calc `active_subscriptions` の 1 箇所にしかない。require 行は「この操作はその条件で
ゲートする」という適用宣言であり、behavior ごとに独立した事実である。意味を変更する
ときに触るファイル位置が常に 1 箇所であること — これが DRY の実利であり、
fspec はそれを参照解決の機械検査で保証する。

### 3.11 external エンティティ

Room / Plan / User / Department は参照するがライフサイクルは範囲外、と宣言できる
`external` を設けた。これがないと網羅性検査 C-03(全エンティティに生成経路)が
マスタ系で常に偽陽性になり、検査自体が信用を失う。「この仕様が管理する状態」と
「前提として与えられる状態」の境界を機械可読にする装置である。

## 4. 入れなかったもの(と理由)

| # | 入れなかったもの | 理由 |
|---|---|---|
| 4.1 | 画面・UI(レイアウト、遷移図、項目定義) | 設計層の関心事。仕様側は behavior の allow / require / エラーカタログを提供し、画面制御はランタイム API(`can` / `validate`)で参照する |
| 4.2 | 非機能要件(性能・可用性・セキュリティ基盤) | 機能仕様と粒度も検証手段も異なる。別文書。認可だけは機能の意味に不可分なので allow として言語内に残した |
| 4.3 | エラーメッセージ文言・i18n | 文言は UI 設計の成果物。仕様はコード(識別子)まで。コード⇔文言表は導出物のカタログに設計層で付与する |
| 4.4 | 決済処理(決済手段、リトライ、失敗時遷移) | 外部システム連携の設計事項。仕様上は「課金事実の記録 = Charge の生成」までを真実とし、境界を entity Charge に固定した |
| 4.5 | 通知・メール等の副作用 | 今回の課題に不要。入れるなら effect 文に `emit <event>` を足し、イベントカタログを導出する拡張が素直(構文の拡張点として確保) |
| 4.6 | 汎用ワークフロー/承認フロー機構 | lifecycle + behavior で個別に書ける。汎用機構は言語を肥大させ、決定論的検査を難しくする |
| 4.7 | テストケース記述 | require / rule / transition から正常系・異常系のテスト骨子が機械導出できる(WORKFLOW D-06)。手書きテスト仕様は導出物と二重になる |
| 4.8 | ロール継承 | §3.7 |
| 4.9 | import / 可視性制御 | §3.6 |
| 4.10 | match 式 | if / atom 比較で足りる。enum 網羅チェック付き match は有用だが v1 の必須ではない(拡張候補) |
| 4.11 | Date 型 | DateTime に統一。「日」の解釈(境界・TZ)を組み込み関数の定義に集約(§3.8) |
| 4.12 | 返金・負の金額調整 | 下位プラン変更を「次回更新時適用」と決めたことで不要になった。返金を導入する場合は Charge と対の CreditNote を足す(モデル拡張で対応、言語拡張は不要) |
| 4.13 | 並行性制御(ロック、楽観制御) | 設計層。仕様は「behavior 実行は原子的、rule はコミット前検査」という意味論だけを定め、実現手段(トランザクション分離等)は縛らない |
| 4.14 | クエリのページネーション・整列指定 | API 設計の関心事。仕様のクエリ behavior は「返る集合の定義」まで |
| 4.15 | 仕様のバージョニング・マイグレーション | 運用プロセスの関心事。IR に `fspec_ir` バージョンだけ確保 |
| 4.16 | 多通貨 | 課題スコープ外。`currency` を単一宣言にしたことで Money の型を単純に保てた。多通貨化は Money を通貨タグ付きにする破壊的変更として別途設計する |
| 4.17 | 手書きの依存宣言 | §2・§3.3。導出できるものは書かせない |
| 4.18 | 数量制約つき関係(多重度宣言) | `ref` + rule で表現できる(例: single_active_subscription)。多重度専用構文は rule と意味が重複する |

## 5. 既知の限界

- **L-01 rule の対称性規約**: rule 検査は書き込まれたインスタンスに対してのみ走る
  (SPEC §6.4)。2 インスタンス間の関係制約は述語を対称に書く必要があり、これは
  規約であって型検査では強制できない。リンタで「他インスタンスへの select を含む
  rule」を列挙して人間レビューに回すのが現実的な緩和策。
- **L-02 タイマーと rule の静的整合**: タイマー遷移の effect が rule を破らないことは
  静的には保証できず、C-07 の候補列挙 + 実行時 TIMER_CONFLICT アラートで守る。
- **L-03 表現力の上限**: 集合式は単一エンティティ外延の select に限る(join は
  ネストした select とフィールド参照で書く)。複雑な集計仕様(帳票級)は
  この言語の対象外で、設計層で SQL 等に落とす。
- **L-04 `the()` の部分性**: 単一性が保証されない `the()` は実行時エラーになりうる。
  C-08 で警告するが、完全な静的保証はしない(依存型が要り、言語が重くなりすぎる)。
