# タスク

ソフトウェア開発における「機能仕様」を管理するための独自言語（DSL）を設計せよ。

## 背景と狙い

- 仕様は AI が書き、AI が読み、人間がレビューする。人間が手書きする前提は置かない。
- 上流の要件から、仕様 → 基本設計 → 詳細設計 へと段階的に詳細化していく流れの
  「仕様」レイヤーを担う。下流の設計がこの仕様を参照して導出できることが重要。
- 対象は中規模の業務系 Web アプリケーション（数十機能、複数ロール、状態遷移あり）。
- 既存の自然言語仕様書の不満：同じ制約が複数箇所に散らばって矛盾する、
  網羅できているか判定できない、変更時の影響範囲がわからない。
  DRY であることと網羅的であることを両立させたい。
- 仕様は決定論的に処理できること。同じ仕様ファイルからは常に同じ解釈・同じ導出結果が得られ、
  LLM の推論を挟まずに機械処理できる範囲を最大化する。
- Web アプリケーションに組み込んで使う。実行時に仕様を読み込み、バリデーションや
  画面制御の根拠として参照できることを想定する（ランタイム表現の設計も範囲内）。

## カバレッジ要件

以下の関心事を、この DSL で表現できること。ただし「独立した構成要素として
一級市民にするか」「他の要素の属性として畳むか」「そもそも扱わないか」は
君の設計判断とする。外した／畳んだものは、その理由を明記すること。

- 利用者の種別と権限
- ドメイン上の概念とその関係
- 常に成り立つべき制約と、その違反時の扱い
- 利用者から見た振る舞いの単位
- 時間軸を持つ状態の変化
- 機能間の依存・影響関係

## 成果物

作業ディレクトリ直下に以下を作ること。中身の構成は君に任せる。

1. `spec-lang/SPEC.md` — 言語仕様そのもの
2. `spec-lang/RATIONALE.md` — 設計判断の記録。特に「入れなかったもの」とその理由
3. `spec-lang/example/` — 下記の実証課題を、この DSL で実際に記述したもの
4. `spec-lang/WORKFLOW.md` — この仕様から基本設計・詳細設計をどう導出するか

## 実証課題

設計した DSL で、次の題材の仕様を実際に書き下ろすこと。
机上の言語仕様だけでは不十分で、これが書けて初めて設計が成立したとみなす。

「サブスクリプション課金つきの会議室予約システム」
- 一般利用者・部門管理者・システム管理者の3ロール
- プラン変更、日割り計算、解約後の予約の扱い
- 予約のキャンセル期限と、期限を跨いだ場合の課金
- 重複予約の禁止と、管理者による強制上書き

## 受け入れ基準

1. 実証課題の全要素が、DSL 上で表現されている（自然言語の但し書きへの逃げがない）
2. 同一の制約が2箇所以上に重複して書かれていない
3. 機械可読である（パーサが書ける文法になっている。実装は不要だが、
   曖昧さのない文法定義があること）
4. ある機能を変更したとき、影響を受ける他の仕様を DSL 上で追跡できる
5. WORKFLOW.md に従えば、この仕様から基本設計の入力が機械的に得られる
6. 決定論的に処理できる。パース結果からの導出（不変条件の抽出、影響範囲の追跡など）が
   一意に定まり、Web アプリのランタイムから参照可能な表現を持つ

## 進め方

質問を返さず、この指示だけで完遂すること。判断が割れる箇所は自分で決めて、
その判断を RATIONALE.md に残せ。
