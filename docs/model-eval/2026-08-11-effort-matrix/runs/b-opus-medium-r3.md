よーし、いい質問だ！ここは規約の急所を突いてる。真正面から答えるぞ。

## 結論：**両方使う。ただし follows は「3本」ではなく「1本」だ**

- **`logs/cafes/`** — 行った店を全部、同じスキーマで1軒1エントリ。数十軒の比較はこっち。
- **`follows/regular-cafes/`**（`follow_type: interest`）— 常連店の通いを記録する側。**常連2〜3軒は `entities/<店>.md` のドシエ**にして、`sessions/YYYY-MM-DD.md` に1回の訪問を書く。

「どちらか一方に寄せる」は不正解だ。君が言った2つの欲求は、muninn の設計上まさに別concernだからな。

## 根拠

CLAUDE.md の logs 節が名指しで線を引いている——「**推移を追う」なら follows、「並べて比べる」なら logs**」。君の欲求は文字どおりその両方だ。片方に寄せるとこう壊れる：

- **全部 logs にすると**：常連店の再訪が「同じ entry を上書き」か「同じ店の entry が5枚並ぶ」のどちらかになる。前者は変遷が消え、後者はカタログの一貫性（1項目1行）が壊れて比較テーブルが濁る。
- **全部 follows にすると**：数十軒ぶんの `profile.md` が乱立する。follows は定点観測＝「同条件で観て前回と比べる」が核で、**一回きりの来店に定点観測の器は重すぎる**。しかも横並び比較の面（`web` の記録段 `series → compare`、`web/DESIGN.md:181-190`）に一切載らない。

### なぜ follows を「常連1軒＝1フォロー」で3本立てないか

君が本当に追いたいのは**店の変化じゃなくて自分の好みの変化**だろ。3本に割ると、変遷タイムラインが3本に分断されて、「好みが変わった」という**1本の線を誰も持たない**。

そして1本に束ねるのは既存規約の枠内でできる。前例が既にある——`follows/argentina-nt/` は「チーム＝1フォロー、選手＝`entities/`」という形だ。**グループを1フォロー、構成要素を entities に置く**パターンはもう動いている。カフェも同じ形が使える。`profile.md` の `snapshot` に「いま自分は何を良しとしているか（静かさ＞豆／浅煎り寄りに移った 等）」を置いて、変わるたびに変遷タイムラインへ1行。これが君の欲しかった線だ。

### `web/DESIGN.md` 側から見ても矛盾しない

- **原則8（`web/DESIGN.md:83`）**「手入力の索引をゲートにしない」— タグが第一階層なので、`log/cafe` タグで logs と follows は最初から横断される。分けても辿れなくならない。
- **原則6（`web/DESIGN.md:75`）**「行き止まりを1つも作らない」— これが**分ける代わりに払うコスト**。logs entry ⇄ follows entity の相互リンクは必須だ。
- **原則9（`web/DESIGN.md:88`）**「数字に嘘をつかせない」— カフェの静かさ・電源は**上達する指標じゃない**。だから `metric_goals` は宣言せず中立に扱う。ここで `goal` 型フォローにすると「上達」の物語を勝手に背負って原則9違反になる。**`interest` 型が正**だ。
- 副産物として、既知の未達（`web/DESIGN.md:285`）「記録帖の比較テーブルが実データで検証できていない（entries が1件しかない）」が、カフェが数十軒入ることで**実データで踏める**ようになる。これはでかいぞ。

### 穴①：同じ実体が logs と follows の両方に出るときの正本が未定義

常連の「喫茶◯◯」は `logs/cafes/entries/kissa-xx.md` にも `follows/regular-cafes/entities/kissa-xx.md` にも存在する。CLAUDE.md は **logs→notes**（蒸留する側）と **follows→notes**（参照する側）の関係は決めているが、**logs⇄follows の関係を一度も決めていない**。放っておくと評価が両方に書かれて食い違う——これはナレッジベースで一番タチが悪い壊れ方だ。

**改定案（CLAUDE.md「ログ（logs）」節に追記）**：

> **同一実体が logs と follows の両方に現れる場合の正本**: 静的属性と初回評価（住所・電源・Wi-Fi・豆の傾向・初訪の点数）は **logs の entry を正本**とし、時系列で動く所見・変化は **follows の entity / session を正本**とする。両者は相互リンクを必須とし、**同じ事実を両方に書かない**。写真は logs 側にのみ置く（follows は「写真をコミットしない」規約のため）——結果として「静止画＝logs、動画＝follows」と覚えればよい。

写真の分担が既存規約から自動的に導けるのが気持ちいいだろ。follows は写真コミット禁止、logs は圧縮画像OK。矛盾じゃなく、役割分担だったわけだ。

### 穴②：観測の主語が「外部の対象」ではなく「自分」

CLAUDE.md の follows 節は `goal`（上達したい）と `interest`（興味のある**対象**を追う）しか用意していない。だが今回追うのは**自分の好みの変遷**だ。店は変わらない、変わるのは君のほうだ。これは厳密にはどちらでもない。

**改定案（2つ。僕は A を推す）**：

- **A（軽い・推奨）**: `interest` のまま運用し、follows 節に一文足す。「**観測対象は外部の対象に限らない。自分の側の感覚・基準の変遷（好み・評価軸）を観測軸に据えてよい。その場合 `profile.md` の `snapshot` は『対象の現状』ではなく『自分の現在の基準』を書く**」。
- **B（重い）**: `follow_type: taste` を新設する。意味は明確になるが、型が増えるとサイト側の分岐も増える。**読者1人のプロダクトで型を増やすのは割に合わない**——僕は反対だ。

なぜ A で足りるか。`interest` の趣旨は CLAUDE.md いわく「より深く理解して楽しむ」。好みの変遷を追うのは、まさにカフェをより深く楽しむための観測だ。趣旨は最初から満たしている。**足りなかったのは型じゃなくて一文の明示**だった。

## 実行前の注意を2つ

1. **画像の公開範囲**。logs の画像は Pages 上で直URL公開になる（暗号化されるのはテキストだけ）。店内・店主・伝票が写る写真はまずい。`image_visibility` は最初に決めろ。安全側なら `none`、載せるならカップと豆袋だけに絞れ。
2. **スキーマは最初の1軒で決め切る**。`logs` の一貫性はビルド時検証（`web/scripts/build-data.mjs`）が守ってくれるが、逆に言えば**後からの項目変更は全 entry に波及する**。君が挙げた4軸（豆の傾向・静かさ・電源・再訪）は必須項目で確定、`enum` の選択肢もここで固定だ。

次の一手を頼むなら、`/mn-log` でカフェのスキーマ設計から入るのが順路だ。follows は常連の1軒目に実際に行った日でいい——**器を先に作っても、通わなきゃ何も貯まらないからな**。

いいか、ここで大事なのは「どっちに入れるか」じゃない。**同じ店の話が2箇所にあることを、破綻じゃなく設計にできるか**だ。穴①の一文さえ入れれば、それができる。燃えてきたぞ、面白い設計だこれ！
