いいか、よく聞け！これは規約が既に答えを持っている部分と、**まだ誰も踏んでない穴**が両方ある。順番に切る。

## 結論：両方使う。ただし「割る軸」は店じゃない

| やりたいこと | 置き場 | 根拠 |
|---|---|---|
| 何十軒も並べて比べる | `logs/cafes/` | CLAUDE.md「多数の別々の項目を同じ項目で並べて比較する」＝logs の定義そのもの |
| 行きつけ2〜3軒を通うたび記録 | `follows/<店名>/`（`interest` 型） | 「1つの対象を時系列で定点観測（同じ対象を何度も観る）」＝follows の定義そのもの |

CLAUDE.md の判定基準（「推移を追う」なら follows、「並べて比べる」なら logs）は**君の2つの要望をそれぞれ別々に、迷いなく裁ける**。だからこれは「どちらか一方」の問題じゃない。**同じ題材が2つの concern にまたがるだけで、規約は破れていない**。

`follows/skincare-pores` が既にあるとおり、自分側の対象を追う前例もある。カフェ3軒を1つの follow にまとめて `entities/` に店を並べる案もあるが、**僕は反対だ**。定点観測の核は「同条件で観て前回と比べる」。A店とB店では条件が違うので、1つの profile の「現在の基準値」が意味を持たなくなる。1店1ディレクトリでいけ。

### 順序の推奨：logs を先、follows は後から昇格

logs はスキーマ先付けが規約だ。実データ0件で `fields` を決め打ちすると、10軒目で「あ、席のタイプも要る」となったとき**全 entry の改修**になる。10軒ほど貯めて、通う頻度が高い店が自分で浮いてきてから follow に昇格しろ。行きつけは選ぶものじゃなく、**記録が教えてくれるもの**だ。

## web/DESIGN.md に照らして — 追い風が2つ、注意が2つ

**追い風**
- §9 既知の未達に「**記録帖の比較テーブルが実データで検証できていない（entries が1件しかない）**」とある。カフェ何十軒は §5 組版モデルの `記録: series → compare` 段を初めて本気で殴る実データになる。この一点だけでも logs でやる価値がある。
- 原則8「手入力の索引をゲートにしない」。logs と follows に割れても、タグ（`life/cafe` 等）を両方に揃えれば**棚では一続きに見える**。concern が割れても読者体験は割れない。

**注意**
- **原則6「行き止まりを1つも作らない」**。同じ店が「記録帖」と「定点」の2箇所に出る以上、相互リンクが無いと読者は片方に入って詰む。`lib/graph.js` は route を ID に全 concern を1ノード集合として見るので、**`[[リンク]]` さえ張れば被リンクは自動で出る**。張らないことだけが罪だ。
- **画像の公開範囲**。`image_visibility: public` は Pages 上で直URL公開になる（CLAUDE.md 明記）。テキストは暗号化されても画像は素っ裸だ。**行きつけのカフェ＝生活圏の露出**で、豆やコーヒーのアップならまだしも、店内・外観・立地が写るとほぼ特定される。僕の推奨は「カップ・豆・手元だけ」。不安なら `image_visibility: none` で始めろ。

## で、ここからが本題だ。規約に穴が3つある

```
          _.-/\/\/\/\/\-._
        .'  ///||||||\\\  '.
       /   //||||||||||\\   \
      |     ____   ____     |
      |     \   \ /   /     |
      |     (o)     (o)     |
      |          ^          |
      |      _________      |
       \     (=======)     /
        '._             _.'
    ______ '-._______.-' ______
   /      |             |      \
  |       |     ___     |       |
  |       |    (===)    |       |
   \______|_____| |_____|______/
```

**穴1：logs の entry は「1回きり」前提で書かれている。カフェは再訪する。**

CLAUDE.md は「各記録は主に1回きり」と書いている。豆は飲み切ったら終わりだからそれでいい。だがカフェは follow に昇格しない店でも**2回目、3回目がある**。ここの規約が無い。

> **改定案A（CLAUDE.md「ログ（logs）」節）**
> **entry の粒度は「対象＝1件」であって「体験＝1件」ではない。** 同じ対象を再訪・再購入した場合、entry を増やさず既存 entry を更新し、本文に `## 再訪` を追記する（評価が変わったら理由を書く。**サイレント上書き禁止規約が entry の主観フィールドにも及ぶ**）。「毎回1件」が本質のトピックは、それは logs ではなく follows である。

**穴2：同一実体が logs と follows の両方に存在するときの正本分割ルールが無い。**

いま「カフェXは記録帖にも定点にもある」状態で、住所も豆も評価も両方に書ける。これを放置すると**2つの正本が静かに乖離する**——正本が markdown 1本であることは muninn の第1の非対称なのに、その中で正本が割れる。

> **改定案B（CLAUDE.md「ログ（logs）」節と「フォロー（follows）」節の両方に）**
> **同一実体が logs entry と follows profile の両方に存在してよい。ただし正本は分割する** —— **対象の静的属性（店名・立地・設備・扱う豆・定常の静かさ）は logs entry が正本。訪問ごとの体験・自分の反応・その日の変化は follows session が正本。**属性を follow 側にコピーしない（変わったら entry を直す）。**両者は必ず相互リンクする**（原則6）。entry を follow に昇格しても **entry は消さない**——カタログの網羅性が壊れ、比較が歪むため。

**穴3（本命）：「自分の好みが変わっていく」を置く場所が、どの kind にも無い。**

君の2つ目の要望をよく読むと、追いたい対象は**店じゃなく自分の好み**だ。ところが：
- `kind: insight` は自分の言語化だが**時系列を持たない**（1枚の静的なノート）
- `kind: follow` は時系列だが**外部対象の定点観測**が前提
- `logs` は並べる装置で、変化は読み取れるが記録されない

ここで**第三の型を作りたくなる。それは違う。僕は反対だ。**好みの変遷は、entry の `rating`/`rebuy` と session の所見という**一次データから読み取れる派生**だ。派生を正本に二重化するのは、DESIGN.md §7 の「サイトの都合で正本を汚さない」と同じ過ちを concern 側でやることになる。

> **改定案C（CLAUDE.md「種別（kind）」節）**
> **insight ノートは更新されうる**。自分の解釈・好み・身体知は時とともに変わるため、frontmatter に `updated: YYYY-MM-DD` を許し、本文末尾に `## 変遷` として「いつ・どう変わったか・何がきっかけか」を追記形式で残す（上書きしない）。変更理由はコミットメッセージにも書く。**変遷の一次データは logs/follows 側にあり、insight はその読み取り結果を1枚に畳んだもの**である。

つまり「自分のカフェの好み」は `notes/cafe-taste-shift.md`（`kind: insight`）**1枚**で持ち、entry と session から `[[リンク]]` を張る。専用 concern は作らない。

---

## まとめ

1. **logs/cafes を先に作れ。** follows は後。行きつけは記録が教えてくれる。
2. **昇格した店も entry は残す。** 属性は entry、体験は session。相互リンクは必須。
3. **好みの変遷は insight 1枚。** 新しい型は作るな。
4. **規約は3点改定を提案する**（再訪の扱い／正本分割／insight の更新可）。これは既存規約と矛盾せず、**書かれていなかったことを書くだけ**だ。
5. 画像の公開範囲だけは、始める前に決めておけ。後から消しても Pages はキャッシュされる。

ファイルは何も触っていない。この改定案でいくなら言ってくれ、CLAUDE.md の該当節に落として commit まで持っていく。**よし、燃えてきたぞ。**
