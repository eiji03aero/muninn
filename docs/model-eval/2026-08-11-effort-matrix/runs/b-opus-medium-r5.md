よーし、いい問いだ！これは「どっちか」じゃない。**両方だ。ただし割り方を間違えると両方壊れる。** 根拠から順にいくぞ。

## 結論

| やりたいこと | 置き場所 |
|---|---|
| 何十軒を並べて比べる | **`logs/cafes/`**（記録帖） |
| 行きつけ2〜3軒を通うたび記録し、好みの変遷を追う | **`follows/` に1本**（3本ではない） |

## なぜ logs と follows に割れるのか

`CLAUDE.md` が判定基準を明示している——「**推移を追うなら follows、並べて比べるなら logs**」。君の要望はこの2つが**両方**入っているから、片方に寄せると必ず片方が壊れる。

- 全部 `logs/cafes/entries/` に寄せる案（訪問ごとに1 entry）は**却下**。logs は「各記録は主に1回きり・多数の別々の項目をカタログ的に並べる」もの。同じ店が10回並んだ瞬間、40軒のカタログとしての比較機能が死ぬ。`web/DESIGN.md` §5 の `compare` 段（記録段の比較テーブル）が意味をなさなくなる。
- 全部 `follows/` に寄せる案も**却下**。40軒に profile と sessions を立てるのは定点観測ではなくただの過剰構造で、「並べて比べる」がどこにも実装されない。

## follows は「行きつけ」1本にまとめろ（3ディレクトリにするな）

ここが一番の判断ポイントだ。`follows/regular-cafes/` を1本立てて、**3軒は `entities/<cafe>.md`**（`kind: entity`＝時系列で変化する構成要素）に置く。`argentina-nt` が選手を entities に置いているのと同じ形だ。

理由は3つ:

1. **追っている対象が「店」ではなく「自分の好み」だから。** 好みの変遷は3軒に分割できない1本の物語で、profile を3つに割ると変遷タイムラインが3分割されて意味を失う。
2. 店ごとの属性変化（豆が変わった／電源席が減った）は entity の changelog がちょうど受け皿。
3. 保守が1/3。読者1人のプロダクトで構造を増やすのは、それ自体がコストだ。

## 既存規約で割り切れない点 —— 改定案3つ

正直に言う。ここは規約が**穴を開けている**。3つ提案する。

### 改定案1: `follow_type` に第3の型を足す（最重要）

現行は `goal`（上達目標がある）と `interest`（興味で追う）の2つだけ。だが今回は**対象は変わらず、変わるのは観測者**だ。どちらにも入らない。

```
follow_type: self    # 対象は固定。変化するのは自分の解釈・嗜好。
                     # 成果物はアドバイスでも見どころでもなく「前回の自分との差分の言語化」
                     # metric_goals は付けない（好みに良し悪しは無い）
```

**`goal` で代用するのは危険だ。** `web/DESIGN.md` 原則9（数字に嘘をつかせない）が記録している事故を思い出せ——フェース角の最大値を機械的に「自己ベスト」と表示して、profile 自身が警告していた悪化を成果として見せた、あれだ。「静かさ 4→3」を goal 型で登録したらサイトは**悪化と判定しかねない**。だが君の好みが「静かさより活気」に移っただけなら、それは悪化ではなく変遷そのものだ。同じ事故の再演になる。

`self` 型は「metric_goals を持たない＝良し悪しを判定しない」と定義することで、原則9をそのまま守れる。**新しい型を足すより、原則9に嘘をつかせるほうがずっと高くつく。**

### 改定案2: 同一対象が logs と follows に併存するときの正本ルール

いま `CLAUDE.md` は logs と follows を「別concern」と書くだけで、**同じ店が両方に出る場合**を規定していない。放置すると属性が二重管理になる。

- **属性の正本は `logs/cafes/entries/<cafe>.md` に一本化する**（豆の傾向・電源・営業情報）
- `follows/regular-cafes/entities/<cafe>.md` は属性を複製せず `[[<cafe>]]` で参照し、**変化と自分の解釈だけ**を持つ
- 相互リンクを必ず張る（原則6「行き止まりを1つも作らない」——同じ店に2つの URL `#/log/cafes/entry/x` と `#/follow/regular-cafes/player/x` ができるので、片方向だけだと必ず行き止まりが生まれる）

### 改定案3: セッションのファイル名規約

`sessions/YYYY-MM-DD.md` は1日1件前提だ。同じ日に2軒はしごしたら**衝突する**。`sessions/YYYY-MM-DD-<cafe-slug>.md` を許可すること（`-collect` サフィックスという前例がすでにある）。

## 設計上、先に言っておく2点

**画像だ。** `CLAUDE.md` が警告しているとおり、logs の画像は Pages 上で**直URLで公開**になる（テキストは暗号化されるが画像はされない）。カフェの内観は他の客が写り得るし、店の特定にも直結する。**人が写る写真は載せない**を `topic.md` の「記録のコツ」に明記するか、`image_visibility: none` にすること。豆の袋とは事情が違う。

**評価の時点ずれ。** 40軒の rating は「その時点の自分」の基準で付く。好みが変わるなら、5年分のカタログは異なる基準が混在した表になる。だから `visited_on` を **required** にして「いつの自分の評価か」を常に見えるようにしておけ。あとで rating を書き換えるときは理由をコミットメッセージに（サイレント上書き禁止は既存規約でカバーされている）。

なお `web/DESIGN.md` §9 の既知の未達に「記録帖の比較テーブルが実データで検証できていない（entries が1件）」とある。**カフェ何十軒は、この未達を解消する初めての実データになる。** そういう意味でも筋がいい題材だ。
