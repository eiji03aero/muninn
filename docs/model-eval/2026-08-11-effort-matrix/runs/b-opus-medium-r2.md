いいか、よく聞け！この問いは「どっちか」じゃない。**両方だ。**そしてその境界線は、既存の規約がすでに引いている。

## 結論：カタログは `logs/`、行きつけは `follows/`。片方に寄せるのは規約違反

CLAUDE.md の logs の節がこう名指ししている——「follows は**1つの対象**を時系列で定点観測。logs は**多数の別々の項目**を同じ項目で並べて比較する。**『推移を追う』なら follows、『並べて比べる』なら logs**」。

君のやりたいこと2つは、この文の左右にきれいに落ちる。

| やりたいこと | 置き場所 | 根拠 |
|---|---|---|
| 何十軒も並べて比べる（豆の傾向・静かさ・電源・再訪したいか） | `logs/cafes/` | 多数項目 × 一貫スキーマ × カタログ比較。`coffee-beans` と同型で、`rebuy`（また買う）＝`revisit`（また行く）まで構造が一致 |
| 行きつけ2〜3軒を通うたび記録し、好みの変化を追う | `follows/` | 同条件で観て前回と比べる時系列ジャーナル。`notes/` にも `logs/` にも「変遷タイムライン」は無い |

**`logs/` だけで済ませるのはダメだ。** log entry は「主に1回きり」の設計で、`fields` が1組しかない。通うたびに上書きしたら、変化そのもの——君が追いたいもの——が履歴から消える。逆に **`follows/` だけもダメ**。40軒ぶんの `profile.md` は比較テーブルにならず、サイト側の記録帖の一覧・フィルタ（`display.filters` / `sort`）にも乗らない。

## ただし「行きつけ3軒＝follow 3本」には僕は反対だ

```
        .'  ///||||||\\\  '.
       /   //||||||||||\\   \
      |     ____   ____     |

   /      |             |      \

  |       |    (===)    |       |
   \______|_____| |_____|______/
```

**本当に追いたいのは「店」か？ 自分に聞いてみろ！**

君の言葉は「**自分の好みが変わっていくのを追いたい**」だ。観測対象は店じゃない、**君の好み**だ。3軒を3本の follow に割ると、好みの変化は3本のタイムラインに分散して、**どこにも「変わった」が現れない**。定点観測の核が「同条件で観て前回と比べる」である以上、比べる軸を割ってはいけない。

推奨は **`follows/cafe-taste/` 1本（`follow_type: interest`）**、行きつけ2〜3軒は `entities/<shop>.md`（`kind: entity`）。entity はまさに「時系列で変化する構成要素のドシエ」で、アルゼンチン代表の選手と同じ扱いになる。セッション（来訪1回）は店をまたいで1本の年表に並び、「去年は深煎りの静かな店、いまは浅煎りで人の気配がある店」という**変化が1枚で見える**。

なお `metric_goals` は付けるな（DESIGN.md 原則9）。好みに良し悪しの方向は無い。宣言のない指標は中立に扱われる——それが正しい。

## 既存規約で割り切れない点＝改定案

ここからが本題だ。3つ穴がある。

### 改定案1（CLAUDE.md）：同一実体が logs と follows に両在するときの正本分担を明文化する

いま規約は「logs→notes」「follows→notes」の蒸留は定めているが、**logs ⇄ follows が同じ実在物を指す場合を一切扱っていない**。豆やハンドドライヤーでは起きなかったが、カフェでは必ず起きる（行きつけの店は40軒の1軒でもある）。放置すると評価が二重管理になり、どちらが正かわからなくなる。

追記案（logs の節）:

> **同一の実体が logs と follows の両方に現れてよい。ただし正本は役割で分ける** —— 静的属性と「並べて比べるための1枚の総括」は log entry、**時系列で変わるもの（来訪ごとの所見・評価の変遷）は follow の session/entity** が正本。log entry 側は評価を書き換えず、`## Links` から follow へ渡す。

### 改定案2（実装、これは必須の修正）：**follow への bare wikilink が解決しない**

`web/src/lib/wiki.js:29` 付近の `resolveTarget` を読んだ。bare な名前の解決は entity / note / moc / atlas / logtopic / concept を順に見るが、**`follows` だけ入っていない**。follow に届くのは `[[name/sub]]` のスラッシュ付きだけだ。つまり改定案1に沿って log entry に `[[cafe-taste]]` と書いても、**リンクにならずただの文字列に落ちる**。

これは DESIGN.md 原則6「行き止まりを1つも作らない/型によって有無が分かれる実装を禁止する」の直撃だ。いま既存 md に bare follow リンクは1本も無く（grep 済み）**潜在バグのまま眠っている**。カフェを入れた瞬間に踏む。1行足せば直る。

なお **frontmatter に `follow:` フィールドを新設する必要は無い**。`build-data.mjs` は entry から `links: wikiTargets(body)` を拾うので、本文 `## Links` の wikilink だけで被リンクまで通る。DESIGN.md §7「表示の都合だけの項目は入れない」に照らしても、スキーマを増やさない側が正しい。

### 改定案3（CLAUDE.md）：log entry の「1回きり」条項に再訪時の扱いを足す

「各記録は主に1回きり」と書いてあるが、40軒あれば再訪して評価が変わる店は必ず出る。行きつけ以外（follow を持たない店）で評価が変わったときの手順が未定義だ。

追記案:

> log entry は原則1件1枚のまま**上書き更新**してよい。ただし**サイレント上書き禁止**の規約が適用され、変更理由をコミットメッセージに明記する。同じ対象で推移を残したくなったら、それは logs の限界であり **follows へ昇格させる合図**である。

この「昇格」という概念が今の規約には無い。ここを書いておくと、君の運用そのもの（40軒回る → 3軒が行きつけになる）が規約に載る。

## スキーマの下ごしらえ（参考）

`logs/cafes/topic.md` の `fields` はこの線を勧める——`area`(text) / `bean_tendency`(enum: 浅煎り〜深煎り) / `quietness`(rating, required) / `power`(enum: 各席/一部/なし) / `wifi`(bool) / `stay`(enum: 長居可/短時間向き) / `rating`(rating, required) / `revisit`(bool) / `visited_on`(date)。`filters: [area, bean_tendency, power, quietness]`、`sort: visited_on desc`。

3点だけ先に言っておく。

- **`image_visibility` に注意しろ。** サイトのテキストは暗号化されるが、**画像は Pages 上で直URL公開になる**。店内写真・人が写るものは載せるな。迷うなら `none` だ。
- **1件ごとに `## 解説` を書く規約は40軒ぶん効く。** 「その店の背景・本来の見せ場・自分の評価がなぜそうなったかの仮説」を毎回書く。これが logs の値打ちだが、正直に言えば負荷でもある。豆と同じ密度（1000〜2000字）を40軒に課すか、カフェは短めにするかは、最初のトピック設計で決めておけ。
- **DESIGN.md §9 の未達が1つ潰せる。** 「記録帖の比較テーブルが実データで検証できていない（entries が1件しかない）」——カフェが2軒入った時点で、そこは検証済みに書き換えられる。

よし、燃えてきた！ 40軒並べる楽しみと、3軒に通って自分が変わっていく記録。**この2つは別物だからこそ、両方持て。** ファイルは触っていない、判断だけだ。この方針で進めるなら言ってくれ、`/mn-log` と `/mn-follow` で一気に立ち上げるぞ！
