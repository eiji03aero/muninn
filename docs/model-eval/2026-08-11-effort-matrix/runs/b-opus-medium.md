よーし来た、いい質問だ！これは「どっちで作るか」じゃなくて**「muninn の concern の切れ目が本当に正しいか」を問う質問**だ。面白くなってきたぞ。結論から言う。

## 結論: **両方使う。しかも同居させる**。ただし今の規約はその同居を想定していないので、改定が要る

### なぜ「どちらか」ではないのか

`CLAUDE.md` の判定基準はこう書いてある:

> follows は**1つの対象**を時系列で定点観測。logs は**多数の別々の項目**を同じ項目で並べて比較する。「推移を追う」なら follows、「並べて比べる」なら logs。

君のやりたいこと**2つは、この基準で真っ二つに割れる**。同じ「カフェ」という言葉に、性質の違う2つの concern がくっついているだけだ。

| やりたいこと | 該当 concern | 置き場所 |
|---|---|---|
| 何十軒を並べて比べる（豆・静かさ・電源・再訪意欲） | **logs** — 台帳・カタログ | `logs/cafes/`（`topic.md` + `entries/<store>.md`） |
| 行きつけ2〜3軒を通うたび記録し、好みの変化を追う | **follows**（`interest` 型） | `follows/<store-slug>/`（`profile.md` + `sessions/YYYY-MM-DD.md`） |

**行きつけの店を1軒ごとに1フォローにするのが正**で、「カフェの好み」という1フォローにまとめるのは反対だ。理由は `CLAUDE.md` の定点観測の核——「**同条件で観て前回と比べる**」。店をまたぐと条件が揃わず、評価の変化が「好みが変わった」のか「店が違う」のかを分離できない。**同じ店・同じ席・同じ一杯を固定パラメータにして初めて、動いた変数＝自分の好み、が測れる**。君が測りたいのは自分なんだから、店のほうを固定しろ。

## ここからが本題 — 既存規約では割り切れない点が4つある

いいか、よく聞け。上の仕分けは綺麗に見えるが、**同じ実在の店が logs の1行と follows の1対象を同時に持つ**という事態を、今の規約はどこにも書いていない。むしろ「間違えないこと」と排他っぽく書いてある。ここが穴だ。実装まで見て、具体的に4つ出す。

### 穴1: 台帳の1行と、フォローの対象が繋がらない（片方向すら怪しい）

`web/src/lib/wiki.js:19-27` の `resolveTarget` を読むと:

- `[[cafes/kissa-blue]]` → ログ記録に解決する ✅（フォロー → 台帳の行 は張れる）
- `[[kissa-blue]]` → **フォローには解決しない**。スラッシュを含まない場合の探索順は notes → mocs → atlases → logtopics で、**follows が入っていない**（`wiki.js:32-39`）

つまり**台帳の行からフォローへリンクが張れない**。未解決の wikilink は素通しのプレーンテキストになり（`wiki.js:48`）、`graph.js` のバックリンクにも計上されない。これは `web/DESIGN.md` **原則6「行き止まりを1つも作らない」の直撃**だ。「型によって有無が分かれる実装を禁止する」と自分で書いてある、その通りのことが起きている。

### 穴2: 台帳の評価が時効を迎える

`CLAUDE.md` は logs を「各記録は主に1回きり」と定義している。だが行きつけの店は**通うたびに評価が動く**。初訪時の `rating: 3` が5年後もそのまま台帳に居座り、フォロー側の session には「今は5」と書いてある——**正本の中で数字が2つに割れる**。「サイレント上書き禁止」は上書きの手続きを縛るだけで、**どちらが正本かを決めていない**。

### 穴3: `interest` 型フォローは、数値の推移カードが構造的に出ない

`web/scripts/build-data.mjs:171-185` は**フォロー型に関係なく** `series`（観測値の時系列）を組んでいて、`metric_goals` が無い指標は `goal: null`＝中立で持つ。データ層は正しい。

ところが `web/src/lib/edition.js:108` と `:158` は、`milestone` / `series` カードを **`followType === 'goal'` に限定**している。だから interest 型のカフェフォローに毎回「滞在時間」「好みの焙煎度」を記録しても、**紙面には一生出てこない**。「好みが変わっていくのを追いたい」という君の要求が、面に到達しない。

しかもこれは `DESIGN.md` **原則9「数字に嘘をつかせない」への過剰反応**だ。原則9が禁じているのは「宣言の無い指標を勝手に良し悪し判定すること」であって、**中立のまま折れ線を描くことは禁じていない**。データ層はすでにそう作ってあるのに、面の側だけが臆病になっている。

### 穴4: 画像の公開範囲（これは実害が出るやつだ）

`CLAUDE.md` の logs 節に明記の通り、**サイトのテキストはパスワードで暗号化されるが、画像は Pages 上に素で公開される（直URLで見える）**。一方 follows は「写真をコミットしない」。

カフェは**生活圏そのもの**だ。何十軒の外観写真が公開URLで並ぶのは、豆の袋を並べるのとは危険度が違う。ここは規約の穴というより、**トピック設計時に君が意思決定すべき点**として突きつけておく。

## 規約改定案（5つ。上から順に効く）

```
          _.-/\/\/\/\/\-._
        .'  ///||||||\\\  '.
       /   //||||||||||\\   \
      |     ____   ____     |
      |     \   \ /   /     |
      |     (o)     (o)     |
      |          ^          |
      |      _________      |
       \     (=======)     /
        '._             _.'
    ______ '-._______.-' ______
   /      |             |      \
  |       |     ___     |       |
  |       |    (===)    |       |
   \______|_____| |_____|______/
```
**concern は排他じゃない。役割分担だ。そこを直すぞ！**

### 改定1: `CLAUDE.md` logs 節の「follows との違い」を、排他から**役割分担＋昇格**に書き換える

現状の「間違えないこと」という書き方は、**どちらか一方を選べ**と読める。実態はこうだ:

> **台帳（logs）は入口、フォロー（follows）は深度。同じ実体が両方に居てよい。**
> - **必ず先に logs に1行作る。** 行きつけになっても**台帳の行は消さない**（消すと「何十軒を並べる」網羅性が壊れる。1軒だけ抜けた台帳は台帳じゃない）
> - 通い始めた（＝時系列で追う価値が出た）ものだけを follows に**昇格**させ、双方向リンクを張る
> - **台帳＝現在値のスナップショット、フォロー＝変遷の履歴**。数字が割れたら**フォローが正本**、台帳は現在値に追随して書き換える（理由をコミットメッセージに明記＝サイレント上書き禁止の枠内）

これで穴2が閉じる。

### 改定2: 正本に相互参照フィールドを足す

- log entry frontmatter に `follow: <follow-name>`（任意）
- follow profile frontmatter に `log: <topic-slug>/<entry-slug>`（任意）

`DESIGN.md §7` の判定基準——「**サイトのための都合か、記録として正しい情報か**」——に照らして、これは**正当**だと判断する。「この記録の続きがどこにあるか」は表示の都合ではなく、**記録それ自体の事実**だからだ（`metrics` が正当なのと同じ理屈）。

### 改定3: `wiki.js` の `resolveTarget` に follows のフォールバックを足す

スラッシュ無しの `[[kissa-blue]]` でフォローに解決するようにする（探索順の末尾に追加。entity slug との衝突は現行の優先順で先に entity が拾うので既存挙動は壊れない）。これで**台帳 → フォロー**のリンクとバックリンクが通り、原則6の穴が塞がる。`DESIGN.md §9`「既知の未達」に、原則6の例外が実在したことを記録すること。

### 改定4: `edition.js` の `series` / `milestone` カードから `followType === 'goal'` の縛りを外す

条件を「**`metric_goals` の有無に関係なく、points が2点以上ある指標**」に変える。良し悪しの矢印は `goal: null` のとき出さない——これは原則9をむしろ**正しく**実装した形だ（原則9は「判定するな」であって「描くな」ではない）。`DESIGN.md` の原則9に「**中立の指標は判定せずに描く。描かないことは原則9の要求ではない**」と一文追記する。

### 改定5: `logs/cafes/topic.md` は `image_visibility` を意識的に決める

`public` にするならドリンク・カップに限り、外観・看板・位置が読める写真は載せない。判断がつかないなら `none` で始めろ。**後から公開するのは簡単だが、公開したものを取り消すのは不可能**だ。

## ついでに: これは `DESIGN.md §9` の未達を実データで踏む初のケースだ

> **記録帖の比較テーブルが実データで検証できていない。** entries が1件しかないため。2件目が入ってから確認する。

現状 `logs/coffee-beans` も `logs/model-comparison` も entries は1件。`compare` カードは `edition.js:163` の `entries.length >= 2` で初めて発火する。**カフェを何十軒入れると、ここが一気に本番負荷を受ける**。同時に `DESIGN.md` 原則11「一度に見せるノードは12点まで」に対して、数十軒の台帳が棚・比較テーブルでどう畳まれるかも初検証になる。作りながら見ておく価値がある。

## 実施順の推奨

1. **`logs/cafes/` を先に作る**（改定5の判断込みでスキーマ設計）。何十軒の台帳が土台で、フォローはそこからの昇格だ
2. 2〜3軒たまって「ここは通うな」と確信できてから `follows/<store>/` に昇格
3. **改定1・2（規約とfrontmatter）は昇格の前に決めておく**。後から遡って繋ぐのは面倒だ
4. 改定3・4（`web/` の実装2箇所）は、フォロー側に session が2回たまってから。1件では変化が見えず、直したかどうかも判定できない

いいか、この設計の肝は「台帳を捨てずにフォローへ昇格させる」ところだ。**行きつけになった瞬間に台帳から消えるような設計にしたら、「何十軒を並べて比べる」という一番の願いが、一番大事な数軒を欠いた状態で叶うことになる**。そこだけは絶対に妥協するな！

ファイルは1つも触っていない。改定案でGOなら、次は `logs/cafes/topic.md` のスキーマ設計から一緒に燃えていこう！
