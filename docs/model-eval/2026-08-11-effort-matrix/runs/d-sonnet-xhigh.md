## 設計

### 全体方針
サーバ運用者が中身を読めない（R2）という制約から、**サーバは「暗号文の中継役」に徹し、検索・マージなど中身を解釈する処理はすべてクライアント側で行う**ローカルファースト構成にする。同期は暗号化された差分（オペレーション）の交換、検索はデバイス上のFTSインデックス、というのが骨格。

```
[PC クライアント]                 [スマホ クライアント]
  ローカルDB (SQLite)               ローカルDB (SQLite)
  ├ CRDTドキュメント(本文)          ├ CRDTドキュメント(本文)
  ├ FTS5 全文索引                  ├ FTS5 全文索引
  └ 鍵: MK/AK (メモリ+OSキーチェーン) └ 鍵: MK/AK (メモリ+OSキーチェーン)
        │        ▲                      │        ▲
        │暗号文の │暗号文の                │        │
        │push    │pull                   │        │
        ▼        │                       ▼        │
   ┌─────────────────────────────────────────────┐
   │                同期サーバ                      │
   │ ・ユーザ/メモ単位の「暗号化オペレーションログ」   │
   │   (append-only, 中身は解釈しない)               │
   │ ・KDFパラメータ(salt等。非秘匿)                  │
   │ ・OPAQUE認証レコード(パスフレーズそのものは非保持)│
   │ ・メタデータ: メモID/更新時刻/サイズ/デバイスID    │
   │ → 平文・復号鍵は一切保持しない                    │
   └─────────────────────────────────────────────┘
```

### 構成要素
- **クライアント**: PC/スマホとも同一構成。ローカルSQLite内に (a) CRDTドキュメントストア (b) FTS5全文索引 (c) 暗号鍵キャッシュ、を持つ。ここが「正」のデータであり、サーバは常にレプリカの一つに過ぎない。
- **同期サーバ**: ユーザごとの暗号化オペレーションログを保存・配信するだけの薄いリレー。中身のマージや検索は一切行わない。
- **認証サーバ機能**: OPAQUE（非対称PAKE）でアカウント認証を行う。理由は後述（鍵の扱い参照）。

### 鍵の扱い（R2, R4）
1. サインアップ時、パスフレーズから **Argon2id**（サーバ管理外の十分なコスト設定）でマスターキー(MK)を導出する。saltはサーバに保存するが非秘匿情報。
2. MKは「アカウントキー(AK)」（本文暗号化に使う実鍵、ランダム生成）をラップするためだけに使う。AK自体はMKで暗号化された小さな封筒（数十バイト）としてサーバに置く。
   - MKで直接本文を暗号化せず、AKを間に挟むのは、将来パスフレーズを変更してもAKの再ラップだけで済み、全メモの再暗号化が不要なため。
3. 各メモ（正確にはCRDTの差分オペレーション）はAKから HKDF で導出したサブキーを使い、XChaCha20-Poly1305などのAEADで暗号化する。ノンスはランダム生成（24byteなら衝突確率は無視できる）。タイトル・タグなど**メタデータも含めすべて暗号化**する（本文だけでなくタイトルも平文でサーバに置かない、というのがR2の厳密な読み方）。
4. アカウント認証は**OPAQUE**を使い、パスフレーズ由来の値をサーバに一切送らない・サーバも「クラック可能な検証子」を持たない設計にする（従来のパスワードハッシュ保存方式は、サーバ侵害時にオフライン総当たりの的になるため避ける）。認証用鍵とAKラップ用のMKは、HKDFのinfo文字列を変えて用途分離する。

**新端末追加フロー（R4）**:
1. アカウントID＋パスフレーズを入力
2. サーバからKDFパラメータ(salt)とAK封筒(数十byte)を取得 → その場でAKを復元（Argon2idの計算に0.5〜1秒程度）
3. メモの一覧メタデータ（ID・更新時刻・タイトルの暗号文など、1万件でも数百KB〜数MB程度）を取得・復号し、即座に一覧UIを表示
4. 本文本体とFTS索引は「直近開いたメモ・直近更新されたメモ」を優先度付けてバックグラウンドで取得・復号・索引構築
→ ここまでで数秒。ユーザは待たされずにメモの閲覧・新規作成・編集を始められる。全件の検索網羅は背景同期の進捗に依存する（詳細は「要件について」参照）。

### 同期と競合解決（R1）
- 各メモを1つの**CRDTドキュメント**として管理する（本文はテキストCRDT、タイトル/タグ/フォルダなどはLWWレジスタ）。CRDTなのでオフライン中の編集同士も後から自動マージでき、ユーザに手動マージを迫らない。
- クライアントはローカルの編集をオペレーション（差分）として蓄積し、暗号化してサーバにpush。他デバイスは自分のカーソル位置以降のオペレーションをpullし、復号してローカルCRDTに適用するだけ。**サーバはオペレーションの中身を見ずに保存・配送するだけ**でよく、マージロジックは一切持たない＝R2との相性が良い。
- 削除は論理削除（トゥームストーン＋ゴミ箱30日保持など）にし、「片方は削除・片方は編集」という競合でもデータが消えないようにする。
- オペレーションはキー入力ごとではなく数秒デバウンス／バックグラウンド移行時にflushし、ログの肥大を抑える。
- **履歴の肥大化対策**: CRDTは編集履歴が伸び続けると同期・再生コストが増える。全デバイスが受信済みのオペレーションは定期的にスナップショットへ圧縮（GC）し、新端末が最初から全履歴を再生しなくて済むようにする。これはR4（新端末を数秒で使えるようにする）を1万件×10万字というR5のフル規模でも成立させるために必須。

### 検索の実現方式（R3）
- サーバに平文がない以上、**全文検索はクライアント側でしか実現できない**。各デバイスはローカルSQLiteの **FTS5**（トークナイザ調整＋トライグラム等）でメモ本文の索引を持つ。
- 1万件×最大10万字（最悪ケースで数GB規模）でも、FTS5はローカルの逆引き索引による検索であり、クエリはミリ秒〜数十ミリ秒オーダーで返る。E2EEメモアプリ（Signal Desktopなど）でも同様にローカルFTSで「即座」を実現している実績がある。
- 索引は編集の都度インクリメンタルに更新する。新端末では前述のとおり優先度付き背景同期でメモ本体を取り込みながら索引も段階的に構築する。

### スケールに関する補足（R5）
- 1メモ最大10万字・最大1万件という最悪ケースでは、ユーザあたりの平文総量が数GBに達しうる。ローカルストレージ容量的には現代のPC/スマホで問題ないが、初回全同期の帯域・時間は無視できないため、上記の「優先度付き背景同期」が設計上重要になる。
- 暗号化前にzstd等でテキストを圧縮しておくと、ストレージ・同期帯域を削減できる（暗号化後は圧縮が効かないため順序が重要）。

## 要件について

要件自体に矛盾はないが、**要件間の緊張関係**と、**字義通りに読むと曖昧・見落としが生じやすい点**がいくつかあったので、採用した判断とともに記す。

1. **R2とR3の緊張関係**: 「サーバは平文を一切持たない」を厳格に守ると、全文検索エンジンはサーバ側に置けない（サーバ側に索引を置くなら索引にトークン化された平文相当の情報が渡ってしまう）。→ **検索は完全にクライアントサイドで行う**という設計判断を採った。副作用として、各デバイスはメモ全量（の少なくとも検索対象部分）をローカルに保持する必要があり、ストレージ・帯域コストが発生する。ユーザ規模が今後大きく伸びる場合はここがボトルネックになりうる。

2. **R3とR4の緊張関係**: 「数秒で使い始められる」対象が、1万件フルの検索網羅まで含むのか、閲覧・編集の再開までを指すのかで実現難易度が大きく変わる。R5の最悪値（数GB相当）を素直に全同期しようとすると、モバイル回線では数秒では終わらない。→ **「数秒」はメタデータ一覧の取得と鍵の復元＝閲覧/編集を始められる状態までとし、全文検索の完全網羅は優先度付きの背景同期で追いつかせる**という解釈を採用した。この解釈が意図と異なる場合（＝新端末でも即座に全件検索が効く必要がある場合）、要件を満たすには初回同期のUXに「索引構築中」の状態を許容する仕様変更が必要になる。

3. **R2の対象範囲の曖昧さ**: 「メモの中身」が本文だけを指すのか、タイトル・タグ・フォルダ名なども含むのかが未指定。多くのE2EEメモアプリは一覧表示の都合でタイトルだけ平文管理してしまいがちだが、それは「サーバ運用者が中身を読めない」の趣旨に反しうる。→ **タイトル・タグを含め、ノートに関わる文字列情報はすべて暗号化する**という厳格な解釈を採用した。

4. **R2とアカウント復旧の非両立**: サーバが復号鍵を一切持たないため、パスフレーズを忘れた場合、運用者側での「パスワードリセット」に相当する救済策が原理的に存在しない（できるとすればR2違反になる）。→ これは要件の不備というより本質的なトレードオフだが、ユーザー影響が大きいため明示しておく。対策として、サインアップ時に一度だけ表示する高エントロピーな**リカバリーコード**（AKを別経路でラップする鍵）を発行し、パスフレーズ喪失時の唯一の救済路とする設計を推奨する（今回の設計には runtime 上の追加コンポーネントとしてのみ触れ、必須要件には含めていない）。

5. **メタデータの秘匿はR2の対象外**: 「中身を読めない」は本文・タイトル等のコンテンツに対する機密性の話であり、メモ件数・更新頻度・おおよそのサイズ・同期タイミング・接続元IPなどのメタデータはサーバから完全には隠せない（同期を成立させるために必要な情報のため）。これはE2EEシステム全般に共通する限界であり、要件の不備ではないが、「運用者は一切何もわからない」という誤解を避けるため明記しておく。

6. **R4とR2（鍵配布方式）の整合**: 「新端末をパスフレーズだけで数秒以内に使い始められる」を満たすため、既存端末による承認（デバイスリンキング）方式ではなく、**パスフレーズから決定論的に同じ鍵を導出できる方式**を採用した。これにより他デバイスがオフラインでも新端末を即座に有効化できる一方、アカウントの安全性が完全にパスフレーズ強度に依存する（サーバ側総当たり耐性はArgon2idのコストパラメータのみに依存）。パスフレーズの強度確保（長さ・辞書チェック等)をオンボーディングUIで強制することを前提とする。

上記以外の点（R1〜R5そのものの内容）に矛盾・実現不可能な要求は見当たらなかった。
