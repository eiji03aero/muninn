## 設計

### 0. 全体像

```
[端末A/PC]        [端末B/スマホ]        [新端末C]
   |  ローカルDB(暗号化)    |                    |
   |  CRDTドキュメント      |                    |
   |  ローカル索引          |                    |
   +----------+------------+--------------------+
              |  暗号化済みブロブのみ（TLS上）
        +-----v---------------------------------+
        |  サーバ（ゼロ知識ストア）               |
        |  ・不透明IDのオブジェクトストア          |
        |  ・追記専用の更新ログ（内容は復号不能）   |
        |  ・索引バケット（暗号化）               |
        |  ・鍵配布メタ（salt / wrapped MK）      |
        +---------------------------------------+
```

サーバは **一切の復号鍵を持たない**。行うのは「不透明なIDに紐づく暗号ブロブの保管・追記・配布」と「認証・課金・レート制限」のみ。

---

### 1. 構成要素

| 層 | 役割 |
|---|---|
| クライアント（PC / スマホ / Web） | 暗号化・復号、CRDTマージ、索引構築、検索実行。**すべての知的処理はここ** |
| ローカルストア | SQLite（デスクトップ/モバイル）／ IndexedDB+wa-sqlite（Web）。ノート本文・CRDT状態・索引を保持。OSキーチェーンの端末鍵でat-rest暗号化 |
| 同期サーバ | 更新ログの追記・配信、オブジェクト保管、索引バケット保管。内容は不可読 |
| 鍵サービス（同サーバ内） | `salt`・`wrapped master key`・公開鍵ディレクトリの配布のみ |

### 2. 鍵の扱い

#### 2.1 鍵階層

```
パスフレーズ
   │ Argon2id(salt, m=64MiB, t=3, p=4)   ← 目標 ~600ms（モバイル実測で調整）
   ▼
  KEK ──(AES-256-GCM で復号)──► MK（マスタ鍵, 256bit ランダム）
                                 │  wrapped_MK はサーバ保管
                                 │
     ┌───────────────┬───────────┼──────────────┬──────────────┐
     ▼               ▼           ▼              ▼              ▼
   CK             IK            STK           NK            IDK
 (本文鍵)      (索引値鍵)   (語のHMAC鍵)   (名前導出鍵)   (端末IDキーペア)
     │
     └─► 各ノートに DEK（ランダム）。DEK は CK でラップして
         ノートヘッダに格納（→ 将来の共有時は相手の公開鍵で再ラップするだけ）
```

- 導出はすべて `HKDF-SHA256(MK, info="notes/v1/<用途>")`。
- サーバに置くのは `salt` と `wrapped_MK` のみ。**パスフレーズもKEKもMKも送らない。**
- ノートIDは `NK` から導出した不透明な128bitランダム値。サーバはタイトルもパスも見ない。
- 端末ごとに X25519 キーペア（IDK）を持ち、端末追加時に既存端末が承認して端末公開鍵をディレクトリに登録。**失効した端末を締め出すためのMKローテーション**（新MK生成 → 残る端末の公開鍵で配布 → 以後の書き込みは新MK）に使う。

#### 2.2 新端末の起動シーケンス（R4）

```
1. アカウント識別子入力 → salt + wrapped_MK を取得        (~100ms)
2. Argon2id で KEK 導出                                  (~600ms)
3. MK アンラップ、サブ鍵導出                              (~1ms)
4. 「軽量メタ層」を一括DL・復号 → 一覧が出る              (~1s)
5. 使用開始。本文と索引は背景で流し込む
```
合計 **2秒前後**。ステップ4の軽量メタ層が設計の要（後述）。

### 3. データモデルと同期

#### 3.1 ノートの表現

1ノート = **ブロック列のCRDT**。

```
Note {
  id:        opaque 128bit
  header:    Enc_CK{ DEK, createdAt }              ← 小さい・めったに変わらない
  meta:      Enc_DEK{ title, updatedAt, tags, 先頭200字 }   ← 軽量メタ層に載る
  body:      ブロック（≒段落）ごとに分割した CRDT
             block_i: Enc_DEK{ yjs update / snapshot }
}
```

本文を**ブロック単位で別々に暗号化**する理由：10万文字（UTF-8で約300KB）のノートを1文字直しただけで300KBを再暗号化・再送するのを避けるため（R5対応）。1ブロックは目安4KB、超えたら分割。

#### 3.2 同期プロトコル

サーバ側は **追記専用ログ** だけを持つ：

```
POST /log   { noteId, deviceId, seq, lamport, ciphertext, sizeBucket }
GET  /log?since=<serverCursor>   → 暗号ブロブの列
```

- サーバは中身を見ずに **順序付けと配信** のみ。`seq` はデバイス単位の単調増加で、再送はサーバ側で `(deviceId, seq)` により冪等に弾かれる。
- オフライン中の編集はローカルの送信キューに積まれ、復帰時にそのまま流れる（R1）。ローカル書き込みが確定してからキューに入るので、**送信前に落ちても失われない**。
- サーバは「順序の権威」ではない。因果順は各更新に埋め込んだ Lamport 時刻とベクタで**クライアントが**再構成する。サーバの並べ替えや欠落は結果に影響しない。

#### 3.3 競合解決

- **本文テキスト：CRDT（Yjs / YATA 系）による自動マージ。競合ダイアログを出さない。**
  同じ段落を2端末が同時に編集しても、両方の挿入が意図した位置に残る。これが「オフライン編集が失われない」の実質的な保証（R1）。
- **タイトル・タグ**：タイトルは LWW-Register（Lamport時刻＋端末IDでタイブレーク）、タグは OR-Set。
- **削除**：即時の物理削除はしない。`deleted` フラグを **削除が編集に勝つ（delete-wins）** ではなく **OR-Set 的な「削除 vs 復活は復活が勝つ」** で扱い、30日のゴミ箱を経て物理削除。オフライン端末が古い状態で削除を上書きする事故を防ぐため。
- **ログの肥大化**：クライアントが定期的にノート単位でスナップショット化する。`(noteId, epoch)` を進めて新スナップショットを書き、全端末の確認カーソルが epoch を超えたら旧更新をサーバから削除依頼。**サーバは中身を読めないので、圧縮の判断は必ずクライアント側**。

### 4. 検索の実現方式（R3）

平文をサーバに置けない以上、**サーバ側の全文検索エンジンは使えない**。かといって「全ノートを落として復号してから検索」では新端末が数秒で立ち上がらない（R4と衝突）。両立させるため、索引を**暗号化された取り寄せ可能なバケット**として持つ。

#### 4.1 トークナイズ

- NFKC 正規化 → 小文字化 → 記号除去。
- **日本語・中国語・韓国語：文字 2-gram（bigram）**。形態素解析器は端末間で辞書バージョンがずれると索引が壊れるため使わない。
- **英数字：単語トークン ＋ 先頭3文字以上のエッジn-gram**（前方一致検索用）。

#### 4.2 暗号化転置索引

語 `t`、ノート `n` に対して：

```
bucketId  = HMAC(STK, t)[0..15]           ← サーバから見える唯一の手がかり
entryId   = HMAC(STK, t ‖ n)              ← 冪等な追加・削除キー
value     = Enc_IK{ noteId, tf, positions要約, noteVersion }
```

- 索引は `(entryId → value)` の**集合**であり、追加・削除が可換かつ冪等 → 複数端末が同時更新しても**マージが自明**（CRDTのOR-Set相当）。`noteVersion` により、古い端末の遅れた削除が新しい追加を消さない。
- ノート更新時、クライアントは「旧bigram集合 と 新bigram集合 の差分」だけを索引更新として送る。
- 索引はあくまで**導出物**。壊れても本文から完全に再構築できる。

#### 4.3 検索の実行

```
クエリ「暗号化 設計」
  → bigram: 暗号,号化,設計
  → 各 bucketId を算出
  → ① ローカル索引にあれば即座に引く（0〜数ms、オフラインでも動く）
     ② なければ該当バケットのみサーバから取得（数十KB、~50-150ms）
  → entry を復号 → noteId 集合を積集合
  → bigram由来の偽陽性を除くため、候補ノートのみ復号して実文字列照合
  → BM25 でランキング（tf は索引に、df はバケットサイズから、
     全ノート数はローカルメタから）→ スニペット生成
```

1万件・平均2KBなら索引エントリは概ね1500万件・実体で数十MB規模。ローカルに載ってしまえば積集合は**数ms**。ネットワーク経由でも**200ms以内**で「体感即座」を満たす。候補が数千件に膨らむ一般的すぎる bigram は、バケットサイズ上限を超えた時点で「stop-gram」扱いにして他の語で絞ってから照合に回す。

#### 4.4 3層のデータ取得（R4との両立の肝）

| 層 | 内容 | 1万件での概算 | いつ取る |
|---|---|---|---|
| **L1 メタ層** | ノートID・タイトル・更新日時・タグ・先頭200字 | 圧縮後 **2〜4MB** | 起動直後に一括。**これで一覧とタイトル検索が即使える** |
| **L2 索引** | 暗号化バケット | 数十MB | 背景で流し込み。完了までは必要バケットのみ都度取得 |
| **L3 本文** | ブロック実体 | 最大1GB | 開いたノート＋最近使った分だけ。LRUで上限管理 |

新端末は L1 だけで「使い始められる」。L2 の背景同期が終わって初めて**完全なオフライン全文検索**が成立する。

### 5. サーバが見えるもの／見えないもの

| サーバに見える | 見えない |
|---|---|
| ノート数、各ブロブのサイズ（**64KB単位にパディング**して丸める）、更新時刻、端末数、アクセスパターン、アクセスされた bucketId | 本文、タイトル、タグ、検索語そのもの、ノートIDと内容の対応 |

`bucketId` の観測により、サーバは「同じ語が繰り返し検索された」ことや語の出現頻度分布を統計的に推測しうる（Searchable Symmetric Encryption の既知のリーク）。緩和として、検索時に**ダミーバケットを混ぜる**、L2 の背景同期を完了させて以後の検索を完全ローカル化する、索引更新を**バッチ化＋ランダム遅延**で送る、を行う。

## 要件について

要件そのものに、そのままでは成立しない箇所が3つある。いずれも設計側で吸収したが、**判断が要件の解釈を変えている**ので明示する。

### 問題1（重大）R2 × R3 × R4 は素直には同時に満たせない

- R2 を厳格に取ると、サーバは検索インデックスを作れない。
- ならばクライアントで検索するしかないが、それには全ノートの本文（最悪1GB）が手元に要る。
- しかし R4 は「新端末が数秒で使い始められる」ことを要求する。数秒で1GBは落ちない。

**採用した判断：**「検索できる」と「本文が手元にある」を分離した。暗号化転置索引（§4.2）を本文と独立に同期し、さらに L1/L2/L3 の3層に分けた（§4.4）。新端末は L1（数MB）だけで一覧とタイトル検索を得て「使い始め」、全文検索は L2 バケットの都度取得で即座に成立し、背景同期の完了後に完全ローカル化する。

**理由：**「即座に検索が返る」と「全データをローカルに持つ」は別の要求であり、後者を後回しにできると気づけば衝突が解ける。代償として、**新端末は L2 同期が終わるまでオフライン全文検索ができない**（オンラインなら可）。ここは要件を厳密には満たしていないので、そう扱ってよいか確認したい。

### 問題2（重大）R2 の「平文を一切持たない」は達成できるが、「運用者が何も知り得ない」は達成できない

内容は読めない。しかしノート件数・サイズ・編集時刻・アクセスパターン・検索バケットのアクセス頻度は、暗号化しても構造上サーバ側に残る。「毎週金曜の夜に大量のメモが更新される」「特定の語が繰り返し検索されている」といったメタデータからの推測は防げない。

**採用した判断：** サイズパディング、不透明ID、索引更新のバッチ化＋ランダム遅延、ダミークエリ混入で緩和し、残るリークを§5に明記した。これを消しきるには ORAM や PIR が要るが、レイテンシが1〜2桁悪化して R3 を壊すため採らなかった。

**理由：** R2 の文言（「メモの中身を読めてはならない」）は満たしている。ただし「サーバは何も分からない」と対外的に説明するとそれは不正確になる。

### 問題3（要件の欠落）パスフレーズ紛失時の復旧が定義されていない

R2 と R4 を素直に実装すると、**パスフレーズを忘れた瞬間に全データが永久に失われる**。サーバは復旧を手伝えない（手伝えるなら R2 が壊れている）。チーム利用なら、退職・端末紛失・忘却は必ず起きる。

**採用した判断：** 鍵階層を「MK を KEK でラップする」形にして、**同じ MK を複数の経路でラップできる**ようにした。

1. パスフレーズ由来の KEK（通常経路）
2. **リカバリキー**（初回セットアップ時に必ず表示・保存させる256bitの文字列）
3. 既存端末からの QR／近接転送による直接移送 ← 実運用ではこれを主経路に推奨

**理由：** 要件に無いが、無ければ製品として運用できない。加えて、これは R4 にも効く。パスフレーズ入力＋Argon2id は最速でも0.6秒前後を消費し、しかもパラメータを軽くすると総当たり耐性が落ちる（強度と R4 が直接トレードオフになる）。QR 移送を主経路にすればこのトレードオフ自体を回避でき、パスフレーズは復旧用に格下げできる。

### 問題4（軽微）R5 の上限が CRDT と噛み合わない

10万文字のノートを単一の CRDT ドキュメントとして扱うと、編集履歴のメタデータがモバイルのメモリと同期帯域を圧迫する。**ブロック分割（§3.1）と定期スナップショット圧縮（§3.3）で対応した。** 圧縮の判断はサーバができない（中身が読めない）ので、クライアント側の責務として設計に組み込んである。

### 問題5（要確認）「チームで使う」と要件本文が食い違う

冒頭は「チームで使うメモアプリ」だが、R1〜R5 はすべて**単一ユーザの複数端末**しか規定していない（R5 も「1ユーザあたり」）。メモの共有・共同編集・権限管理は要件に無い。

**採用した判断：** 共有機能は実装しないが、**後から足せる形だけ用意した**。ノートごとにランダムな DEK を持たせ CK でラップする構造（§2.1）にしてあるので、共有時は DEK を相手の公開鍵で再ラップするだけで済み、本文の再暗号化は不要。端末承認用の X25519 鍵ペアがそのまま相手先の公開鍵として使える。

**理由：** 要件に無いものを勝手に作らない。ただしゼロ知識設計では鍵階層を後から変えるのが極めて高くつく（全データの再暗号化が要る）ため、拡張点だけは今のうちに開けておくべきと判断した。**チーム共有が実際にスコープに入るなら、鍵失効・メンバー離脱時の再暗号化コストの検討が別途必要**で、これは設計の規模を一段変える。
