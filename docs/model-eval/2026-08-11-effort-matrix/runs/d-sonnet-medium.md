## 設計

### 全体構成

```
[端末A: PC]                    [同期サーバ]                    [端末B: スマホ]
 ┌─────────────┐              ┌──────────────┐              ┌─────────────┐
 │ ローカルDB    │  暗号化blob   │ 暗号化blobの   │  暗号化blob  │ ローカルDB   │
 │ (SQLite)     │ ───────────> │ 追記ログ保管    │ <─────────── │ (SQLite)     │
 │ + CRDT本体   │ <─────────── │ (中身は読めない) │ ───────────> │ + CRDT本体   │
 │ + FTS5全文index│            │ + salt/wrapped │              │ + FTS5全文index│
 └─────────────┘              │   DEK          │              └─────────────┘
                               └──────────────┘
```

サーバはユーザ認証・暗号化blobの保管/配信・鍵の暗号化コピーの保管のみを行う「無知なリレー」。復号・検索・マージはすべて端末側。

### 鍵の扱い（R2, R4）

- 新規登録時、端末は乱数でユーザ用データ鍵 **DEK** を生成（これで全メモを暗号化）
- パスフレーズは Argon2id + 端末非依存のsalt（saltはサーバに置いてよい、秘密ではない）で **KEK** を導出。KEKは端末外に出さない
- DEKをKEKでラップ（AES-KW等）した「wrapped DEK」だけをサーバに保存
- 新端末追加（R4）: ログイン → パスフレーズ入力 → 端末内でKEK導出 → wrapped DEKをサーバから取得しローカルで復号 → 数百ms〜1秒程度でDEK取得完了。ここは要件の「数秒」を満たせる
- パスフレーズ変更は「DEKの再ラップ」のみで済み、全メモの再暗号化は不要

メモ本文はサーバに届く前に端末でDEK暗号化される。サーバは暗号文とタイムスタンプ以外を持たない。

### 同期・競合解決（R1）

- メモ本文は**テキストCRDT**（Yjs/Automerge相当）として管理。編集はローカルで即座に操作ログ（update chunk）として生成
- 各updateはDEKで暗号化してからアップロード。サーバは中身を解釈せず、note IDごとの追記専用ログとして保管するだけ
- オフライン中の編集はローカルに溜め、オンライン復帰時に未送信updateを送信＋未取得updateを受信
- CRDTのupdateは**可換**なので、どんな順序・どんな端末構成で適用してもマージ結果は一致し、手動コンフリクト解決UIは不要
- タグ・フォルダ等のメタデータはOR-Set/LWW-registerで同様にCRDT化
- ログが際限なく伸びないよう、端末側で定期的にスナップショット化してからサーバ側の古いupdateを圧縮（サーバはスナップショットの暗号文を保持するだけで内容は関与しない）

### 検索（R3, R5）

- 全文検索はサーバに投げず、**各端末のローカルFTS5インデックス**（復号後の平文から構築）で行う
- 10,000件×最大10万文字 ≒ 最大1GB程度のテキスト量はFTS5で十分実用速度（数十ms）が出る規模
- CRDT updateが適用されるたびに差分だけインデックス更新（全文再構築はしない）ので、大きいメモの編集でも検索の即応性は落ちない
- ローカルインデックスは端末のディスク上に平文相当で存在するため、OSレベルのディスク暗号化・端末ロックに依存する（後述）

## 要件について

問題を4点見つけたので、採用判断とともに記載する。

**1. R2（サーバは平文非保持）とR3（即座な全文検索）はサーバ側検索を排除する**
サーバが暗号化のみ持つ以上、サーバ側で全文検索インデックスを作ることはできない（検索可能暗号は実用上の速度・秘匿性トレードオフが大きく不採用）。そのため検索は各端末のローカルインデックスで行う設計とした。副作用として、各端末は自分がアクセスするメモの全文をローカルに平文相当で保持することになる（後述4とも関連）。矛盾ではなくR2の必然的帰結として処理した。

**2. R4「数秒で使い始められる」とR5「1万件×10万文字」の規模は文字通りには両立しない**
モバイル回線で最大1GB相当のデータを数秒でダウンロード・復号・全文インデックス化するのは非現実的。そこで「使い始められる」を段階的に解釈し、
 - 鍵導出とメタデータ（タイトル一覧・更新日時）の同期は数秒で完了させ、閲覧・新規作成はすぐ可能にする
 - 本文は開いたメモから優先取得＋バックグラウンドで残りをプリフェッチ
 - 全文検索の網羅範囲もバックグラウンド同期の進捗に応じて拡大する
という設計にした。「全メモがすぐ検索対象になる」ことまでは数秒では保証できない点は明示しておく。

**3. 「チームで使う」の意味が仕様上あいまい**
R1は「複数端末で同じメモを編集」としか書いておらず、「チーム」が①各メンバーが自分のメモを複数端末で使う、②メンバー間でメモを共有編集する、のどちらかが不明。今回は①（1ユーザー＝複数端末、鍵は1ユーザー1DEK）を前提に設計した。②が必要な場合は、メモ単位のDEKをメンバーごとの公開鍵でラップして配布する仕組み（招待・失効管理を含む）への拡張が要るため、要件として明確化してほしい。

**4. パスフレーズ紛失時の扱いが未定義**
E2EEである以上、パスフレーズを忘れるとDEKを復元する手段がなく、全メモが永久に読めなくなる。リカバリーキーの発行やソーシャルリカバリー等のバックアップ手段を持たせるかはUX上のトレードオフ（持たせない＝最強の機密性だが誤操作でデータ全損リスク）なので、要件として意思決定が必要。今回は「バックアップ手段なし（最も安全側）」をデフォルトとして採用した。
