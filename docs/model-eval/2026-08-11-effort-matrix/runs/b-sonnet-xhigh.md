## ① 何十軒を並べて比較したい → これは `logs` で決まりだ

迷いなし。CLAUDE.mdの定義そのままだ。

> logs は**多数の別々の項目を同じ項目で並べて比較する（各記録は主に1回きり）**
> follows との違い: follows は**1つの対象**を時系列で定点観測。logs は**多数の別々の項目**を同じ項目で並べて比較する

「豆の傾向・静かさ・電源・再訪したいか」は、まさに `fields` に設計すべき比較軸だ。既存の `logs/coffee-beans/topic.md` と完全に同型のパターンで、新規トピック `logs/cafes/` を切ればいい。fields案（あくまで叩き台）:

```
store(店名, text, required) / area(エリア, text)
roast_lean(豆の傾向, enum: light/medium/dark/わからない)
quiet(静かさ, rating) / outlet(電源, bool) / wifi(bool)
rebuy(また来たいか, bool) / rating(総合評価, rating) / visited_on(date)
```

`coffee-beans` の「また買う」が効いてるように、ここでも「また来たいか」を必ず入れろ。あとで見返す時に一番効くやつだ。

## ② 行きつけ2〜3軒の変遷を追いたい → 骨格は `follows` だが、既存の型に無理に押し込むな

ここが本題だ。「1対象を時系列で定点観測し、sessionsに毎回書き、profileのタイムラインで変化を追う」という**骨格**は間違いなく follows のものだ。だが `follow_type` を見てみろ——`goal` と `interest` の2つしかない。

```
goal型:     ベースラインと比較して目標に向けたアドバイスを返す
interest型: 対象への理解を深めて楽しむ。見どころ・深掘り
```

君がやりたいのは**どっちでもない**。

- **goal型は違う。** 目標もアドバイスも無い。「行きつけのカフェでもっと酸味を追求すべきだ」なんてアドバイス、意味不明だろう。無理にgoal型にすると、存在しない目標をでっち上げることになる。不正確だ。
- **interest型も違う。** interest型が観測してるのは**対象の側の変化**（アルゼンチン代表の布陣が変わる、選手が入れ替わる）。だが君が追いたいのは逆だ——店は同じでも**自分の好みの方が変わっていく**。矢印の向きが逆なんだ。

念のため `web/` の実装も見てきたが、`edition.js`・`thumb/model.js`・`daily/pages.jsx` に `followType === 'goal'` の二値分岐がハードコードされていて、goal以外は自動的にinterest扱い（「もっと楽しみたい」というコピーが出る）になる。ここに無理やり突っ込むと、自分の嗜好記録なのに「見どころ・深掘り」という体で表示される。実装レベルでもズレが確定してる。

これは**規約の穴**だと判断する。既存の型でごまかさず、素直に改定案を出すぞ。

### 改定案

**`follow_type` に3つ目の型を追加する。** 仮称 `taste`型（他に `preference`型でもいい、命名は君の語感優先で）。

```
taste型: 対象そのものではなく、対象と接するたびに変わる自分の嗜好・感覚を定点観測する。
         目標もアドバイスも書かない。書くのは所感と「前回からの変化点」だけ。
```

必要な変更点（今回はファイルを触らないので提案のみ）:

1. **CLAUDE.mdの「フォロー（follows）」節** — `follow_type` の説明に taste型を追記
2. **`templates/follow-profile.md`** — `follow_type: goal # goal=... / interest=...` のコメント行に taste型を追記
3. **`web/src/lib/edition.js`（108, 158行目）と `faces/thumb/model.js`（151行目）と `faces/daily/pages.jsx`（202行目）** — 現状 `goal`/`else` の二値分岐になっていて、taste型を作った瞬間に「else＝interest扱い」の誤表示が起きる。ここは分岐かコピー出し分けの改修が要る
4. **`web/DESIGN.md`** — サイト側の変更を伴うので、規約通り同じコミットで更新が必要（実装だけ変えて思想を古びさせるな、が原則11の運用ルールだ）

### 対象の切り方も一言

3軒それぞれを別の `follows/` ディレクトリにするより、`follows/favorite-cafes/` を1つ作って、3軒を `entities/` に入れることを勧める。理由はシンプルだ——君の一次関心は「自分の嗜好プロファイルの変遷」であって、店はその入れ物にすぎない。店ごとに割ると「先月は浅煎り派だったのに最近は深煎りに寄ってきた」みたいな横断的な変化がタイムラインに出てこない。1本にまとめてこそ追える変化だ。

（ただし `templates/follow-entity.md` は今のところ「役割・強み」みたいな選手ドシエ向けの語彙になってる。カフエに転用するなら軽い読み替えは要るが、大改修じゃない）

### まとめ

| やりたいこと | 判定 | 理由 |
|---|---|---|
| 何十軒を並べて比較 | `logs/cafes/` | 規約でスッと割り切れる。coffee-beansと同型 |
| 行きつけ2〜3軒の好みの変遷 | `follows/favorite-cafes/`（entities分割） | 骨格はfollowsで合ってるが、`follow_type` に3つ目の型（taste型）が要る規約の穴。goal/interestに押し込むのは不正確なのでやらない |

②は既存の型でごまかせば今すぐ着手できるが、それをやると**サイトの表示もCLAUDE.mdの説明も嘘をつくことになる**。ここで妥協せず規約から直す方が、あとで効いてくるぞ。ファイルはまだ何も触ってない——この判断でいくかどうか、決めてくれ！
