## 設計

### 全体構成

```
┌─────────────┐        暗号文のみ         ┌──────────────────┐        暗号文のみ         ┌─────────────┐
│  Device A   │ ───────────────────────▶ │   Sync Server     │ ───────────────────────▶ │  Device B   │
│ (PC/スマホ)  │ ◀─────────────────────── │ (盲目なストレージ)  │ ◀─────────────────────── │ (PC/スマホ)  │
└─────────────┘   push/WS通知              └──────────────────┘   push/WS通知              └─────────────┘
  ├ Yjs Doc(平文はメモリ内のみ)               ├ note_id別の暗号化updateログ
  ├ ローカルDB(SQLite, 暗号文/平文キャッシュ) ├ wrapped MasterKey + salt
  └ SQLite FTS5 全文検索インデックス          └ OPAQUE認証情報(パスワード等価物なし)
```

サーバは「暗号化されたバイト列を、誰宛か分からないまま保管して転送するだけ」の盲目なリレーに徹する。復号・マージ・検索は全部クライアント側。

### 鍵の扱い(R2, R4)

- パスフレーズは**サーバに一切送らない**。認証はOPAQUE(非対称PAKE)を使い、サーバはパスワード等価情報すら持たない。
- パスフレーズ → Argon2id(ユーザごとのsalt、salt自体は非秘匿でサーバに置いてよい) → KEK
- ランダムなMaster Key(MK)を生成し、KEKでラップ(AEAD wrap)してサーバに保存する(数百バイトの小さな暗号文)。
- 実際のノート暗号化には MK を直接使わず、`HKDF(MK, note_id)` でノート単位の鍵を都度導出する。1ノートの鍵が漏れてもMKやほかのノートに波及しない。
- 新端末追加(R4): パスフレーズ入力 → OPAQUEでログイン → salt+wrapped MKを取得(小さい)→ Argon2id(~0.5〜1秒程度にチューニング)でローカル復号 → MK取得。ここまでで数秒。以降のノート本文同期は後述のとおり段階的に行う。

### 同期と競合解決(R1)

各メモをCRDTドキュメント(Yjsを想定、Y.Text)として扱う。

- 編集すると差分(binary update)が生成される
- その差分をノート鍵でAEAD暗号化(XChaCha20-Poly1305等)してサーバへpush
- サーバは `note_id / seq / device_id / timestamp` のメタデータと暗号文をそのまま追記型ログに保存し、他端末へWebSocketでリレーするだけ(中身は読めない・読む必要もない)
- 受信側は復号して `Yjs.applyUpdate()` を呼ぶだけで、順序に関係なく自動的にマージされる(CRDTなので手動コンフリクト解消UIが不要)
- オフライン中の編集はローカルoutboxに溜め、オンライン復帰時にflush。受信側も同様に未適用updateを取り込む → オフライン編集の消失なし
- ログ肥大化対策として、クライアント側で定期的にスナップショット圧縮 → 圧縮済み状態を再暗号化してアップロード → 古いupdateはサーバに削除依頼(中身を見ずに「このseq以前は消してよい」と伝えるだけ)
- ノート一覧・タイトル・削除状態なども別のCRDT(Y.Map)として同じ仕組みで同期し、タイトルも含めて暗号化する(R2を厳密に満たすため)。削除はtombstoneにして「削除 vs 同時編集」の競合でも復元可能にする

### 全文検索(R3)

サーバが平文を持てない以上、検索はサーバ側ではできない → **完全にクライアントローカルで実現する**。

- 各端末でSQLite FTS5(またはFlexSearch等)のローカルインデックスを保持
- 復号したノート本文が確定するたびに増分インデックス更新
- 1万件×最大10万文字(最大約1GB相当)でも、FTS5のトライグラム/ポーターインデックスならローカルではサブ100msオーダーで検索可能
- 副次的なメリット: 検索クエリ自体がサーバに一切送られないため、「サーバ運用者はメモの中身も検索語も知り得ない」というR2の趣旨をむしろ強化できる。サーバ側検索用の秘匿検索(searchable encryption)方式は情報漏洩(アクセスパターン漏れ等)のリスクがあるため、あえて採用しない

### 容量制御(R5)

- クライアント側で1メモ10万文字・1ユーザ1万件を能動的にチェックして拒否
- サーバ側は暗号文なので厳密な文字数検証はできないが、暗号文サイズ(≒平文サイズ+固定オーバーヘッド)とnote_id数の上限でおおよそのクォータを強制する(完全な検証は原理的に不可能。後述)

## 要件について

問題ではなく、要件間のトレードオフとして明示的に判断した点が2つある。

**1. R4「数秒で使い始められる」とR5の最大データ量(最大約1GB相当)の関係**

新端末で1万件・最大10万文字/件のメモを全件ダウンロード・復号・索引構築まで完全に終わらせるのは、回線状況次第では数秒では終わらない可能性がある。
→ R4は「MK復号(≈Argon2idの1秒程度)が完了し、新規メモの作成・直近編集したメモの閲覧ができる状態」を指すと解釈し、全件本文とFTS索引の完全同期はメタデータ先行取得＋更新日時が新しい順の段階的バックグラウンド同期とした。全件が揃うまでは検索結果が一部欠ける可能性がある旨をUI上明示する設計とする。

**2. R2(サーバは平文を一切持たない)とパスフレーズ紛失時の扱い**

サーバがパスワード等価情報もMKの平文も一切持たない設計上、パスフレーズを完全に忘れた場合、既存データを復元する手段が原理的に存在しない(これはR2を満たすための必然的な帰結であり、バグではない)。要件にリカバリ要件の記載がないため、今回はこの制約を受け入れる設計とした。もし復旧手段が必要なら、別途「印刷可能なリカバリコードでMKを二重にラップする」仕組みを追加する必要があるが、それは新たな要件として別途合意すべき事項。

上記2点以外は、要件間の矛盾や実現不可能性は見当たらなかった。
