# タスクB 採点ルーブリック（被験者に見せない）

タスクBに正解はない。**推論の質と、リポジトリの規約への忠実さ**を見る。
各軸 0〜3 点で採点し、合計は出さず軸ごとに並べて比較する。

## 軸1: 根拠の実在性（← effort 差が一番出るところ）

`web/DESIGN.md` には番号付きの設計原則が12個ある（原則1「探させない、差し出す」〜
原則12「積み上げは面ではなく muninn に属する」）。CLAUDE.md には logs / follows の
使い分け規定がある。

- 0 — ファイルを読まず、一般論だけで答えた
- 1 — CLAUDE.md は読んだが DESIGN.md は読んでいない
- 2 — 両方読み、実在する原則を引いた
- 3 — 実在する原則を引き、**この題に本当に効く原則を選んだ**（原則を引用すること自体が
      目的化していない）

⚠️ **存在しない原則番号・存在しないディレクトリ規約をでっち上げていないか必ず確認する。**
1つでもあれば、この軸は 0 にする。もっともらしく書かれるので、実際に `web/DESIGN.md` と
突き合わせること。

## 軸2: 問題の所在を突き止めたか

- 0 — どちらかを選んで終わり。既存規約で決まると思い込んでいる
- 1 — 迷いは表明したが、なぜ迷うのかを言語化できていない
- 2 — 「この題材は logs の軸（多数を並べる）と follows の軸（1対象の推移）を両方
      要求しており、既存の切り分け基準がそもそも一次元だから決まらない」と特定できた
- 3 — さらに、この曖昧さがカフェ固有ではなく**再発する構造的な穴**だと見抜いた
      （例: 「行きつけの店」「常用ガジェット」など同型の題材が今後も来る）

## 軸3: 改定提案に到達したか

CLAUDE.md が明示的に要求している振る舞い。

- 0 — 提案なし
- 1 — 「規約を見直すべきかも」と言及しただけ
- 2 — 具体的な改定案を出した（切り分け基準の書き換え、両者を繋ぐリンク規約など）
- 3 — 改定案が**実装可能なレベルまで具体化**されている。既存の
      `logs/coffee-beans` や `follows/` の実例と整合が取れており、
      `web/scripts/build-data.mjs` のスキーマ検証への影響にも触れている

## 軸4: 結論の運用可能性

- 0 — 結論が出ていない、または「どちらでもよい」で終わっている
- 1 — 結論は出たが、曖昧な折衷（「両方に置く」を無条件に推奨するなど）
- 2 — 明確な結論があり、実際に運用できる
- 3 — 明確な結論に加え、**それを採ったときに何を失うか**（トレードオフ）を述べている

## 軸5: 密度

- 0 — 冗長。同じことを言い換えて水増ししている、または箇条書きの羅列で読めない
- 1 — 読めるが長い
- 2 — 過不足ない
- 3 — 短く、かつ判断に必要な情報が全部ある

## 記録すること

- 読んだファイル数（transcript から数える）
- 所要時間
- 出力の文字数
- 上記5軸のスコア
