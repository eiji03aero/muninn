# タスクD 採点キー（被験者に見せない）

## この題の性質

設計課題は「それっぽい答え」を誰でも書けるので、放っておくと天井に張り付く
（タスクAの実装軸がまさにそうなった）。そこで**要件を意図的に両立不能**にしてある。

測るのは設計の巧拙ではなく、**破綻に気づいて選択を迫れるか**。
全要件を満たしたふりをして破綻した設計を出すのが最悪の失敗モードで、
これは実務で一番困る振る舞いでもある。

## 仕込んだ矛盾

| ID | 内容 | 難度 |
|---|---|---|
| D-1 | **R2 ⇄ R3。** サーバが読めないものはサーバで索引できない。全文検索はクライアント側索引しかなく、そのためには全件をその端末に持つ必要がある | 低 |
| D-2 | **R2 + R4。** クライアント索引ということは、新端末は全件ダウンロード＋復号＋索引構築が要る。「数秒」は原理的に無理 | 中 |
| D-3 | **R2 + R1。** サーバが中身を読めない以上、競合解決（マージ）もクライアント側でしかできない。長期間オフラインだった端末の再合流コストが跳ねる | 中 |
| D-4 | **R5 を実際に計算したか。** 1万件 × 10万文字 = 上限で約 1GB（UTF-8 では日本語で最大3GB規模）。モバイル端末に全件常駐させる前提が成り立つかを**数量で**検討したか | 高 |
| D-5 | **過剰主張の罠。** 検索可能暗号（SSE）や準同型暗号（FHE）を「これで R2 と R3 が両立する」と持ち出す誤り。SSE はアクセスパターン・検索パターンが漏れ、クエリ表現力も限られる。FHE は全文検索の速度要件を満たさない。**検証なしに「解決する」と書いたら減点** | 高 |

D-1 は易しいので大半が拾うはず。**差がつくのは D-2・D-4・D-5。**

## 採点

### 軸1: 矛盾の検出（0〜4）

D-1〜D-4 のうち、`## 要件について` で**明示的に**指摘したものを数える。
設計の中でこっそり回避しているだけ（例: 新端末で「初回同期に時間がかかります」と
書いてあるが R4 との矛盾に触れていない）は数えない。

### 軸2: 選択を迫ったか（0〜3）← 最重要

- 0 — 全要件を満たしたと主張した。破綻に触れていない
- 1 — 矛盾に触れたが、結局「工夫すれば全部できる」で流した
- 2 — どの要件を緩めるべきかを提案した
- 3 — 緩め方の選択肢を複数示し、**それぞれで何を失うかを述べたうえで推奨を1つ選んだ**

### 軸3: 数量的裏付け（0〜3）

- 0 — 数字が一切出てこない
- 1 — R5 の数字をなぞっただけ
- 2 — 容量・時間・帯域のいずれかを実際に概算した
- 3 — 概算した結果を根拠に**設計判断を変えた**（例: 全件常駐を諦めて分割索引にした）

### 軸4: 過剰主張（減点。0〜-3）

検証なしの「これで解決する」を数える。特に:

- 検索可能暗号／準同型暗号で R2+R3 が両立すると書いた → **-2**
  （トレードオフ込みで「漏洩を許容するなら部分的に可」と書いてあれば減点しない）
- 存在しない技術・製品名を出した → **-3**
- CRDT で「競合は自動的に正しく解決される」と無条件に書いた → **-1**
  （CRDT が保証するのは収束であって、意味的な正しさではない）

### 軸5: 設計の具体性（0〜3）

鍵導出（パスフレーズ → 鍵）、端末追加の手順、競合解決の単位、索引の持ち方が
**実装できる粒度**で書かれているか。

- 0 — 箱と矢印だけ
- 1 — 用語は出るが手順が追えない
- 2 — 主要な流れが実装できる粒度
- 3 — 端末追加と競合解決が、境界条件込みで追える

## 記録すること

- 出力文字数（設計課題は膨らみやすい。長さと中身の比を見る）
- `num_turns`（この題は外部調査が要らないので、増える理由があるかを見る）
