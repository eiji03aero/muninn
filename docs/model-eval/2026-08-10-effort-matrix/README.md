# モデル × effort 比較実験（2026-08-10）

`{sonnet, opus} × {medium, high, xhigh} × {タスクA, タスクB}` = **12ケース**。
同じ入力を与えて出力を比べ、**モデルの特性と effort の使い分け**を掴むのが目的。

## 何を測ろうとしているか

- **effort（medium→xhigh）で動くもの**: 探索量、自己検証、仕様の穴・矛盾に気づくか、
  代替案を潰すか。→ **もっともらしい誤答が用意されている題**で差が出る（＝タスクA）
- **モデル（sonnet↔opus）で動くもの**: 切り分けの筋、抽象度の選び方、文章の質、
  押し返せるか。→ **正解が一意でない判断もの**で差が出る（＝タスクB）

全員が正解する題も全員が失敗する題も情報量ゼロなので、
どちらも「難しすぎず、うっかりミスが仕込める」ラインに置いてある。

## ファイル

| ファイル | 用途 | 被験者に見せるか |
|---|---|---|
| `task-a.md` | タスクAの課題文（穴と矛盾を仕込んだ仕様書） | **見せる**（丸ごと貼り付ける） |
| `task-b.md` | タスクBの課題文（`---` で囲まれた部分だけ） | 囲み内**のみ**見せる |
| `answer-key-a.md` | タスクAの欠陥一覧・テストケース・期待値 | ❌ |
| `rubric-b.md` | タスクBの5軸ルーブリック | ❌ |
| `scoresheet.md` | 12ケースの記入表 | ❌ |
| `runs/` | 各ケースの生出力を保存する場所 | ❌ |

## 走らせ方

各ケースは**必ず新規セッション**で走らせる（文脈汚染を避ける）。

```
1. セッションを起動
2. /model sonnet        （または /model opus）
3. /effort medium       （または high / xhigh）
4. 実際に反映されたか画面で確認する  ← 重要
5. 課題文を貼り付ける
6. 出力を runs/<task>-<model>-<effort>.md に保存する
```

**手順4を飛ばさないこと。** `/effort` は、そのモデルに launch-default effort hold が
かかっている間は `Not applied` を返して何も起きない。気づかずに走らせると medium と
xhigh が同じ設定で回っていた、ということになる。`Not applied` が出たケースは記録から除外する。

### タスクAはリポジトリの外で走らせる

タスクAは課題文が自己完結しているので、**muninn とは無関係の空ディレクトリ**で走らせる。
こうすれば `answer-key-a.md` を読まれる可能性がゼロになり、12ケースの入力が完全に揃う。

### タスクBはリポジトリ内で走らせる

タスクBは `CLAUDE.md` と `web/DESIGN.md` を読ませるのが主眼なので、muninn の中で走らせる。
このとき採点キット自体がリポジトリ内にあるので、広めに grep されると
`rubric-b.md` が見つかる可能性はゼロではない。気になるなら、走らせる前に

```bash
git stash push -- docs/model-eval/2026-08-10-effort-matrix
```

でキットを退避し、採点時に `git stash pop` で戻す。

## 採点

1. 12ケース分の出力を `runs/` に揃える
2. **ラベルを剥がす**。ファイル名を `01.md`〜`12.md` にリネームし、対応表を別に持つ
3. `answer-key-a.md` / `rubric-b.md` に従って採点する
4. 対応表を戻し、`scoresheet.md` に転記する

ラベルを見ながら採点すると「opus のほうが良いはず」というバイアスがそのまま結果になる。
剥がす手間をケチらないこと。

## 結果の読み方（重要）

**n=1 なので、小さい差は誤差。** 「xhigh のほうが少し良い気がする」程度の差は結論にしない。
拾ってよいのは、はっきり出た差だけ:

- T-1（矛盾）を指摘した / しなかった
- 実装テストが 5/8 と 8/8 のような明確な差
- 存在しない原則をでっち上げた / でっち上げなかった

所要時間とトークン消費も記録しておくと、「xhigh はコスト N 倍で得るものがこれだけ」
という判断ができる。**これが最終的に欲しい答え。**
