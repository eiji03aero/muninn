## 設計

### 全体構成

```
[PCクライアント]                              [スマホクライアント]
 ローカルDB(平文, 端末暗号化ストレージ内)          同左
  ├─ 各メモのCRDT状態                          ├─ 各メモのCRDT状態
  ├─ FTS全文検索インデックス(SQLite FTS5等)      ├─ FTS全文検索インデックス
  ├─ MK/DEK(メモリ上、端末キーチェーンで保護)      ├─ MK/DEK
  └─ 未送信outbox(暗号化差分)                    └─ 未送信outbox
        │ ▲                                        │ ▲
        │ │ 暗号化CRDT差分 / スナップショット           │ │
        ▼ │                                        ▼ │
   ┌────────────────────────────────────────────────────┐
   │              サーバ(ゼロ知識・中継役)                    │
   │ ・note_idごとの暗号化op log + 最新暗号化スナップショット   │
   │ ・wrapped_mk (パスフレーズ由来鍵で包んだマスター鍵、数KB) │
   │ ・メタデータのみ: note_id / version / updated_at / size│
   │ ・WebSocket / push で差分をファンアウト                │
   │ （平文・検索インデックス・パスフレーズは一切持たない）      │
   └────────────────────────────────────────────────────┘
```

サーバの役割は「暗号化ブロブの保管と配送」だけに限定する。文書の意味を解釈する処理（検索・マージ判断）はすべてクライアント側で行う。

### 鍵の扱い(R2)

- 署名/ログインとは別に、パスフレーズ → Argon2id(端末側で計算, 約1秒程度に調整) → KEK を導出。KEKは端末外に一切送信しない。
- アカウント作成時にランダムなマスター鍵(MK)を生成し、KEKでラップしてサーバに保存(`wrapped_mk`、数KB)。
- メモごとに個別のDEKを生成し、MKでラップしてメモの暗号文に添付。個別鍵にする理由は、将来メモ単位の共有・失効を可能にし、鍵漏洩時の被害範囲を1メモに限定するため。
- 本文はAEAD(XChaCha20-Poly1305等)で暗号化。AAD(関連データ)に`note_id`とversionを含め、暗号文の付け替え・リプレイを検出可能にする。
- サーバが持つのは暗号文・`wrapped_mk`・メタデータ(件数、サイズ、更新時刻、アクセスパターン)のみ。これらメタデータ自体は原理上残る(ゼロ知識暗号化の一般的な限界)が、本文平文は運用者・侵害者いずれからも到達不能。

### 同期と競合解決(R1)

- 各メモをテキストCRDT(Automerge/Yjs系のRGA等)として表現する。オフライン中の編集はローカルCRDT状態に即時反映され、`outbox`に暗号化差分として溜まる。
- オンライン復帰時、outboxの暗号化差分を`(note_id, device_id, 論理クロック)`付きでサーバへpush。サーバはこれをnote単位の追記専用opログに積み、他デバイスへファンアウトするだけで中身は解釈しない。
- 各デバイスは受信した暗号化差分を復号しCRDTへ適用。CRDTのマージは可換・結合的・冪等なので、適用順序や重複があっても収束し、オフライン編集が失われることはない(単純なLast-Write-Winsは編集を破棄しうるためR1の「失われずに反映される」を満たさず、不採用)。
- opログの肥大化対策として、複数端末がオンラインな時に機会的にスナップショット圧縮(マージ済み状態を新しいベース暗号文として再アップロード)し、全端末が確認済みの古いopを削除する。削除も同様にCRDTのtombstoneとして扱い、保持期間後に物理削除。

### 検索の実現方式(R3)

R2(サーバは平文を持たない)とR3(全文検索)は本質的にトレードオフの関係にある。検索可能暗号化(searchable encryption)はアクセスパターン漏洩などの弱点があり実用強度が低いため採用せず、**検索は各端末のローカルインデックスのみで完結させる**方式を選ぶ。

- 各端末はオフライン編集のため元々ローカルに平文を保持している。この平文に対してSQLite FTS5等のローカル転置インデックスを構築する。
- メモの作成・更新(自端末での編集/他端末からのマージ結果)のたびに該当行をインデックスへupsertする増分更新とし、通常時に全件再構築は不要。
- 1万件×最大10万文字(最大合計約1GB)程度のテキストに対するローカル転置インデックス検索はPC・スマホの現行スペックで数十ms〜100ms程度に収まり、要件の「体感で即座」を満たす。サーバ側スケーリングの問題として扱う必要がない。

### 新端末追加(R4)とR5との接続

「パスフレーズを入れてから数秒で使い始められる」を、**全件同期完了までの時間ではなく、アカウントへの復号鍵アンロックと編集開始が可能になるまでの時間**と定義する。

1. (数秒) パスフレーズ入力 → 端末内でKEK導出(Argon2id) → 小さな`wrapped_mk`をサーバから取得 → MKを復号。この時点でメモの新規作成・リアルタイム受信は可能。ネットワークで転送するのは数KBのみで、件数(最大1万件)に依存しない。
2. (バックグラウンド、段階的) まずnoteのメタデータ一覧(id/更新時刻/サイズ、数百KB程度)を取得して一覧・タイトル表示を先に整える。続いて本文暗号文を更新日時の新しい順に優先してストリーム取得し、復号しながらローカルDB・FTSインデックスへ順次投入する。
3. 検索・全文表示は同期済み分から段階的に利用可能とし、未同期分がある間は「n件同期中」等の表示で明示する。

## 要件について

以下、要件そのものに内在する問題点と、それに対して採用した判断を述べる。要件の記述自体に誤りがあるわけではないが、互いに緊張関係を持つため、設計上の解釈を明示しておく。

1. **R2とR3は文字通りには両立しない**
   サーバ側の全文検索(Elasticsearch等)は必然的に平文または平文相当の情報をサーバに置く。「サーバは平文を一切持たない」を厳密に守るなら、検索はクライアント側ローカルインデックスに限定するしかない。
   → 採用判断: 検索を完全にローカル実行方式にした。理由: 検索可能暗号化などサーバ側で暗号化のまま検索する手法は実用強度・性能の面で本要件(1万件即座検索)に見合わない。オフライン編集のため端末には元々平文がある前提なので、追加の情報漏洩は発生しない。

2. **R4「数秒」とR5(最大1万件×10万文字、合計最大約1GB)は文字通りには両立しない**
   新端末で全件をダウンロード・復号・インデックス化するのに数秒しかかからない、というのは通信・CPU双方の観点で非現実的な場合がある(特にモバイル回線)。
   → 採用判断: 「使い始められる」を「鍵のアンロックと新規編集・リアルタイム受信が可能になる」ことと定義し、既存全件の取り込みは優先度付き・段階的なバックグラウンド同期とした。鍵アンロック自体(`wrapped_mk`取得+Argon2id)は件数に依存せず数秒で完了するため、この解釈であればR4は満たせる。全件が完全に検索可能になるまでの時間は明示的にR4の対象外とした。

3. **「チームで使う」と実際の要件(R1〜R5)の間にギャップがある**
   タスク冒頭は「チームで使うメモアプリ」だが、R1〜R5はいずれも「1ユーザが複数端末で使う」ことしか規定しておらず、複数ユーザ間でのメモ共有・権限・可視範囲については一切言及がない。
   → 採用判断: 本設計は「1ユーザ×複数端末の同期」のスコープに限定した(要件に明記されたことのみを満たす設計とした)。チーム内でのメモ共有(他ユーザとの鍵共有、ACL、共有メモのCRDTマージ範囲など)が必要な場合は追加要件として別途定義・設計が必要であり、本設計には含めていない。

4. **パスフレーズのみでの新端末追加は、デバイス単位の承認・失効の仕組みを持たない**
   ゼロ知識構成(サーバはパスフレーズ由来鍵以外で復号できない)である以上、パスフレーズさえ知っていれば誰でも新端末を追加でき、既存端末側からの事前承認や事後の個別デバイス失効を組み込んでいない。
   → 採用判断: R4が「数秒」という明確な時間制約を課しているため、QRコードによる既存端末ペアリングのような追加確認ステップは入れず、パスフレーズ単独でのアンロックを採用した。これはセキュリティ上のトレードオフとして意図的に許容している(パスフレーズ漏洩時の被害範囲が広がる)。より強い制御が必要なら、数秒制約を緩めるか、鍵アンロック後にバックグラウンドで非同期の端末通知/失効機能を追加する形になる。
