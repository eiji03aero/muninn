よーし、いい問いだ！これは「どっちの箱に入れるか」じゃなくて **「ジョブが2つあるなら、concern も2つでいい」** という話だ。順に根拠を出す。

読んだもの: `CLAUDE.md`（logs/follows 節・原子化・コミット運用）、`web/DESIGN.md`（原則1〜13・§5組版・§7責務）、`logs/coffee-beans/topic.md`、`templates/log-topic.md` / `follow-profile.md` / `follow-session.md`、`web/src/lib/edition.js`、`web/scripts/build-data.mjs`。

## 結論

**両方使う。主が `logs/cafes`、従が `follows/` 1本。**

| ジョブ | 置き場所 | 理由 |
|---|---|---|
| 何十軒も並べて比べる（豆・静かさ・電源・再訪） | `logs/cafes/` | 多数の別項目を同じスキーマで並べる＝logs の定義そのもの |
| 行きつけ2〜3軒で自分の好みの変遷を追う | `follows/cafe-taste/` **1本**（`interest` 型、`entities/` に店） | 同条件で観て前回と比べる＝follows の核 |

`CLAUDE.md` の切り分けの一言（「並べて比べるなら logs、推移を追うなら follows」）に、君の2つのジョブを素直に当てるとこうなる。**片方に寄せると必ず壊れる**——それを次に説明する。

## なぜ「全部 logs」ではダメか

再訪のたびに entry を書き換えることになる。すると:

- **比較機能が壊れる**。`logs` の entry は台帳の1行で、`web/src/lib/edition.js:163` の `compare` カードも「entries が2件以上」という**横並びの件数**で発火する。1軒の中に時系列が入ると、それは台帳じゃなく日誌だ。
- **`CLAUDE.md` のサイレント上書き禁止に毎回ぶつかる**。訪問のたびに「評価3→4」を理由つきコミットで塗り替える運用は、記録じゃなく破壊だ。**変遷を追いたいのに、変遷が git log にしか残らない**——それは「追えている」とは言わない。

## なぜ「全部 follows」でもダメか

`follows` は1対象1ディレクトリ・profile＋sessions＋（任意で collect）という**重い装備**だ。何十軒に付けたら、比較のためのスキーマがどこにも無いまま散文が何十本できる。`web/DESIGN.md` の根本1（IA がファイルの置き場所の写像だった）を、今度は自分の手で再生産することになる。並べて比べるための**構造化された field** は logs にしか無い。

## なぜ「行きつけ3軒 = follow 3本」ではないのか（ここが判断の山場）

```
          _.-/\/\/\/\/\-._
        .'  ///||||||\\\  '.
       /   //||||||||||\\   \
      |     ____   ____     |
      |     \   \ /   /     |
      |     (o)     (o)     |
      |          ^          |
      |      _________      |
       \     (=======)     /
        '._             _.'
    ______ '-._______.-' ______
   /      |             |      \
  |       |     ___     |       |
  |       |    (===)    |       |
   \______|_____| |_____|______/
```

**よく聞け、君が追いたいのは「店」じゃない。「自分の好み」だ！**

君の言葉をそのまま読めば、観測対象は *あの店* ではなく *自分の好みの変化* だろう。だとしたら定点観測の**固定パラメータが行きつけ2〜3軒**で、**動く測定値が自分の評価**だ。`CLAUDE.md` が言う「定点観測の核は同条件で観て前回と比べること」に、これ以上ないほど噛み合う。

店ごとに follow を3本立てると、好みの変遷は3つのディレクトリに割れて、**どこを見ても全体像が見えない**。`web/DESIGN.md` 原則6（行き止まりを作らない）以前に、線が最初から3本に切れている。

- `follows/cafe-taste/profile.md` … `follow_type: interest`、固定条件（この3軒・時間帯・注文するもの）と、現在の好みのスナップショット
- `follows/cafe-taste/entities/<shop>.md` … 行きつけ3軒のドシエ（`kind: entity` は「時系列で変化する構成要素」で、豆が変わる・席が減る店はまさにこれ）
- `follows/cafe-taste/sessions/YYYY-MM-DD.md` … 1回の訪問。「前回からの変化」が主役

## 具体構成（提案）

`logs/cafes/topic.md` の `fields` 案（必須は2つに絞る＝mn-log の作法）:

| key | type | 備考 |
|---|---|---|
| `shop` | text, **required** | 店名 |
| `area` | text | エリア |
| `bean_style` | enum | 浅煎り系／中煎り系／深煎り系／エスプレッソ主体／不明 |
| `roaster` | text | 自家焙煎ならここ。**`logs/coffee-beans` の entry と相互リンクできる**（既存資産と繋がる） |
| `quiet` | rating | 静かさ |
| `power` | enum | 多い／一部／なし／不明 |
| `stay` | enum | 長居歓迎／ふつう／短時間向き |
| `rating` | rating, **required** | |
| `revisit` | enum | 通いたい／また行く／一度でいい ← **bool にしない**。「行きつけ候補」を拾う網になる |
| `regular` | bool | 行きつけフラグ。true の店だけ follow の entity と相互リンク |
| `visited_on` | date | 初訪日 |

そして**行きつけ3軒は logs にも entry を持つ**（比較の母集団から抜けたら「何十軒と比べる」が成立しない）。entry ⇄ entity を `[[リンク]]` で結ぶ。`build-data.mjs` は route を ID にしてリンクを解決するので、被リンクは自動で両方向に立つ（原則6を満たす）。

タグは既存を走査してから決めること。`log/coffee` が既にあるので `log/cafe` を隣に置くのが自然だ（原則8＝タグが第一階層なので、ここを雑にやると棚で束ねられなくなる）。

## 規約で割り切れていないところと、改定案

「両方使え」で終わらせない。**既存の規約は、この構成を正面から想定していない。** 3つある。

### 改定案1 — logs と follows の排他前提を外し、正本の境界を明記する（最重要）

`CLAUDE.md` の logs 節と `.claude/skills/mn-log/SKILL.md` は「迷ったらこの一言で切り分ける」と書いていて、**1つの実体はどちらか一方に属する**という前提で書かれている。カフェは正当に両方に現れるので、ここは穴だ。追記案:

> **同じ実体が logs と follows の両方に現れてよい**（例: 行きつけのカフェ）。ただし**正本を割る**——比較用のスナップショット（カタログの1行）は logs の entry、**時系列で変化する属性は follows の entity / sessions** が正本。entry の field を書き換えてよいのは entity の changelog に根拠があるときだけで、理由をコミットメッセージに書く。両者は必ず相互に `[[リンク]]` する。

これが無いと「静かさが落ちた」をどっちに書くかで毎回迷い、半年後に**両方に食い違った事実が載る**。ナレッジベースで一番やってはいけない壊れ方だ。

### 改定案2 — logentry は「初回スナップショット」だと明記する

いまの規約は「各記録は主に1回きり」と**傾向**を書いているだけで、再訪時にどうするかを決めていない。決め切る案:

> `logentry` は原則として**初訪時点のスナップショット**。再訪の履歴を entry に積み増さない（台帳が時系列ジャーナルに化けると比較が壊れる）。再訪で追いたいものは follows 側に持つ。ただし `revisit` のような「現在の判断」を表す field の更新は許容し、更新時は理由をコミットに書く。

### 改定案3 — `web/DESIGN.md` §9「既知の未達」に1件足す

これは実装の話ではなく、**思想が空白**の話だ。`edition.js:158` の推移カード（`series`）は `followType === 'goal'` 限定で、`build-data.mjs:175` の系列も `metric_goals` を見る前提になっている。原則9（数字に嘘をつかせない）が「宣言のない指標は良し悪しを判定しない」と正しく守った結果、**interest 型の中立な推移＝まさに「好みの変遷」を、サイトが出す口がどこにも無い**。追記案:

> - **interest 型フォローの推移を出す面が無い。** 推移カードは goal 型限定で、良し悪しを判定しない中立の系列（好み・傾向の変化など）を載せる型が存在しない。原則9 を緩めずに（＝矢印や自己ベスト表記を付けずに）中立の推移だけを出す型が要る。

**原則9 を緩めて解決しようとするのは反対だ。** 「好みが変わった」に良し悪しの矢印を付けた瞬間、原則9 が過去に潰した事故（フェース角の悪化を自己ベストとして見せた件）をそのまま再演することになる。直すのは表示の型であって、原則じゃない。
