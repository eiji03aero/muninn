## 設計

### 0. 前提となる脅威モデル

- サーバ運用者・サーバ侵入者は**保存データと通信をすべて見られる**（honest-but-curious ＋ 改ざん・巻き戻しを試みる能動的攻撃者）。
- 端末とクライアントバイナリは信頼する（後述の I1 で条件を明記）。
- 保護対象は**本文・タイトル・タグ・検索クエリ**。保護できないものは**件数・サイズ・更新時刻・アクセスパターン**（I4）。

---

### 1. 全体構成

```
┌──── 端末A: PC（全複製） ─────────────┐   ┌──── 端末B: スマホ（部分複製） ─────┐
│ UI                                    │   │ UI                                  │
│ ├ CRDTエンジン (Y.Text + HLC)         │   │ ├ CRDTエンジン                      │
│ ├ 検索エンジン (bigram転置 + Roaring) │   │ ├ 検索エンジン（索引は全件保持）    │
│ ├ 暗号層 (XChaCha20-Poly1305 / Ed25519)│  │ ├ 暗号層                            │
│ └ ローカルDB (SQLite; 端末鍵で暗号化) │   │ └ ローカルDB（索引＋直近/ピンのみ） │
└──────────────┬────────────────────────┘   └──────────┬──────────────────────────┘
               │        暗号文のみ（AEAD + デバイス署名）│
               └───────────────┬─────────────────────────┘
                               ▼
        ┌──────────────────────────────────────────────┐
        │ サーバ（ゼロ知識・ダムストア。復号鍵を持たない）│
        │  note_log   : ノート別・追記専用の暗号化更新列  │
        │  blocks     : 内容アドレス指定の暗号化ブロック  │
        │  manifests  : 索引/スナップショットの構成表     │
        │  vault      : wrapped MK, OPAQUE レコード      │
        │  devices    : MK署名済みデバイス簿             │
        └──────────────────────────────────────────────┘
```

サーバの責務は 4 つだけ：**認証（OPAQUE）／追記ログの全順序付け（ユーザ単位の単調 seq）／内容アドレスblobの保管と配信／変更通知の push**。マージも索引もしない（できない）。

---

### 2. 鍵の扱い

```
passphrase ──OPRF(サーバ保持鍵)──▶ hardened_pw ──Argon2id(salt, m=128MiB,t=3,p=1)──▶ KEK
KEK ──AEAD unwrap──▶ MK（256bit ランダム。ユーザ端末で生成、平文は端末外に出ない）
MK ──HKDF──┬─ K_meta       メタデータ束
           ├─ K_note_root ──HKDF(note_id ∥ epoch)──▶ K_note（ノートごと）
           ├─ K_index      検索索引セグメント
           └─ K_devsign    デバイス簿の署名鍵（Ed25519）
```

- **パスフレーズは MK を包むだけ**。パスフレーズ変更＝再ラップのみで、本文の再暗号化は不要。
- **ノート鍵は導出**（ランダム鍵＋鍵配布リストにしない）。鍵一覧を同期する必要がなく、新端末は MK 一つで全件を開ける ⇒ R4 の前提。
- **AEAD は XChaCha20-Poly1305**（192bit ランダム nonce ＝端末間でカウンタ調整が不要）。**AAD に `{note_id, block_idx, epoch, schema_ver}` を必ず入れる**。サーバがブロックを入れ替え・別ノートに付け替える攻撃を防ぐ。
- **認証は OPAQUE**。サーバはパスフレーズも検証子も平文で見ない。ただし vault blob を握っている運用者はオフライン辞書攻撃が可能 ⇒ I3 で対処。
- **デバイス失効**：`epoch` を +1 し、以後の書き込みを新 epoch 鍵で行う。既存データは**開いた順に遅延再暗号化**（1GB を同期再暗号化しない）。紛失端末が既に読んだ内容は取り戻せない ⇒ 失効は「今後の漏洩を止める」操作だと UI で明言する。
- **端末ローカル**：SQLite ファイルは端末固有鍵（OS Keychain / Keystore、Web は非 extractable CryptoKey）で暗号化。MK はメモリ上のみ、ロック時に破棄。

### 3. データの流れと同期

**書き込み（オフライン中も同じ経路）**

```
編集 → CRDT更新 (Y.Text) → 即ローカル索引に反映（体感0ms）
     → K_note でAEAD暗号化 → デバイス鍵でEd25519署名 → outbox に積む
     → オンライン時 outbox を flush → サーバが note_log に追記し seq を採番
```

**読み込み**

```
GET /changes?since=cursor → 暗号化更新の配列 → 署名検証 → 復号 → CRDT適用 → 索引を差分更新
WebSocket /live で新 seq を push（オンライン時は数百ms反映）
```

**競合解決**

| 対象 | 方式 | 挙動 |
|---|---|---|
| 本文 | シーケンス CRDT（Y.Text / RGA系） | 文字単位で自動マージ。どちらの編集も消えない。手動解決 UI 不要 |
| タイトル・ピン | LWW-Register（HLC） | 後勝ち。壁時計ではなく HLC なので端末の時刻ズレに強い |
| タグ | OR-Set | add-wins。同時 add/remove は add が残る |
| 削除 | `deletedAt`(HLC) の LWW フラグ | ソフト削除。`deletedAt` より新しい編集があれば自動復活。ゴミ箱から復元可、30日で完全削除 |

CRDT なので**適用順序に依存せず収束する**。オフライン期間の長短は正しさに影響しない。

**ログ圧縮**：CRDT 更新列とトムストーンは放置すると肥大するため、更新数が閾値を超えたノートで、その時点で最新の端末が**スナップショット（CRDT状態のシリアライズを暗号化）**を上げ、`version ≤ snapshot` の更新の GC をサーバに指示する。サーバは中身を読めないので、圧縮の判断は必ずクライアント側が行う。

**サーバの改ざん・欠落・巻き戻しの検出**：各更新に `{device_id, デバイス内連番, 直前更新のハッシュ, 観測したログヘッドのハッシュ}` を含めて署名する。デバイス単位のハッシュ鎖で自分の更新の削除を検出し、ヘッドハッシュの相互参照で「端末Aにだけ古い履歴を見せる」フォーク攻撃を検出する。検出時は同期を止めて警告。

### 4. 検索の実現方式

サーバは平文を持てないので**検索は 100% クライアント側**。暗号化検索（SSE）は使わない — アクセスパターンから内容が復元される既知の攻撃があり、R2 の精神に反するため。

**正規化**：NFKC → 小文字化 → 全角/半角統一 → 濁点・長音正規化。スクリプト種で分割し、**CJK は 2-gram、ラテン/数字は語＋前方一致トライ**。形態素解析器を使わない（辞書の同期・版ズレ・未知語の問題を持ち込みたくないため）。

**索引構造**：`term → Roaring Bitmap（(note_id, block_idx) の詰め合わせ）` の転置索引。本文は **8KB ブロック単位で暗号化**し、ポスティングもブロック粒度にする。これにより一致箇所を含むブロックだけを復号すればスニペットが作れる。

イミュータブルなセグメント形式（LSM 風：ベースセグメント＋差分セグメント、定期マージ）で保持し、各セグメントを 1〜4MB の**内容アドレス指定ブロック**に切って `K_index` で個別に暗号化してサーバに置く。→ 差分同期が効く。

**検索の実行**（1万件・平均2KB想定）

1. クエリを正規化 → bigram 列に分解
2. Roaring Bitmap の AND → 候補ブロック集合（**< 5ms**）
3. df / doclen から BM25 でスコアリング → 上位20件
4. 上位のブロックだけ復号 → **フレーズ照合（bigram AND の偽陽性を除去）**＋スニペット生成（**< 30ms**）

合計 **数十ms**。R3 を満たす。ローカルに無いブロックのみサーバから取得（数百KB、それでもサブ秒）。

**索引の共有がR4の鍵**：索引を新端末でゼロから作ると 20MB の本文に対して WASM で 5〜15 秒かかる。そこで**索引はサーバに暗号化して置き、新端末はダウンロードして復号するだけ**にする。索引スナップショットは真実の源ではなく**キャッシュ**なので、どの端末が上げても構わない（`version = カバーする同期カーソル` を付けて CAS で更新、競合は無害）。端末は最新スナップショットを取得後、ログの差分だけ増分索引する。

---

### 5. 新端末のタイムライン（R4）

| 時刻 | 完了すること | 転送量 |
|---|---|---|
| 0.0s | パスフレーズ入力 | — |
| ~1.0s | OPRF + Argon2id → KEK → **MK 復号完了** | 数KB |
| ~2.5s | **メタデータ束**（1万件分の id/タイトル/タグ/HLC/冒頭200字）復号 → **一覧が表示され、任意のノートを開ける**（本文はオンデマンドで1件 <200ms） | 1〜2MB |
| ~4s | **浅い索引（全1万件のタイトル＋冒頭512字）** → 全件を対象に「浅い検索」が効く | ~1MB |
| ~6s | **直近1000件の全文索引セグメント** → 実用上の全文検索が成立 | 2〜3MB |
| 以降 | 残りの索引セグメント → 本文ブロック（新しい順） をバックグラウンド取得 | 20〜30MB |

**「数秒で使い始められる」＝ 一覧・閲覧・編集・浅い全件検索＋直近の全文検索が 5秒前後で成立**、という定義。検索 UI には常に `全文索引: 3,420 / 10,000件` を表示し、未索引範囲があることを隠さない。2回目以降の起動は差分（数百KB）のみ。

### 6. 端末プロファイルとストレージ（R5）

| | PC（全複製） | スマホ（部分複製） |
|---|---|---|
| 索引 | 全件 | **全件**（軽量なので必ず持つ） |
| 本文 | 全件 | 直近300件＋ピン留め＋開いたもの（LRU、上限500MB） |
| オフライン編集 | 全件可 | **ローカルにある本文のみ可**。未取得ノートは閲覧・編集不可（I5） |

平均2KB/件なら全体 20MB でスマホも全複製できる。最大値（1件10万字×1万件＝約1GB）に張り付いた場合のみ部分複製に切り替わる。

### 7. 要件対応まとめ

| | 実現手段 | 状態 |
|---|---|---|
| R1 | CRDT ＋ ローカルファースト outbox ＋ 追記ログ | 充足（スマホは部分複製の制約あり → I5） |
| R2 | クライアント側 AEAD、鍵はサーバに一切渡らない、OPAQUE 認証 | 充足（配信経路とメタデータに留保 → I1, I4） |
| R3 | クライアント側 bigram 転置索引＋Roaring＋BM25 → 数十ms | 充足 |
| R4 | 導出鍵方式（鍵配布不要）＋段階的同期＋暗号化済み索引の配布 | 5秒前後で充足（全文索引の完了はより後 → I2） |
| R5 | ブロック単位暗号化、セグメント索引、部分複製 | 平均的な分布で充足（最大値張り付き時は I2） |

## 要件について

問題を 5 つ見つけた。いずれも設計を壊すものではないが、要件の文言のままでは成立しないため、以下の判断で置き換えた。

### I1. R2「サーバは平文を一切持たない」は、Web配信のままでは成立しない

保存データを暗号化しても、**クライアントコードをサーバ運用者が配信している限り、運用者は特定ユーザにだけ鍵を送出する JS を配れる**。この経路が塞がっていない E2EE は、運用者に対しては実質的に無防備になる。

**採用した判断**：R2 の保証範囲を「**保存データと通信**」に限定して明記し、配信経路は別立ての対策で担保する。第一級クライアントは**署名付きネイティブ／インストール済みPWA**とし、更新は TUF 方式（鍵分離・ロールバック防止）。ビルドは再現可能にし、成果物ハッシュを公開ログに載せて第三者が検証できるようにする。ブラウザ版は「利便性のための劣後経路」と位置づけ、UI 上でその旨を表示する。
**理由**：技術的に解決不能な部分を「解決した」と書く方が危険だから。ユーザが何を信頼しているかを正確に伝えることが E2EE の一部だと考える。

### I2. R3・R4・R5 は最大値では同時に満たせない

R5 の上限（10万字 × 1万件 ≒ **1GB**）では、bigram 転置索引だけで数百MB になる。R3（全1万件の全文検索）を新端末で成立させるには索引全体が要り、それを **R4 の「数秒」で転送するのは帯域の物理制約で不可能**（100Mbps でも数十秒〜数分）。平均2KB/件という現実的な分布でも索引は 20〜30MB で、10Mbps 回線なら 20 秒前後かかる。

**採用した判断**：R4 の「使い始められる」を**段階的な機能開放**として定義し直した（第5節の表）。5秒時点で「一覧・閲覧・編集・全件の浅い検索・直近1000件の全文検索」が成立し、全件全文検索は完了次第拡張される。進捗は `3,420 / 10,000件` として常時表示し、**検索範囲を偽らない**。
**理由**：「体感で即座」（R3）は検索の**実行時間**の要求であって、初期同期時間の要求ではない。ここを分離すれば R3 は完全に満たせる。逆に R4 の「全機能が数秒」を守るために検索範囲を黙って絞ると、ユーザは「ヒットしなかった＝存在しない」と誤解する。これは最悪の失敗モードなので、透明な劣化を選んだ。

### I3. R2 ＋ R4 の組み合わせで、パスフレーズが単一の防壁になる

R4 が「パスフレーズだけで数秒」を求める以上、**既存端末による承認を必須にできない**（承認する端末がオフラインなら R4 を破る）。すると MK を包む vault blob がサーバ上にあり、**サーバ運用者はオフライン辞書攻撃をかけられる**。同時に、パスフレーズを忘れた時点でデータは原理的に復旧不能だが、要件にその扱いが無い。

**採用した判断**：(a) OPRF を挟み、パスフレーズの伸長にサーバ保持鍵を関与させる（OPRF鍵も盗まれれば無効化されるが、攻撃コストは上がり、正常時はレート制限が効く）。(b) Argon2id を最弱端末基準で m=128MiB/t=3 に設定。(c) **パスフレーズ強度の下限を強制**（diceware 6語相当・約77bit 未満は登録不可）。(d) 要件外だが**リカバリキット**（初回に生成する高エントロピー鍵で MK を別途ラップ、印刷/保管を促す）を追加した。(e) 「既存端末による新端末承認」は任意設定として用意し、R4 とのトレードオフを明示して既定は OFF。
**理由**：R4 を満たす限りパスフレーズ以外の防壁は置けないので、パスフレーズ自体の強度を製品側で担保するしかない。またリカバリ手段の欠落は、E2EE 製品で最も多いユーザ被害なので、要件に無くても入れるべきだと判断した。

### I4. R2「一切」はメタデータを含めると厳密には偽

暗号化しても、サーバは**ノート件数・各ノートのサイズ・編集の時刻と頻度・どのノートをいつ開いたか・端末数と IP** を見られる。「毎晩23時に同じ1件を編集している」といった推測は成立する。

**採用した判断**：R2 を「**サーバは本文・タイトル・タグ・検索クエリの平文を持たない**」と再定義し、残る漏洩をプライバシーポリシーに列挙する。緩和として、暗号文を 4KB 境界のサイズバケットにパディング、更新の即時 flush をジッタ付きバッチ化、本文ブロック取得をノート単位でなくブロック集合単位でまとめて要求する。アクセスパターンの完全秘匿（ORAM 等）は**採用しない**。
**理由**：ORAM は 1GB 規模で数十倍の帯域増を招き、R3・R4 を確実に壊す。防げないものを列挙して伝える方が、防げたふりをするより実害が小さい。

### I5. R1「複数端末でオフライン編集」と R5 の上限が、スマホで衝突する

1ユーザ最大 1GB を全端末に完全複製する前提は、スマホでは非現実的（端末容量・モバイル通信量）。

**採用した判断**：スマホは**索引は全件・本文は部分複製**とする。R1 の「オフライン中の編集」の適用範囲を「**ローカルに存在する本文**（直近300件＋ピン留め＋既読分）」に限定し、未取得ノートはオフライン時に鍵アイコンで明示する。ユーザが明示的にピン留めすれば任意のノートをオフライン対象にできる。平均的なデータ量（〜数十MB）では自動的に全複製になるため、この制約が表に出るのは上限に近いユーザだけ。
**理由**：検索の完全性（索引は全件）とオフライン編集の完全性のどちらかを削るなら、**索引を残す方**が損失が小さい。「あるはずのメモが検索に出ない」は不信を生むが、「オフラインで開けないメモがある」は理由が明快で回復可能だから。
