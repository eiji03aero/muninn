## 1. 総評（3行）

3案とも根本原因の診断（IAがファイル置き場の写像／横断インフラの欠如／③想起の停止）は概ね正しく捉えているが、勝敗を分けたのは**Phase 1の身の丈**だった。A案はPhase 1だけで5つの訴えのうち4つを実質解消し、既存90件のノートを1行も書き換えずに済む設計で最もリスクが小さい。B案は診断の厳密さ（282本のリンク実測）で随一だがPhase 1が3案中最重量（純増約600行＋大きめのリファクタ）で自壊気味、C案は想起ループの解として最も鋭いが心臓部が既存59件への`recall`後付けというPhase 1のコンテンツ負債に依存している。

## 2. 案別評価

### 案A「テーマに着地するナレッジベース」

**一言評（辛口）**: IA再設計としては3案中もっとも構造的で誠実。ただし「テーマ7つに全部収まる」という賭けの上に立っており、健康28件（毛穴/髪/栄養/入浴/睡眠/ストレス）を1つに束ねる判断が外れたら中核（テーマ・ハブ）がそのまま弱点になる。本人もリスクとして正直に認めている点は評価するが、認めているだけで解決していない。

**基準①〜⑤**

| 基準 | 点数 | 根拠 |
|---|---|---|
| ①課題適合 | 8/10 | A/B/C/Dは構造的に効く（ボトムタブ＋1行ジョブ文＋`/guide`、全文検索＋テーマハブ＋orphan警告、理由付きバックリンク）。Eは「MOCの素朴さ」は解決するが観測グラフ・比較表はPhase2/3待ちで、Phase1時点では未解決 |
| ②実装現実性・段階性 | 8/10 | Phase1が「+520/−260→実質+260行」で見積もりが細かく内訳がある。90件のノート本文を1行も触らずに済む設計（テーマはtagsから導出）は移行コストの正直な最小化として優秀 |
| ③継続性 | 7/10 | バックリンク・検索はビルド時自動導出で手入れ不要。一方テーマ境界は手動キュレーションで、新ジャンルが増えると「その他」に落ちる運用が発生する。依頼キュー（localStorage）は「反映しなければ罪悪感が形を変えて残る」と自ら認めるリスクで、3ヶ月放置に一番弱い箇所 |
| ④文脈適合 | 9/10 | ボトムタブ・空セクション非表示（原則4）・テーマ巡回による偏在対策など、モバイル/1人/低頻度/不均一コンテンツへの目配りが最も精緻 |
| ⑤情報設計の強度 | 9/10 | 「動詞のナビ／目的語の器」を分離する設計原則が一貫していて、`build-data.mjs`の擬似コードまで踏み込んでいる。3案中最も検証可能な設計 |

**Phase 1 の精査**
- 内容: ボトムタブ4、`build-data.mjs`にテーマ組み立て・バックリンク・orphan警告、`moc/*.md`5件のtheme化＋新規2件、`/themes`＋`/t/:theme`最小版、`/search`（bigram全文検索）、ノートのバックリンク表示・タグクリック化、ホーム簡素化（KPI/59バッジ撤去）、`/guide`、`/notes`・`/logs`・`/moc/:slug`廃止。
- 行数見積もり: 既存1,560行に対し **+520/−260 → 正味+260行（+17%)**。案の中では明確に一番細かく内訳が示されている。
- 5つの訴えのうち解消数: **4/5を実質解消（A・B・C・D）、Eは「MOCの素朴さ」のみ解消で観測グラフ・比較表はPhase2/3待ちのため部分解消止まり**。Phase1単体でも大半の訴えに答えられる設計になっている点は3案中最も強い。

**致命的な弱点**: 中核である「テーマ・ハブ」が7つの手動キュレーションに依存しており、境界判断（特に「健康」28件の分割/統合）を誤ると入口そのものが機能不全になる。本人がリスク①として認め「1週間使って粒度を見直す前提」としているが、それは**リスクの告白であって解決策ではない**——外れた場合の被害（IA全体の作り直し）が3案中もっとも大きい。

**光る点**:
1. バックリンクを「リンク元が書いた理由」ごと逆流させる発想（既存のリンク規約 `- [[x]] — 理由` を活用）。実装コストを抑えつつ課題Dに直接効く筋の良い一手。
2. 「スマホで読む・Macで書く」という実際の運用分断を、依頼キューという形で正面から設計に組み込んでいる（他2案は書き込み動線をやや軽視）。

### 案C「muninn 日報：探させない、編集して差し出す」

**一言評（辛口）**: 「閲覧日で紙面を組む＝更新が止まっても面は死なない」という発想は、低頻度更新という文脈に最も鋭く刺さっている。想起（③）の解も3案中もっとも野心的で、影SRS＋自己修復同期という設計は技術的に一番洗練されている。だが**その心臓部（再読カード）はPhase 1完了条件として既存knowledge 59件全件への`recall:`フィールド後付けを要求しており**、これは3案の中で唯一「アプリコードの行数」だけでは測れない実質的な追加コストをPhase 1に埋め込んでいる。本人も正直に書いているが、正直であることと軽いことは別問題。

**基準①〜⑤**

| 基準 | 点数 | 根拠 |
|---|---|---|
| ①課題適合 | 8/10 | デスク（A/B）・棚＋探す＋切り口ピル（C）・バックリンク＋「次の1枚」（D）・スパークライン＋比較表（E）と5つの訴えに正面から対応表を作っている。ただしPhase1時点でDの主要UI（「ここへ来る道」表示）はPhase2送りで、自己申告も「課題A・B・Cの半分」止まり |
| ②実装現実性・段階性 | 6/10 | Phase1のアプリコードは+520/−180＝**純増約340行**でA・Bの中間だが、**Phase1の完了条件として knowledge 59件全件に `recall:` フィールドを後付けする**ことを明記している。これは単なる1行追記ではなく、mn-review基準（①答えを含めない②タイトルの言い換えにしない③理由・関係・適用を問う）を満たす良問を59本作る編集作業であり、「1〜2セッションで現実的」という見積もりは楽観的。ここをやらないと「本案の尖り」である再読カードが骨抜きになると自ら認めている以上、実質的なPhase1コストは行数以上に重い |
| ③継続性 | 9/10 | 3案中最も「サボっても死なない」設計。紙面が**ビルド日ではなく閲覧日**で組まれるため、pushが2週間止まっても毎朝別の紙面が出る。影SRSは端末ローカルで即座に効き、答え合わせ伝票を送らなくても体験自体は破綻しない（「失敗しても現状より悪くならない」と明記）。同期もbuild側`srs.last`との比較で自己修復するため、A案の依頼キューより破綻しにくい |
| ④文脈適合 | 9/10 | 「短時間・片手で毎日めくる」という新聞的体験は、モバイル・低頻度更新という文脈に3案中もっとも噛み合っている。ゴルフ47%偏重も「テーマ均等ローテーション」「在庫マップで隠さず見せる」で正面から扱っている |
| ⑤情報設計の強度 | 8/10 | 面＝読む／棚＝俯瞰する／探す＝当てる／デスク＝頼む、という「読む姿勢」でIAを割る発想は一貫していて、「面が担うのは読む姿勢だけ。面で答えられないジョブに面は答えようとしない」という線引きも明快。ただしバックリンクの構造的保証という点では案Bの統一ノードシェルにやや譲る |

**Phase 1 の精査**
- 内容: ボトムタブ4枚＋ルート再編、面（`edition.jsx`：題字・スロット構成・リード・袖・連載・内訳）、再読カード＋影SRS＋伝票（`recall.js`）、探す（全文横断・スニペット）、デスク（伝票・できること5枚・在庫の健康）、`build-data.mjs`（gitメタ／backlinks／recall／due廃止／edition）、KPIタイル・DueBadge・NotesIndex・Moc削除、`mn-research`/`mn-review`/`templates/note.md`のskill改修、**既存59件への`recall`一括backfill**、`pages.yml`に`fetch-depth: 0`。
- 行数見積もり: アプリ+build合計で **+520/−180 → 正味+340行（既存の+22%）**。ただし上記の通り**59件の`recall`backfillという行数に現れないコンテンツ負債がPhase1の出荷条件**に含まれる。
- 5つの訴えのうち解消数: 自己申告で**A・Bは解消、Cは半分（探すのみ・棚はPhase2）、D・Eは未着手（Phase2/3）**——実質**2〜2.5/5**。案Aの4/5には及ばない。ただし根本3（想起と定着）は数値上5つの訴えには入らないが、Phase1で最も踏み込んで手を付けている点は加点材料。

**致命的な弱点**: 想起カードという「本案の心臓部」が、既存knowledge 59件全件への`recall:`フィールド後付けという**Phase1の出荷条件**に依存している。backfillをやらなければ「タイトルと本文を伏せてタグと文脈一文だけ見せる」劣化版にdegradeすると自ら認めており、**刷新の目玉が最初から保険付きの半完成品になりうる**。良問を59本用意する作業は「1件1行」と言うほど軽くなく、良し悪しの判断基準（答えを含まない・タイトルの言い換えでない・理由/関係/適用を問う）を満たすには人（Claude）による1件ずつのレビューが必要で、これは案A・Bが避けた「90件（や59件）は一切触らない」という安全策をわざわざ手放している。

**光る点**:
1. 「紙面はビルド日ではなく閲覧日で組む」という設計。pushが止まっても毎日違う紙面が出る＝**更新頻度が低いという文脈的制約に対する最も的確な解**で、他2案には無い発想。
2. 影SRS＋自己修復同期（`srs.last >= pending.date`で反映済み判定）は、送信を忘れても日々の体験が壊れず、送った瞬間に正本が追いつく。案Aの依頼キューより一段技術的に洗練されている。

## 4. 勝者と理由（5行）

**勝者は案A「テーマに着地するナレッジベース」。** 決め手は②実装現実性で、Phase 1が3案中もっとも軽く（純増約260行）、かつ**それだけで5つの訴えのうち4つ（A・B・C・D）を実質解消する**という即効性を両立している点にある。B案はPhase 1が最重量（純増約600行）な上に未完成タブを晒すリスクがあり、C案は想起ループの解が最も鋭いが心臓部を既存59件への`recall`後付けというコンテンツ負債の上に建てており、どちらも「Phase 1で価値が届く」という最重要基準でAに一歩譲る。既存90件のノート本文を1行も書き換えずに済む設計は、1人運用・低頻度更新というこのKBの文脈において失敗コストを最小化する現実的な選択でもある。ただし中核の「7テーマへの手動キュレーション」が外れた場合の被害はA案が最大であり、勝者確定ではなく条件付き採用として扱うべき（§6）。

## 5. 敗者から必ず移植すべき要素

優先度付きで、A案の実装に組み込むことを推奨する。

1. **【最優先・即着手】B案: `build-data.mjs`のfollow session wikilink抽出バグ修正（+5行）。** どの案が勝っても直すべき実バグ（21〜24本のエッジが失われている）。A案のバックリンク実装に統合コストゼロで組み込める。
2. **【優先】B案: 「つながり」ブロックを全ノード型（note/concept/entity/session/logentry）に例外なく必ず付ける、という構造的保証。** A案は現状ノートページのバックリンク表示のみを明記しており、follow/atlas/logs側の「つながり」記述がB案ほど徹底されていない。「行き止まりを1つも作らない」という原則をA案のPhase1範囲に明文化して持ち込むべき。
3. **【優先】C案: 依頼キューの同期判定を「`site.generatedAt > entry.date`での一律破棄」ではなく、「対象ノートの`srs.last`が実際に追いついたかで判定する自己修復同期」に差し替える。** A案自身がリスク②として認めている「キューが同期しないまま溜まる」問題への直接の処方箋になる。
4. **【中】C案: 「閲覧日で計算する」という発想を、A案のホーム「続きから」「今日の1問」の鮮度判定に適用する。** ビルド日基準の計算をやめてクライアントの実時刻で評価すれば、push が数週間止まっても面が古びない。低頻度更新という文脈に直接効く。
5. **【中】B案: テーマ未所属ノートの扱いを「orphan警告のみ」ではなく「宣言が無くてもタグ第2階層へ自動フォールバックする」設計に強化する。** 粒度決定を急がせず、後から直せる猶予を作る（§6のリスク処方箋とも直結）。

## 6. 勝者案の最大のリスクと処方箋

**最大のリスク**: 7テーマの手動キュレーション、特に「健康」28件（毛穴/髪/栄養/入浴/睡眠/ストレス）を1つに束ねるか分割するかの判断を誤ると、テーマ・ハブという中核そのものが機能不全になる。A案自身「IAの失敗はここでしか起きない」と認めている通り、被害範囲が3案中最大。

**処方箋**:
1. 移植要素5（B案のタグ第2階層フォールバック）を最初から組み込み、テーマ未所属＝即警告ではなく「一時的に自動グルーピングされた状態で運用しながら手直しできる」猶予を作る。

## 8. やめるべきこと（作らない／削るべきもの）

- **`/notes` 90件フラットリスト・`/logs`トピック一覧・`/moc/:slug`生markdown表示** — 3案とも一致して廃止対象。タイトル文字列以外の手がかりを持たない一覧はテーマ・ハブと検索に完全に代替されるべきで、延命の理由がない。
- **ホームのKPIタイル2×2と「復習期限N」バッジ全種** — 3案とも「麻痺した数字」として全廃で一致。`note.due`のようなビルド日基準フラグごと削除し、クライアント側の実時刻判定に置き換える。
- **follow の「蘊蓄」タブ（タグ交差による推定リンク）** — テーマ・ハブ／棚が同じ機能をより明示的に代替する。重複UIとして削る。
- **B案の統一ノードシェルへの全面移行は今回やらない。** 設計思想（全型共通の「つながり」スロット）だけ移植し、Follow/Atlas/LogTopicの実装を丸ごと差し替えるリファクタはA案の身の丈に合わない。atlas（450行・基準線）は無改修のまま残す。
- **C案の「号数（累計コミット数）」「edition」というジャーナリズム的演出は採用しない。** `git log`依存とCIの`fetch-depth: 0`変更という余分なインフラリスクを、得られる体験価値（数字の演出）に見合わない出費として見送る。閲覧日ベースの鮮度計算という**考え方**だけを移植すれば十分。
- **テーマ／島／棚のいずれであれ、自動導出（force-directedグラフ・完全自動クラスタリング）には手を出さない。** 3案とも「決定的レイアウト」「手動宣言＋フォールバック」で一致しており、これは正しい判断。90〜300ノート規模で自動グラフ描画に投資するのは時期尚早。
