# muninn Web（GitHub Pages ビューア）現状分析

作成日: 2026-07-31 / 対象コミット: `6cc727f`
目的: 「機能が多くて把握しにくい・情報があるのに辿り着けない・繋がりが見えない」という課題に対して刷新方針を立てるための、**現状の事実の書き出し**。評価や提案は最後の章にのみ含む。

---

## 1. muninn とは（前提）

- **正本（source of truth）は git リポジトリの markdown 群**。Obsidian は任意の閲覧ビューア。
- **書き込みは Claude Code のスラッシュコマンド経由**（`/mn`, `/mn-research`, `/mn-follow`, `/mn-learn`, `/mn-log`, `/mn-review` …）。
- **Web アプリ（GitHub Pages）は読み取り専用のビューア**。ユーザーが「見る」ためだけの面。
  - 唯一の例外は atlas の概念ページにある「深掘りを依頼（コピー）」ボタン（Claude に貼るプロンプトをクリップボードに入れるだけ）。
- **5 つの concern** で構成される:

| # | concern | 置き場 | 生成コマンド | 性質 |
|---|---------|--------|--------------|------|
| ① | 客観知識の蓄積 | `notes/` (`kind: knowledge`) | `/mn`, `/mn-research`, `/mn-process-inbox` | 原子ノート（単語カード） |
| ① | 独自の知見・身体知 | `notes/` (`kind: insight`) | 同上 | クイズ対象外の原子ノート |
| ② | スキル・対象のフォロー | `follows/` | `/mn-follow`, `/mn-collect` | 1対象の時系列ジャーナル |
| ③ | 想起と定着 | `review-log.jsonl` + 各ノートの `srs` | `/mn-brief`, `/mn-review` | 間隔反復・横断合成 |
| ④ | 体系的な学習 | `atlas/` | `/mn-learn` | 知識グラフ＋読む順路（教科書） |
| ⑤ | トピック別の記録 | `logs/` | `/mn-log` | スキーマ固定の記録帖（台帳） |

設計思想としては「①がバラバラの原子なら、④は読み物として体系立てる順路。④で読んで理解し、④が①に蒸留し、③が定着させる。⑤は比較の楽しみを生み、そこから①に蒸留する」——**concern 同士が相互リンクで有機的に繋がること**が狙い。

## 2. データモデル（サイトが受け取るもの）

`web/scripts/build-data.mjs` が markdown を走査して `site.json` に正規化する。frontmatter は構造化データとして取り、**body は生 markdown のままクライアントに渡してブラウザで描画**する。

```
site = {
  generatedAt: "YYYY-MM-DD",
  notes:     [{ slug, title, kind, tags[], created, srs{next,interval}, due, body, links[] }],
  mocs:      [{ slug, title, tags[], body, links[] }],
  follows:   [{ name, title, followType, status, goal, tags[], coach, formation,
                snapshot[], rivals[], baseline[], focus[], nextMatches[],
                body, links[], entities[], sessions[] }],
  atlases:   [{ slug, title, tags[], routes[{id,label,desc,order[]}], body, links[],
                concepts[{ slug, title, gist, status, created,
                           edges{requires[],contrasts[],leadsTo[],elaborates[]},
                           notes[], tags[], body, links[] }] }],
  logtopics: [{ slug, title, tags[], created, imageVisibility,
                fields[{key,label,type,options[],unit,required,max}],
                display{subtitle,badge,cardFields[],filters[],sort},
                intro, links[], entries[{slug,title,created,image,fields{},body,links[]}] }],
}
```

補足:
- `links[]` は body 中の `[[wikilink]]` を抽出したもの。**アウトバウンドのみ**。バックリンク（被リンク）は計算していない。
- `due` は `kind: knowledge` かつ `srs.next <= 今日` のフラグ。
- ビルドは **logs のスキーマ検証で落ちる**（必須欠落・enum 外・rating 範囲外）。一貫性の砦として機能している。
- atlas は **エッジ参照整合性を検証**（存在しない概念を指すエッジ・ルートはビルド失敗）。
- notes / follows には同等の検証がない（`kind` と `title` の存在チェックのみ）。

→ **ゴルフが全体の半分**。残りは 1〜9 件の細い山が並ぶロングテール。トピックの厚みが極端に不均一。

### 3.3 SRS（間隔反復）の稼働実態 — **重要**
- `kind: knowledge` 59 件の `srs.next` は **最も新しいもので 2026-07-27**。つまり **59 件すべてが「復習期限」状態**。
- `review-log.jsonl` は **1 行**（2026-06-20 の 1 問だけ）。
- → **③想起と定着のループは事実上停止している**。ホームの「復習期限 59」は達成不可能な数字として常時点灯し、バッジとして意味を失っている。

### 3.4 コンテンツの粒度
- notes 平均 1.8 KB（最小 563 B / 最大 3.5 KB）。**読むのに 1 分以内の短文**が大半。
- follow の `profile.md` は frontmatter に構造化データ（baseline / focus / snapshot / next_matches）を持ち、body に散文＋変遷テーブル。**リッチだが、サイトでは frontmatter 部分しかカード化されていない**。
- follow の `sessions/*.md` は body 全文が生 markdown（計測値の表・所見・アドバイス）。**構造化されていない**。
- atlas の concept は読み物（散文）＋型付きエッジ。muninn の中で**最も設計が進んだ画面**。

### 4.3 各ページの中身

**`/` ホーム**（縦 1 本のスクロール、上から順に）
1. KPI タイル 2×2 — 復習期限 / ノート数 / アトラス概念(執筆済/全) / フォロー数
2. アラート行 — 復習期限があれば 1 行、直近の次戦があれば 1 行
3. 「直近の更新」— notes/sessions/concepts/log-entries を日付降順で混ぜた **最新 7 件**（色ドットで種別）
4. 「学習アトラス」— アトラスカード（執筆進捗バー付き）
5. 「フォロー」— フォローカード
6. 「ログ」— ログトピックカード
7. 「ノート / 蘊蓄」— 「全ノートを見る」カード ＋ MOC のピルボタン列

**`/notes` ノート一覧**
- AppBar 内に検索 Input（**タイトルとタグの部分一致のみ**。本文は検索対象外）
- MOC ピルボタン列
- 90 件を「復習期限が先 → タイトル昇順」でフラットに列挙。カードは「タイトル ＋ kind チップ ＋ 復習バッジ」だけ

**`/note/:slug` ノート**
- kind チップ / 復習バッジ / `next` 日付 / タグチップ / 本文 markdown
- **バックリンクなし。関連ノートの提示なし。前後移動なし**。行き止まり。

**`/moc/:slug` MOC**
- markdown をそのまま描画するだけ（手書きのリンク一覧が読める）。**自動生成ではなく手入力**。

**`/follow/:name` フォロー**
- 上部に `snapshot`（箇条書き）カード ＋ 次戦
- タブ:
  - interest 型（argentina-nt）: スカッド / 日程 / 蘊蓄 / タイムライン / 概要
  - goal 型（golf, skincare）: ダッシュボード / タイムライン / 蘊蓄 / 概要
- 「ダッシュボード」= 目標テキスト＋ベースラインのタイル 2 列＋重点課題カード。**数値は静止したタイル。推移グラフはない**
- 「タイムライン」= `sessions/*.md` の body を日付見出し付きで**全文縦積み**
- 「蘊蓄」= `follow.tags` と `note.tags` の**交差でノートを引っ張る**（唯一の自動クロスリンク）

**`/atlas/:slug` アトラス**（実装の完成度が最も高い）
- 「ルート」ビュー: 読了率バー ＋ 番号付きステッパー（読了は ✓）。複数ルートをピルで切替
- 「マップ」ビュー: `requires` の最長鎖で深さを決める決定的レイアウトの **SVG 知識グラフ**。エッジ 4 種を色・破線で描き分け、読了ノードは点灯。横スクロール
- 読了状態は **localStorage**（`mn.atlas.<slug>.read`）

**`/atlas/:slug/concept/:cslug` 概念**
- 読み物本文 ＋ 「つながり」ボックス（**アウトバウンド＋インバウンド両方**を 7 種のラベルで表示）
- 「ここから深掘りする」= Claude 向け依頼プロンプトをクリップボードにコピーするボタン
- 「キーポイント（覚える用）」= `notes:` で蒸留先に指定したノートへのリンク
- ルート内の前後ナビ（‹ 前 / 次 ›）

**`/logs`, `/log/:topic`, `/log/:topic/entry/:slug` ログ**
- トピックカード（サムネ＋最新記録＋件数）→ 記録の 2 列グリッド（画像＋タイトル＋★＋チップ）→ 記録詳細（画像＋スキーマ順のフィールド表＋本文）
- `display.filters` に指定したフィールドで絞り込みピルが出る

### 4.4 共通 UI 部品（`ui.jsx`）
`AppBar`（sticky、‹戻る / ⌂ホーム）、`Chip` / `Chips`、`DueBadge`、`Card`、`Center`、`Loading`、`Md`（`[[wikilink]]` を内部リンクに変換して ReactMarkdown で描画）。

### 4.5 ナビゲーション構造
```
ホーム ──▶ セクション ──▶ 詳細
  ▲                          │
  └──── ⌂ホーム / ‹戻る ──────┘
```
- **グローバルナビゲーション（ボトムタブ／サイドバー／ハンバーガー）が存在しない**
- 詳細から横に移動する手段は、atlas の「つながり」と follow の「蘊蓄」タブ、および本文中の `[[wikilink]]` だけ
- **検索は `/notes` ページの中にしかなく、グローバル検索がない**

## 5. 技術的制約（刷新案が守るべき箱）

1. **完全静的**。バックエンドなし。すべて `site.json` をクライアントで復号して動かす。書き込み UI は作れない。
2. **全データが起動時に一括ロード**される（現在 307 KB）。逆に言えば**クライアント側の横断計算・全文検索・グラフ構築は自由にできる**（コストはビルド時 or 初回ロード時）。
3. **正本は markdown**。サイトは派生。サイトのために markdown のスキーマを増やすことは可能（`build-data.mjs` を変更）だが、**過去コンテンツの一括書き換えはコストになる**。
4. **書き込み動線は Claude Code**。サイトからできるのは「Claude に渡すプロンプトを作る」ところまで（atlas の深掘りボタンが先行実装）。
5. **モバイル主体・ダーク固定・PWA**。iOS safe-area 対応済み。
6. **パスワード保護**。ただし **`logs` の画像だけは Pages 上で素の公開**（直 URL で見える）。

## 6. ユーザーの来訪動機（ジョブ）と、現状の対応

ユーザーは 1 人（＝本人）。書いたのも本人。それでも「何があるか分からない」と言っている、という前提で整理する。

| # | 来訪動機（ジョブ） | 典型的な状況 | 現状の受け皿 | 実態 |
|---|-------------------|-------------|-------------|------|
| J1 | **今日やることある?** | 起動直後の 3 秒 | ホームの KPI ＋アラート行 | 「復習期限 59」が固定表示で麻痺。行動に繋がらない |
| J2 | **あれ何だっけ（ピンポイント想起）** | 会話中・作業中に思い出したい | `/notes` の検索 | **タイトルとタグしか当たらない**。本文・follow・atlas・logs は検索対象外。グローバル検索の入口もない |
| J3 | **暇つぶし・回遊（セレンディピティ）** | 通勤中・寝る前 | ホームの「直近の更新」7件 | 7 件を見たら終わり。**過去の 90 ノートに戻る導線が「全ノートを見る」フラットリストしかない** |
| J4 | **腰を据えて学ぶ** | まとまった時間 | `/atlas` のルート／マップ | 実装は良い。ただし**アトラスが 1 件しかなく、ホームでの存在感が中段のカード 1 枚** |
| J5 | **比べて選ぶ** | 豆を買う前 | `/log/coffee-beans` | 記録 1 件（サンプル）なので比較機能が空回り。**比較テーブル／ソートは未実装**（絞り込みのみ） |
| J6 | **予習する** | 試合前 | `/mn-brief`（**Claude 側のみ。サイトに面がない**） | サイトで予習ブリーフィングを読む手段がゼロ |
| J7 | **進捗を確かめる** | 練習後・週末 | follow のダッシュボード＋タイムライン | ベースラインは**静止した数字**。5 セッション分の HS/ミート率/総距離の**推移が可視化されていない**（markdown の表を目で追う） |
| J8 | **入れたものを確認する** | 記録直後 | ホームの「直近の更新」 | ここは機能している |
| J9 | **何ができるんだっけ（システム自体の把握）** | ふと思い出したとき | **なし** | サイトに「muninn の使い方 / 何を投げれば何になるか」の説明が一切ない。5 concern の名前（ノート・フォロー・アトラス・ログ・MOC）は**内部用語のまま画面に露出**している |

## 7. 訴えられた課題 → 現状からの根本原因

### 課題A「機能が多く、何ができるのか把握しにくい」
- ホームが**7 セクションの縦積み**で、各セクションが「何のためのものか」を説明しない。
- 画面に出る語彙が **muninn 内部の concern 名**（ノート / 蘊蓄 / フォロー / 学習アトラス / ログ / MOC）。ユーザーの目的語（覚える / 追う / 学ぶ / 比べる / 探す）に翻訳されていない。
- **サイト側に書き込み動線がほぼ無い**のに、「何ができるか」＝ 実際には Claude Code 側のコマンド群のこと。**この非対称がどこにも説明されていない**（atlas の深掘りボタンだけが例外的に橋を架けている）。

### 課題B「何ができるんだっけがわからない」
- A と同根＋**再訪時の記憶の手がかりがない**。ヘルプ／オンボーディング／空状態の説明文がゼロ（`/logs` の空表示に「`/mn-log` でトピックを作る」と書かれているのが唯一）。

### 課題C「情報があるはずなのに辿り着けない」
- **グローバル検索がない**（`/notes` 内の検索も**タイトル・タグのみ、本文非対象**）。
- **タグが frontmatter にしかなく、タグから引く画面がない**。42 件ある `sports/golf` を一覧する手段が、`/notes` で「golf」と打つことだけ。
- MOC が**手書き**なので、新しいノートが増えても索引に載る保証がない（`/mn-regen-moc` を回さない限り古びる）。
- `/notes` の 90 件フラットリストは、**タイトル文字列以外の手がかり（タグ・日付・トピック・kind）で絞る手段を持たない**。
- 発見系の面（ランダム / 未読 / 孤児ノート / 関連度）が一切ない。

### 課題D「情報の有機的な繋がりが分かりにくい」
- **バックリンクを計算していない**（`links[]` はアウトバウンドのみ）。ノートは開いたら行き止まり。
- **concern をまたぐリンクが構造として存在しない**。実際にあるのは:
  - concept → notes（`notes:` フィールドによる明示的な蒸留リンク）
  - follow → notes（**タグの交差**という間接的な推定）
  - 本文中の `[[wikilink]]`（人力）
  - この 3 つだけ。ノート側からは concept にも follow にも log にも戻れない。
- **グラフ表現は atlas 内にしか存在しない**。「哲学アトラスの概念」と「philosophy タグのノート」が別世界として描かれる。
- タグは表示されるが**クリックできない**（`Chips` はただの装飾）。

### 課題E「各機能がそこで見やすい形に落とせていない」
- **notes**: markdown をそのまま出すだけ。59 件の knowledge に対し「覚える」ための UI（クイズ・自己テスト・カード表）がサイト側にない。
- **MOC**: 生 markdown。索引という機能に対して素朴すぎる。
- **follows(goal)**: 時系列の数値（HS・ミート率・総距離が 5 回分ある）を**グラフにしていない**。定点観測の本質が「前回と比べる」であるのに、比較 UI がない。
- **follows(interest)**: スカッドはカード並びまでは良いが、フォーメーション図・対戦カレンダーといった「サッカーらしい見せ方」に落ちていない。
- **atlas**: 良い。ここが基準線。
- **logs**: グリッド＋絞り込みまでは良いが、**比較テーブル／ソート／散布**がなく「並べて比べる」という設計思想が UI に到達していない。
- **③想起と定着**: サイトに面が存在しない（`/mn-review` も `/mn-brief` も Claude 側のみ）。**5 concern のうち 1 つがビューアに欠落している**。

### 課題の要約（構造）
```
根本1: 情報構造（IA）が「ファイルの置き場所」の写像になっている
       → 画面が concern 名で分かれ、ユーザーの目的で分かれていない
根本2: 横断のインフラが無い（全文検索・タグ索引・バックリンク・グラフ）
       → データはあるが、辿る手段だけが欠けている
根本3: ③想起と定着 が Web に存在しない
       → 「蓄積を回収して楽しむ」という muninn の目的が、見る面で完結しない
根本4: 各 concern のデータ構造が持つリッチさに、表示が追いついていない
       → 数値は静止、markdown は素通し、タグは装飾
```

## 8. 刷新で「守るべきもの」と「変えていいもの」

**守るべきもの（触るとコンセプトが壊れる）**
- 正本は markdown、サイトは派生ビルドという関係
- ダーク基調のグラス質感（muninn のトーン。ユーザーが気に入っている前提で維持）
- モバイルファースト・PWA・safe-area
- パスワード 1 枚で全部読める手軽さ
- atlas のマップ／ルートという「グラフ＋順路」の二層モデル
- 完全静的（バックエンドを増やさない）

**変えていいもの（むしろ変えるべき）**
- ホームの構成・情報階層（縦積み 7 セクション）
- ナビゲーション構造（グローバルナビ不在）
- 画面に出す語彙（内部 concern 名 → ユーザーの目的語）
- `site.json` のスキーマ（バックリンク・全文検索インデックス・タグ索引・数値時系列をビルド時に生成してよい）
- ルート設計（9 ページに縛られない）
- 「Claude に投げるプロンプトを作る」動線の拡張（atlas の深掘りボタンを一般化してよい）

**未確定（刷新案が答えを出すべき論点）**
- ③想起と定着 をサイトにどう載せるか（静的サイトで SRS の状態更新はできない。localStorage か、Claude へのプロンプト生成か、読み専のクイズか）
- concern 名をユーザーに見せ続けるか、目的語に翻訳するか
- ホームを「ダッシュボード」にするか「入口」にするか「フィード」にするか
- 90 ノート（うち 47% がゴルフ）という**不均一なコンテンツ量**に耐える IA か
