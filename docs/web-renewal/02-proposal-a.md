# 案A — muninn Web 刷新提案「テーマに着地するナレッジベース」

提出日: 2026-07-31 / 対象コミット: `6cc727f` / 前提資料: `01-current-state.md`

---

## 0. まず、案Aの名前について（出発点の読み直し）

与えられた出発点は **「目的語ドリブン IA」** だった。補足では動詞（思い出す／探す／学ぶ／追う／比べる／覚える）で画面を割る方向が示されている。

ここで一度立ち止まった。**動詞だけで画面を割ると、それは concern の言い換えにしかならない**からだ。

| 動詞 | 実際に着地する場所 |
|------|-------------------|
| 学ぶ | `atlas/` |
| 追う | `follows/` |
| 比べる | `logs/` |
| 覚える | `srs` |
| 探す | 検索 |

1:1 の同義語辞書である。ラベルが「学習アトラス」から「学ぶ」に変わるだけで、**情報構造は 1mm も動いていない**。根本1（IA がファイルの置き場所の写像）は解決しない。

そして人は、動詞だけを持って来訪しない。「覚えたい」ではなく「**ゴルフのフェース角のこと**を思い出したい」と来る。**動詞は入口の言葉、目的語は情報の器**だ。案Aの名は「目的語ドリブン」であって「動詞ドリブン」ではない——この名前に忠実であることを選んだ。

だから本案はこう組む:

- **ナビゲーションは動詞で名乗る**（＝画面上に常に「何ができるか」が出ている。案Aの最優先要件を満たす）
- **情報構造は目的語＝テーマで組む**（＝ゴルフ／健康／サッカー／哲学／中東／宇宙／コーヒー）
- **concern 名（ノート・フォロー・アトラス・ログ・MOC）はナビから消し、テーマの中の「役割」に降格する**

## 1. コンセプト

> **muninn を「5つの concern」から「7つのテーマ」に読み替える。動詞で入って、テーマに着地する。**

- ボトムタブ4つ（**いま／テーマ／さがす／おぼえる**）が「今このアプリで何ができるか」を常時画面に置く。ホームに戻らなくても横に動ける。
- 中核は **テーマ・ハブ**。「ゴルフ」を開けば、観測グラフ・42件の知識・関連する読み物・記録が**1画面に束ねて**出る。concern を横断した繋がりが、初めて目に見える形になる。
- 書き込みは今まで通り Claude Code。サイトは読む面に加えて「**Claudeへの依頼をためる面**」になり、貯めた依頼をまとめて1回で渡す。

## 2. 設計原則（判断が割れたときの拠り所）

### 原則1: 動詞で入り、テーマに着地する
ナビ・見出し・空状態の文言は動詞（ジョブ）で書く。情報の器はテーマ（目的語）で作る。**この2つを混ぜない**。「アトラス一覧」のような concern の器はもう作らない。

### 原則2: 1画面に1ジョブ、1ジョブに1つの次の一手
各画面は冒頭1行で自分の役目を名乗る（「おぼえる — 思い出して、定着させる」）。主要アクションは1つに絞る。**選択肢を並べるのは麻痺の原因**であって、機能の豊かさの表現ではない。今のホーム7セクション縦積みの逆を行く。

### 原則3: 数えるな、1つ出せ
バックログ（復習期限59件）は**表示しない**。今日の1件だけを出す。進捗は「借金がいくら残っているか」ではなく「**どこまで進んだか**」で語る。debt メーターは行動を止め、progress バーは行動を促す。

### 原則4: 空セクションは描かない。空は「次の一手」に変換する
`「フォローはありません」` のようなゼロ状態は**禁止**。何も無いなら何も描かない。描くなら「記録を1件足す（依頼をコピー）」という行動にする。**これがコンテンツ量の不均一（90ノートのうち47%がゴルフ、logs は1件）に耐える唯一の方法**。

### 原則5: サイトは「読む面」＋「意図の面」。書くのは Claude
迷ったら書き込み UI ではなく**依頼プロンプトを作る**。atlas の深掘りボタンを全concernに一般化し、さらに「ためて、まとめて渡す」まで持っていく。

## 4. サイトマップ / IA

```
muninn
│
├─ /                      【いま】       tab1  今日ひらいて最初に見る面
├─ /themes                【テーマ】     tab2  7テーマのグリッド
│   └─ /t/:theme           テーマ・ハブ  ★本案の中核
├─ /search                【さがす】     tab3  全文検索・タグ・ランダム・全件
├─ /recall                【おぼえる】   tab4  今日の1問・カバレッジ・依頼キュー
│
├─ /guide                  muninn の使い方（タブではない。? から）
│
└─ 詳細（テーマ・ハブと検索から入る葉）
    ├─ /note/:slug                   知識・気づき
    ├─ /follow/:name                 観測（ダッシュボード/タイムライン/スカッド/日程）
    │   └─ /follow/:name/e/:slug     人物・構成要素のドシエ
    ├─ /atlas/:slug                  読み物（ルート/マップ）※現状維持
    │   └─ /atlas/:slug/c/:cslug     概念        ※現状維持＋バックリンク
    └─ /log/:topic                   記録帖（グリッド/比較表）
        └─ /log/:topic/e/:slug       1記録
```

**全13ルート**（現状 11）。内訳は「面」6＋「葉」7。葉はコンテンツ型が5種ある以上これ以上減らせない。面のうちタブは4に固定した。

**廃止する3ルート**:
- `/notes` — 90件フラットリスト。`/search`（空クエリ＝全件・絞り込み付き）とテーマ・ハブに吸収
- `/logs` — トピック一覧。トピックはテーマに属するのでテーマ・ハブから入る
- `/moc/:slug` — `/t/:theme` に 301 相当のリダイレクト

**リネーム**: `/follow/:name/player/:slug` → `/e/:slug`。フォローは汎用（人物に限らない）なので `player` は不適切。

### テーマの定義（7テーマ）

テーマは**自動導出しない。明示的に宣言する**。境界（「健康」を1つにするか3つに割るか）は本人にしか決められないからだ。既存の `moc/*.md` を**テーマ・マニフェスト**に格上げする——手書きのリンク列挙をやめ、frontmatter に「どのタグ・どのフォロー・どのアトラス・どのログがこのテーマか」を宣言し、本文は導入の散文だけ残す。

| テーマ | notes | フォロー | 読み物 | 記録 | 既存MOC |
|--------|-------|---------|--------|------|---------|
| ゴルフ | 42 (`sports/golf`) | golf-driver-distance (goal) | — | — | ○ golf |
| 健康 | 28 (`health/*` 6サブタグ) | skincare-pores (goal) | — | — | ○ health |
| サッカー | 7 (`sports/football`) | argentina-nt (interest, 選手10) | — | — | ○ football |
| 哲学 | 7 (`philosophy*`) | — | philosophy (概念11) | — | 新規 |
| 中東 | 6 (`geopolitics/*`) | — | — | — | ○ middle-east |
| 宇宙 | 7 (`science/*`) | — | — | — | ○ science |
| コーヒー | 0 | — | — | coffee-beans (1) | 新規 |

（`moc/home.md` はテーマではなく `/themes` に置換されるので廃止。`language/vocabulary` `knowledge/zettelkasten` の2件は「その他」に落ち、ビルドが警告する。）

**7枚のグリッドは、コンテンツが増えても増えない**。これが IA の安定性を担保する。ノートが 90→300 になってもテーマは 7〜10 のままで、増えるのは各ハブの中身だけだ。

## 5. ナビゲーション構造

### グローバルナビ: ボトムタブ4つ（新規）

現状最大の欠落。**モバイル主体なのにグローバルナビが無く、横移動は `‹戻る` と `⌂ホーム` だけ**という状態を解消する。

```
┌──────────────────────────────────┐
│   いま     テーマ    さがす   おぼえる │
│    ◉        ○        ○        ○   │
└──────────────────────────────────┘
   ↑ position: sticky, bottom: 0
     padding-bottom: env(safe-area-inset-bottom)
     背景は glass（既存 .glass トークン流用）
```

| tab | ラベル | 1行ジョブ文（画面上部に表示） | 対応するジョブ |
|-----|--------|------------------------------|---------------|
| 1 | **いま** | 今日ひらいて、最初に見るところ | J1 今日やることある? / J8 入れたもの確認 |
| 2 | **テーマ** | 関心ごとから入る | J3 回遊 / J4 学ぶ / J5 比べる / J7 進捗 |
| 3 | **さがす** | 覚えていることから引く | J2 ピンポイント想起 |
| 4 | **おぼえる** | 思い出して、定着させる | J6 予習 / 定着 |

「テーマ」だけが名詞である点は意図的だ。ここに動詞（「めぐる」「みる」）を当てると意味が薄くなり、原則1の「器は目的語」とも衝突する。**ラベルで足りない分は1行ジョブ文が背負う**——これが原則2の役割だ。

### 階層の深さ: 最大3

```
tab → テーマ・ハブ → 詳細（ノート/セッション/概念/記録）
tab → 検索結果 → 詳細
```
4階層目を作らない。概念→概念の前後移動は同階層内の移動として扱う。

### 横移動の手段（現状は本文中の `[[wikilink]]` だけ）

1. **ボトムタブ**（どこからでも4つの面へ）
2. **テーマ・チップ**: すべての葉ページの AppBar に所属テーマを出す（`‹  ゴルフ ›`）。1タップでハブに戻る。**これが横移動の背骨**。ノートから隣のノートへ、セッションから関連知識へ、常にハブ経由で1〜2タップ
3. **バックリンク**（葉→葉、逆方向）
4. **タグチップ**（クリックでテーマ内絞り込み）
5. **本文中の `[[wikilink]]`**（現状維持）

3. **読み物**（atlas がある場合のみ） — ルート進捗バー＋「次は◯◯」。哲学テーマではここが最上位
4. **記録**（log がある場合のみ） — 直近3件のサムネ横スクロール＋「並べて比べる ›」
5. **知識** — サブタグ絞り込みチップ＋**被リンク数降順**でノート8件＋「あと N 件」。★ は被リンク3件以上
6. **つながり** — テーマ内 `[[]]` グラフのプレビュー（ノード8以上のときのみ）
7. **Claudeに頼む** — そのテーマで意味のある依頼だけを出す（ゴルフ＝観測を記録／健康＝記録を足す／哲学＝次の章を書く）

**重要なインタラクション**
- **被リンク数でのソートが、手書き MOC の順序を置き換える**。「6件から参照」されているノートは本人が繰り返し土台にしているノートで、実際にゴルフでは `飛距離＝HS×ミート率` と `私の飛距離方針` がそれに当たる。**索引を自動生成する最良の信号は、本人の過去のリンク行動**である
- サブタグチップは複数選択可。選択状態は URL クエリに載せる（`?tag=driver`）ので共有・戻るが効く

**空状態**: 該当 concern が無いセクションは**描かない**（原則4）。コーヒーのテーマは「記録」1ブロック＋「Claudeに頼む」だけの短いページになるが、それは**スカスカではなく「小さいが完結した世界」**だ。逆に「フォローはまだありません」と書けば、その瞬間にスカスカになる。

### 6.10 【使い方】 `/guide`

**目的**: 課題A・Bの直球。「何を投げると何になるか」。
**主要ブロック**
1. **1枚の絵**: 「Claudeに話す → markdown が増える → ここで読む」の3段
2. **翻訳表**（この案の重要な誠実さ）:

| 画面の言葉 | 中身 | 内部 concern | 投げるコマンド |
|-----------|------|-------------|---------------|
| 知識 | 調べて得た客観的事実 | `notes/` knowledge | `/mn` `/mn-research` |
| 気づき | 自分で言語化した知見 | `notes/` insight | `/mn` |
| 観測 | 1つの対象を定点で追う | `follows/` | `/mn-follow` `/mn-collect` |
| 読み物 | 順路つきの教科書 | `atlas/` | `/mn-learn` |
| 記録 | 同じ項目で貯める台帳 | `logs/` | `/mn-log` |
| テーマ | 関心ごとの束ね | `moc/` | `/mn-regen-moc` |
| おぼえる | 間隔反復クイズ | `srs` | `/mn-review` |
| 予習 | 横断合成ブリーフィング | — | `/mn-brief` |

3. **ためこみ状況**: どのテーマにも属さないノート・被リンク0のノート・stub の概念を一覧（＝手入れの入口）。ビルド警告と対になる

**設計判断**: concern 名を**完全に隠さない**。正本は markdown で、書くときは `/mn-log` と打つ。読む語彙と書く語彙が乖離すると、かえって「何ができるか」が分からなくなる。**ナビからは消し、`/guide` にだけ残して橋を架ける**——これが「concern名を見せ続けるか、目的語に翻訳するか」への答えだ。

### 8.3 `build-data.mjs` への追加（擬似コード）

```js
// ---------- ① テーマ組み立て ----------
const themes = mdFiles('moc').filter(f => fm(f).kind === 'theme').map(t => {
  const noteIds = notes.filter(n =>
    n.tags.some(tag => t.tags.some(p => tag === p || tag.startsWith(p + '/')))
  ).map(n => n.slug);
  return { ...t, noteIds,
    subgroups: buildSubgroups(t, noteIds),
    headline: latestEvent(t),                 // sessions / concepts / entries / notes の最新1件
    counts: countByKind(t) };
});
// 逆引き: note.theme / follow.theme / atlas.theme / logtopic.theme を書き戻す
// どのテーマにも属さないノートは orphans.untheme に入れ、警告して**ビルドは通す**
//（logs のスキーマ検証と違い、テーマ未所属は「壊れ」ではなく「手入れ待ち」だから）
if (orphans.untheme.length) console.warn(`⚠ テーマ未所属のノート ${n}件: ...`);

// ---------- ② バックリンク ----------
const back = new Map();                       // id -> [{ id, type, theme, title, why }]
for (const doc of allDocs) {                  // notes / concepts / sessions / entities / entries / themes
  for (const { target, why } of parseLinksWithReason(doc.body)) {
    const r = resolveTarget(target);           // wiki.js と同じ解決規則をビルド側にも置く
    if (r) back.get(r.id).push({ id: doc.id, type: doc.type, theme: doc.theme,
                                 title: doc.title, why });
  }
}
// muninn のリンク規約 `- [[x]] — 理由` から理由を取り出す
function parseLinksWithReason(body) {
  return body.split('\n').flatMap(line =>
    [...line.matchAll(/\[\[([^\]|]+)(?:\|[^\]]+)?\]\]/g)].map(m => ({
      target: m[1].trim(),
      why: (line.match(/\[\[[^\]]+\]\]\s*[—-]\s*(.+)$/) || [])[1] || null,
    })));
}
doc.inDegree = back.get(doc.id)?.length ?? 0;  // ハブノート浮上に使う

// ---------- ③ 観測の時系列 ----------
// 正: session frontmatter の metrics:（今後 /mn-follow が書く）
```

### 8.4 全文検索: **ビルドではなく起動時にクライアントで作る**

`site.json` は既に**全 body を含んでいる**（307KB）。検索インデックスをビルド時に足すと payload が倍増する。だから**起動時に復号済みデータからクライアントで組む**——**payload 増ゼロ**。

```js
// lib/search.js（新規・約70行、依存ゼロ）
export function buildSearch(site) {
  const docs = [...notes, ...concepts, ...sessions, ...entities, ...entries, ...themes]
    .map(d => ({ id, type, theme, title, tags,
                 text: strip(d.body) }));       // markdown記号・wikilink括弧を除去
  const postings = new Map();                   // bigram -> Set<docIndex>
  docs.forEach((d, i) => for (const g of bigrams(d.title + ' ' + d.tags + ' ' + d.text))
                            postings.get(g).add(i));
  return { docs, postings };
}
// 日本語は形態素解析器を積まずに bigram で通す（125文書・約250KB → 構築 100ms 未満）
// スコア = タイトル一致×5 + タグ一致×3 + 本文 tf + 新しさの微加点
```

コンテンツが10倍（900ノート）になったらビルド時生成に移す。**その判断ラインを明記しておく**。

## 9. ③想起と定着 の解

### 9.1 診断: なぜループが死んだか

`review-log.jsonl` は1行。59件全部が「復習期限」。だが**原因はサイトにクイズUIが無いことではない**。

1. **儀式のコストが高すぎる**。30秒の行為（1問答える）のために、ターミナルを開き Claude Code を起動し `/mn-review` を打つ、という2分の準備がいる。**準備 > 行為**の構造は必ず死ぬ
2. **「59」が罰として機能している**。減らない借金の額を毎回見せられれば、人は画面を閉じる
3. **新規ノートの `next` = 作成日**という規約により、書けば書くほど借金が増える。**書く行為と覚える行為が対立関係にある**

### 9.2 解: 3層構造

#### 層1 — 「今日の1問」: サイトで完結する自己採点（Phase 2）

**なぜ自己採点か。** 静的サイトは問題を生成できない。しかも muninn の `title` は原子化ルールにより**内容を言い切る形**（＝答えそのもの）になっているので、タイトルを見せた時点で「答え当て」は成立しない。

そこで **「答え当て」ではなく「自己説明（Feynman チェック）」**にする。

```
表: タイトル（＝主張）を見せる → 「これを自分の言葉で説明できる?」
裏: 本文を展開して自己照合
自己評価: [できた] [あやしい] [だめ]
```

これは `mn-review` の採点基準（「本人の言葉で要点を再構成できて初めて q>=4」）と**同じ認知行為**であり、59件のノートを1件も書き換えずに今日から回る。

**出題の決定性とテーマ巡回**:
```js
const today = localISODate();                 // ビルド日ではなく端末の今日
const seed  = daysSince('2026-01-01', today);
const theme = themesWithKnowledge[seed % themesWithKnowledge.length];   // ★テーマを巡回
const pool  = theme.knowledge
  .filter(n => effectiveNext(n) <= today)     // site.json の srs.next に localStorage を重ねた値
  .sort((a, b) => a.srs.next.localeCompare(b.srs.next) || a.slug.localeCompare(b.slug));
const card  = (pool.length ? pool : allDue)[ seed % Math.min(pool.length, 5) ];
```
- **1日中同じ問題**（リロードで引き直せない）。引き直せると賭博になり、コミットが消える
- **テーマ巡回**により、47%のゴルフが出題の47%を占めない。哲学も宇宙論も中東も定期的に回ってくる。**偏在への2つ目の具体的対処**

#### 層2 — 「依頼キュー」: 正本への書き戻し（Phase 2）★副次の尖り

自己採点の結果は localStorage に**先行書き込みログ**として貯まる。

```js
// mn.queue = [{ kind:'review', slug, q, date }, { kind:'deepdive', atlas, concept }, ...]
```

「おぼえる」タブの下部に **[ Claudeに渡す（6件） ]**。押すと1つのプロンプトが生成されクリップボードへ:

```
/mn-review 以下はサイトで自己採点した結果。この通りに srs を更新し、
review-log.jsonl に追記して push して（出題はしなくてよい）。

- golf-clubhead-speed-... q=4 (2026-07-29)
- anaximander-apeiron-... q=2 (2026-07-30)
- niacinamide-reduces-... q=5 (2026-07-31)

あわせて、以下の深掘りも頼む。
- atlas philosophy / socrates から「エレンコスの限界」を深掘り
```

**これが本案の設計思想の核**だ。サイトは書き込みできないが、**書き込みの"意図"は溜められる**。読むのはスマホ、書くのは Mac、という現実の分断を、キューが橋渡しする。日曜に1回貼れば1週間分が正本に反映される。

**整合の規則**（重要）: localStorage のエントリは `site.generatedAt > entry.date` になったら破棄する（＝正本が追いついたとみなす）。二重反映も、古いローカル状態の居座りも起きない。

**リセットの一手**: 初回だけ「59件の期限を仕切り直す」ボタンを置く。押すと `/mn-review` 向けに「全 knowledge の `next` を今日から30日に散らして初期化して」という依頼を生成する。**借金を一度チャラにして、1日1問のペースに合う分布に置き直す**。これが「59件麻痺」への直接の処置だ。

#### 層3 — 「予習」: `/mn-brief` の面（Phase 3）

サイトは新しい散文を合成できないが、**素材の組み立てはできる**。テーマ・ハブに「予習」ブロックを条件表示（`next_matches` が7日以内）:

- 直近スナップショット（すでに構造化されている）
- 注目する構成要素（`deep_dive: true` の entity）＋ 直近 changelog
- そのテーマの knowledge から**3問**（今日の1問と同じカード形式）
- **[ Claudeに詳しいブリーフィングを頼む ]** → `/mn-brief argentina-nt` をコピー

**80%（手持ちの事実の組み立て）はサイトが、20%（新しい統合）は Claude が**やる。

### 9.3 「59件常時点灯」への回答（まとめ）

| 打ち手 | 内容 |
|--------|------|
| **数字を消す** | ホームの KPI タイルと「復習期限 59」バッジを撤去。`note.due` を site.json から削除 |
| **1件に絞る** | サイトが見せる復習面は「今日の1問」だけ。バックログの総量は**どこにも表示しない** |
| **progress で語る** | 「おぼえる」に `▓▓▓░░ 8/59 触れた` ＋直近7日のドット。減らない借金 → 増える手ごたえ |
| **偏りを均す** | 出題はテーマ巡回で選ぶ |
| **一度チャラにする** | 「59件の期限を仕切り直す」依頼ボタン（初回のみ） |

## 11. 捨てるもの・トレードオフ・リスク

### 捨てるもの（明示的に）

| 捨てるもの | 理由 |
|-----------|------|
| **`/notes` の90件フラットリスト** | タイトル文字列以外の手がかりを持たない一覧は、90件で既に破綻している。検索とテーマが代替する |
| **ホームの KPI タイル 2×2** | 「ノート90」「フォロー3」は行動に繋がらない。数えることをやめる（原則3） |
| **「復習期限 N」バッジ全部** | 罰として機能している。`note.due` ごと削除 |
| **MOC の手書きリンク列挙** | 5ファイルの本文を削る破壊的変更。古びる構造そのものを捨てる。**コミットメッセージに理由を明記する** |
| **follow の「蘊蓄」タブ** | 関連ノートはテーマ・ハブが担うので重複。タグ交差という推定リンクはハブ側で「タグが同じノート」と明示ラベルを付けて残す |
| **`/logs` トピック一覧** | トピック1件のためのページ。テーマから入る |
| **ナビゲーションからの concern 語彙** | 「アトラス」「フォロー」「ログ」「MOC」。`/guide` にだけ残す |

### トレードオフ（引き受けるもの）

1. **テーマは手動キュレーション**。新しい関心を始めたときテーマを作らないと「その他」に落ちる。→ **自動化しない**。テーマ境界（健康を1つにするか3つに割るか）は本人にしか決められない。代わりにビルド警告と `/guide` の手入れ一覧で運用する
2. **自己採点は Claude 採点より甘い**。曖昧な答えを自分で「できた」にしてしまう。→ **頻度を取る判断**。今の失敗は精度ではなく回数（1年で1問）だ。厳密採点は「Claudeに出題を頼む」ボタンで併存させる
3. **localStorage は端末ローカル**。iPhone で採点しても Mac では見えない。→ 依頼キューで正本に戻す設計にしたが、**反映するまでは端末ローカル**。これは静的サイトの構造的限界であり、隠さない
4. **`/search` にタブを1枠使った**。検索を AppBar 常設にすれば枠が浮くが、iOS で AppBar に入力欄を常設するとキーボードとの相性が悪く、かつ「探す」がジョブとして独立して強い（J2）ので独立させた
5. **URL が変わる**（`/notes` `/moc/*` `/player/*` 廃止）。個人1人用なのでブックマーク破壊のコストは小さい、と割り切る

### リスク（正直に）

1. **【最大】テーマの粒度を間違えると全部崩れる。**
   「健康」を1つにすると28件の中身がバラバラ（毛穴・髪・栄養・入浴・睡眠・ストレス）、3つに割ると各8件で薄い。**IA の失敗はここでしか起きない**。
   → 対処: Phase 1 で7テーマを実装して**1週間実際に使い、粒度だけを見直す前提で始める**。マニフェストは frontmatter なので、粒度変更のコストは「md を数ファイル編集して再ビルド」で済む。**この案は粒度を後から変えられる形で作ってある**——それがマニフェスト方式を選んだ最大の理由だ
2. **反映を1度もしなければ、麻痺は形を変えて残る。** localStorage に30件溜まって、それが新しい罪悪感になる。
   → 対処: キューが10件を超えたら「おぼえる」に反映を促す帯を出す。それでも押されないなら、**この案の③は失敗と認める**。判定は1ヶ月後の `review-log.jsonl` の行数（§12）
3. **依頼キューは「スマホで読む→Macで書く」を前提にしている。** 実際に貼らないなら死ぬ機能。
   → 対処: だから **Phase 2 に置いた**。Phase 1 の価値をこの賭けの人質にしない
4. **metrics 抽出は既存セッションのテーブル書式に依存**。書式が揺れるとグラフが欠ける。
   → 対処: frontmatter を正とし、フォールバックは「取れた点だけ描く・欠測は点を打たない」。**2点未満ならグラフを描かない**
5. **起動時の検索インデックス構築が体感を悪くする可能性**。現状125文書で100ms未満と見積もったが、復号（PBKDF2 200k）の後に更に処理が乗る。
   → 対処: 初回描画をブロックしない（`requestIdleCallback` で構築、完了まで検索タブは「準備中」）。900ノート規模になったらビルド時生成に移す
6. **哲学・コーヒーの新規テーマは MOC が存在しない**＝ホーム(`moc/home.md`)経由の既存導線を壊す。
   → 対処: Phase 1 で `moc/home.md` を廃止し `/themes` に置換するので、そもそも導線が変わる。Obsidian で見る場合の入口が失われる点は許容（Obsidian は閲覧専用の任意ビューア）
