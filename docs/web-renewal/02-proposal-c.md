# 刷新提案C — 『muninn 日報』：探させない、編集して差し出す

作成日: 2026-07-31 / 前提: `01-current-state.md` / 対象コミット: `6cc727f`

---

## 1. コンセプト

> **muninn を「探す道具」から「読む媒体」に変える。蓄積を毎朝ひとつの紙面に編集して差し出す、自分ひとりのための日報。**

- ユーザーは検索窓と向き合わない。**開いたら、もう組んである**。今日読むべき3本の再読、進行中の連載、書庫から引いた特集が、上から順に並んでいる。
- 紙面は**ビルド日ではなく「閲覧日」で組む**。push が2週間止まっても、毎朝ちがう面が出る。編集の材料は「新着」ではなく**「忘却」**だから、材料は枯れない。
- ただし**面は4つのタブの1つにすぎない**。「あれ何だっけ」には全文検索、「何があるんだっけ」には在庫マップ、「何ができるんだっけ」にはデスク。編集は**既定であって唯一ではない**。

---

## 2. 設計原則

判断が割れたときは、上から順に優先する。

1. **探させない、差し出す。** 検索は最後の手段であって最初の手段ではない。既定の動詞は「めくる」。
2. **紙面は閲覧日で組む。** ビルド時にやるのは「素材の下ごしらえ」まで。「今日どれを載せるか」はクライアントが `new Date()` で決める。更新が止まっても面は動く。
3. **数えるのは「やった量」であって「借金」ではない。** 未消化の件数をバッジで出さない。「復習期限 59」のような達成不能な数字は画面から全廃する。
4. **一番豊かな在庫は、すでに書いて忘れた90本。** 新着は面の一部でしかない。編集エンジンの主燃料は忘却である。
5. **書き込みは「伝票」にして束ねる。** サイトは意図を localStorage に貯め、Claude に**一括で**渡す。1タップ1往復にしない。

## 3. 根本原因への対応表

### 根本1〜4

| 根本 | この案の対応 |
|---|---|
| **根本1: IAがファイル置き場の写像** | ページを concern で割るのをやめ、**読む姿勢**で割る（面＝めくる / 棚＝俯瞰する / 探す＝当てる / デスク＝頼む）。ボトムタブ4枚がそのまま4つの姿勢。concern（notes/follows/atlas/logs）は**ページ名から消し**、面の中の「記事 / 連載 / 記録 / 記録帖」という紙面語彙に翻訳する |
| **根本2: 横断インフラが無い** | ビルド時に **①バックリンク逆引き ②タグ横断在庫（tagIndex） ③MOCセクション分解 ④git由来の最終更新日** を生成。クライアントで**全文検索**（site.json 307KB は全部メモリ上にあるので専用インデックス不要）。タグは**押せるようになり**、押すと `/shelf/:tag` の横断棚板に飛ぶ |
| **根本3: ③想起と定着が Web に無い** | 面のセンターに **「今日の再読」3枚**を常設。伏せ記事 → めくる → 自己判定。判定は**ローカル影SRS**で即座に効き（体験上はSRSが動いている）、溜まった判定は**答え合わせ伝票**として `/mn-review` に一括反映する。→ §9 |
| **根本4: データのリッチさに表示が追いつかない** | session frontmatter に `metrics:` を足して**スパークライン**へ。log は entries≥2 で**比較テーブル**へ。MOC は生 markdown をやめ**セクション＝特集の束**として構造化。note は `recall:` を足して**問いとして出せる**ようにする |

### 課題A〜E

| 課題 | 効く要素 |
|---|---|
| **A: 機能が多く把握しにくい** | **デスク（`/desk`）**が「muninn に何を投げると何になるか」を**ユーザーの目的語**（覚える／追う／学ぶ／比べる／思い出す）でカード化し、各カードに**投げる例文とコピーボタン**を置く。「説明ページ」ではなく「発射台」なので読まれる |
| **B: 何ができるんだっけがわからない** | 同上。加えてデスク下段の**「在庫の健康」**（想起の問いが無い記事 52 / 数値未記入の観測 5 / どこからも辿れない記事 7）が、**何をすればこのシステムが良くなるか**を毎回思い出させる |
| **C: 情報があるのに辿り着けない** | **探す（全文・全concern横断・スニペット付き）** ＋ **棚の在庫マップ**（何をどれだけ持っているかを面積で見せる） ＋ **切り口ピル**（久しく読んでない／孤立している／一度も再読していない） ＋ **押せるタグ**。発見系の面がゼロだった状態を4方向から埋める |
| **D: 繋がりが分かりにくい** | **バックリンクを全concernで計算**し、記事の末尾に「ここへ来る道」として文脈付きで出す。**特集カード**が「タグ束をハブ起点＋リンク2ホップ」で**繋がりの形そのものを面に載せる**。`tagIndex` により「philosophy タグのノート」と「哲学アトラスの概念」が同じ棚板に並ぶ |
| **E: 各機能が見やすい形に落ちていない** | notes→伏せ記事＋バックリンク／MOC→編集済みの束カード／follow(goal)→スパークライン＋前回比／follow(interest)→次戦カウントダウン＋予習ブリーフ面／logs→比較テーブル／atlas→現状維持（基準線）＋連載カードで面に昇格 |

## 5. ナビゲーション構造

**ボトムタブ4枚（sticky・safe-area対応）を新設する。** グローバルナビ不在という現状最大の構造欠陥を、モバイル前提の最も素直な形で埋める。

```
   面 ⇄ 棚 ⇄ 探す ⇄ デスク        ← 常時いつでも横移動（階層0）
    │    │
    ▼    ▼
  記事 / 連載 / 定点 / 記録帖       ← 詳細（階層1）
    │
    ▼
  概念 / 人物 / 1記録               ← 詳細の詳細（階層2）
```

- **深さは最大2階層**。現状と同じだが、どの階層からもタブで階層0の4面に1タップで戻れる。
- **横移動の手段**（現状は atlas のつながりと follow の蘊蓄タブしか無かった）を4つ追加する:
  1. **押せるタグ** — あらゆる画面のタグチップが `/shelf/:tag` へ飛ぶ（現状はただの装飾）
  2. **バックリンク「ここへ来る道」** — 記事・概念・人物の末尾に、被リンク元を**リンク元の一文つき**で列挙
  3. **「次の1枚」** — 記事の末尾に、同タグ・未再読・被リンクの近いノートを1枚だけ差し出す（行き止まりの解消）
  4. **AppBar の ⌕** — どの詳細ページからも検索を開ける
- AppBar の「‹戻る / ⌂ホーム」は維持（ホーム = 面）。

## 6. 各ページの設計

### 6.1 面（`/`） — 今日の紙面 ★主要

**目的**: J1（今日やることある?）／J3（暇つぶし・回遊）／J8（入れたものを確認）。**「開いて3秒で、今日読むものが決まっている」**。

**主要ブロック（上から順）**

| # | ブロック | 内容 |
|---|---|---|
| 1 | 題字（sticky） | `muninn` ／ 第N号（＝累計コミット数）／ **閲覧日**（クライアント）／ 「更新 4日前」（generatedAt との差） |
| 2 | リード | その日いちばんの1枚。速報→節目→新章→予習→特集→復刻 の順で在庫のあるものが落ちてくる（§7） |
| 3 | 袖 | 0〜2行の小見出し。次戦カウントダウン／未送信の伝票 |
| 4 | **今日の再読 ×3** | 伏せ記事カード。横スワイプ or 縦積み。**本案の心臓部**（§9） |
| 5 | 連載 | 読んでいるアトラスルートの次の未読章＋読了バー |
| 6 | 特集 | MOCセクション（人間編集済みの束）を3〜4本のリンクとして展開 |
| 7 | 記録 | goal follow のスパークライン／log の比較ミニ表／次戦 |
| 8 | 今号の在庫 | `90記事 / 11章 / 8観測 / 1記録帖` ＋ 棚・探す・デスクへの導線 |

**重要なインタラクション**
- 再読カードの **「めくる」** — 伏せ → 記事全文（ノートは平均1.8KB＝1分以内）→ 「わかった / あやしい」
- 特集カードの見出しタップ → `/shelf/:tag` の該当束にアンカー
- リード・連載カードは全面タップで遷移。**カードは全部押せる**（現状の「直近の更新」行と同じ触感を全カードに）

**空状態**
- 全カード型が在庫切れになるのは「ノートが0件」のときだけ。それ以外は必ず**特集か復刻**が落ちてくるので、**面が空になることは構造的に起きない**（§7の在庫切れ連鎖）。

### 6.2 棚（`/shelf`） — 在庫マップ ★主要

**目的**: J9・課題B/C の**網羅把握**。「何があるんだっけ」に、リストではなく**面積**で答える。

**主要ブロック**

1. **在庫マップ** — タグ（テーマ）をタイル状に並べ、**タイル面積を件数に比例**させる。ゴルフが画面の4割を占め、`language/vocabulary` が点として存在する——この**不均一さそのものを可視化**する。各タイルには concern 別の内訳バー（記事 / 章 / 観測 / 記録）。
2. **切り口ピル** — 発見系。`新着` / `久しく読んでいない`（git最終更新が古い順） / `孤立している N`（被リンク0） / `未読の章 N` / `一度も再読していない N`。押すと下のリストが差し替わる。
3. **編集済みの束（MOC）** — `moc/*.md` の `##` セクションを束カードとして列挙。「ゴルフ ▸ 7束」「健康 ▸ 4束」。**人間が編集した索引**を最上位の閲覧単位として復権させる。

**インタラクション**: タイルタップ → `/shelf/:tag`。棚板は「編集済みの束（そのタグに対応するMOCセクション）」を上に、「その他（束に入っていないもの）」を下に置き、**MOCの取りこぼしが目に見える**ようにする（`/mn-regen-moc` を回す動機になる）。

**空状態**: タグが3件未満のときは在庫マップを出さず、フラットな全件リストに落とす（初期の数週間はこちらが自然）。

### 6.3 デスク（`/desk`） — できること＋伝票 ★主要

**目的**: 課題A/B の直球回答。そして**サイト→Claude の書き込み動線の集約**。「何ができるか」を説明するページと「それをやる」ページを**同じページにする**のが肝（説明だけのページは読まれない）。

**主要ブロック**

1. **未送信の伝票** — 面や記事での操作が溜まったもの。`答え合わせ 7件` / `深掘り依頼 1件` / `次の章 1件` / `繋ぎ直し 2件`。**「ぜんぶコピー」** で1つのプロンプトになる。
2. **できること** — 5枚のカード。concern 名ではなく**目的語**で見出しを立てる。
   - **覚える** — 調べた事実を1枚ずつに分けて貯め、期日が来たら面に出す ／ 例文「〜を調べて notes にして」📋
   - **追う** — 1つの対象を同じ条件で観測して前回と比べる ／ 例文「今日のスイング見て」📋
   - **学ぶ** — トピックを知識グラフと読む順路で体系立てる ／ 例文「〜のアトラス作って」📋
   - **比べる** — 同じ項目で多数を貯めて並べる ／ 例文「これ記録して」📋
   - **思い出す** — 試合前に蓄積を束ねて予習する ／ 例文「アルゼンチンの予習させて」📋
3. **在庫の健康** — 決定的に数えられる「穴」と、その修復依頼のコピーボタン。
   - `想起の問いが無い記事 52` → `/mn-recall-backfill` 相当の依頼文
   - `数値未記入の観測 5` → session に `metrics:` を書かせる依頼文
   - `どこからも辿れない記事 7` → 繋ぎ直し依頼（候補タグ付き）
   - `未執筆の章 5` → `/mn-learn` 執筆依頼

**インタラクション**: 全ボタンがクリップボードコピー（atlas の先行実装と同じ）。コピー後1.8秒だけ「✓ コピーした」。

**空状態**: 伝票0件のときは伝票ブロックごと非表示。健康が全部0なら「在庫はきれいだ」と1行で締める（**バッジは出さない**＝原則3）。

### 6.4 探す（`/search`）

**目的**: J2（あれ何だっけ）。**編集された面が構造的に答えられない唯一のジョブ**なので、独立タブにする。

- **入力**: AppBar 直下に単一の入力欄（オートフォーカス）。

### 6.5 記事（`/note/:slug`）

**目的**: J2/J3 の着地点。**現状「行き止まり」なのが最大の欠陥**。

- 上: タグチップ（**押せる** → 棚板へ）。復習バッジは廃止。かわりに `最後に読んだ: 12日前`（ローカル影SRS）を小さく。
- 中: 本文（markdown）。
- 下1: **「ここへ来る道」** — バックリンクを**リンク元の一文つき**で列挙。concern 横断（他ノート／概念の本文／follow session／MOCセクション／log entry）。
- 下2: **想起** — `recall` があれば「この記事の問い」を表示し、「わかった / あやしい」を打てる（面と同じ影SRS へ）。
- 下3: **「次の1枚」** — 決定的に1枚だけ。優先順: ①同タグかつ未再読で最も期限超過 → ②被リンクを共有するノート → ③同じMOC束の隣。**「1枚だけ」なのが重要**（選ばせない）。

### 6.6 定点（`/follow/:name`）

- **上部**: snapshot（維持）＋ 次戦カウントダウン。
- **goal型**: タブ構成を廃止し、**推移グラフを最上段**へ。`series` から折れ線＋直近値＋前回比＋自己ベストマーカー。その下に重点課題（維持）、その下に**折りたたまれたセッション**（見出し＝profile の変遷タイムライン1行、開くと session 全文）。**現状「タイムライン＝全文縦積み」で読めないのを、1行サマリで畳む**。
- **interest型**: 次戦カード（**予習ブリーフがあれば見どころ3点を展開**）→ スカッド（維持）→ 日程 → 蘊蓄（タグ交差、維持）。
- 空状態: sessions 0 のとき「まだ観測がない」＋観測依頼のコピーボタン。

### 6.7 連載（`/atlas/*`）

**現状が基準線なので原則そのまま維持**。追加は3点のみ。
- 概念ページの `notes:` 蒸留リンクに加えて、**逆向き**（記事→概念）のバックリンクを記事側に出す。
- 「深掘りを依頼」ボタンを**押した瞬間コピーではなく伝票に積む**方式にも対応（デスクで束ねて送れる）。従来の即コピーも残す。
- 未執筆(stub)の章に「執筆を依頼」ボタン（デスクの健康と同じ導線）。

### 6.8 記録帖（`/log/:topic`）

- **entries ≥ 2 で「比較」ビューを既定**にする。`fields` の `number` / `rating` / `enum` / `bool` を列にした**横スクロールのソート可能テーブル**。列ヘッダタップでソート、`rebuy: true` の行をハイライト。

- 絞り込みピル（維持）。

## 7. 編成ルール

### 7.1 面割り（スロット）— ランキングではなく「段」

面はスコア順のフィードでは**ない**。**固定の段があり、各段に適格なカード型が優先順で並ぶ。**在庫が無ければ次の型に落ちる。これが「材料が枯れても面が死なない」ことの構造的保証。

| 段 | 枠 | 適格カード（優先順） | 全在庫切れ時 |
|---|---|---|---|
| 題字 | 1 | `masthead` | 常時ある |
| リード | 1 | `speed` → `milestone` → `chapter-new` → `brief` → `feature` → `revival` | **起きない**（記事1件以上なら `revival` が必ず出る） |
| 袖 | 0–2 | `countdown` → `slip`(伝票) | 段ごと非表示 |
| 再読 | 3 | `recall` | 「今日の再読はない」1行 ＋ `revival` を1枚繰り上げ |
| 連載 | 1 | `chapter` → `chapter-request` | アトラス0件なら `atlas-request`（学びたいトピックを立てる） |
| 特集 | 1 | `feature`(MOC節) → `feature`(タグ束) → `orphan` | 記事3件未満なら段ごと非表示 |
| 記録 | 0–2 | `series` → `compare` → `countdown` | 段ごと非表示 |
| 内訳 | 1 | `inventory` | 常時ある |

### 7.2 カード型の定義

すべて**ビルド時データ＋閲覧日＋localStorage のみ**から決定的に計算される。乱数は使わない（日付シードのハッシュで日替わりを作る）。

| 型 | 発火条件 | 鮮度 | 在庫切れ時の代替 |
|---|---|---|---|
| `speed` 速報 | 最新 `created` または `updated`(git) が **generatedAt から2日以内** のコンテンツ | 3日 | → `milestone` |
| `milestone` 節目 | goal follow の最新 session の `metrics` が、それ以前の全 session の最大/最小を更新 | 7日 | → `chapter-new` |
| `chapter-new` 新章 | `status: written` かつ `created` が7日以内かつ**未読**(localStorage) の概念 | 7日 | → `brief` |
| `brief` 予習 | `follows/*/briefs/` に、**未来7日以内の次戦**に対応するブリーフがある | 試合日まで | → `feature` |
| `feature` 特集 | **常時**。MOCセクション（3件以上のリンクを持つ節）を日替わりローテーション。無ければ `tagIndex` で3件以上のタグ束を生成 | — | → `revival` |
| `revival` 復刻 | **常時**。`kind:knowledge/insight` のうち git `updated` が最も古い群から日替わり選択 | — | （最終手段。記事1件でも出る） |
| `recall` 再読 | `kind: knowledge` かつ 影SRS/frontmatter の `next <= 閲覧日` | 判定するまで | 3枚に満たなければ埋めない |
| `chapter` 連載 | アクティブルート（最後に読んだ概念を含むルート）の**次の未読 written 概念** | — | 全読了 → `chapter-request` |
| `series` 記録 | goal follow で `series` の点が **2点以上** | 30日（最新 session から） | → `compare` |
| `compare` 比べる | log トピックで `entries.length >= 2` | — | 出さない |
| `countdown` 次戦 | `nextMatches` の最初の1件が**未来** | 試合日まで | 出さない |
| `slip` 伝票 | localStorage の未送信伝票が **3件以上** | — | 出さない |
| `orphan` 孤立 | 被リンク0 かつ アウトバウンド0 の記事が1件以上 | — | 出さない |

### 7.3 「材料が枯れる」問題への回答（論点1）

3つの機構で解いている。

1. **紙面は閲覧日で組む。** ビルド時にやるのは素材の下ごしらえだけ。「今日どれを載せるか」はブラウザが `new Date()` で決める。**push が2週間止まっても、再読3枚・特集・復刻・連載は毎日入れ替わる。**（実装上の帰結として、`due` フラグのビルド時計算は廃止し `srs.next` をそのまま渡す。）
2. **常時在庫のカード型を2つ用意した。** `feature`（テーマローテーション）と `revival`（最古参の再登場）は**記事が1件でもあれば必ず出る**。リード枠は必ずこの2つまで落ちるので、**空のリードは構造的に発生しない**。
3. **主燃料が「新着」ではなく「忘却」。** 90記事のうち58件は一度も再読されていない。1日3枚で回しても**約1ヶ月分の在庫**があり、再読するたび影SRSで次回が先送りされるので、**在庫は使うほど未来に分散する**。新規投入がゼロでも編集は成立する。

**日替わりローテーション（決定的）**:

```js
const dayIndex = (d) => Math.floor(d.getTime() / 86400000);      // 1970からの日数
const hash32   = (s) => [...s].reduce((h,c)=>(h*31+c.charCodeAt(0))|0, 7) >>> 0;
// 特集: テーマ配列を安定ソートし、日で回す
const featureOfDay = (themes, today) => themes[ dayIndex(today) % themes.length ];
// 復刻: 最終更新が古い上位20件から日で1件
const revivalOfDay = (oldest20, today) => oldest20[ dayIndex(today) % oldest20.length ];
// 再読の日替わり加点: 毎日およそ1/7の記事が浮上する
const rotationBonus = (slug, today) => ((hash32(slug) + dayIndex(today)) % 7 === 0 ? 20 : 0);
```

## 9. ③想起と定着 の解 ★本案の尖り

### 9.1 問題の整理

- 静的サイトなので **`srs` を書き戻せない**。
- knowledge 59件が**全件期限切れ**で、「復習期限 59」は達成不能な数字として点灯し続けている。
- `/mn-review` は1セッション1問。59件を消化するには59回 Claude Code を起動する必要があり、**構造的にループが回らない**（review-log が1行なのはユーザーの怠慢ではなく設計の帰結）。

### 9.2 解 — 3つの手

#### 手1: 「期限」を数から**順番**に変える

- **「復習期限 N件」という表示をサイトから全廃する。** KPIタイルも `DueBadge` も削除。
- かわりに面のセンターに **「今日の再読」ちょうど3枚**。残り56件はどこにも数字として出さない。
- キューは決定的に計算される:

```js
// クライアント。today = new Date()。shadow = localStorage の影SRS
function recallQueue(site, shadow, today) {
  return site.notes
    .filter(n => n.kind === 'knowledge')
    .map(n => {
      const s    = shadow[n.slug] ?? n.srs ?? {};
      const next = s.next ?? n.created;
      const over = daysBetween(today, next);
      if (over < 0) return null;                       // 期日前は出さない
      return { n, score:
          Math.min(over, 120)                          // 遅延（120日で頭打ち＝古参の独占を防ぐ）
        + (s.last ? 0 : 25)                            // 一度も再読していない
        + Math.min(n.backlinks.length, 6) * 4          // ハブ度（重要な記事）
        + (n.recall ? 8 : 0)                           // 良い問いが用意されている
        + rotationBonus(n.slug, today) };              // 日替わり浮上（§7.3）
    })
    .filter(Boolean).sort((a,b) => b.score - a.score).slice(0, 3);
}
```

- ポジティブなカウンタだけ残す: **「今週 12件 再読した」**（影SRSの `last` から算出）。借金ではなく成果を数える（原則3）。

#### 手2: 「クイズUI」ではなく **伏せ記事**として出す

muninn のノートは**タイトルが言い切り形**（規約）＝**タイトル自体が答え**。だから想起カードは**タイトルを伏せ、`recall` の問いだけを見せる**。

```
  ┌────────────────────────────┐
  │ ゴルフ / 飛距離            │   ← タグだけ見せる（文脈の手がかり）
  │                            │
  │ 芯を食う（ミート率）で稼げ │   ← recall（frontmatter）
  │ る距離に上限があるのはなぜ │
  │ か。大幅増の本丸は何か。   │
  │                            │
  │      〔 めくる 〕          │
  └────────────────────────────┘
            ↓ tap
  ┌────────────────────────────┐
  │ ドライバー飛距離はほぼボー │   ← タイトル（＝答え）
  │ ル初速で決まり、芯化は"タ  │
  │ ダの距離"だが上限約1.5…    │
  │                            │
  │ ドライバー飛距離を決める主 │   ← 本文全文（平均1.8KB＝1分以内）
  │ 因はボール初速で、それは…  │
  │                            │
  │  〔 わかった 〕〔 あやしい 〕│
  └────────────────────────────┘
```

- **これは「テスト」ではなく「読み物」である**——ここが本案の設計思想。新聞のコラムを読む感覚のまま、想起が起きる。「クイズを始める」という**モード切替がない**ので、起動コストがゼロ。
- `recall` が無いノートへのフォールバック: タイトルと本文を伏せ、**タグ＋作成日＋バックリンクの文脈一文**だけを見せて「これ、何の話だったか？」→ めくる。**degrade するが壊れない**。

#### 手3: 判定は **ローカル影SRS** で即効かせ、**答え合わせ伝票**で正本に落とす

```js
// わかった=q4 / あやしい=q2。mn-review と完全に同じ SM-2 簡易版を使う（＝収束する）
function gradeLocal(prev, ok, today) {
  let { interval = 0, ease = 2.5 } = prev ?? {};
  const q = ok ? 4 : 2;
  if (q < 3) interval = 1;
  else interval = interval === 0 ? 1 : interval === 1 ? 6 : Math.round(interval * ease);
  if (q >= 3) ease = Math.max(1.3, ease + (0.1 - (5-q)*(0.08 + (5-q)*0.02)));
  return { last: today, interval, ease, next: addDays(today, interval) };
}
// localStorage
//   mn.recall.shadow  : { slug: {last, interval, ease, next} }   ← キューが即座に反映
//   mn.recall.pending : [ {slug, verdict, date} ]                ← 未送信の伝票
```

- **その場で効く**: 「わかった」を押したノートは影SRSにより**明日はもう出ない**。次は6日後。**サーバに何も送っていないのに、体験としてはSRSが動いている**。これが「ループが回る」ことの実体。
- **正本に落とす**: デスクの「答え合わせ N件」から1タップでコピー:

```
/mn-review 一括反映（サイト由来）。以下は muninn のサイトで自己採点した再読の結果。
出題はせず、各ノートの srs を SM-2 で更新し review-log.jsonl に追記して commit/push して。
わかった=q4 / あやしい=q2 で採点済みとして扱うこと。

- golf-driver-distance-is-ballspeed-smash-is-free-but-capped-300-needs-speed : わかった (2026-07-31)
- warm-bath-activates-parasympathetic-serotonin-endorphin : あやしい (2026-07-30)
- anaximander-apeiron-indefinite-arche : わかった (2026-07-30)
...
```

- **自己修復する同期**: 次のビルド後、`site.notes[slug].srs.last >= pending.date` なら「反映済み」と判定して `pending` から削除し、影SRSをサーバ値で上書きする。**ローカルとサーバが同じ SM-2 式を使っているので、値は必ず一致する。** 送信を忘れても影SRSで日々の体験は成立し、送った瞬間に正本が追いつく。乖離が発生しない設計。

### 9.3 「編集された面」の弱点への正面回答（論点4）

**編集は既定であって唯一ではない。** 4タブのうち、**面は1枚**にすぎない。

| 弱点 | 受け皿 | どう答えるか |
|---|---|---|
| **ピンポイント想起（あれ何だっけ）** | **探す（`/search`）** | 全concern・**本文込み**の全文検索。スニペット付き。0件なら「調べて記録してもらう」プロンプトに変換。**ボトムタブの3枚目＝常時1タップ**で到達可能。現状は `/notes` の中にタイトル検索が埋まっているだけだった |
| **網羅把握（何があるんだっけ）** | **棚（`/shelf`）** | 在庫マップで**全在庫を面積で一望**。「ゴルフが半分、あとは細い山」という現実の偏りを**隠さずに見せる**。切り口ピル（孤立している／久しく読んでない／一度も再読していない）で90件のロングテールに角度をつけて入れる |
| **システムの把握（何ができるんだっけ）** | **デスク（`/desk`）** | 目的語カード＋例文＋コピー。説明と実行が同じページ |

面が担うのは「読む姿勢」だけ。**面で答えられないジョブには、面が答えようとしない。**そこが本案の潔さである。

## 11. 捨てるもの・トレードオフ・リスク

### 捨てるもの（明示的に）

| 捨てるもの | 理由 |
|---|---|
| **ホームのKPIタイル 2×2** | 「復習期限59」を筆頭に、**数字が行動に繋がっていない**。数えることをやめる |
| **`DueBadge`（復習バッジ）を全画面から** | 常時点灯して意味を失っている。麻痺の原因そのもの |
| **`/notes` の90件フラットリスト** | タイトル文字列以外の手がかりが無い。棚と検索に吸収 |
| **`/moc/:slug` の生 markdown 表示** | 索引という機能に対して素朴すぎる。セクション構造化して棚と特集へ |
| **`/logs` のトピック索引ページ** | トピック1件のために1ページは過剰。棚と面に吸収 |
| **follow の「タイムライン全文縦積み」** | 読めない。1行サマリに畳んで開閉に変更（情報は失わない） |
| **「一覧で全部見える」という保証** | 面はその日の編集結果しか出さない。**面に出なかったものは面には無い**。棚と検索が代替する |

### トレードオフ

1. **編成ロジックがビルドとクライアントに分散する。** 「素材＝ビルド／編成＝クライアント」という境界線を守らないとすぐ壊れる。→ `edition.js` 1ファイルに編成を集約し、**カード型の定義テーブル（§7.2）をそのままコードにする**ことで守る。
2. **markdown スキーマが増える（`recall` / `metrics` / `chart_metrics` / `briefs/`）。** 正本を汚す。→ すべて**任意フィールド**で、無ければ degrade する設計にした。過去コンテンツの一括書き換えは `recall` 59件と `metrics` 5件のみ（backfill 済みなら以後は skill が自動で書く）。
3. **編集は本人の期待とズレることがある。** 「今日それじゃない」と思う日が必ず来る。→ **棚と検索がその日の逃げ道**。面から棚へは1タップ。逃げ道が無ければこの案は独善になる。
4. **「今日の再読3枚」は少ない。** 一気に20件消化したい日には物足りない。→ 3枚消化後に「もっと読む」で次の3枚を出す（**ただし既定では出さない**。既定を3枚に固定することが麻痺解除の本体）。
5. **git 依存が増える。** `fetch-depth: 0` を忘れるとビルドが `updated`/`issue` を失う。→ git メタが取れないときは `created` にフォールバックし、**ビルドは落とさない**（logs のスキーマ検証と違い、ここは砦にしない）。

### リスク

| リスク | 影響 | 緩和 |
|---|---|---|
| **`recall` の backfill をやらないまま Phase 1 を出す** | 面の心臓部（再読カード）が「タイトル伏せただけ」の弱いものになり、刷新の主張が空振りする | **Phase 1 の完了条件に backfill を含める**。59件・1件1行なので現実的。degrade 設計はあるが、それは保険であって出荷基準ではない |
| **答え合わせ伝票を誰も送らない** | 正本の `srs` が永久に止まり、review-log は1行のまま | 影SRSにより**送らなくても日々の体験は成立する**（＝失敗しても現状より悪くならない）。加えて伝票3件以上で面の袖に出す・デスクに常設・一括コピー1タップ、と摩擦を極限まで下げた。**それでも送られないなら「Webから想起する」ことだけが残る**——それでも現状（review-log 1行）より良い |
| **`feature` がMOCに依存し、MOCが古い** | 特集が古い束を出し続ける | タグ束フォールバックが常にある。加えて棚板が「束に入っていない記事」を可視化するので、`/mn-regen-moc` を回す動機が生まれる（依存が**改善圧力**に転化する） |
| **コンテンツ量が少なすぎる面（logs 1件・atlas 1件）** | 記録段・連載段が貧相 | 空状態を「依頼カード」にした（`compare` 不発時は「もう1件記録すると比べられる」＋コピーボタン）。**空状態が導線になる**設計 |
| **ゴルフ47%の偏りが面を支配する** | 毎日ゴルフの再読・ゴルフの特集になる | `feature` はテーマを**均等ローテーション**（件数で重み付けしない）。`recall` は日替わり浮上ボーナスで分散。**在庫マップでは偏りをあえて隠さず見せる**（隠すのは不誠実） |

## 12. 成功の定義

1人用なので定量指標は無理筋。**行動が変わったかで見る。**

| # | 成功の兆候 | 現状 |
|---|---|---|
| 1 | **`review-log.jsonl` が伸び始める。** 1行 → 月20〜40行のペース。しかも「1問ずつ」ではなく**答え合わせ伝票が数件〜十数件まとめて**入る | 1行（2026-06-20 以降ゼロ） |
| 2 | **書いた記憶のないノートを、週に一度は開く。** 復刻・特集・棚の「久しく読んでない」経由で、6月に書いたまま忘れていた記事に再会する | 「直近の更新7件」を見たら終わり |
| 3 | **「何ができるんだっけ」を Claude に聞かなくなる。** デスクの例文をコピーして投げるようになる。とくに**サイトで見つけた穴**（孤立記事・stub章・空の比較表）から依頼が始まる | サイトに説明がゼロ |
| 4 | **観測した直後に、Claude ではなくサイトを開く。** グラフが動くから見に行く。「HS46.3で自己ベスト」が線として見える | 数値は静止タイル、推移は markdown の表 |
| 5 | **記事を開いて行き止まりで戻る、が減る。** 「ここへ来る道」か「次の1枚」で先へ進む回数が、戻る回数を上回る | 記事は全部行き止まり |
| 6 | **PWAを「暇なとき開く」ようになる。** 用事があるから開くのではなく、**読むものがあるから開く**。これが達成できたら、muninn は道具から媒体になっている | 用事があるときだけ |

**逆に、次が起きたら失敗である**（正直に書いておく）:
- 面をスクロールせず、毎回すぐ検索タブに逃げる → 編集が信用されていない。編成ルールの重み設計をやり直す
- 「今日の再読」を1週間押さなくなる → 伏せ記事という形式が本人に合っていない。素直に一覧型クイズへ戻す
- 伝票が30件を超えて放置される → 送信の摩擦がまだ高い。PWA の共有シートや URL scheme 経由の起動を検討する

## 付録: この案の一行要約

**muninn は「探す道具」をやめて「毎朝ちがう面が出る自分だけの日報」になる。編集の燃料は新着ではなく忘却で、忘却は在庫が尽きない。そして紙面の心臓は "伏せ記事" ——テストではなく読み物として想起が起き、判定はローカルで即効き、溜まったら伝票1枚で正本に落ちる。**
