## 0. まず、現状分析に一つ訂正を入れる

提案の前に、事実を一つ更新しておく。**「muninn のリンクは疎である」は正しくない。** 実測した。

```
notes/ 内の [[wikilink]] 総数        282 本（90ノート = 平均 3.1本/ノート）
アウトリンク 0 本のノート             2 件
被リンク 0 の「真の孤児」（moc除く）   2 件（cliche / zettelkasten）
複数タグを持つノート                  9 / 90 件
```

リンクは疎ではない。**密度は十分にある。問題は密度ではなく「配置」だ。**

タグ分布と実際のリンクを重ねると、muninn は 1 個のグラフではなく**ほぼ交わらない 7〜8 個の島**でできている。

```
ゴルフ 42 ●●●●●●●●●●●●●●●●●●●●●  ← 島の中は超高密度（MOCに9セクション）
からだ 28 ●●●●●●●●●●●●●●            ← 髪/肌/入浴/睡眠の4クラスタ
サッカー 7 ●●●●                      ← + follow entities 10
宇宙   7 ●●●●
哲学   7 ●●●●                      ← + atlas concepts 11
中東   6 ●●●
                島と島をつなぐリンク ≒ 0 本
```

つまり真の症状はこうだ。

> **島の中はよく歩ける。だが「島がいくつあって、どれがどれくらいの厚みなのか」を見る画面が存在しない。**
> ホームは concern（機能）で 7 分割され、`/notes` は 90 件のフラットリスト。**どちらも「島」を見せていない。**

オーナーの「いっぱい情報があるはずなのに、何があるのかわからない」は、**ノートが見つからない**という訴えではなく、**自分の知識の地形が見えない**という訴えである。ここを外すと刷新は失敗する。

そして重要な帰結が 2 つ。

1. **90ノードの force-directed グラフを描くと、7 個の団子が浮かぶだけの絵になる。** 情報量ゼロ。案Bの素朴な実装は最初から死んでいる。
2. **グラフの単位を「ノード」から「島」に上げれば、全体は 8 ノードで描ける。** 毛玉は物理的に発生しない。

この 2 点が、本案の設計全体を決めている。

## 1. コンセプト

> ### muninn を、5つの機能ではなく **8つの島がある一枚の地続きの土地**にする。

- **島（テリトリー）が第一階層になる。** 「ノート／フォロー／アトラス／ログ」ではなく「ゴルフ／からだ／哲学」で分かれる。ゴルフの島には、知識ノート42枚も、飛距離の定点観測も、MOCの索引も**同じ地面の上に**並ぶ。concern の壁を IA から消す。
- **グラフは「ページ」にしない。** muninn に `/graph` は作らない。グラフは**全ページの下部に必ず居る「つながり」ブロック**という周辺視野になる。俯瞰したいときの全体図は、ノードではなく**島レベル（8点）の星図**として、ホームの一等地に常設する。
- **「何ができるか」は一覧で説明せず、行く先々の「たずねる」ボタンに解体する。** ノートを見ていれば「これでクイズを出して」、島にいれば「この島の索引を作り直して」。機能名を覚える必要をなくす。

## 2. 設計原則（判断が割れたときの拠り所）

### 原則1: 一度に描くノードは 12 個まで。超えたら「束」に畳む
グラフ可視化の失敗はすべて「全部見せようとした」ことから起きる。全体図は島（8点）。島の中は**束（MOC の `##` 見出し）**単位で 9 点。束の中身がノード。**どの階層でも視界に入るのは 12 点以下**。この上限を破る画面を作らない。

### 原則2: レイアウトは決定的。force-directed を使わない
既存 `atlas.jsx` の `layoutGraph()`（`requires` 最長鎖で深さを決める）は正解の方向。**同じデータなら毎回同じ場所に描かれる**ことが、記憶の手がかりになる。物理シミュレーションで毎回ぬるぬる動く図は、覚えられない＝ナビゲーションにならない。

### 原則3: 図は必ずリストで代替可能にする。図は近道であってUIの本体ではない
「つながり」の正本はテキストリスト（既存 `Concept` ページの実装が既にこの形で、現状分析でも「実装の完成度が最も高い」と評価されている）。SVG はその**上位互換の近道**として置くだけ。図が読めない状況（小さい画面・スクショ・老眼）でも情報に到達できることを保証する。

### 原則4: 自動生成のエッジは、人力のエッジと**同じ強さで表示しない**
`[[wikilink]]` は「本人がそうだと言った」宣言。語彙一致は「機械がそう推測した」。この 2 つを同じ見た目で並べると、ナレッジベースの信頼が壊れる。人力＝実線・見出し付き。自動＝別ブロック・弱色・「思わぬ隣人」という**推測であることを名乗る**ラベル。

### 原則5: 麻痺するシグナルは出さない
「復習期限 59」は 59/59 が該当していて、**常時点灯＝情報量ゼロ**。これは指標ではなく壁紙である。刷新後に置くシグナルは「**動くもの**」だけ。動かない数字は KPI タイルごと捨てる。

| 根本 | 内容 | 本案のどの要素が効くか |
|---|---|---|
| **根本1** | IA がファイルの置き場所の写像。concern 名で画面が分かれている | **テリトリー（島）を第一階層にする。** ホーム＝星図（8島）、`/t/:id`＝島。concern はページ分割の軸から降りて、島の中の「層」（知る／追う／記録）という**タブの一段**に格下げされる。`/notes` `/logs` という concern 単位のインデックスページは廃止 |

| **根本3** | ③想起と定着 が Web に存在しない | **SRS を Web に載せない。「復習」を「回遊のついでの想起」に作り変える**（§9）。命題タイトルを表にして本文を隠す＝カードがそのまま自己テスト。採点・スケジュール更新は Claude へのプロンプト生成で橋を架ける |
| **根本4** | データ構造のリッチさに表示が追いついていない（数値は静止、markdown は素通し、タグは装飾） | **統一ノードシェルの「本体スロット」を型別コンポーネントで差し替える**（§6.3）。follow(goal) は sessions の数値表をビルド時にパースして**推移スパークライン**に。log は**比較テーブル＋ソート**に。タグは押せるようにする（島＋型のフィルタとして機能） |

| 課題 | 生の声 | 効く要素 | 効き方 |

## 4. サイトマップ / IA

**5ルート**（現状 9 ルート → 5）。ページを減らし、1ページあたりの働きを増やす。

```
/                          ホーム — 星図（8島）＋今日の入口3枚＋新着
│
├─ /t/:territory           テリトリー（島） ← 第一階層
│    ├ 知る    …… 束（MOCの##見出し）ごとのノート／概念
│    ├ 追う    …… その島の follow（推移・観測・次戦）
│    └ 地図    …… 束レベルの決定的レイアウト図（≤12点）
│
├─ /n/:type/:slug          ノード（統一シェル） ← 第二階層
│    type ∈ note | concept | entity | session | logentry | follow | atlas | logtopic
│    共通: ヘッダ(島への横移動) / 本体(型別) / つながり / たずねる / 前後
│
├─ /find                   さがす — 全文検索・型/島/期間フィルタ・発見（ランダム/未読/最近）
│
└─ /ask                    たずねる — 文脈アクション ＋ コマンド帳 ＋ muninn の仕組み
```

### 廃止するルート

| 廃止 | 行き先 |
|---|---|
| `/notes`（90件フラットリスト） | `/t/:id`（島）と `/find`（検索）に分解。**「全ノート一覧」という画面自体を持たない** |
| `/moc/:slug`（生 markdown） | `/t/:id` の「知る」に吸収。MOC は**表示物ではなく島の索引データ**になる |
| `/logs`（トピック一覧） | ホームの星図（コーヒーは1つの島） |
| `/follow/:name`, `/follow/:name/player/:slug` | `/n/follow/:name`, `/n/entity/:slug` |
| `/atlas/:slug`, `/atlas/:slug/concept/:cslug` | `/n/atlas/:slug`, `/n/concept/:cslug` |
| `/log/:topic`, `/log/:topic/entry/:slug` | `/n/logtopic/:slug`, `/n/logentry/:slug` |

**旧URLは HashRouter のリダイレクト表で受ける**（PWA のホーム追加やブックマークが死なないため）。

## 5. ナビゲーション構造

### グローバルナビ：ボトムタブ 3 つ（新設）

```
   ⌂ ホーム        ⌕ さがす        ✳ たずねる
```

- **固定表示**（`env(safe-area-inset-bottom)` 対応）。現状の「グローバルナビが存在しない」を直接解消する。
- タブを 3 つに絞る理由：**タブ数＝ユーザーが覚える機能数**である。5 concern を 5 タブにしたら課題A/Bは何も解決しない。「見る（ホーム）／探す／頼む」の 3 動詞だけを覚えてもらう。

### 階層の深さ：最大 3

```
ホーム（星図）─▶ 島 ─▶ ノード
                        └─▶ ノード（つながりで横移動・無限）
```

「島 → ノード」の 2 タップで**必ず**目的物に着く。現状の「ホーム → セクション → 詳細」と深さは同じだが、**中間層が「機能」から「自分の興味」に変わる**のが本質。

### 横移動（ここが本案の生命線）

| 手段 | 場所 | 内容 |
|---|---|---|
| **つながりブロック** | 全ノード詳細の下部（例外なし） | 前提／発展／対比／深掘り／**被リンク**／共起／思わぬ隣人 |
| **島バッジ** | 全ノード詳細のヘッダ右 | `ゴルフ ›` — 常に「今いる島」へ 1 タップで戻れる |
| **束内の前後** | ノード下部 | 同じ束の前後（atlas ルートの prev/next を全型に一般化） |
| **押せるタグ** | ノード・島 | タップ → `/find?tag=...`（現状「ただの装飾」を機能化） |
| **本文中の `[[wikilink]]`** | 本文 | 既存の `Md` を維持 |
| **検索** | 全画面のボトムタブ | どこからでも 1 タップ |

**「行き止まりのページを 1 つも作らない」** ——これを実装レベルで保証するのが、次節の統一シェル。

## 6. 各ページの設計

### 6.1 `/` ホーム

**目的（ジョブ）**: J1「今日やることある?」／ J3「暇つぶし・回遊」／ J8「入れたものを確認」。そして最重要の **J9「何があるんだっけ」に、星図という一枚の絵で答える**。

```
┌──────────────────────────────────┐
│ muninn                2026-07-31 │  極薄バー
├──────────────────────────────────┤
│                                  │
│     ●ゴルフ           ●からだ     │   ★ 星図（Constellation）
│      42                28        │     ・8島だけ。決定的レイアウト
│         ╲            ╱           │     ・円の大きさ = ノード件数
│      ○サッカー ── ●哲学           │     ・明るさ = 最近触った度合い
│        17              18        │       （localStorage）
│                                  │     ・細い線 = 島どうしの語彙エッジ
│   ○中東    ○宇宙    ○コーヒー      │     ・冷えている島は暗く沈む
│     6        7         1         │     ・高さ約190px / 横スクロール無し
│                                  │
│   8つの島 · 137ノード · 今週 +3   │
├──────────────────────────────────┤
│ 今日の入口                        │   ★ 固定KPIを捨てて置く3枚
│ ┌──────────────────────────────┐ │
│ │ ▸ 続きから                    │ │   ①最後に読んでいた場所の続き
│ │   哲学 / ルート「歴史でたどる」 │ │
│ │   次は「アリストテレス」        │ │
│ └──────────────────────────────┘ │
│ ┌──────────────────────────────┐ │
│ │ ? 思い出せるか                 │ │   ②タイトルだけ見せる＝自己テスト
│ │  「ヘッドスピードは腕を速く振る │ │     本文は隠れている
│ │   ことではなく…」              │ │
│ │                     [ めくる ] │ │
│ └──────────────────────────────┘ │
│ ┌──────────────────────────────┐ │
│ │ ❄ しばらく行っていない          │ │   ③最も長く触れていない島
│ │   中東 — 34日                  │ │
│ └──────────────────────────────┘ │
├──────────────────────────────────┤
│ 新着                              │   （現状で唯一機能しているブロック）
│  ● コーヒー豆：エチオピア…   2日前 │   色ドットは concern 色ではなく島色
│  ● ゴルフ：2026-07-27 の観測 4日前 │
│  ● 哲学：ト・アペイロン      4日前 │
│                        すべて  ›  │
├──────────────────────────────────┤
│   ⌂ ホーム    ⌕ さがす    ✳ たずねる │
└──────────────────────────────────┘
```

**重要なインタラクション**
- 星図の島タップ → `/t/:id`。**長押しでその島の在庫がポップ**（「知識42・観測5・索引9束・未整理3」）。
- 「思い出せるか」の `[めくる]` → その場で本文が展開（画面遷移しない）。展開した瞬間に localStorage の `touched` を更新。**これが muninn の"復習"の実体**（§9）。
- 「今日の入口」3枚は日付シードの決定的選択。**同じ日に何度開いても同じ**（ランダムに変わると「さっきのアレ」が消える）。

**空状態**: 島が 0 個 → 星図の位置に「まだ島がない。Claude に `/mn` で何か記録すると、ここに最初の島ができる」＋コピーボタン。3枚のカードは条件を満たさないものを消すのではなく、**その枠に「まだ無い理由」を書く**（例:「観測がまだ1件。2件目からここに変化が出る」）——空状態を機能の説明の場に使う。

## 7. 接続モデルの設計

### 7.1 ノード型（8種を1つの集合に統一）

```js
node = { id, type, title, gist, territory, date, tags[], due?, status? }
type ∈ note | concept | entity | session | logentry | follow | atlas | logtopic
id  = `${type}:${slug}`   // 名前空間衝突を防ぐ（現状 wiki.js は型を跨いで名前解決していて危うい）
```

`moc` はノードにしない。**MOC は「島の索引データ」に格上げされ、ノードであることをやめる**（生 markdown ページを廃止する根拠）。

### 7.2 エッジ型と生成規則

| # | 型 | 出所 | 強度 | 生成規則 | 現状の本数 |
|---|---|---|---|---|---|
| 1 | `wikilink` | 人力 | **強** | 全 md の `[[t]]` を抽出 → `resolveTarget` で型付き id に解決。**双方向にインデックス** | 282（notes）＋ 21（sessions・**現状ビルドで捨てられている**）＋ entities 20+ |
| 2 | `distill` | 人力 | **強** | `concept.notes[]` → note。**逆向き（note→concept）を新規に生成** | 7 |
| 3 | `member` | 構造 | **強** | follow→entity / follow→session / atlas→concept / logtopic→logentry / territory→* | 全件 |
| 4 | `cluster` | 人力 | **強** | MOC の `##` セクション内に並ぶノート同士（＝本人が同じ見出しに置いた） | golf 9束・health 4束・football 3束・middle-east 2束・science 1束 |
| 5 | `cooccur` | 自動 | 中 | **同一コンテナ（session / concept本文 / logentry）から共に参照された**ノート対 | 例: 2026-07-27 の観測が引く4ノートは互いに共起 |
| 6 | `lexical` | 自動 | 弱 | **異なる島に属するノード間**の語彙一致（TF-IDF コサイン）。上位2本/ノードのみ | 新規（島間の唯一の橋） |
| 7 | `temporal` | 自動 | 弱 | 同日〜3日以内に created されたノート（＝同じ調査セッション由来） | 新規 |

### 7.3 タグを**エッジにしない**という判断

タグ共起を辺にすると、`sports/golf` の 42 件が総当たりで **861 本**の辺を生む。密度は上がるが情報量はゼロ（「ゴルフのノートはゴルフのノートと関係がある」）。

> **タグ＝島の境界。wikilink＝島内の道。この役割分担を混ぜない。**

これは他案が踏みやすい地雷なので明記しておく。**タグ共起は接続の答えではない。** 唯一の例外が §7.4。

### 7.4 「島と島をつなぐ橋」— 自動推論を使う唯一の正当な場所

実測どおり、人力リンクは**すべて島の内側**にある。島の外への橋は **1 本も無い**。ここだけは自動推論の価値が本物になる。

```js
// 日本語なので形態素解析なし。カタカナ列・漢字列・ラテン語・数値+単位をトークン化
const TOKEN = /[ァ-ヶー]{2,}|[一-龥]{2,}|[A-Za-zＡ-Ｚａ-ｚ]{3,}|[0-9]+(?:\.[0-9]+)?[a-z%°]*/g;

const df = new Map();                       // 文書頻度
for (const n of nodes) for (const t of new Set(tokens(n.title + n.body))) inc(df, t);

function vec(n) {                            // TF-IDF ベクトル（上位40語に切る）
  const tf = count(tokens(n.title + n.body));
  return topN([...tf].map(([t, c]) => [t, c * Math.log(N / df.get(t))]), 40);
}

for (const [a, b] of pairs(nodes)) {
  if (a.territory === b.territory) continue;      // ★ 同じ島は作らない（自明だから）
  const sim = cosine(vec(a), vec(b));
  if (sim >= THETA) cand.push({ from: a.id, to: b.id, type: 'lexical', weight: sim,
                                shared: topSharedTokens(a, b, 3) });  // 理由を必ず持たせる
}
edges.push(...topPerNode(cand, 2));               // 1ノードあたり最大2本。爆発を止める
```

**設計上の要点 3 つ**
- **同じ島の中では生成しない。** ゴルフ同士が似ているのは当たり前で、ノイズにしかならない。
- **必ず「理由」を持たせる**（共有トークン上位3語）。UI では「共通語彙: 交感神経, 力み」と表示する。**理由の言えない自動リンクは出さない。**
- **1ノードあたり2本まで。** これがあるから毛玉にならない。閾値 `THETA` はビルド時に分布をログ出力して調整（初期値 0.18、生成本数が全体で 40 本を超えるなら上げる）。

期待される実際の橋の例（実データから）：
- 「ヘッドスピードは"ブレーキを外す"効率化」（ゴルフ）⇄「呼吸停止は交感神経を上げる」（からだ）── 交感神経／力み
- 「アルケー＝万物の根源」（哲学）⇄「重元素は星で作られる＝我々は星屑」（宇宙）── 根源／生成
- 「ヒズボラは国家内国家」（中東）⇄「レバノンの宗派配分制」（中東・同島なので生成せず）

**この機能の名前は「思わぬ隣人」。** 検索でもリンクでもない、**muninn が自分の代わりに気づいてくれる**唯一の場所として位置づける。

### 7.5 モバイルでの可視化 —「毛玉にならない」具体策

**muninn に `/graph` ページを作らない。** グラフは 3 つのスケールに分解され、それぞれが 12 点以下に収まる。

| スケール | 場所 | 点の数 | 描き方 |
|---|---|---|---|
| **島レベル** | ホームの星図 | **8** | 決定的レイアウト（島サイズで降順→2〜3行に配置）。円＝島、細線＝`lexical` エッジの本数。360px 幅・高さ190px に収まる。**横スクロールしない** |
| **束レベル** | 島の「地図」タブ | **≤12** | 束を長方形、束間の `wikilink` 本数を線の太さに。既存 `layoutGraph()` の深さ方式を流用 |
| **近傍レベル** | ノード詳細 | **1ホップのみ** | **図を描かない。型別の見出し付きリスト。** 既存 `Concept` ページの「つながり」実装が完成形（現状分析でも最高評価）——これを全型に横展開する |

そして原則1〜3の再掲：**12点超は束に畳む／レイアウトは決定的／図はリストで代替可能。** この 3 つを守る限り、毛玉は構造的に発生しない。

**「グラフの絵を見せれば解決」ではない。muninn のグラフは、絵ではなく"どのページにも下部に必ず居るリスト"として実装される。** これが本案の中核主張である。

### 8.2 テリトリー定義（過去コンテンツの一括書き換えを避ける）

**90 個のノートには一切触らない。** 島の定義は **seed 側の frontmatter 6〜10 ファイルだけ**に集約する。

```yaml
# moc/golf.md の frontmatter に3行足すだけ
territory: golf
territory_label: ゴルフ
territory_tags: [sports/golf]
```

```js
// ---- territories ----
const seeds = [...mocs, ...follows, ...atlases, ...logtopics].filter(s => s.territory);
const terrs = groupBy(seeds, s => s.territory);          // 同じ id の seed はマージ

// ノートは自分の第1タグが territory_tags に一致する島へ（複数該当なら宣言順で先勝ち）
for (const n of notes) {
  n.territory = terrs.find(t => t.tags.some(tag => n.tags.includes(tag)))?.id ?? 'misc';
}
// concept/entity/session/logentry は親（atlas/follow/logtopic）の島を継承する
```

宣言が無い場合のフォールバックは「タグ第2階層で自動島」。**宣言ゼロでも動き、宣言するほど島が良くなる**——段階導入できる形にしておく。

### 8.3 束（cluster）＝ MOC の `##` 見出し

```js
// MOC の本文を `##` で分割し、各セクション内の [[wikilink]] をメンバーにする
function clustersFromMoc(moc) {
  return moc.body.split(/^## +/m).slice(1).map(sec => ({
    label: sec.split('\n')[0].trim(),
    members: wikiTargets(sec).map(resolveId).filter(Boolean),
  }));
}
// MOC の無い島: atlas.routes を束に / logtopic.display.filters を束に / 無ければ日付順
// unfiled = その島のノート − 全束メンバー   ← 索引の陳腐化を site.json に出す
```

**「MOC は手書きなので古びる」という現状分析の指摘を、`unfiled` という一列のデータで可視化する。** これが `/t/:id` の `⚠ どの束にも入っていない` になる。

### 8.4 バックリンク（最優先・最小コスト）

```js
const edges = [];
const push = (from, to, type, w = 1, reason) => {
  if (from && to && from !== to) edges.push({ from, to, type, weight: w, reason });
};

for (const n of allNodes)                       // ★ sessions も含める（現状バグの修正）
  for (const t of wikiTargets(n.body)) push(n.id, resolveId(t), 'wikilink');

  for (const s of c.notes) push(c.id, `note:${s}`, 'distill');
for (const t of terrs)
  for (const cl of t.clusters) for (const [a, b] of pairs(cl.members)) push(a, b, 'cluster', 0.5);

// 隣接リストを双方向で作る ← ここが「行き止まり」を殺す1行
const adj = {};
for (const e of edges) {
  (adj[e.from] ??= { out: [], in: [] }).out.push(e);
  (adj[e.to]   ??= { out: [], in: [] }).in.push(e);
}
```

### 8.5 セッションの数値パース（follow(goal) の推移）

golf の session は `| 指標 | 値 |` の markdown テーブルで統一されている（5回分すべて）。

```js
const METRIC_MAP = { '総距離':'total', 'キャリー':'carry', 'ボール初速':'ballSpeed',
  'ヘッドスピード':'hs', 'ミート率':'smash', '打ち出し角':'launch',
  'バックスピン':'spin', 'フェース角':'face' };

function parseMetrics(session) {
  const out = {};
  for (const [, k, v] of session.body.matchAll(/^\|\s*([^|]+?)\s*\|\s*([\d.\-]+)/gm)) {
    const key = METRIC_MAP[k.trim()];
    if (key) out[key] = parseFloat(v);
  }
  return Object.keys(out).length ? { date: session.date, ...out } : null;
}
// パースできない session は静かに落とす（スキーマを強制しない＝正本の自由度を守る）
```

**注意**: notes / follows にはスキーマ検証が無い（現状分析 §2）。ここで**検証を増やしてビルドを落とすことはしない**。数値が取れなければスパークラインを出さないだけ。**サイトの都合で正本の書き味を縛らない**というのが muninn の思想（CLAUDE.md「正本は markdown、サイトは派生」）。

### 8.6 全文検索（クライアント側）

`site.json` に `search.docs`（正規化済みテキスト）を入れ、**索引の構築は初回検索時にクライアントで**行う（起動を遅くしない）。外部ライブラリを足さず、`indexOf` ベースの部分一致＋ n-gram 前方一致で十分（137ノード・約 300 KB のテキスト量なら 10ms 未満）。日本語の分かち書き問題を避けられるのが利点。

## 9. ③想起と定着 の解

**論点**: 静的サイトでは SRS の状態を書き戻せない。59 件全部が期限切れで麻痺している。

### 9.1 結論：SRS をサイトに載せない。「復習」を「回遊のついでの想起」に作り変える

3 段階の解。

#### ① 「復習期限」バッジと KPI を**全廃**する

59/59 が該当する数字は指標ではない。現状分析も「バッジとして意味を失っている」と書いている。**残すと嘘をつき続ける。** `DueBadge` コンポーネントを削除し、`site.json` の `due` フラグも UI から切り離す（データは残すが表示しない）。

#### ② 命題タイトルを利用した「めくり」を、全ノードカードの既定の振る舞いにする

muninn には他のナレッジベースに無い資産がある——**タイトルが命題として言い切られている**（CLAUDE.md 原子化ルール）。

> 「ヘッドスピードは腕を速く振ることではなくチェーン全体の出力で、上げる鍵は主に"ブレーキを外す"効率化にある」

**このタイトルを見て中身が言えるなら、それは覚えている、ということだ。** だから専用のクイズ画面を作らない。

- ホームの「思い出せるか」カード ── タイトルだけ出して `[めくる]` で本文展開。
- 島の束を開いたときの箇条書き ── これがそのまま**59枚の単語カードを並べた表**として機能している。
- 展開／ノードを開いた時点で `localStorage: mn.touched[id] = 日付` を記録。**正誤も間隔も計算しない。触ったかどうかだけ。**

**回遊が復習になる。** これが「一枚の知識グラフ」という案Bの筋と、③想起と定着 が最も自然に融合する形である。

#### ③ 「冷たさ（coldness）」を、麻痺しない唯一のシグナルにする

```js
coldness(node) = 今日 − (touched[id] ?? created)     // localStorage ベース
territory.coldness = median(そのノードたちの coldness)
```

- ホームの星図で**冷えた島は暗く沈む**（明るさ＝最近触った度合い）。
- 「❄ しばらく行っていない — 中東 34日」カード。
- **これは必ず動く。** 触れば明るくなり、放置すれば沈む。59 固定の代わりに、**行動が即座に反映されるシグナル**を置く。

#### ④ 本気の採点は Claude に投げる（サイトは出題の入口）

`atlas` の「深掘りを依頼（コピー）」ボタンの一般化。ノード／島／ホームに `[ これでクイズを出して ]`。

```
/mn-review このノート「golf-clubhead-speed-…」で出題して。
サイトで見返していて、たぶん覚えていない。採点と srs 更新までお願い。
```

同様に、フォロー／島には `[ 予習ブリーフィングを作って ]` → `/mn-brief argentina-nt`。**J6「予習する」にサイト側の面が生まれる。**

### 9.2 なぜ localStorage で SRS を再実装しないのか

やろうと思えばできる。だが**やらない**。理由は 3 つ。

1. **正本が二重化する。** SRS の状態は markdown の `srs:` にあるのが muninn の設計（「srs をノート自身に同居させる」）。localStorage にもう一つ持てば、必ず食い違って、どちらが正しいか分からなくなる。**「正本は markdown」を破る変更は、コンセプトを壊す。**
2. **端末を変えたら消える。** PWA を iPhone とデスクトップの両方で使う運用に耐えない。
3. **そもそも SRS は止まっていた。** `review-log.jsonl` は 1 行。復習が回っていないのは UI が無いからではなく、**「59件の期限切れ」という絶望的な数字を毎回見せられているから**である。UI を足すのではなく、**麻痺の原因を取り除く**のが正しい処方。

## 11. 捨てるもの・トレードオフ・リスク

### 捨てるもの（意図的に）

| 捨てるもの | 理由 |
|---|---|
| **「全ノート一覧」という画面** | 90件フラットリストは、手がかりがタイトル文字列しかない時点で機能していない。島＋検索で代替。**「全部を見る」体験は失われる**（＝これが最大の喪失。§下記リスク3） |
| **「復習期限」バッジ・KPIタイル 2×2** | 常時点灯で情報量ゼロ。壁紙を剥がす |
| **`/moc/:slug` の生 markdown ページ** | MOC は表示物ではなく島の索引データになる。**MOC を「読む」体験は消える** |
| **サイト内の SRS 表現** | 正本の二重化を避ける（§9.2） |
| **画面上の concern 名の一部**（「蘊蓄」「MOC」「アトラス」） | 「アトラス」は残す（本人の語彙として定着している）。「蘊蓄」「MOC」は消す |
| **9ページ構成** | 5ルートへ。ページ数を減らすので**1ページあたりの実装が重くなる** |

### トレードオフ

1. **島の定義に人手が要る。** `territory:` 宣言（8ファイル）を書かないと島が正しく切れない。宣言が腐ると島がズレる。→ 宣言ゼロでもタグ第2階層でフォールバックする設計にして、**壊れないが良くならない**状態を最悪ケースにした。
2. **`site.json` が 307KB → 約 450KB。** 初回ロード＋PBKDF2 200k 復号が数百ms 伸びる可能性。→ グラフの隣接リストは最も嵩張るので、Phase 1 時点で実測し、必要なら `adj` を捨ててクライアント計算に切り替える（137ノードなら 5ms 未満）。
3. **統一シェルへの移行は大きなリファクタ。** 既存の `Follow` / `Atlas` / `LogTopic` を本体スロットに移植する必要がある。**atlas はコードを触りたくない（基準線だから）** ので、シェルの外側だけ被せて中身は現状のコンポーネントをそのまま呼ぶ形にする。

### リスク（正直に）

| # | リスク | 深刻度 | 対策 |
|---|---|---|---|
| **R1** | **島が増えると星図が破綻する。** 8島なら美しいが、20島になったら毛玉問題が島レベルで再発する | 高 | **12島を上限**と先に決める。超えたら「大きい順に11島＋その他」に畳む規則をビルドに入れておく。**この規則を後から考えると必ず間に合わない** |
| **R2** | **`lexical`（思わぬ隣人）がノイズしか出さない可能性。** 日本語のトークン化を形態素解析なしでやるので精度は保証できない | 中 | Phase 3 に置いて、**最後に賭ける**設計にしてある。閾値を上げて出ないなら「橋は無い」と表示するだけ。**この機能が死んでも Phase 1・2 の価値は一切減らない** |
| **R3** | **「全部を見る」を失うことへの後悔。** 90件フラットリストは無能だが、「全部ここにある」という安心感は与えていた | 中 | `/find` の入力ゼロ状態を「発見モード」にして、**島を横断した全ノードにいつでも触れる**ようにする。それでも足りなければ島画面に「この島の全件」を足す |
| **R4** | **「たずねる」がコピペ運用である以上、摩擦は消えない。** iOS でサイト → Claude Code アプリの往復は面倒 | 中 | 構造的に解けない（バックエンド無し・書き込みは Claude 側という制約）。**摩擦を隠さず、代わりに「引数が全部埋まった状態」でコピーさせる**ことで往復回数を最小化する |
| **R5** | **ゴルフが47%という偏りは IA では直らない。** 島にしても「ゴルフの島が異常にでかい」という事実は残る | 低 | むしろ**星図でそれが一目で分かるのが正しい**。「自分は今ゴルフに偏っている」と見えることは欠陥ではなく機能。細い島を殺さないよう「❄ しばらく行っていない」で引き戻す |
| **R6** | **`unfiled`（未整理）が常に多いと、新しい「麻痺する数字」になる** | 中 | 原則5の自戒。**件数バッジではなく「Claudeに索引を作り直させる」ボタンとセットでしか出さない**。行動に繋がらない数字は置かない |

## 12. 成功の定義

1人用なので定量指標は無意味。**行動の変化**で書く。

### 一次（これが起きなければ失敗）

- **起動から 10 秒以内に「今日読む1件」が決まり、実際に開く。** 現状は「復習期限 59」を見て何もせず閉じる。
- **1セッションあたりに開くノード数が 1〜2 → 5 以上になる。** 「つながり」ブロックからの遷移が起きているということ。**回遊が発生したかどうかが、案Bの成否そのもの。**
- **「これ何だっけ」と思ったとき、Obsidian でも `git grep` でもなく、このサイトを開くようになる。**

### 二次（muninn の思想が回り出した証拠）

- **ゴルフ以外の島に、月1回以上入る。** 47% 偏重の KB で細い島が死んでいないこと。
- **「たずねる」からコピーしたプロンプトで Claude を起動する回数が、週1回以上。** サイトが読む面から**書き込みの入口**に変わったということ。現状 `atlas` の深掘りボタンしかない橋が、KB 全体に架かった証拠。
- **`review-log.jsonl` が 1 行から増える。** 「めくる」で覚えていないと自覚 → `[これでクイズを出して]` を押す、という導線が働いたということ。**行数そのものより「1行で止まっていない」ことが重要。**
- **`unfiled`（束に入っていないノート）が増え続けない。** 島画面で見えるので `/mn-regen-moc` が定期的に回るようになる。**サイトが正本の健全性を保つ側に回った。**

### 最終（1年後の姿）

> **オーナーが人に muninn を説明するとき、「ノートとフォローとアトラスとログがあって…」ではなく、「ゴルフと哲学とアルゼンチンの島があって、たまに島の間に橋がかかる」と言う。**

内部の concern 名が、本人の口から消えること。それがこの刷新の完成である。
