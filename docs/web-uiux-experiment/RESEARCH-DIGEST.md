## A. 分野を横断して何度も出てきた結論（＝ほぼ確定した法則）

### A-1. ジェスチャは「発見可能性を売って速度を買う」取引である
- 成立条件は3つ揃ったときだけ: **①語彙が3〜4種以内 ②方向とメタファが一致（右=前進/肯定、左=後退/破棄） ③既存の運動パターンの延長**（pull-to-refresh がスクロールの延長として成功した理由）。
- Clear（2012・全ジェスチャUI）は後年オンボーディングを追加せざるを得なかった。
- **Snapchat の反証が重い**: 2017-18にジェスチャ→タブへ「わかりやすく」改修したら既存ヘビーユーザーが猛反発（署名運動）。**「わかりやすいが遅い」への退行は、習熟したユーザーには改悪である。**
- 逆向きの教訓: muninn のユーザーは n=1・毎日使う本人。**学習コストを払う気がある稀なケース**。ただし「久しぶりに開いて操作を忘れた」時のリカバリ（可視の逃げ道）は必ず要る。

### A-2. 画面下1/3が「操作領域」、上は「見る領域」
- Hoober 2013（実地観察 1,333件）: 片手持ち49% / 片手持ち＋反対の指36% / 両手15%。**親指がタップの75%を担う**。
- 解は2系統: **恒常的な再配置（Samsung One UI の viewing area / interaction area）** か **一時的な呼び出し（Apple Reachability）**。
  → **前者のほうが学習コストが低い**（何も覚えなくていい）。Reachability は「知らない人は存在しないのと同じ」。
- 画面端起点の弧（Path の扇メニュー、Pie Controls）は親指の可動域と物理的に一致するので強い。
  ただし **OS が既にその端を占有していないか**を必ず確認する（iOS の左端＝戻る、下端＝ホーム）。

### A-3. force-directed のグラフビューは「デモ映えするが使われない」の代表格
- Obsidian / Roam 双方で一致した評価。目安として**50ノート未満なら読める／200ノート超で毛玉化／500超でパフォーマンスも死ぬ**。
- 実際に機能している代替（Breadcrumbs, Excalibrain, Tana Live Search, Wikipedia プレビュー）は例外なく
  **「物理シミュレーションをやめて、型付き・整列済み・テキストベースにする」**方向に収束している。
- muninn の既存原則（force-directed を使わない・決定的配置・12点まで）は**この分野の結論と完全に一致**している。破らないこと。

### A-4. 「ズームはナビゲーションの答えではない」（Zoom is not navigation）
- Pad++ → ZoomWorld/Archy → Prezi → Windows 8 セマンティックズーム、**全部同じ結論に収束**。
- Prezi の最頻出苦情は "motion sickness"。ズーム＋パン＋回転の複合は前庭感覚とのミスマッチで酔う。
- 生き残っている解は **Focus + Context**（Furnas 1986 の DOI: `重要度 − 焦点からの距離`）。焦点は詳細に、周辺は**消さずに縮退させる**。
- **20年以上生き残った唯一の実用例が macOS Dock の拡大鏡**＝ **2D全体ではなく「1次元の帯」に fisheye を適用したもの**。実装も軽い。

### A-5. 無限キャンバス／横カラム積みは、モバイル幅で原理的に死ぬ
- Miller columns は1カラム数百px必要。Andy Matuschak の stacked pages も横幅を食う。
- Obsidian Canvas / Heptabase / Scrintal / Milanote、**全社が「モバイルは劣化版か閲覧専用」に落ち着いている**。
- **muninn が読み専用なのはむしろ有利**（編集の複雑さを最初から持たない）が、横カラムは iPhone では諦めること。
- ピンチズームは**二本指前提**＝片手最適化と正面衝突する。tldraw がわざわざ「ダブルタップ＋ドラッグ」を足したのはこのため。

### A-6. 空間の効能は「200点の一望」ではなく「十数点の定位置化」に宿る
- Kinopio の無料枠は100カード。muninn の既存原則は12点。Dock が扱うのも十数個。
- Heptabase の配置が空間記憶として効くのは、**位置が計算結果ではなく"意図"の産物**だから。
  毎回計算し直される配置は記憶の手がかりにならない。
- ミニマップ研究の警告: 常時表示の俯瞰図は便利だが**自前の空間把握（＝定着）を阻害する**。muninn の目的（想起・定着）とは相性に注意。

### A-7. 一つの入力欄が「検索・作成・実行」を兼ねると、モードが消える
- **Notational Velocity（2005）が原点**: 検索欄がそのまま作成欄。打つそばから全文インクリメンタル絞り込み、**ゼロヒットならそのまま Return で新規作成**。
  「検索している」のか「作っている」のかを**事前に決める必要がない**。
- 系譜: Canon Cat の LEAP キー（Raskin, 1987）→ NV → Spotlight/Alfred/Raycast → Cmd+K 文化。
- **muninn への翻訳**: 「ゼロヒット → 新規作成」を **「ゼロヒット → Claude への依頼」**に読み替えると、読み専用という制約下で同じ構造が成立する。
  「muninn に無かった」ことが、次の蓄積の入口になる——これは既存実装の思想とも一致している。
- Raskin の **quasimode**（押している間だけ有効・離せば必ず戻る）は、誤操作が原理的に起きないモードの作り方。トグル型のモードは事故の温床。

### A-8. モバイルでインクリメンタル検索をやるときの落とし穴
- **Google Instant は2017年に廃止された**。理由はモバイル化——小さい画面・タップ入力・毎キー再描画のコストが見合わなくなった。
- ソフトキーボードは**画面の40〜50%を占有する**。デスクトップのコマンドパレット（中央オーバーレイ＋下に長いリスト）をそのまま持ち込むと結果がキーボードに隠れる。
- ただし **muninn は全データがメモリ上にあり200ノード規模**なので、素の総当たりで数ms。**技術的コストはゼロに近い**。問題は純粋にレイアウトの問題。

### A-9. 「遷移する前に覗ける」がナビゲーションコストを一番安く削る
- Wikipedia の Page Previews（2018〜、ログアウトユーザーにデフォルト有効）。リンククリックの大半は「これ何？」の確認であり、**遷移→読了→復帰という重いサイクルを踏ませる必要がない**。
- 線形・テキストベースなので**画面サイズに関わらず崩れない**。今回調査した尖ったUIの中で**モバイル適応性が最も高い**。
- **muninn はここで圧倒的に有利**: リンク規約が `- [[x]] — なぜ関連するか` なので、
  プレビューに **「リンク元が書いた理由」ごと**出せる。Wikipedia より一段リッチな文脈をタダで持っている。**この武器を使わない案は弱い。**

### A-10. ラジアル／マーキングメニューは速いが、反復頻度がないと育たない
- Callahan et al. 1988（被験者33名）: パイメニューはリニアメニューより**選択時間が約15%速い**（p<0.01）。標的面積が3,500〜6,000px²（リニアは1,000〜2,000px²）＝Fitts的に有利。
- マーキングメニュー（Kurtenbach & Buxton）は**方向の記憶が残る**ので初心者→熟練者の移行が自然。ただし**階層を深くすると熟練者でも頭打ち**。
- **項目数8超で優位性が消える**（ウェッジが狭くなる）。中心付近の選択はどの方式でも精度が落ちる。
- ⚠️ **muninn のリスク**: 1日数分・低頻度の利用では、Maya や格ゲーほどの反復回数が確保できず**覚える前に忘れる**。
  → 採用するなら「方向を忘れても目で見て選べる」状態を必ず併設する。

### A-11. 判定の粒度: 2択 vs 4択
- Anki は4段階（Again/Hard/Good/Easy）。実測ではユーザーの39.8%が「Againに一番時間をかけEasyに一番かけない」直感的パターンを示す＝評価自体は低コスト。
- ただし **Hard と Good の境界を誤解しているユーザーが多い**という指摘も定番。
- muninn は既に2択＋「一言を書いたか」で q を3段階に分岐させている（5/4/2）。**この設計は理にかなっている**（判断は2択のまま、精度は行動から推定する）。

### A-12. 触覚は「確信」を作る。が、**iOS Safari には Vibration API が無い**
- `navigator.vibrate()` は Safari（macOS/iOS）で**一度も実装されていない**（2025-26時点でも未対応）。
- 確認できた唯一の代替は iOS 18+ の `<input type="checkbox" switch>` トグルがネイティブ触覚を発火するハック。
  **ユーザーの明示的なクリック操作に紐づく必要**があり、任意タイミングでの発火・リズムの作り分けは不可能。
- **結論: 触覚に依存する設計は PWA では絵に描いた餅。** 確信は**視覚と音**（と、操作の即時性）で作ること。

### A-13. 組版は「情報の重み付け装置」である。密度は敵ではない
- フラットなカードリストは**全記事を同じ重要度で提示してしまう**。紙面は「今日の一番」「小さい扱い」を視覚的サイズと位置で先に伝える。
- Bloomberg Businessweek（2010年 Turley/Schwartz 改革）は**記事の性格ごとに組版のルールを変える**モジュール型紙面をWebに持ち込んだ。ただし「尖りすぎ」は持続せず2017年に落ち着いたトーンへ回帰している。
- Bloomberg Terminal: **情報密度＝信頼のシグナル**という逆説（トレーダーは"スカスカな画面"を信用しない）。
- Tufte: 情報を減らすのではなく**視線移動を減らす**（サイドノート、スパークライン、small multiples）ことで「多いのに読める」を作る。
- The Marginalian: 蓄積型の個人メディアでは**「これだけの物量を一人が書き続けている」という事実自体**が最大の説得力になる（総量を隠さず出す）。

### A-14. 速度は機能である
- Superhuman は「100ms未満は"瞬時"と知覚される」を製品哲学の中心に据え、社内目標は50ms。
- 「速そう」ではなく「◯ms以内」という**具体的な閾値**を持つと、アニメーションを削る等の実装判断がぶれない。
- muninn は全データがメモリ上なので**この閾値を守るのは容易**。守れないとしたら、それは自分で入れた演出のせい。

## B. 越えてはいけない線（デザイナー全員が守る／判定可能な形）

> ⚠️ これは暫定版（既存リサーチから導出）。人間工学の専門調査が上がり次第、正式版に差し替える。

1. **主要操作（ナビゲーション・判定・入力）は、画面下端から 250px 以内**に置く。上1/3に置いてよいのは「読むもの」だけ。
2. **タップ標的は最低 44×44 CSS px**（Apple HIG）。密集する場合は 48px（Material）に寄せる。WCAG 2.2 の 2.5.8 は最低 24×24 を要求する。
3. **隠しジェスチャだけで到達できる機能を作らない。** すべてのジェスチャに、**目で見て辿れる代替経路**を必ず用意する（Reachability の教訓）。
4. **ジェスチャの語彙は4種以内。** 方向と意味は1:1で固定し、画面ごとに変えない。
5. **画面の左端 20px からの横スワイプを自前のジェスチャに使わない**（iOS の戻るジェスチャと衝突する）。画面下端の数px〜十数pxも同様（ホームインジケータ）。
6. **不可逆・重要な判定（想起の わかった/あやしい）を、取り消し不能な1ジェスチャで確定させない。** 数百msのキャンセル猶予か、Undo を必ず持つ。
7. **ピンチズームを主要操作にしない**（二本指＝片手最適化と矛盾）。ズームが要るなら、タップでレベルを切り替える離散ズームにする。
8. **一度に見せるノードは12点まで。** 図は必ずリストで代替可能にすること。
9. **`prefers-reduced-motion: reduce` で「動きなし・完成形を即表示」に落ちること。** パン＋ズーム＋回転の複合演出は作らない（Prezi 酔い）。
10. **操作の反応は 100ms 以内**（Superhuman 基準）。アニメーションは `transform` と `opacity` のみ。`width/height/top/left` をアニメーションさせない。
11. **触覚（バイブ）に依存しない。** iOS Safari には Vibration API が無い。
12. **`backdrop-filter` を縦スクロールするカード全部に付けない**（iOS Safari で GPU ブラーが毎フレーム走りフレーム落ちする）。使うなら固定要素1枚に限定し、blur は 8〜16px。
13. **入力欄の `font-size` は 16px 以上**（iOS Safari の自動ズームを防ぐ）。
14. **日本語入力（IME）の変換確定 Enter を、ショートカット/送信として誤処理しない**（`isComposing` を見る）。
15. **未消化件数のバッジを出さない。**「今週N件やった」型の増えるカウンタのみ可。

## C. 「破ってよい定石」（今回むしろ破るべきもの）

1. **画面上部の AppBar と ‹戻る**。上1/3は親指が届かない。戻るは別の場所・別の手段でよい。
2. **ボトムタブ4つ**。タブは「同格の目的地が4つある」ことの表明にすぎない。目的地の関係が同格でないなら、別の構造のほうが正しい。
3. **均一なカードの縦リスト**。全部を同じ重みで出すのは「編集していない」ことの表明（A-13）。
4. **1画面1目的**。モードレスに統合できるなら統合したほうが速い（A-7）。
5. **ミニマルであること自体**。密度は敵ではない。無編集な密度が敵（A-13）。
6. **ダーク＋グラス**。muninn のトーンではあるが、今回は聖域にしない。紙・インク・ターミナル・リソグラフ、どれも候補。
7. **アニメーションで「気持ちよさ」を出すこと**。100ms を超える演出は、この用途では単なる遅延。
8. **フォルダ/一覧ページ**。「置き場所の写像」は既に廃止済み。復活させない。

## D. muninn 固有の"未使用の武器"（どの案も何かしら使うこと）

| 武器 | 中身 | なぜ強いか |
|---|---|---|
| **理由つき被リンク** | `- [[x]] — なぜ関連するか` という規約が全リンクに理由を持たせている | Wikipedia プレビューより一段リッチな「相手が書いた理由」ごと逆流できる。他のPKMには無い（A-9） |
| **型付きエッジ** | 連載の `requires / contrasts / leads-to / elaborates` | 型があるからこそ整列した決定的レイアウトが作れる（A-3の"生き残った代替"の条件を最初から満たしている） |
| **全データがメモリ上** | 200ノード・復号済み | 総当たり検索も横断計算も数ms。**インクリメンタル検索の技術的コストがゼロ**（A-8） |
| **極端に不均一な在庫** | ゴルフ47%、記録帖1件 | 均等グリッドに逃げるとこの事実が消える。**偏りをそのまま描くこと自体が情報**（既存の面積ツリーマップの思想） |
| **指標の良し悪しの宣言** | `metric_goals` で up/down/中立 | 数値の色・強調を正当に出せる。宣言がないものは中立に扱う |
| **閲覧日で組む** | ビルド日ではなくクライアントの `new Date()` | push が止まっても面が毎日入れ替わる |
| **依頼テキストの生成** | サイトの唯一の"書き込み" | ゼロヒットを次の蓄積の入口に変換できる（A-7） |
