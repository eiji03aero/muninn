# リサーチ: コマンド駆動・モードレス・テキスト起点UI

muninn刷新のための参考資料。「入力欄がアプリの主役」という設計思想の系譜を、具体例・原理・muninnへの適用案・技術的勘所の順でまとめる。

---

## 1. 具体例（プロダクト別）

### 1.1 Quicksilver（macOS, 2003〜）
- URL: https://qsapp.com/ （GitHub: blacktree/Quicksilver）
- 時期: 2003年公開。開発は事実上停止（最終メジャー更新は2010年代前半）だが、オープンソースとして今も動く。「生きているが枯れている」扱い。
- 仕組み: ホットキーで呼び出し、1段目に対象（アプリ・ファイル・連絡先など）をあいまい入力で絞り込み、2段目にその対象への「動作」を選ぶ、という**主語→動詞**の二段階文法。単なるランチャーでなく「名詞を検索して動詞を適用する」操作文法を確立した最初期の例。
- 削った操作コスト: Dock/Finderへのマウス移動、フォルダ階層のたどり直し。
- 効く理由: あいまい一致（fuzzy match）により、正確な名前を覚えていなくても数文字で候補が絞られる。学習するほど入力文字数が減る（頻度学習）。
- 破綻・批判点: 開発停滞により後継のAlfred/LaunchBarに主要ユーザーが流出。UIの発見可能性は低く（プラグイン機能は事実上隠しコマンド）、新規ユーザーの立ち上がりが遅い。

### 1.2 LaunchBar（macOS, 1997〜）
- URL: https://www.obdev.at/products/launchbar/
- 時期: 1997年〜。現役、Objective Developmentが継続開発中。
- 仕組み: Quicksilverと同系統の二段階文法だが、よりファイル・連絡先・カレンダー中心。「学習的略語」（例: 頭文字だけで候補が1位に上がる）を強く重視。
- 効く理由: 使うほど個々のクエリが短くなる適応的ランキング。
- 批判点: Quicksilver同様、機能の発見可能性はドキュメント頼み。

### 1.3 Alfred（macOS, 2010〜）
- URL: https://www.alfredapp.com/
- 時期: 2010年〜、現役。Powerpackで「Workflows」というノーコード自動化を追加し、ランチャーから「個人用オペレーティングレイヤー」に進化。
- 仕組み: 呼び出しキー+入力文字列でアプリ起動・計算・Web検索・スニペット・clipboard historyなどを一つの入力欄に集約。
- 効く理由: 「何をするにもまず同じ窓を開けばいい」という**単一入り口**の一貫性。モード切り替えなしに検索・実行・計算が同じフィールドで完結する。
- 破綻・批判点: macOS専用。iOS/Windows展開なし（後述4章）。

### 1.4 Spotlight（macOS, 2005〜 / iOS, 2007〜）
- URL: Apple公式
- 時期: macOS Tigerで2005年導入、iOSにも搭載され現役。
- 仕組み: システム標準の全文・メタデータ即時検索。⌘Spaceで即座に検索フィールドにフォーカス。
- 効く理由: OS標準化によりショートカットを覚える負荷がゼロに近い（誰でも同じキーで同じ場所に行ける）。
- 批判点: サードパーティランチャー（Alfred等）に比べ拡張性・アクション性が弱く、「検索はできるが実行の語彙が薄い」という指摘が多い。

### 1.5 Raycast（macOS, 2020〜 / iOS・Windows は2024年からベータ）
- URL: https://www.raycast.com/
- 時期: 2020年ローンチ。現役、急成長中。2024年後半にiOS/Windows版のアルファ/ベータを発表（本稿執筆時点でモバイル版は限定的機能）。
- 仕組み: Quicksilver系譜の後継として、拡張機能（Extensions）・AI Commands・Cmd+Kのアクションパネルを統合。「呼び出し→検索→アクションパネルで詳細操作」という三層構造。
- 削った操作コスト: 個々のSaaSアプリを開いてUIを探す手間。「テキストを選択→ホットキー→AIコマンド実行」で他アプリを開かずに変換・要約などが完結。
- 効く理由: コマンドパレット文化とAIを組み合わせ、「一つの入力欄が起動・検索・実行・生成のすべてを兼ねる」を拡張。
- 批判点: モバイル版は2024年時点でまだアルファ。iOSでは常駐ホットキー起動ができないため、macOS版と同じ体験を再現できていない（4章で詳述）。

### 1.6 VS Code Command Palette（Ctrl/Cmd+Shift+P, 2015〜）／Sublime Text Command Palette（2008年代〜が起源）
- URL: https://code.visualstudio.com/docs/getstarted/userinterface
- 時期: Sublime Textが先行してCmd+Shift+Pの「コマンドパレット」概念を普及させ（2008年前後）、VS Codeが2015年の公開時に踏襲・大衆化。現役。
- 仕組み: メニュー階層をすべてフラットなあいまい検索リストに変換。「メニューを探す」から「名前を打つ」へ操作を転換。
- 効く理由: アプリの機能数が数百〜数千に達すると、階層メニューのナビゲーションコストが線形に増えるが、コマンドパレットは検索コストがほぼ一定（入力文字数に依存）。
- 批判点: 「隠しキーボードショートカットはUIに手がかりがないと誰も使わない」という指摘（後述、GitHubのCommand Palette機能フラグの低利用率の例）。

### 1.7 Slack のクイックスイッチャー／Cmd+K（〜2017年代に一般化）／Linear（2019〜）
- URL: https://linear.app/ 、Slack公式ヘルプ
- 時期: Slackは早期からCmd+Kのチャンネルジャンプを持ち、Linearは創業時（2019年）からキーボードファーストを製品哲学の中心に据えた。両方現役。
- 仕組み: Linearでは「すべての操作にキーボードショートカットがある」ことを前提に設計されており、Cmd+Kコマンドパレットはその入口の一つに過ぎない。`C`で課題作成、`X`でアクションメニュー、`S`でステータス変更など、1〜2キーの単文字コマンドが並ぶ。UIにヒントを常時表示し、使いながら覚えさせる。
- 効く理由: マウス操作をゼロにできると、操作間の視線移動・往復のコストが消える。「ツールが消えて、作業だけが残る」という設計哲学。
- 批判点: 学習コストは新規ユーザーにとって高く、キーボード前提の設計は非エンジニア職種には過剰なこともある。

### 1.8 Notational Velocity / nvALT / nvUltra（★重点）
- Notational Velocity: https://notational.net/ 　開発者 Zachary Schneirov。2005年頃公開、2011年ごろ更新停止（現在もダウンロード可・動作する「終わったが現役で使われている」ソフト）。
- nvALT: https://brettterpstra.com/projects/nvalt/ 　Brett Terpstraによるフォーク。ほぼ開発停止だが今も使うユーザーが多い。
- nvUltra: https://rywalker.com/research/nvultra 　Brett TerpstraとFletcher Penneyによる正式後継。**2019年頃からプライベートベータのまま**、2026年時点でも「Coming Soon」表記。開発は継続中（2025年12月・2026年5月にベータフォーラム投稿あり）だが約7年間未リリースという異例の長期ベータ。
- 仕組み（最重要ポイント）: **検索欄が同時に作成欄でもある**。ウィンドウを開くと入力欄以外にほぼ何もない（ボタンなし＝マウスレス前提の設計）。入力するそばから全ノートの全文をインクリメンタルにフィルタし、一致するノートがリスト表示される。**該当ノートがなければ、そのままReturnキーで「今入力した文字列をタイトルにした新規ノート」が生成される**。逆に既存ノートのタイトルを打ち始めると、関連ノートが下に並び、選んで開くこともできる。つまり「検索」「絞り込み」「新規作成」「開く」という4つの別々の操作が、キー入力とReturnキーの2アクションに収斂している。
- 削った操作コスト: 「新規作成ボタンを探す」「保存場所を選ぶ」「ファイル名を打つダイアログ」「検索と作成でウィンドウ/モードを切り替える」という、通常のノートアプリに存在する意思決定と画面遷移をすべて消している。
- 効く理由: ユーザーの意図（「これについて書きたい/見たい」）を言語化した瞬間、システムがそれを検索クエリとしてもタイトル候補としても同時に評価する。**ユーザーは「検索している」のか「作成している」のかを事前に決める必要がない**——これはRaskinのモードレス原則（後述2章）の実例そのもの。
- 破綻・批判点: 開発が止まりやすい（実際NV・nvALTともほぼ停止、nvUltraは7年未リリース）。要因の一つとして、UIが極端に禁欲的（検索欄だけ）なため差別化要素を足しにくく、商業的持続性が低いという分析がある。また新規ユーザーには「検索窓しかない」ことが最初は不安（「保存されたのか？」の確認不能感）を生むという批判もある（フォルダ・ファイル管理に慣れたユーザーには不安）。

### 1.9 Everything（voidtools, Windows, 2009〜）
- URL: https://www.voidtools.com/
- 時期: 2009年公開、現役・活発に更新中。
- 仕組み: NTFSのマスターファイルテーブル（MFT）を直接読み、全ファイル名を事前索引化。検索欄に入力するたびインクリメンタルに結果をフィルタ（実質ミリ秒未満）。
- 効く理由: 「索引化＋インクリメンタルフィルタ」の組み合わせにより、Windows標準検索が数秒かかるところを体感即時にした。muninnの「全データがクライアントメモリに載っている」という前提と設計思想が一致する好例。
- 批判点: Windows専用、NTFS前提。ファイル名検索が主でコンテンツ検索は別機能。

### 1.10 fzf（junegunn, 2013〜）
- URL: https://github.com/junegunn/fzf
- 時期: 2013年公開、現役・非常に活発（ターミナルツールのデファクト標準の一つ）。
- 仕組み: 標準入力の行リストをあいまい一致でインクリメンタルにフィルタし、選択結果を標準出力に返す「フィルタとしてのUI」。シェル履歴（Ctrl-R）、ファイル選択（Ctrl-T）などに広く統合される。
- 効く理由: 「一致条件を順不同・非連続でもよい」というあいまい一致アルゴリズムにより、`srcmain`のような省略入力で`src/components/Main.tsx`にヒットする。単一の汎用UIパターンを無数のツールに横展開できる（Vim, Git, tmux, シェル履歴などに同じ操作感を持ち込める）。
- 批判点: CLI前提のためGUI/モバイルへの直接移植は難しい。

### 1.11 Google Instant（2010〜2017、終了済み）
- URL: （Google公式、当時の発表）
- 時期: 2010年開始（Marissa Mayer主導）、2017年に廃止。
- 仕組み: 検索ボックスへの入力ごとに（Enter不要で）結果ページをリアルタイム更新。
- 効く理由: 1クエリあたり2〜5秒短縮とGoogleは主張。
- 廃止理由（重要な失敗事例）: モバイル検索が過半数を占めるようになり、**小さい画面・遅い当時のモバイル回線・タップ主体の入力ではキー入力ごとの全ページ再描画がコストに見合わなくなった**。「デスクトップ全盛期に最適化された機能が、モバイル主流化で成立しなくなった」という、モバイルへの示唆が強い失敗例。

### 1.12 Algolia InstantSearch（2012年創業〜）
- URL: https://www.algolia.com/
- 時期: 現役。search-as-you-typeをプロダクト化し、ミリ秒オーダー（数十ms）の応答を売りにする。
- 効く理由: 「入力の途中で結果が変わる」体験のためには、バックエンド側もprefix検索・タイポ許容などをミリ秒で返す設計が必須という技術的裏付けを与える。

### 1.13 Superhuman（2015年創業、2017年ローンチ〜）
- URL: https://superhuman.com/
- 時期: 現役。
- 仕組み: Gmail創業者Paul Buchheitの「100msルール」（100ms未満の応答は「瞬時」と知覚される）を製品哲学の中心に採用。社内目標は50ms未満。全操作にキーボードショートカットを用意し、Cmd+Kのコマンドライブラリで発見可能性を担保。
- 効く理由: Amazonの調査（100ms遅延で売上1%減）やGoogleの調査（500ms遅延でトラフィック20%減）を引用し、「速度そのものが機能」という立場を取る。
- 批判点: 月額課金が高額（プレミアム価格帯）で、キーボードショートカット学習のオンボーディングコストをどう下げるかが継続的な課題。

### 1.14 Warp（ターミナル, 2021年〜）
- URL: https://www.warp.dev/
- 時期: 現役。
- 仕組み: コマンドと出力を「ブロック」単位でまとめ、複数行対応のコマンド入力欄（構文ハイライト・カーソル移動対応）を持つ。AIをコマンド生成に統合しつつ「生成物を必ず可視化する」透明性を重視。Cmd/Ctrl+Shift+Pのコマンドパレットも搭載。
- 効く理由: 伝統的ターミナルの「編集しにくい1行入力欄」という制約を、GUI的な入力体験に置き換えつつCLIの速度を保持。

### 1.15 Fig（ターミナル自動補完, 2020〜2024, 終了済み）
- URL: https://github.com/withfig/autocomplete （旧本体は終了）
- 時期: 2020年設立、2023年8月にAmazon（AWS）が買収、2024年9月1日にスタンドアロン製品を終了しAmazon Qへ統合。
- 仕組み: 既存シェルの上にIDE的なオートコンプリートのポップアップを重ねる。
- 失敗の含意: 有望なUXパターンでも、単体プロダクトとしての商業的持続性（マネタイズ）が伴わないと買収・サービス終了に至るという事例。ターミナルUXの改善は評価されるが、それ単体で大きなビジネスにするのは難しいことを示す。

## 2. モードレス設計思想（Jef Raskin / The Humane Interface）

- 出典: *The Humane Interface*（Jef Raskin, 2000年出版）。Wikipedia: https://en.wikipedia.org/wiki/The_Humane_Interface
- 中核主張: 「モード」とは同じ入力が状況によって異なる結果を生む状態であり、Raskinは**モードは可能な限り排除すべき**と主張した。「モードはエラー・混乱・不必要な制約・複雑さの重大な発生源である」という趣旨の言葉を残している。
- **quasimode（クワジモード）**: 完全にモードレスにできない場合の次善策として、「ユーザーが物理的な動作を維持している間だけ有効なモード」を提唱。Shiftキーを押している間だけ大文字になる、のような**押している間だけ発動し、離せば必ず元に戻る**設計（＝spring-loaded mode）。Caps Lockのような「トグル型モード」は誤操作の温床になるため避けるべき、との対比で説明される。
- **Monotony（単調性）の原則**: 「1つのアトミックな操作を達成する方法は1つだけにすべき」という主張。同じ操作にボタン・メニュー・ショートカットと複数の経路を用意することはRaskinにとってはむしろ認知負荷を増やす設計とされる（この点は現代の「複数の入り口を用意する」UX標準とは逆の立場で、賛否が分かれる原則）。
- **Canon Cat（1987年）とLEAPキー**: Raskinが自身の思想をもっとも完全に実装したハードウェア。アプリケーションという概念自体がなく、すべてのテキストが単一の連続した「文書ストリーム」として存在する。ファイルシステムもない。「LEAP」という専用キーを押しながら文字を打つと、文書内を**インクリメンタルに前方/後方検索してジャンプする**。これがメニュー・ダイアログ・ファイルブラウザの代替となった。1987年に発売されたが、Canon社内の政治的事情により数ヶ月で販売終了（製品自体の失敗ではなく組織的要因による打ち切り、という評価が一般的）。
- muninnへの含意: NVの「検索欄が作成欄も兼ねる」設計は、Canon CatのLEAPキー思想の直接の子孫と言える。「検索」と「作成/実行」を別モードにしないことが、Raskin以来一貫した「効くパターン」の核。

## 3. テキスト第一・検索先行UIのまとめ原理

上記事例群から、ジャンルを横断する共通原理を抽出する。

1. **入力欄の意味は固定しない（テキストは意図の器であり、コマンド名ではない）**
   NV、Spotlight、Alfred、Raycast、ChatGPTはいずれも「何を入力するか」を事前に規定しない。同じフィールドが検索・作成・実行・計算のいずれにもなり得る。ユーザーは「今から検索する」「今から作る」という**メタ的な決定を最初に下す必要がない**。

2. **フィルタは即時（インクリメンタル）でなければ「検索」ではなく「クエリ発行」になる**
   Google Instant、Everything、fzf、Algoliaはいずれも「打つたびに絞り込まれる」体感速度を核心的な価値としている。数百ms以上のラグが入ると、ユーザーは無意識に「Enterを押して確定してから見る」という別モードの操作に退行する（＝インクリメンタル性が失われるとモードレスの利点も失われる）。

3. **失敗した検索（ゼロヒット）を「次のアクションの起点」に転用する**
   NVの「検索して見つからなければそのままノート作成」が最も純粋な例。検索の失敗を「エラー」として扱わず、「新規作成の意図表明」として自然に受け取る設計は、入力欄を万能にする鍵。

4. **モードは"押している間だけ"の一時的なものにとどめる（quasimode）**
   永続的なモード切り替え（トグル）はユーザーの記憶に負荷をかけ、事故（違うモードだと思い込んだまま操作）を招く。Shiftキー、LEAPキーのように「離せば元に戻る」設計にすると事故が起きない。

5. **発見可能性は「隠す」のではなく「使いながら教える」設計で補う**
   コマンドパレット系の最大の弱点は新規ユーザーの発見可能性の低さ。Linearはショートカットヒントを常時UIに表示し、Raycastはアクションパネル（Cmd+K）自体を「今使える操作の一覧」として機能させることで、「隠しコマンド」と「学習可能なショートカット」の中間を実現している。**発見可能性をゼロにした省力化（Fig, GitHub Command Palette機能フラグ低利用の例）は使われずに終わる。**

6. **速度は機能である。100ms/50msという具体的な閾値を持つと設計判断がぶれない**
   Superhumanの事例が象徴的。「速そう」ではなく「◯ms以内」という具体的閾値を持つことで、アニメーションを削る・先読みキャッシュするといった実装判断に一貫性が出る。

## 4. モバイルにおけるコマンドUI（なぜ来ないか）

- **ハードウェアキーボード前提が崩れる**: Quicksilver/Alfred/LaunchBar/Raycast(macOS版)/fzfはいずれも「グローバルホットキー1発で常駐ウィンドウを呼び出す」ことが起点になっているが、iOSはサードパーティアプリにシステム全体のホットキー登録権限を与えない（サンドボックス制約）。Raycastが2024年後半にiOS版アルファを出したのも、この「呼び出し」の再設計が最大の課題だったとみられる（未確認: Appleの具体的なAPI制約の一次資料までは今回未到達）。
- **ソフトキーボードが画面の40〜50%を占有する**: 親指操作の到達範囲（thumb zone）は画面下2/3程度とされ、ソフトキーボード表示中は残りの可視領域がさらに圧縮される。デスクトップのコマンドパレット（画面中央にオーバーレイ＋下に長いリスト）をそのままモバイルに持ち込むと、結果リストがキーボードに隠れる。
- **Google Instantの廃止（2017年）が象徴的**: 「入力毎に全部再描画する」体験はモバイルの回線・処理能力・画面サイズでは成立しなかった、とGoogle自身が事実上認めた形の撤回。
- **タップ操作は"あいまい入力"と相性が悪い**: あいまい一致検索は「多少ミスタイプしても候補が絞られる」ことが前提だが、ソフトキーボードでの入力自体がすでに低速・誤字が多いため、恩恵よりコストが先に立つという指摘がある。
- **モバイルの代替解**:
  - iOS Spotlight（下スワイプ）: OS標準検索に統合し、サードパーティが個別に「呼び出し」を再発明しなくて済む形に収斂。
  - Arc Search「Browse for me」（2024年、iOS向け）: 検索ボックス1つに「検索する」「AIに要約させる（Browse for me）」の二択ボタンを添えるだけの単純化。ただし親会社The Browser Companyは2025年5月にArc本体の新機能開発を停止しDiaへピボット（2025年10月にAtlassianが買収）。**Arcは現在も動作しセキュリティパッチのみ提供、新機能追加はない**という「延命状態」。単一入力欄への統合という発想自体は評価されつつ、ビジネスとしての持続性は別問題であることを示す事例。
  - Perplexity: 検索ボックスの見た目をあえて従来のGoogle検索に似せ、「キーワードだけでも使える／文章でもよい」という**入力形式を強制しない**ことで学習コストを下げている。

## 5. 自然言語入力・プロンプト欄を主役に据えたUI

- **ChatGPT/Claude**: 画面中央の空白テキストボックスのみ、という極端な最小主義。良い面は「何でも受け付ける」自由度だが、"blank canvas problem"（何を打てばいいか分からず固まる）という批判が明確にある。OpenAIは温度・トークン数などのパラメータを意図的に隠し、初心者の意思決定麻痺を避けたが、これは同時に上級者の制御性を犠牲にする判断でもあった（賛否両論）。
- **Raycast AI Commands**: テキスト選択→ホットキー→AIコマンド実行、という「範囲選択＋コマンド」の組み合わせ。プロンプトをコマンドとして保存・再利用できる点がChatGPTの都度入力と異なる。
- **Notion AI**: スラッシュ`/`で通常コマンドパレット、スペースキーでAI専用パレットに切り替える二段構え（同じ入力の起点から分岐する設計）。
- **Arc Max / Browse for me**: 検索と要約生成の境界をユーザーに意識させない試み。

## 6. キーボード操作最適化の極北

- **Superhuman**: 100ms/50msという定量目標、Cmd+Kコマンドライブラリ、Split Inbox。「三時間/週の時短」を謳う。
- **Linear**: 「すべての操作にショートカットがある」ことを前提にした設計。UI自体がヒントを常時表示し、覚えなくても迷わず、覚えれば加速するという二層構造。
- **vim（hjkl / モーダル編集）**: Bill Joyが1976年前後にADM-3A端末（矢印キーがh/j/k/lに印字されていた）上でviを開発したことに由来。**モーダル編集はハードウェア制約への適応から生まれた設計**であり、後から見て「ノーマルモード/インサートモードの分離」という一般化された設計思想として定着した。Raskinのモードレス主義とは対照的な系譜（vim自体はRaskin的には「モードの多用によりエラーを誘発する設計」の代表例だが、数十年使われ続けている実例でもある——原則の普遍的な正しさに対する反証としても引用に値する）。
- **Emacs Helm / Ivy**: ミニバッファ補完の二大流派。Helmは「Emacs全体の挙動をHelmの世界観で統一する」網羅性志向、Ivyは「軽量・最小限・UIを散らかさない」志向。同じ問題（候補の絞り込みUI）に対する二つの設計思想が併存している点が参考になる（muninnでも「多機能統合型」か「最小限特化型」かの選択に相当）。

## 7. muninnへの適用案（5つ、ボツ理由つき）

前提の再確認: 読み専用（書き込みUIなし）、主戦場iPhone片手操作、全データはクライアントメモリ上（記事90本・ノード200）、4ジョブ（①今日読む②俯瞰③ピンポイント想起④Claudeへの依頼作成）。

### 案A: 「単一入力欄」をアプリの起動画面にする（NV型フロントドア）
アプリを開くと下タブではなく、まず全画面幅の検索/コマンド欄が現れる。入力すると即座に記事・ノート・follows・logsを横断してインクリメンタルにフィルタ（200ノードなのでクライアント側で数ms、Everything/fzf型のインクリメンタル検索が技術的に成立する）。ゼロヒットの場合は「Claudeへの依頼としてコピー」ボタンに自然につながる（NVの「ゼロヒット→新規作成」を、読み専用の制約下で「ゼロヒット→依頼テキスト生成」に翻訳する）。
- **ボツになりうる理由**: 4ジョブのうち①（今日読むものを差し出される）と②（俯瞰）は「何も入力しない状態」が本体であり、検索欄ファーストのUIとは相性が悪い。検索は「向こうから来る」ジョブには効かず、「こちらから探しにいく」ジョブ（③想起、④依頼作成）にしか効かない。全画面を検索欄に明け渡すと、①②のための面が犠牲になる可能性が高い。

### 案B: Cmd+K相当を"どの画面からも1アクションで呼べる"オーバーレイにする（Alfred/Raycast型）
下タブ構成は残しつつ、画面のどこからでも（例: 下タブ左端に固定した検索ボタン、またはpull-to-search的なジェスチャ）オーバーレイのコマンドパレットを呼べるようにする。パレット内は「検索結果」と「アクション」（例: 「このノートをフォローに追加」「このトピックのブリーフィングを作る」といった、実データではなく**Claudeへの依頼テキストを組み立てる操作**）を両方リストする。
- **ボツになりうる理由**: 読み専用アプリなので「アクション」の種類が本質的に少ない（せいぜい5〜6種の依頼テンプレート）。Alfred/Raycastが強い理由は「拡張性のある動詞の多さ」にあるが、muninnではそれが構造的に薄いため、コマンドパレットを作っても「検索窓の皮を被った検索窓」で終わる可能性がある。

### 案C: ジョブ③（ピンポイント想起）専用に、NV型の検索=結果一体画面を作る
現状の「検索タブ」を、NVそのものの操作感（検索欄1つ、結果はカードでなくテキストの見出しリスト、タップで即記事）に作り替える。片手操作前提でキーボードは画面下部に出るため、結果リストは**入力欄のすぐ下**（画面上部)に出す設計にする（キーボードに隠れない配置）。
- **ボツになりうる理由**: iOSソフトキーボードは画面下半分を覆うため、「結果を画面上部に出す」設計は動線として不自然（人間は入力した直後に視線を下に落とす傾向がある一入力欄UIの通例と逆になる）。すでに指摘した「モバイルでインクリメンタル検索のUXがデスクトップ通りには機能しない」問題を、muninn固有の再検証なしに輸入するリスクがある。

### 案D: 「④Claudeへの依頼を作る」ジョブを、NVの検索=作成一体パターンで実装する
これはmuninnの構造に最もハマる可能性が高い案。検索欄に自由文を打つと、①既存ノート・follows・logsへの一致をインクリメンタル表示しつつ、②その入力文字列をそのまま「Claudeへの依頼テキストの下書き」として"伝票"に積める、という二重表示にする。NVの「検索⇄作成」の境界消失を、muninnでは「検索⇄依頼作成」の境界消失に対応させる。ゼロヒットのときこそ「これはnotesにない知識だ、Claudeに聞こう」という自然な導線になる。
- **ボツになりうる理由**: 依頼テキストは通常、単なる文字列コピーでは済まず前後の文脈（対象ノート・タグ・関連リンク）が要る場合が多く、「検索欄に打った1行がそのまま依頼になる」ケースは実際には少数派かもしれない。案自体の効果を検証するには実際のinbox運用ログ（何を依頼しているか）を先に分析すべき。

### 案E: quasimode的な「長押し=プレビュー、離す=戻る」操作をカード/リストに導入する
永続的なモード切り替え（例: 編集モードON/OFF的なトグル）を避け、Raskinのquasimode原則に倣って「押している間だけ」発動する操作を導入する。例: リスト上のノートを長押ししている間だけ関連ノート・MOCへのリンクをプレビュー表示し、指を離すと通常表示に戻る。片手操作・読み専用という制約と相性が良い（誤操作しても指を離せば必ず元の状態に戻る安全性）。
- **ボツになりうる理由**: iOSのシステムジェスチャ（長押し=コンテキストメニュー、3D Touch相当の別機能）と衝突しやすく、独自の長押し挙動を割り込ませるとOS標準の期待を裏切るリスクがある。また「押している間だけ」という操作はテキストベースのquasimode（Shiftキー）ほど自然にタッチ操作へ翻訳できない（指が画面を覆ってプレビュー対象が見えなくなる、という物理的矛盾がある）。

## 8. Web (PWA) で再現する際の技術的勘所

1. **iOSのソフトキーボードは「オーバーレイ」ではなく「ビューポートのリサイズ」として扱われる**
   `window.innerHeight`は変化せず、`visualViewport.height`だけが縮む。キーボード表示時にレイアウトを追従させたい場合は`window.visualViewport`の`resize`イベントを監視する必要がある（`window`の`resize`はキーボード開閉では発火しないケースがある）。CSS新プロパティ`interactive-widget=resizes-content`（viewportメタタグ）でこの挙動を明示的に制御できる。

2. **input要素のフォントサイズが16px未満だとiOS Safariが自動ズームする**
   検索欄・コマンド欄は特にこの罠にかかりやすい。`font-size: 16px`以上を明示する。

3. **`touch-action`をhtml要素全体に`manipulation`で設定すると、PWAスタンドアロンモードでキーボードが出ない不具合が報告されている**
   `input/textarea/select`には`touch-action: auto`を個別指定するなど、グローバル指定を避ける。

4. **IME変換中の入力を早合点して処理しない**
   日本語入力はローマ字→変換候補→確定という多段階を経る。`keydown`イベント単体でEnterキーを検知すると、変換候補の確定操作（Enter）を誤って「検索実行」や「送信」と解釈してしまう。`compositionstart`〜`compositionend`の間は`isComposing`フラグを立て、確定前のEnter/矢印キー等を通常のショートカットとして処理しない実装が必須（NV型・コマンドパレット型のいずれでも、日本語入力ユーザーがいる前提なら最優先で潰すべきバグ）。

5. **フォーカス管理: 起動直後に自動フォーカスするかどうかは要検討**
   iOSではJavaScriptからの`input.focus()`はユーザー操作（タップ等）を伴わないと機能しないことが多い（自動でキーボードをポップアップさせられない）。NV型の「開いたら即入力できる」体験をそのまま持ち込むと、初回起動時に「フォーカスされているように見えるがキーボードが出ない」というズレが生じる可能性がある。ホーム画面PWA起動直後の一発目タップで初めてキーボードが立ち上がる設計を前提にする。

6. **ホーム画面PWA（standalone display-mode）特有の癖**
   - safe-area-inset（ノッチ・ホームインジケータ）を`env(safe-area-inset-bottom)`等で必ず考慮しないと、入力欄やツールバーがホームインジケータに隠れる。
   - 複数のPWAインスタンスを同時に開くとキーボード入力が1文字目以降反応しなくなるバグ報告があり（未確認: 特定OSバージョン依存の可能性が高い）、単一インスタンス運用を前提にするか、この既知の不具合を回避するテストを入れる。
   - standaloneモードはSafari本体と挙動が微妙に異なる（アドレスバーがない分、visualViewportの基準点がズレるケースがある）ため、**Safariブラウザタブでの動作確認だけでなく、実機ホーム画面PWAでの確認が必須**（これはCLAUDE.mdのモバイル実機確認ルールとも整合する）。

7. **インクリメンタル検索の実装コストは低い（muninn向けの朗報）**
   全データが復号後クライアントメモリに載っている前提（記事90本・ノード200）なら、Everything/fzf/Algoliaのような「サーバー往復ゼロ・毎キー入力でO(n)フィルタ」は素朴な実装でも数ms〜十数msで返る規模。Algoliaのようなバックエンド最適化は不要で、`requestIdleCallback`や単純なdebounce（体感上は不要な場合が多いが、連続キー入力での再描画コストが気になる場合の保険として）程度の配慮で足りる。
