# 知識管理（PKM/ノートツール）の実験的・尖ったUI — リサーチレポート

対象: muninn 閲覧サイト刷新のための参考調査。「読み専用・iPhone片手・ダーク固定・90ノート規模・リンクに理由が1行付く」という前提に対して、PKMツール史上の"尖った"UIパターンを事例ベースで洗い出す。

すべての事実記述は WebSearch / WebFetch で当たった一次・準一次情報に基づく。確証が取れなかった数値・引用は「未確認」と明記した。

## 1. 具体例（14件）

### 1-1. Andy Matuschak's Working Notes — stacked pages
- **URL**: https://notes.andymatuschak.org/
- **時期**: 2020年〜、現在も更新中（生きている・研究環境として継続運用）
- **仕組み**: リンクをクリックすると、遷移せず**新しいカラムが右側に追加**される。前のカラムは消えずそのまま残り、横スクロールで行き来できる。状態はURLの `stackedNotes` クエリパラメータの連なりで表現される（例: `?stackedNotes=zAAA&stackedNotes=zBBB...`）ため、URLそのものが「どの経路でここまで来たか」の完全な記録になる。
- **何のコストを削ったか**: 「戻るボタンを押して元の文脈を再構築する」コスト。ブラウザ履歴は時間順に1本道しか保持しないが、stackingは**辿った経路を空間的に並べて全部同時に見える状態**にする。
- **なぜ効くか**: 物理的なツェッテルカステンで複数のカードを机に並べて見比べる体験のデジタル再現。「クリック（連想）」という行為自体が、消えない永続的なオブジェクト（カラム）になる。
- **破綻・批判**: Matuschak自身、これを製品としてリリースしていない（"まだ非常に初期の研究環境"と明言）。Maggie Appleton の批評 "Tools for Thought as Cultural Practices, not Computational Objects" は、Tools for Thought 言説そのものが「白人男性・北米・工科大学関係者」に偏った狭いコミュニティの産物であり、**ノートを書く力は道具ではなく何年もかけて身につく文化的実践**だと指摘する（該当エッセイは未完成のドラフトで、後半の「なぜノートアプリが使われなくなるか」の議論は未執筆——本文からは確認できず）。横カラムは**幅を必要とする**ため、iPhone幅では原理的に成立しない。

### 1-2. Ted Nelson's Xanadu / OpenXanadu — transclusion
- **URL**: https://xanadu.com/ 、2014年公開の "Origins" デモ
- **時期**: 構想は1960年代、OpenXanaduとして2014年6月に一部公開。**事実上ほぼ死んでいる**（2014年時点で「オープンと言いつつオープンソースではない」状態、その後の実利用の広がりは確認できず）。
- **仕組み**: 引用文が元テキストと**視覚的に接続されたまま**（縦のカラーバーで出典に接続）複数の文脈に同時に存在できる。コピペではなく、単一の実体を複数箇所から参照する。
- **何のコストを削ったか**: コピペによる「複製が元から乖離していく」問題（引用のドリフト）。
- **なぜ効くか**: Roamのブロック参照・埋め込みや、Notionの同期ブロックの直接の思想的祖先。
- **破綻・批判**: 50年以上かけても主流化しなかった。双方向リンク・永続URL・バージョニングという前提インフラをWebが結局実装しなかったため。2014年のデモも「ブラウザハックによる実演」の域を出ていない。

### 1-3. ZigZag / Zzstructure（Ted Nelson）
- **URL**: https://www.dgp.toronto.edu/~mjmcguff/research/zigzag/（McGuffinによる研究的実装の解説）
- **時期**: 1990年代設計。**製品として広く出荷されたことはなく、研究プロトタイプのまま**。
- **仕組み**: セルが複数の「次元（dimension）」に沿って同時にリスト・グリッド・ツリーとして接続される。1つのセルが文脈によってリストにもグリッドにもツリーにも見える。
- **何のコストを削ったか**: 「書く時点で単一の階層構造を確定しなければならない」という強制。
- **なぜ効くか**: 「同じノートが年表としても、トピック別索引としても、リンクグラフとしても見える」という発想の元ネタとして興味深い。
- **破綻・批判**: 2Dセルグリッドをパンして操作するUIがついに主流の操作メタファーを獲得できず、Nelson自身のデモ以外にほぼユーザーがいない。学習コストが極端に高いことが不採用の主因とされる。

### 1-4. Bret Victor — "Explorable Explanations"
- **URL**: http://worrydream.com/ExplorableExplanations/（2011年エッセイ）
- **時期**: 2011年。ジャンルとしては現在も生きている（Nicky Case, Vi Hart, Dan Shiffman など後継者多数）。
- **仕組み**: 静的な文章の中にドラッグ可能なパラメータ付き小型ウィジェットを埋め込み、「もし〜だったら」を読者が実際に動かして確認できるようにする。単発のインタラクティブ図と違い、**読者の注意を特定の現象に意図的に誘導する**点が特徴。
- **何のコストを削ったか**: 「頭の中でシミュレーションする」認知負荷を、実際に触れる小さな計算機に肩代わりさせる。
- **なぜ効くか**: Active reading（能動的読書）は記憶定着に効くという主張（muninnの想起・定着コンセプトと親和性が高い）。
- **破綻・批判**: ジャンルとしてはニッチ・職人技のまま留まった——1本1本が作り込みの手作業で、汎用的な「探索可能ノート」オーサリングツールは一度も一般化していない。90ノート規模で個別に作り込むのは非現実的。

### 1-5. Miller columns（macOS Finder Column View）
- **URL**: https://en.wikipedia.org/wiki/Miller_columns
- **時期**: NeXTSTEP File Viewer（1986年）由来、Mac OS X 10.0（2001年）でFinderに実装。**現在も現役**（Finder, iTunes系ブラウザ, ファイル保存ダイアログ等）。
- **仕組み**: 階層の各レベルが専用カラムを持ち、選択すると次のレベルが右に新カラムとして開く。前のカラムは残るので、経路全体（＝実質的なパンくずリスト）が常に画面に出ている。
- **何のコストを削ったか**: ドリルダウン型ナビゲーションの「自分が今どこにいるか分からなくなる」問題。パンくずリストを別途表示する必要がない——カラムの並び自体がパンくずになる。
- **なぜ効くか**: ファイルシステムが厳密な木構造（親は1つ）だからこそ機能する。Matuschakのstackingはこれをグラフ（親が複数＝被リンクが複数）に一般化したものと言える。
- **破綻・批判**: 1カラムあたり数百pxの横幅が必要で、**狭い画面では原理的に2カラム以上並ばない**。iPhone幅でのMiller columns体験は事実上不可能——横カラム系パターンがモバイルで軒並み死ぬ、という本レポートの結論の直接的な根拠。

### 1-6. Roam Research
- **URL**: https://roamresearch.com/
- **時期**: 2019年公開、2020年に大きな話題性のピーク、現在も存続（月額$15）だが勢いは明確に落ちた。
- **仕組み**:
  - **Shift+クリック**でページを右サイドバーに、遷移せず追加表示。複数ページ・複数ブロックをサイドバーに積み重ねられ、それぞれ独立にスクロール可能（＝Matuschakの横積みの縦版・マルチペイン版）。
  - **ブロック参照**（`((block-id))`）と**ブロック埋め込み**（`{{embed: ((id))}}`）により、段落単位でXanaduのtransclusionを実装。埋め込みブロックを編集すると元・全埋め込み先が同期する。
- **何のコストを削ったか**: 「このアイデアはどのページに属するか」を事前に決める負担。Daily Notesを受け皿にし、ブロック参照で後から構造化する設計思想。
- **なぜ効くか**: リンクの多いグラフを、文脈を失わずに複数同時に読める。
- **破綻・批判**: **「みんな契約したが誰も使い続けなかった」の代表例**として頻繁に引き合いに出される。Daily Notes起点の運用は未整理の山を生み、後から読み返しにくい。グラフビューはObsidian同様「ハイボール（毛玉）化」して機能しない。モバイルWebアプリは明示的に「トグル・箇条書き・テキストが同じ小さな画面に密集して操作しづらい」と批判されており、Obsidianモバイルより悪いという評価がある。

### 1-7. Obsidian グラフビュー + Breadcrumbs / Juggl / Excalibrain
- **URL**: https://obsidian.md/ 、 https://community.obsidian.md/plugins/breadcrumbs 、 https://juggl.io/ 、Excalibrain（Obsidianコミュニティプラグイン）
- **時期**: Obsidianは2020年〜現在も市場支配的・活発に開発中。Juggl は**更新が長期間止まっており、2024年に「プラグインが動作しない」報告あり——事実上メンテナンスがほぼ止まっている状態（完全な廃止と断定はできず、"未確認"）**。Breadcrumbs / Excalibrain は現役。
- **仕組み**: 標準グラフビューは物理シミュレーション（force-directed）でノードを配置。r/ObsidianMD コミュニティの一致した評価は「見て楽しいが操作には使えない」。目安として**50ノート未満なら構造が読める**が、**200ノート超で"毛玉化"**、**500ノート超でパフォーマンスも実用外**になるとされる（コミュニティ内の目安であり厳密な学術数値ではない）。ノートの優先度・ステータス・更新日時などは表示されず、接続の有無しか分からない。
  - 代替として登場した各プラグインは全て「物理シミュレーションをやめて、型付き・整列された表示に置き換える」方向で収束している: **Breadcrumbs**はリンクに親子・前後などの型を持たせ、ノート上部にテキストのパンくずリストとして表示（グラフですらない）。**Excalibrain**は日付・被リンク数・フォルダ階層でソートした木構造にレイアウトし直す。**Juggl**は型付きエッジをスタイリング可能な形で表示。
- **何のコストを削ったか / なぜ効くか**: 「今どのノートを読むべきか」の意思決定コストは、接続の有無だけでは解決しない——**構造（型）と順序（ソート）が要る**、という学び。
- **破綻・批判**: グラフビューは「マーケティング画面としては映えるが日常操作では機能しないPKM機能」の典型例として繰り返し引用される。muninnにとって最も重要な反面教師。

### 1-8. Wikipedia Page Previews（旧 Hovercards / Popups extension）
- **URL**: https://www.mediawiki.org/wiki/Page_Previews 、 https://wikimediafoundation.org/news/2018/04/17/wikipedia-page-previews/
- **時期**: 2018年4月に発表、**現在もログアウトユーザーにデフォルト有効**。
- **仕組み**: 青リンクにホバーすると、冒頭数文＋サムネイル画像がポップアップ表示され、遷移せず内容の見当がつく。
- **何のコストを削ったか**: 「クリック→読む→戻る→文脈を失う」のコストを、**リンククリックの大半（好奇心ベースの"これ何？"確認）**について丸ごと削る。
- **なぜ効くか**: グラフビューと違い**線形・テキストベース**であり、画面サイズに関わらず崩れない。新しい空間的メンタルモデルの学習が不要。
- **破綻・批判**: 目立った批判は確認できなかった（デフォルトオンだが、設定から無効化可能という選択の余地を残している点は評価されている）。本レポート内で調査した尖ったUIパターンの中で**モバイル適応性が最も高い**候補。

### 1-9. Heptabase
- **URL**: https://heptabase.com/
- **時期**: 2022年〜、現在も活発に開発中（2024年タグ機能・Journal強化、2025年AI機能追加）。
- **仕組み**: 無限2Dホワイトボード上に「カード」（本格的なMarkdown・バックリンク・タグを持つ実体としてのノート）を空間配置。同じカードを複数のホワイトボードに置ける。
- **何のコストを削ったか**: 「このノートは1つのフォルダ/1つの親にしか属せない」という強制的な単一所属。
- **なぜ効くか**: Obsidianのグラフビューと違い、**配置がユーザー（実質は書き手）自身の意図で固定される**ため、空間記憶（method of loci）がそのまま機能に使える——物理シミュレーションで毎回レイアウトが変わるグラフビューとの決定的な違い。
- **破綻・批判**: レビューでは「ホワイトボードの編集やPDFへの意味のある書き込みはiPad/デスクトップ前提で、モバイルでは満足に使えない」と明言されている。ホワイトボード＝ポインティングデバイスと広い画面が前提のパターンであることを裏付ける。

### 1-10. Tana（supertags / Live Search）
- **URL**: https://tana.inc/
- **時期**: 2023年〜、現在も活発（4.4/5のレビュー評価、ただし出典サイトは信頼性中程度）。
- **仕組み**: ノードに `#meeting` のようなsupertagを付けると即座に日付・参加者などの型付きフィールドを持つ構造化オブジェクトになる。「Live Search」は保存済みクエリで、条件に合うノードが後からグラフ内のどこに追加されても自動的に一覧へ反映される——**手動参照ではなく、クエリによる自動transclusion**。
- **何のコストを削ったか**: 「索引ページを手作業で更新し続ける」コスト。
- **なぜ効くか**: 構造は後付けで足せるが、一度付けたsupertagはグラフ全体に効いてくる。
- **破綻・批判**: 学習曲線の高さが繰り返し指摘される。supertag設計という「事前スキーマ設計」が要求される点は、Roam/Logseqの「とりあえず書いてから構造化する」という売りと矛盾しがち。

### 1-11. iA Writer / Bear / Craft / Ulysses（Notion的定石への逆張り）
- **URL**: https://ia.net/writer 、 https://bear.app/
- **時期**: iA Writer 2010年〜、Bear 2016年〜、いずれも現役・継続開発中。
- **仕組み**: 意図的に機能を「足さない」。サイドバーツリーを標準で出さない、Focus Modeは編集中の1文以外をグレーアウト、WYSIWYGではなくMarkdown記法の色分けのみ。プロパティパネルもデータベースビュー切替もない。
- **何のコストを削ったか**: 「何を設定すればいいか」という選択・意思決定のサーフェス自体をゼロにする。
- **なぜ効くか**: Notion/Tana/Capacitiesが「もっとビューを増やす」方向にどんどん向かう中、「表示面をそぎ落とす」方向にも十分に商業的な支持者がいることを示す反証。muninnの「書き込みUIを作らない」方針と地続きの思想。
- **破綻・批判**: 明確な批判は今回の調査では確認できず（あくまで機能を絞ったニッチ市場向けとして安定運用されている）。

### 1-12. Anytype / Capacities（「すべてはtypeを持つobject」モデル）
- **URL**: https://anytype.io/ 、 https://capacities.io/
- **時期**: Anytypeは2023年ベータ終了、現在も開発中（local-first・オープンソース）。Capacitiesは2022年〜現役。
- **仕組み**: すべてのノート・タスク・人物・プロジェクトが「Object」であり、「Type」と「Relations（型付き関係）」を持つ。これによりMarkdownファイルの寄せ集めではなく、型付きオブジェクトのグラフになる。
- **何のコストを削ったか**: 「これはノートかデータベース行か」という区別自体をなくす。
- **なぜ効くか**: NotionのDB構造化とObsidian/Roamのリンク自由度の中間点として評価されている。
- **破綻・批判**: オンボーディング時に「そもそもobject typeとは何か」で学習コストが発生すると繰り返し報告されている。Anytypeはモバイルでの機能パリティが弱いと名指しで指摘されている。

### 1-13. Reflect（bidirectional backlinks, daily notes）
- **URL**: https://reflect.app/
- **時期**: 2021年〜、現役。
- **仕組み**: フォルダ階層の代わりにバックリンク＋タグのみで組織化。Daily Notesを起点にする（Roam/Logseq系譜）。
- **何のコストを削ったか**: フォルダのフォルダのフォルダ、という深い階層作りのコスト。
- **なぜ効くか / 破綻**: 特筆すべき破綻の記述は確認できず。競合との差別化点として「速さ」と「ブラウザ拡張での取り込みやすさ」が挙げられている程度。

### 1-14. Niklas Luhmannの物理ツェッテルカステン — Folgezettel番号法
- **URL**: https://zettelkasten.de/introduction/ 、ニクラス・ルーマン文書館 https://niklas-luhmann-archiv.de/bestand/zettelkasten/tutorial
- **時期**: 1950〜1990年代、Luhmann本人の死去（1998年）で運用終了。物理的実践としては**過去のもの**だが、思想的影響は現在のZettelkasten系ツール全般に及ぶ。
- **仕組み**: カードごとにアドレス（例: `21/3d7a`）を持つ。あるカードから派生する思考は、末尾に追加するのではなく**そのカードの番号を分岐させて**（`21/3d7a1`, `21/3d7a2`...）新カードを作る。無関係な離れたカードへの参照は番号とは別に相互参照として記す。
- **何のコストを削ったか**: 目次やインデックスを別途保守するコスト。番号自体が思考の派生関係（系譜）を符号化しているため、あるカードとその物理的な隣（次の1枚）を読むだけで局所的な議論の流れをそのまま追える。
- **なぜ効くか**: 「次の1枚を箱から取り出す」という強制的な連続性・セレンディピティのある閲覧体験。デジタルのwikilinkグラフはジャンプの自由度と引き換えにこの「強制された隣接」を失っている、という議論がzettelkasten.deフォーラムで続いている（結論は出ていない・諸説ある）。
- **破綻・批判**: 現代のデジタルZettelkasten系ツール（Obsidianなど）のほとんどはFolgezettel番号法を採用せず、純粋なリンクグラフに置き換えている。これが本当に失われた閲覧アフォーダンスなのか、単なる紙媒体の制約由来の遺物なのかは議論が分かれている（未確定）。

## 2. 分野から抽出できる原理（6個）

1. **「時間」ではなく「空間」で文脈を持続させる。** ブラウザの戻るボタンは1本道の時系列履歴しか保持しないが、Matuschakのstacking・Roamのサイドバー積み・Miller columns・Heptabaseのキャンバスは、辿った経路や関連ノートを**同時に・空間的に**画面上に残す。「戻れば消える」から「置いておける」への転換が体験の核。
2. **遷移する前に覗ける（Peek before you leap）ことがナビゲーションコストを激減させる。** Wikipediaのホバープレビューが示す通り、リンククリックの大半は「これ何？」という好奇心的確認であり、遷移・読了・復帰という重いサイクルを踏ませる必要がない。
3. **フォースレイアウトのグラフビューはデモ映えする機能であり、日常のナビゲーション手段としてはほぼ確実に機能しない。** Obsidian・Roam双方で「200ノート超で毛玉化、機能不全」という一致した評価が出ている。実際に機能している代替（Breadcrumbs, Excalibrain, Wikipediaプレビュー, Tana Live Search）は例外なく「物理シミュレーションをやめて、型付き・整列済み・テキストベースの表現に置き換える」方向に収束している。
4. **配置に意味を持たせるなら、その配置はユーザー（書き手）が決めたものでなければならない。** Heptabaseの固定キャンバス位置が空間記憶として機能するのは、位置が計算結果ではなく意図の産物だからである。アルゴリズムが毎回計算し直す配置（グラフビューの物理演算）は記憶の手がかりにならない。
5. **プレビュー・索引は「すでに書いた本文」の再利用であるべきで、別フィールドとして書かせてはいけない。** Wikipediaプレビューは記事冒頭の文をそのまま使う。Tanaのsupertagやobject typeモデルが学習コストとして繰り返し批判される一因は、通常の執筆とは別に「構造」を明示的に設計・入力させる点にある。
6. **この分野の"尖った"パターンのほとんどは広い画面幅を前提にしており、モバイル幅では原理的に崩壊する。** カラム積み（Miller columns, Matuschak stacking）、サイドバー並列（Roam）、無限キャンバス（Heptabase）は軒並み「幅」という有限資源を食う。逆に、線形・テキストベースで完結するWikipediaのホバープレビューやLuhmannの「隣の1枚」モデルはナローウィンドウでも崩れない——尖ったUIを狭い画面に持ち込むときは、この違いを最初に踏まえる必要がある。

## 3. muninnへの適用具体案（5つ、ボツ理由つき）

### 案A: `[[wikilink]]` の長押し/タップでプレビューカードを表示する
リンクをタップ長押しすると、遷移せずに「リンク先冒頭+『なぜ関連するか』の1行」をオーバーレイ表示。muninnはリンク規約上、理由が必ず1行付いているため、Wikipediaのプレビューより一段リッチな文脈（＝相手がなぜ書いたか）を追加コストゼロで持っている。静的ビルド（`site.json`）はクライアントに全ノート情報を持っているため、プレビューはネットワーク不要・即時表示できる。
**ボツになりうる理由**: iPhone片手操作では「長押し」がスクロールジェスチャーやiOS標準のリンクコンテキストメニュー（Peek）と衝突しやすく、誤爆でイライラの原因になりうる。また90ノート規模だと実際に遷移して読むコスト自体が低く、プレビュー層を挟む価値が薄い可能性がある。

### 案B: 横カラムではなく縦のアコーディオン積み（垂直stacking）でリンク経路を可視化
リンクをタップすると新ノートが画面下に積み上がり（前のノートはタイトルバーだけの折りたたみ状態になる）、指で戻ると1段折りたためる、Matuschakの横積みの縦版。
**ボツになりうる理由**: スクロール位置保持・折りたたみアニメーションなど実装が繊細でPWA上の作り込みコストが高い。90ノート規模の閲覧では長いホップ数のリンク辿りが稀で、機能を使う場面自体が乏しい可能性が高い。

### 案C: 被リンクを力学グラフではなく「理由による型分け」リストとして見せる
グラフビュー的な可視化はObsidian/Roamの実例からほぼ確実に「見て終わり」になる。代わりに、あるノートを起点に被リンクを「前提知識として引用」「対比として引用」「深掘りとして引用」のように**理由文をもとにグルーピングしたリスト**として提示（Breadcrumbs/Excalibransが物理シミュレーションを型付きリストに置き換えたのと同じ発想）。
**ボツになりうる理由**: 現行のリンク規約は「理由を1行添える」だけで型（前提/対比/具体例…）を明示的にタグ付けしていないため、自動分類はLLM解析頼みになり、既存90本の理由文を再解析するバッチコストが発生する。また `CLAUDE.md` の原則「画面にconcernの内部語彙を出さない」との整合を取るには、リンク型の追加は設計思想レベルの提案としてユーザーに諮る必要があり、勝手には決められない。

### 案D: Luhmannの「隣の1枚」——直前にこのノートへリンクを書いた"きっかけ元ノート"へ1タップで遡るボタン
選択肢が多すぎて何を読むか決められない、というパラドックスを避け、「このノートを書くきっかけになった直前のノート」を1つだけ提示する導線。
**ボツになりうる理由**: muninnのノートには作成日時はあるが、Luhmannの物理番号のような明示的な派生チェーン（どのノートを読んでいてこのノートを書いたか）は現行スキーマに存在しない。created日付の前後関係だけでは「思考の連なり」を正しく表さない可能性が高く、機能としての説得力が下がる。

### 案E: MOC（束）をHeptabase的な"固定位置キャンバス"として扱い、空間記憶を利用する
MOCのfrontmatterに簡易な配置情報（グルーピング程度）を持たせ、サイトの「棚」タブで**毎回同じ場所にある**テーマの束として空間的に見せる。物理シミュレーションではなく意図的固定配置にすることで、Heptabaseの知見（配置がユーザーの意図の産物なら記憶の手がかりになる）を活かす。
**ボツになりうる理由**: 座標をどこでどう決めるか（Claudeが書くたびに整合を取り続けるのは運用コスト）が不明瞭。90ノート・MOC10個未満の規模では、空間配置のメリットが立つほどの複雑さがそもそも存在せず、過剰設計になるリスクが高い。

## 4. Web(PWA)で再現する際の技術的な勘所

- **横カラムstacking（Matuschak型）**: `overflow-x: auto` + `scroll-snap-type: x mandatory` のコンテナに各ノートをflex子要素として追加し、React側の配列stateで開いたノートを保持（完全な画面遷移にしない＝複数ノートを同時にマウントしたまま保つ）。ブラウザ/iOSのスワイプバック・戻る操作と衝突しないよう、Matuschak自身がやっているように**stackの状態をURLクエリパラメータに同期**させ、`history.pushState` で1段開くごとに履歴を積む設計が必要。
- **モバイル幅での縮退**: 横カラム系パターンは画面幅が足りないと原理的に成立しない（Miller columnsの検証結果）。ナロー幅では「1カラムのみ表示＋前のカラムはpushナビゲーションの奥に隠す」形へ自動縮退させる設計にしないと、iPhone一枚画面でMiller columns/stacking系を再現するのは不可能。
- **プレビュー（案A）はタッチデバイスでは`hover`が存在しない**ため、`touchstart`+タイマーによる長押し検出、または専用の小さいアフォーダンス（矢印アイコン等）でのタップ検出に置き換える必要がある。iOS Safari（特にPWA/ホーム画面追加時）はリンク長押しでネイティブのPeek/コンテキストメニューを出すため、`-webkit-touch-callout: none` 等での抑制と、独自プレビューUIとの競合回避を検証すること。
- **transclusion/ライブ同期（Roam/Tana型）はmuninnには不要な複雑さ**: muninnは読み専用の静的ビルドであり、実行時に「編集がどこまで同期されているか」というRoam/Tana/Xanaduが延々と戦ってきた問題自体が存在しない。埋め込み表示をしたい場合はビルド時（`build-data.mjs`）に全transclusionを解決してJSONに埋め込み、クライアントはただのデータ参照で済ませられる——これはこの分野の複雑さのかなりの部分をタダで回避できるmuninn固有の強み。
- **グラフビューは今回の調査結果からほぼ確実に投資対効果が低い**。仮に何か可視化するとしても、実行時の物理シミュレーションはスマホのCPU/バッテリーを食う上に「機能しない」という結論がほぼ出ている領域なので、やるならビルド時に固定レイアウトを計算した静的な型付きリスト/ツリー表示にとどめるべき。
- **キャンバス/ホワイトボード系（Heptabase型）はPWAでの実装コストが高い**: 本格的な2Dパン・ズームエンジンが要り、ブラウザネイティブのピンチズーム・スクロールと`touch-action`のスコープ調整で衝突しやすい。90ノート・単独読者・ダーク固定というmuninnの規模感に対しては投資が過剰になりやすい。
- **最もコストの低い勝ち筋は案A（プレビュー）**: muninnは全ノートをクライアントサイドの`site.json`として既に持っているため、プレビュー表示にネットワークも追加のサーバーサイド処理も不要——本調査で見た中で実装コストと効果の比が最も良い部類。
