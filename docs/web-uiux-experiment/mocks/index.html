muninn 閲覧サイト — 尖ったUIUXの3案

2026-07-31 ／ 8分野の先行事例リサーチ → 3方針の競作 → 人間工学による採点

現行サイトは下タブ4つ・カードの縦リスト・sticky ヘッダという定石のど真ん中にある。実装の質は高いが、 muninn だけが持つ武器——全リンクに「なぜ関連するか」の理由が1行付いているという規約——が、その器に閉じ込められている。 そこで「定石を壊して、実際に速く・楽に使える面を作る」ことだけを目的に、方針の異なる3案を同じ実データで競作させた。 以下の画面はすべて muninn の本物のデータ（記事93本・理由つきリンク91本分）で動いている。

前提 — この面が答えるべき4つのジョブ

  1. めくる — 今日読むものを差し出される（起動直後の3秒。通勤・寝る前）
  2. 見渡す — 「何があるんだっけ」に答える（記事93本／1テーマが47%を占める偏り）
  3. 当てる — 「あれ何だっけ」のピンポイント想起
  4. 頼む — Claude に渡す依頼を作って溜める（サイトにできる唯一の"書き込み"）

心臓部は想起。タイトルが言い切り形＝答えそのものなので伏せ、問いだけを見せて「めくる→わかった／あやしい」。 knowledge 59本すべてに問いが入っているが、59本すべてが復習期限を過ぎている——だから総量は絶対に画面に出さない。

3案

案A親指ひとつ

操作原点はひとつ、方向が意味。画面の上7割から操作要素を1つ残らず追い出す。

核となる一手原点を叩くと答えが出て、原点が2つに割れる。想起という最頻出操作が「同じ場所を2回叩く」まで圧縮される
壊したもの上部AppBar・戻る・ボトムタブ・グラス質感
依拠Hoober の実測（親指がタップの75%を担う）／Samsung One UI の見る・操作の恒常分離／マーキングメニュー（パイは15%速い・Callahan 1988）
最大の賭け方向の記憶が「1日数分」の利用頻度で育つか。育たなければ毎回「押しっぱなし→扇を見る→選ぶ」となり、タブ4つより1手遅くなる

案B一本の欄

打つことが全部。タブもページ遷移も無く、面の中身は欄の中身だけで決まる。

核となる一手Notational Velocity の「見つからなければ、そのまま作る」を、読み専用の制約下で「見つからなければ、そのまま Claude への依頼になる」に翻訳した
壊したもの画面という単位・ページ遷移・上から下へ読む順序
依拠Notational Velocity「検索欄＝作成欄」／Raskin のモードレスと quasimode（欄を消せば必ず元に戻る）／Bloomberg Terminal の密度＝信頼
最大の賭け「上へ積む」組版に体が馴染むか。スクロール位置が下端に固定されるのはチャットの文法であって読み物の文法ではない

案C紙面をめくる

組版が編集判断。縦スクロールを主動作から降ろし、めくる軸（横）と読む軸（縦）を直交させる。

核となる一手記事の欄外に「傍註」としてリンク元が書いた理由を組む。Wikipedia の Page Previews より一段リッチな、muninn だけが持てる紙面表現
壊したもの縦スクロール・均一カード・ダークグラス（紙とインクへ）
依拠Bloomberg Businessweek のモジュール型紙面／Tufte「視線移動を減らす」／日本語組版（明朝×ゴシック・縦組みの柱・Webフォントゼロ）
最大の賭け横めくりが縦スクロールより読みやすいと言えるか。実証研究は割れており確定的優位性がない

人間工学からの採点

Fitts／Steering law／Hoober の親指可動域／Norman & Nielsen のジェスチャ批判／Hick／Raskin のモード論／WCAG 2.2 の ターゲットサイズ基準に照らして、3案それぞれの成立条件と破綻条件を出した。

案A親指ひとつ

成立する条件分岐は1階層・主要動線は最大4／原点を親指の自然域に固定／ヒントを常時表示／VoiceOver 時は標準UIへ縮退

破綻する条件8方向を使うと記憶限界を超える／「上7割は操作要素ゼロ」は初見で原点の存在自体が発見されない／左下起点のドラッグが iOS の戻るジェスチャと物理衝突しうる

案B一本の欄

成立する条件visualViewport への完全対応（生命線）／空欄・入力中・ゼロヒットの3状態を色・記号・文言の複数チャネルで常時可視化

破綻する条件テキストの有無だけで状態が変わる暗黙モードはモードエラーの典型／キーボード表示中は情報が画面上半分に圧縮され、親指可動域の知見と衝突

案C紙面をめくる

成立する条件めくる軸と読む軸の直交はモード論的に比較的安全／現在地インジケータ必須／画面端でなく内側起点のスワイプ

破綻する条件横めくりが縦スクロールより読みやすいという実証は割れており、確定的優位性がない／端起点だと戻るジェスチャと正面衝突／93本規模では位置を見失いやすい

3案共通の判定

想起の2択は Hick 則的に理論上最速（n=2）で強く支持される。ただし左右の意味は全画面・全セッションで固定し、ジェスチャ化するならボタンを必ず並置すること。 リンクのプレビューは有効だが、「長押し＝時間依存の不可視パラメータ」は Norman & Nielsen 批判の典型例——VoiceOver 代替導線が要る。

審査

案B一本の欄 — 最も"使い勝手"に効く

15項目の線をほぼ全て素通りする唯一の案。自前ジェスチャ0・演出0・グラス0で、削った先に残ったのが 「muninn に無かったこと自体が次の蓄積の入口になる」という、この製品にしか成立しない一手だった。 リスクは人間工学ではなく習慣——上向きの組版に体が馴染むかどうか、その一点に集約されている。

案A親指ひとつ — 一手の鋭さは随一、賭けが一番重い

「原点が2つに割れる」は3案で最も鮮烈な瞬間で、最頻出操作を同じ場所を2回叩くまで圧縮している。 ただしマーキングメニューの優位は反復頻度が支える。1日数分の muninn でそれが育たなければ、 毎回「押しっぱなし→扇を見る→選ぶ」となりタブ4つより1手遅くなる。可視の逃げ道を4重に用意したのは、その自覚の裏返しでもある。

案C紙面をめくる — "他にない"の度合いは最大

唯一製品の見た目が別物になる案で、日本語組版と「理由つき傍註」という muninn 固有の資産を最も豊かに使っている。 弱点は骨格側にある——横めくりに読書効率上の確定的優位はなく、操作の刷新ではなく様式の刷新に留まる危険がある。 新聞メタファは「中身がないのに様式だけ真似ない」という自らの設計原則と、常に隣り合っている。

結論

骨格は案B、読む面の組版は案C、想起の一手は案A。

3案は競合ではなく、賭けている層が違う。Bは操作の構造（モードを消す）、Cは情報の重み付け（組版で編集する）、 Aは1操作の物理（指を動かさない）に賭けている。どれか1つを丸ごと採るより、層ごとに勝った案を採るほうが強い。

ただしこれは合成案の推奨ではない。3つを混ぜると、それぞれの案が持っていた「法則がひとつしかないから予測できる」という 最大の美点が壊れる。まず1案を選んで骨格を通し、そのうえで他案の一手を移植するかを判断するのが正しい順序だ。 迷うなら B から始めるのを勧める——実装コストが最も小さく（既存実装から画面数が減る）、失敗したときに一番安く引き返せる。
