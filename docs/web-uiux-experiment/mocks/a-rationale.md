# 案A「親指ひとつ」— 設計の弁明

## 賭けているもの

この案が賭けているのは、**「操作の場所を探す」というコストが、実は muninn で一番大きい無駄だった**という読みだ。Hoober の実測（片手持ち49%、親指がタップの75%を担う／`research/01-thumb-zone.md`）が示すのは、上部のAppBarも下部タブも、押すたびに親指を「どこへ動かすか」の判断を要求しているということ。だから **画面の上7割から操作要素を1つ残らず追い出し、操作を画面下の一点＝「原点」に集約した**。Samsung One UI の「見る領域／操作する領域」の恒常分離（同ファイル 2-3）を、一時的な呼び出し（Reachability）ではなく構造として最後まで押し切った形だ。原点の上には方向で意味が決まる扇が開く——Path の端起点の扇とマーキングメニュー（`research/06-game-hud-radial.md` 1-2）。ただし賭けの成否を分けるのは速度ではなく**忘れたときのリカバリ**なので、そこに設計の重心を置いた。

## 4つのジョブをどう解いたか

**J1 めくる。** 起動＝今日の面。上7割いっぱいに `recall` の問いだけが立ち、タイトルは伏せる。原点をぽんと叩くと本文が出て、**原点が2つに割れる（左＝あやしい／右＝わかった）**。指は原点から一歩も動かない——ここが最も回数を重ねる操作なので、方向ジェスチャすら使わず「同じ場所を2回叩く」に圧縮した。判定直後に6秒間の「↺取り消す」が原点の右に出る。今日の枚数は閲覧日（クライアントの `new Date()`）を種にしたFNVハッシュ順で5枚。同じ日は何度開いても同じ順。

**J2 見渡す。** テーマを件数順の帯グラフで描く。ゴルフ45本が画面を占め、睡眠2本は線にしかならない——**この偏りは事実なので均等グリッドに逃げない**。帯（下部のリール）をはじくと選択中のテーマが上で光り、下端の覗き窓に最近の記事が出る。原点を叩けば降りる。

**J3 探す。** 検索欄は原点の真横（下3割）に置き、結果は上に出す。ソフトキーボードが画面の4〜5割を食う問題（`RESEARCH-DIGEST.md` A-8）に対し、**入力とコントロールは親指帯に、結果は視線帯に**という分担で答えた。ゼロヒットは「ありません」ではなく**その語をそのまま Claude への依頼に変換**する（Notational Velocity の「ゼロヒット→新規作成」の読み替え／A-7）。

**J4 頼む。** 伝票は溜めてコピーするだけ。どの画面からでも原点を↑に引けば頼むへ行き、**いま見ているものが依頼文に付いてくる**。方向の意味は固定でも、運ぶ荷物は文脈が決める。

## 壊した定石と、その根拠

- **ボトムタブ4つを廃止**（`RESEARCH-DIGEST.md` C-2）。目的地4つが同格でないなら、タブは4つ分の面積を等しく浪費するだけ。1点＋方向に畳んだ。
- **AppBarと‹戻るを廃止**（C-1）。戻るは「原点から下へ引く」に移した。上1/3は親指が届かない。
- **均一なカードの縦リストを廃止**（C-3／A-13）。組版は情報の重み付け装置なので、面ごとに組版のルールを変えた（カード／帯グラフ／行リスト／数値グリッド）。
- **backdrop-filter のグラスを捨てた**（線12）。不透明なグラデーションとヘアラインのHUDに置換。iOS Safari の GPU ブラーを一度も走らせない。
- **force-directed グラフは作らない**（A-3）。連載の型付きエッジは「前提／対比／発展／深掘り／蒸留」というラベル付きの帯として出す。決定的で、リストで代替可能。

## 「理由つき被リンク」をどう使ったか

muninn の `linkrefs` は `- [[x]] — なぜ関連するか` という規約を持つ。これを**遷移せずに覗く装置**の中身にした（A-9、`research/03-pkm-tools.md` 案A）。記事を開くと、帯には「ここへ来る道／ここから伸びる道」が並ぶ。1つ選ぶと、**画面下端の覗き窓に「相手が書いた理由」が最初に出て、次に相手のタイトル、最後に相手の想起の問い**が出る。Wikipedia の Page Previews が冒頭数文しか出せないのに対し、こちらは**「なぜ繋がっているか」を先に読ませられる**。跳ぶかどうかは、それを読んでから原点で決める。被リンクは `linkrefs` の逆引きに加え、見取り図（MOC）のセクションと理由、連載の型付きエッジ、章→記事の蒸留関係まで統合した。結果、行き止まりの記事は1本も無い。

## 実装コスト見積り（React + Vite の既存実装からの差分）

- **そのまま残る**: `build-data.mjs`／`site.json`／復号／被リンクの逆引き／SRS更新ロジック。約6割は流用できる。
- **捨てる**: Chakra UI（原点と帯は素のCSS/DOMのほうが確実に速い）、ボトムタブ、AppBar、カード縦リスト、既存のページ分割。
- **新規**: 原点コンポーネント（Pointer Events＋扇の幾何＋利き手ミラー）約400行／帯（scroll-snap＋Dock式フィッシュアイ＋wheel変換）約200行／覗き窓 約150行／面ごとのVIEW・REELアダプタ 10面×50〜120行。
- **工数**: モック相当まで**2〜3日**（1人）。加えて iOS 実機での `env(safe-area-inset-*)` と `visualViewport`（ソフトキーボード時の検索欄追従）の詰めに**+2日**。**合計4〜5日**。
- なお操作領域（下250px）は `--ops` 一変数で決まり、原点・帯・覗き窓・扇の幾何はすべてそこから算出している。safe-area の実測値に合わせて1行変えれば全部が追従する。
- **リスクのある工数**: `setPointerCapture` と `scroll-snap` の同居、PWA standalone とタブ内での inset 差、キーボード表示時に原点が隠れない高さ制御。ここだけは実機で測るまで読めない。

## この案の弱点・落選しうる理由（正直に）

1. **方向の記憶が育たないまま終わる可能性がある。** 1日数分・低頻度という muninn の利用実態では、マーキングメニューが前提とする反復回数に届かない（`research/06-game-hud-radial.md` 案C／A-10）。育たなければ毎回「押しっぱなし→扇を見る→選ぶ」になり、**タブ4つより1手遅い**。この案の最大の弱点であり、可視の逃げ道を4重にしたのはその自覚の裏返しでもある。
2. **「上7割は触れない」が厳しすぎる。** 記事本文中のリンクがタップできないので、初見では「壊れている」と読まれうる。道が帯に並んでいると気づくまでの数秒が確実にコストになる。原則の純度と初見の分かりやすさを引き換えにした。
3. **「操作原点はひとつ」を厳密には守れていない。** 選択（帯）と決定（原点）で2箇所ある。1点だけでN個から選ぼうとすると隠しモードになるため意図的に分けたが、方針からの逸脱ではある。
4. **長いリストで帯が遅い。** ゴルフ45本を帯でスクラブするのは苦しい。探すで補えるが、俯瞰→降りる→選ぶの導線が帯に依存しすぎている。
5. **質感が好みを外す可能性。** HUD寄りに振ったぶん、オーナーが気に入っていたグラスの柔らかさは完全に失われた。「尖っているが冷たい」と読まれうる。
6. **密度は中庸に留めた。** Bloomberg Terminal 的な「密度＝信頼」（A-13）には振り切っていない。上7割を読む専用にした結果、1画面あたりの情報量はむしろ減っている面がある。
