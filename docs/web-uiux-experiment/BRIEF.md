# muninn 閲覧サイト UIUX 実験 — デザイナー共通ブリーフ

このドキュメントは、3人のデザイナーが**共通の前提**として読むもの。
方針（尖り方）は各デザイナーごとに別途指示されるが、**ここに書かれた事実・制約・ジョブは全員が守る**。

---

## 0. この案件の目的

muninn（個人ナレッジベース）の閲覧サイトは、つい先日「日報」メタファで刷新されたばかりで、
実装としては良くできている。しかし **UIUX が"定石的なモダンスマホアプリ"のど真ん中**——
画面下タブ4つ／カードの縦リスト／sticky ヘッダ／グラスモーフィズム——であることにオーナーが不満を持っている。

**目的は「使い勝手を超最適化した、他にない UIUX を作ってみること」。**
「今風で綺麗」は要らない。**尖っていて、かつ実際に速く・楽に使える**ものを作る。
奇抜さのための奇抜さ（＝操作が遅くなる装飾）は落選する。

---

## 1. muninn とは何か（アプリの正体）

- **個人のナレッジベース。ユーザーは1人（オーナー本人）だけ。** 書いたのも本人。
- **正本は git リポジトリの markdown 群。このサイトはその派生ビルド**（捨てても再生成できる）。
- **書くのはターミナルの Claude Code、読むのはこのサイト**、という非対称が全ての前提。
  → **サイトに書き込み UI は作れない。** サイトができるのは「Claude に渡す依頼テキストを作って溜める」ところまで。
- 読むのは **iPhone、片手、寝る前や移動中**。書くのは Mac。
  → 読んでいる最中に思いついた依頼をその場で実行できない。**溜めて後でまとめて渡す**（＝「伝票」という仕組みの理由）。

### 5つの concern（＝中身の種類）

| 内部語彙 | 画面に出す語 | 実体 | 件数 |
|---|---|---|---|
| notes (`kind: knowledge`) | 記事 | 調べて得た客観的事実の原子ノート（1ノート1アイデア）。**間隔反復の対象** | 59 |
| notes (`kind: insight`) | 記事 | 自分で言語化した知見・身体知。クイズ対象外 | 34 |
| follows | 定点 | 1対象を同条件で定点観測する時系列ジャーナル | 3対象 / 観測7回 |
| atlas | 連載・章 | 概念ノード＋型付きエッジ＋読む順路（＝教科書） | 1連載 / 概念11 |
| logs | 記録帖 | 同じ記録項目で多数を貯めて並べて比べる台帳 | 1トピック / 記録1 |
| moc | 束 | 手書きの索引（テーマごとのリンク集） | 6 |

> ⛔ **画面に内部語彙（notes / follows / atlas / logs / MOC / concern）を出さない。**
> 必ず右列の語（記事・定点・連載・章・記録帖・束）か、それに代わる自前の語彙を使う。

## 2. ユーザーの4つのジョブ（これに答えられない案は落選）

| # | ジョブ | 動詞 | 典型的な状況 | 現状の受け皿 |
|---|---|---|---|---|
| **J1** | 今日読むものを差し出される | めくる | 起動直後の3秒。通勤・寝る前 | `/`（面） |
| **J2** | 在庫を俯瞰する「何があるんだっけ」 | 見渡す | ふと全体を確かめたいとき | `/shelf`（棚） |
| **J3** | ピンポイント想起「あれ何だっけ」 | 当てる | 会話中・作業中 | `/search`（探す） |
| **J4** | Claude への依頼を作る／溜める | 頼む | 読んでいて不足に気づいたとき | `/desk`（デスク） |

そして体験の心臓部が **想起（再読）**:
> ノートのタイトルは言い切り形＝答えそのもの。だから**タイトルを伏せて `recall:`（問い）だけを見せ**、
> 思い出してから「めくる」で本文を出し、**わかった／あやしい**の2択を押す。
> クイズ画面に入るという**モード切替が無い**ことが肝（起動コストがゼロ）。

## 3. データの実態（＝デザインが耐えるべき現実）

```
記事 93本（knowledge 59 / insight 34）  平均 1.8KB ＝ 読むのに1分以内の短文
タグ分布は極端に不均一:
  sports/golf            42  ████████████████████ 47%
  health/skincare         9  ████
  sports/football         7  ███
  science/cosmology       7  ███
  health/nutrition        6  ███
  geopolitics/middle-east 6  ███
  philosophy/ancient      5  ██
  health/hair             5  ██
  health/stress 3 / health/bathing 3 / philosophy 2 / health/sleep 2
  language/vocabulary 1 / knowledge/zettelkasten 1
連載 1件（概念11・うち未執筆 stub あり・ルート2本）
定点 3対象（ゴルフ飛距離=goal / 肌の毛穴=goal / アルゼンチン代表=interest・選手ドシエ10人）
記録帖 1トピック（記録1件だけ ＝ 比較機能が空回りしている）
ノード総数はせいぜい 200 程度
```

**重要な現実:**
- **1テーマが全体の半分を占める**。均等グリッドに逃げると、この偏りという事実が消える。
- **記録帖は1件しかない。連載も1本。** 「在庫が薄い面」でも死なない設計が要る。
- **更新は数日〜週単位**。push が2週間止まっても面が古びない仕組みが要る（＝閲覧日で組む）。
- **`recall`（想起の問い）は 59本の knowledge ノート全部に入っている**（欠落ゼロ。`web/DESIGN.md` の「既知の未達」の記述は古いので信じないこと）。
  つまり**想起カードは全記事で"本来の姿"で出せる**。ここは思い切って設計してよい。
- **ただし 59本すべてが復習期限を過ぎている**（`srs.next` の最新が 2026-07-27）。
  → だからこそ「59」という総量を絶対に画面に出さない（＝減らない借金）。**今日の数枚**に切り出すこと。

`mn-data.js` に**実データが全部入っている**（`window.MN`）。モックは必ずこの実データを使うこと。
ダミーテキストで作った画面は評価できない。

### データ構造で使えるもの（全部クライアントのメモリ上にある＝どんな横断計算も数ミリ秒）

- `[[wikilink]]` のリンク。**リンクには「なぜ関連するか」の理由が1行添えられている規約**
  （`- [[x]] — 前提となる知識だから`）。→ **被リンクを「相手が書いた理由」ごと逆流できる**。これは強い武器。
- タグ（階層タグ `health/skincare`）。全 concern を横断する第一階層。
- 連載の型付きエッジ: `requires`(前提) / `contrasts`(対比) / `leads-to`(発展) / `elaborates`(深掘り)。
- 定点の時系列数値 `series`（`metric_goals` で「大きいほど良い/悪い/中立」が宣言されている）。
- SRS 状態 `srs{last, interval, ease, next}`、想起の問い `recall`。
- git 由来の最終更新日 `updated`。

## 4. 絶対に守る制約（破ったら不採用）

1. **完全静的**。バックエンドなし。全データを起動時に復号してメモリに載せる。**書き込み UI は作れない**。
2. **画面に内部語彙を出さない**（§1 の表）。
3. **未消化の件数バッジを出さない**。「復習期限 59」は59件すべてが該当していて**常時点灯＝情報量ゼロの壁紙**だった。
   減らない借金の額は行動を止める。出してよいのは「今週12件 再読した」のような**増えるカウンタ**だけ。
4. **「今日どれを載せるか」はビルド日ではなく閲覧日（クライアントの `new Date()`）で決める**。
5. **日替わりは乱数ではなく日付シードのハッシュ**。同じ日は何度開いても同じ。リロードで引き直せると賭博になる。
6. **行き止まりを1つも作らない**。すべての詳細画面に「ここへ来る道」（被リンク）を例外なく置く。
7. **空状態に「ありません」と書かない**。次の一手（依頼ボタン）に変換する。在庫が無ければその段ごと消す。
8. **数字に嘘をつかせない**。指標の良し悪しは正本の宣言（`metric_goals`）に従う。宣言のない指標は中立に扱う。
   （実例: フェース角は大きいほど悪い。最大値を機械的に「自己ベスト」と出して、profile 自身が警告している悪化を成果として見せた事故がある）
9. **一度に見せるノードは12点まで**。図は必ずリストで代替可能にする（図は近道であって UI の本体ではない）。
10. **90ノードの force-directed グラフは作らない**（毛玉になる）。レイアウトは**決定的**（同じ場所に描かれることが記憶の手がかり）。

## 5. いま壊してよいもの（＝尖らせる余地）

- **画面下タブ4つ**（面／棚／探す／デスク）という構造そのもの
- **カードの縦リスト**という組版
- **sticky AppBar ＋ ‹戻る**というナビゲーション
- **グラスモーフィズム＋ダーク**という質感（オーナーは気に入っていたが、今回は聖域にしない）
- **1画面1目的**というページ分割
- 縦スクロール前提であること
- Chakra UI を使っていること（実装は React で作り直してよい）
- URL 構造（`#/note/:slug` 等）

---

## 6. モックに求めること

- **単一の HTML ファイル**（外部リソース禁止。CSS/JS はインライン）。`window.MN` の実データを使う。
- **iPhone サイズ（390×844 程度）で成立していること**が第一。デスクトップは副。
- **静止画ではなく動くこと**。少なくとも次は実際に触れること:
  - J1: 今日の面を開く → 想起カードを1枚さばく（問い→めくる→判定）
  - J2: 在庫を俯瞰する → 1テーマに降りる
  - J3: 何かを探す → 記事に着地する
  - J4: 依頼を作る／溜める
  - 記事を開く → 被リンク（ここへ来る道）から別の記事へ移動する
- **提案の"核"が一目でわかること**。方針を説明しないと伝わらない案は弱い。
- 実装可能性: React + Vite の静的サイトで作れる範囲。WebGL や重量級ライブラリに依存しない。
