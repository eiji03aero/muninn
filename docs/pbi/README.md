# PBI（実装待ちの作業項目）

`docs/` の他のディレクトリが**決着した設計や経緯の記録**であるのに対し、ここは**これから作るもの**を置く。
着手して完了したら、そのPBIには「完了」と結果を追記して残す（消さない。なぜそう作ったかの経緯になるため）。

## 書き方

1ファイル1PBI。ファイル名は `PBI-<番号>-<英語スラッグ>.md`。中身は次の順:

| 節 | 中身 |
|---|---|
| **なぜやるか** | 背景と目的。この作業をしない場合に何が困るか |
| **ユーザーストーリー** | 誰が・何をしたくて・その結果どうなるか |
| **スコープ** | やること／**やらないこと**（ここを書かないと膨らむ） |
| **受け入れ条件** | **判定可能な形で**書く。「使いやすいこと」のような主観は禁止 |
| **設計メモ** | 実装者が迷う分岐と、その決着。既存コードのどこを触るか |
| **参考資料** | 設計・リサーチへの導線。**実装者がここだけ見れば着手できる状態にする** |
| **依存** | 先に終わっている必要があるPBI |
| **見積り** | 人日。根拠も添える |

## この3本の位置づけ（重要）

`docs/web-uiux-experiment/` で作った3案のうち **A（親指ひとつ）と B（一本の欄）を実装する**。
ただし現行の「日報」を捨てるのではなく、**3つの面を切り替えられる状態**にして実地で比べる。

> ⚠️ **これは恒久構成ではなく実験である。**
> 読者1人のプロダクトで3つの面を維持し続けるのは、単純に保守が3倍になる。
> `web/DESIGN.md` の原則も面ごとに解釈が割れていく。
> だから **PBI-01 の受け入れ条件に「観測期間と、1本に絞る判断のやり方」を含めている。**
> 実験は始め方より**終わらせ方**を先に決めておかないと、ただの負債になる。
