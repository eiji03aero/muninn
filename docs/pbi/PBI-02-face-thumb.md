# PBI-02 — 面「親指ひとつ」を実装する

状態: **未着手** ／ 依存: **PBI-01** ／ 見積り: **4〜5人日**

---

## なぜやるか

現行の面は、押すたびに親指を「どこへ動かすか」の判断を要求している。
Hoober の実地観察（1,333件）では**片手持ちが49%・親指がタップの75%を担う**。
上部の AppBar も下部のタブも、その前提だと**毎回のコストを取り続ける配置**になっている。

この面は「**操作の場所を探す**」というコストを消しにいく。
画面の上7割から操作要素を1つ残らず追い出し、操作を**左下の一点＝原点**に集約する。
Samsung One UI の「見る領域／操作する領域」の恒常分離を、一時的な呼び出し（Reachability）ではなく
構造として最後まで押し切ったかたち。

そして**想起がこの面の主役**になる。muninn で最も回数を重ねる操作だからだ。
原点を叩くと答えが出て、**原点が2つに割れる**（左＝あやしい／右＝わかった）。
指は原点から一歩も動かない。

## ユーザーストーリー

> 読者として、**片手で、親指を大きく動かさずに**今日の再読を何枚もさばきたい。
> 寝る前にベッドで、持ち替えずに終わらせたいからだ。
> そして**上半分は読むことに専念できて**いてほしい。

## スコープ

### やること
- 面「親指ひとつ」の全体（4ジョブすべてが成立すること）
- 原点（単一の操作点）と、そこからの方向による移動
- 帯（候補を選ぶリール）と覗き窓
- 想起の判定を原点で完結させる（めくる → 割れる → 判定 → 取り消し）
- 利き手の左右入れ替え（この面固有の設定）

### やらないこと
- 面の切り替え機構と設定画面（→ PBI-01）
- データ層・被リンク計算・影SRS・伝票（`lib/` の共有分をそのまま使う。**作り直さない**）
- 面Bとの見た目の統一（**揃えないのが目的**）
- 触覚フィードバック（**iOS Safari に Vibration API が無い**。確信は視覚と即時性で作る）

## 受け入れ条件

### 構造（この面の主張そのもの）
1. **画面の上7割に操作要素が1つも無い**（読むためだけの領域）。上部のバーも戻るボタンも無い
2. 操作は下部に集約され、**主要な操作要素はすべて画面下端から250px以内**にある
3. 原点は**常時可視**。「そこが操作の全て」だと一目で分かる
4. 原点からの方向と行き先の対応が**画面をまたいで固定**されている（同じ方向は常に同じ行き先）

### 忘れても使えること ★この面の最大の弱点への手当て
5. 方向を忘れても、**目で見て選べる経路が必ずある**（原点を押し続けると扇が可視表示される等）
6. 隠しジェスチャだけでしか到達できない機能が**ゼロ**
7. 常設の凡例（どの方向が何か）が画面に出ている

### 想起（この面の主役）
8. 問い → 原点を叩く → 答えが出る → **原点が2つに割れて左右で判定**、まで**指が原点から離れずに**完走できる
9. 判定の直後に**取り消し**が出る。時間で消える場合でも、消えたあと取り消す手段が別に残っている
10. 判定は取り消し不能な1ジェスチャでは確定しない（2アクション以上、または猶予がある）
11. 今日の枚数は**閉じた集合**として示す（「1/5枚目」等）。**59という総量は画面に出さない**

### 4つのジョブ
12. **めくる**: 起動＝今日の面。今日読むものが差し出されている
13. **見渡す**: 在庫を俯瞰でき、1テーマに降りられる。**ゴルフが約半分という偏りが見て分かる**
    （均等に並べない。偏りは事実であり、消したら嘘になる）
14. **当てる**: 検索して記事に着地できる。入力欄は親指帯、**結果はソフトキーボードに隠れない位置**に出す
15. **頼む**: Claude への依頼を作り、伝票に溜め、クリップボードへ写せる。
    ゼロヒットは「ありません」で終わらせず、**依頼への入口に変換する**
16. すべての詳細画面に「**ここへ来る道**」（被リンク）があり、**リンク元が書いた理由ごと**読める。行き止まりがゼロ

### 越えてはいけない線（`RESEARCH-DIGEST.md` §B）
17. タップ標的は44×44px以上。密集する箇所は48px
18. **画面左端20pxからの横ドラッグを自前ジェスチャに使わない**（iOSの戻ると衝突）。
    画面最下端の数px〜十数pxも同様（ホームインジケータ）
19. `backdrop-filter` を縦スクロールするカード全部に付けない
20. `prefers-reduced-motion: reduce` で動きが無くなる（完成形が即座に出る）
21. 入力欄の `font-size` は16px以上。IMEの変換確定Enterを誤処理しない（`isComposing` を見る）
22. アニメーションは `transform` と `opacity` のみ

### アクセシビリティ ★モックで一度落とした箇所
23. **原点が支援技術から到達できる**。`<button>`（または `role` と `tabindex` を持つ要素）であり、
    `aria-label` に**現在の意味**が入っている（「めくる」「わかった／あやしいを選ぶ」等）
24. 原点が2つに割れている状態では、**左右がそれぞれ独立したボタン**として公開されている
25. 帯で今どれを選んでいるかが読み上げで分かる

> モックの初版はここを落としていた（この面の主役である原点が、アクセシビリティツリーに存在しなかった）。
> **「隠しジェスチャではない」という主張の根拠がここにある**ので、最優先で担保すること。

### その他
26. 利き手の左右入れ替えができ、設定が永続化される
27. `lib/` の localStorage キーを共有している（PBI-01 の受け入れ条件8）

## 設計メモ

### 原点をどう作るか

`Pointer Events` で統一する（`touch`/`mouse` を個別に扱わない）。
ドラッグ中は `setPointerCapture` でポインタが要素外に出ても追跡を続ける。
`touch-action` は軸を分ける——縦スクロールを殺さずに、原点の上でだけ方向ドラッグを取る。

扇の配置は CSS の二重回転が定石:
```css
transform: rotate(θ) translate(r) rotate(-θ);  /* 配置だけ回して中身は正立させる */
```

### 項目数の上限

**扇の項目は最大でも6〜8**。それを超えるとウェッジが狭くなり、パイメニューの優位（Callahan et al. 1988 で
リニアメニューより約15%速い・p<0.01）が消える。主要動線は**最大4**に絞ること。
階層を深くすると熟練者でも性能が頭打ちになる（Kurtenbach & Buxton）。**1階層で終わらせる。**

### この面が抱える構造的リスク（正直に書いておく）

マーキングメニューの優位は**反復頻度**が支える。muninn は1日数分の低頻度利用なので、
**方向の記憶が育つ前に忘れる**可能性が現実にある。育たなければ毎回「押しっぱなし→扇を見る→選ぶ」となり、
**タブ4つより1手遅くなる**。

受け入れ条件5〜7（忘れても使える）は、その自覚に対する保険である。**ここを削ってはいけない。**
実地で使ってみて「毎回扇を見ている」なら、それがこの面の答え（＝負け）だと判断してよい。

### モックからの移植

モックは**素のDOM操作**で書かれている。React へ移すとき、原点と帯は
**再レンダリングを挟まずに直接触る**（`useRef` でノードを掴む）ほうが確実に速い。
状態は面のルートに閉じ、`lib/` へは触りにいかない。

操作領域の寸法はモックでは CSS 変数1つ（`--ops`）から原点・帯・覗き窓・扇の幾何をすべて算出している。
**この構造を維持すること。** safe-area の実測値に合わせて1行変えれば全部が追従する。
