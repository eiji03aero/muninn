# PBI-03 — 面「一本の欄」を実装する

状態: **完了**（2026-08-01）／ 依存: **PBI-01** ／ 見積り: **3〜5人日**

> 実際どう作ったか・積み残しは末尾の「実装記録」を参照。

---

## なぜやるか

現行の面は4つのタブで「いまどの目的か」を先に宣言させている。だが muninn の4つのジョブは**同格の目的地ではない**。
タブは「同格の行き先が4つある」ことの表明にすぎず、そこに嘘がある。

この面は**「画面」という単位ごと捨てる**。あるのは一枚の面と、下に常駐する一本の欄だけ。
**面の中身は、欄の中身だけで決まる。**

原型は Notational Velocity（2005）——検索欄がそのまま作成欄で、
ユーザーは「これから検索するのか、作るのか」という**メタな決定を先にしなくていい**。
その先祖は Jef Raskin の Canon Cat（1987）の LEAP キーで、
Raskin が最も戒めた「モード」を消すための設計そのものだ。

そして muninn は、その条件を偶然すべて満たしている——**読み手はひとり、全データが200ノードでメモリ上にあり、書き込みが存在しない。**

決め手は最後の一手。NV の「見つからなければ、そのまま作る」を、読み専用という制約下で
**「見つからなければ、そのまま Claude への依頼になる」**へ翻訳できる。
**muninn に無かったという事実そのものが、次の蓄積の入口になる。**

## ユーザーストーリー

> 読者として、**何かを思い出したいとき、いきなり打ち始めたい**。
> どのタブに行けばいいかを先に決めるのが面倒だからだ。
> そして**打って見つからなかったときに、そこで終わりたくない**——
> 「無かった」ことが、そのまま Claude への依頼になってほしい。

## スコープ

### やること
- 面「一本の欄」の全体（4ジョブすべてが成立すること）
- 常駐する入力欄と、その中身で決まる面の状態遷移
- 全concern横断のインクリメンタル絞り込み
- ゼロヒットから依頼への変換
- 想起カードを「打たない状態」の既定コンテンツとして出す

### やらないこと
- 面の切り替え機構と設定画面（→ PBI-01）
- データ層・被リンク計算・影SRS・伝票（`lib/` の共有分をそのまま使う。**作り直さない**）
- 面Aとの見た目の統一（**揃えないのが目的**）
- 専用の検索インデックス（200ノードなら総当たりで数ms。**過剰設計しない**）

## 受け入れ条件

### 構造（この面の主張そのもの）
1. **タブが無い。** 4つのジョブが「別のページ」として存在しない
2. 入力欄が画面下部に**常駐**している
3. **欄を空にすると必ず元の面（今日差し出されるもの）に戻る**
   — 押している間だけのモード（quasimode）であり、トグル型のモードを作らない
4. 面の並びに**法則がひとつだけ**あり、それが全状態で貫かれている
   （例:「欄に近いものほど強い」＝結果も今日の紙面も欄の真上から上へ積む）

### 打たない状態 ★この面の生死を分ける
5. **欄が空のときの面が、この面で一番豊かである**。スクロールするだけで一日ぶんの読み物が成立する
6. 空の状態に少なくとも次が含まれる: 想起カード／今日の一本／定点の推移／連載のつづき／在庫への入口
7. **起動直後に自動でキーボードが出る前提の設計にしない**（iOSでは JS からの `focus()` が効かないことが多い）。
   キーボードが出なくても空欄の面だけで完結する
8. 前回の入力が残った状態で起動しない（**主役である空欄の面が初見で見られなくなる**）

### 打っている状態
9. 打つそばから全concern横断で絞り込まれる（記事・定点・人・章・記録・束）
10. **ソフトキーボードに隠れる場所に何も置かない**。結果は隠れない位置に出る
11. 入力欄の `font-size` は16px以上（iOSの自動ズーム防止）
12. IMEの変換確定Enterを送信/実行として誤処理しない（`isComposing` と `keyCode 229` の両方を見る）
13. `visualViewport` の `resize`/`scroll` を購読し、キーボード表示時も欄が追従する
    （`window.innerHeight` は変化しない。**ここがこの面の生命線**）

### モードの可視化 ★人間工学からの指摘
14. **いまどの状態か（空／絞り込み中／束ねている／依頼／ゼロヒット）が、
    色・記号・文言のうち2チャネル以上で常時見えている**
    → テキストの有無だけで状態が変わる暗黙のモードは、Raskin が言うモードエラーの典型になる
15. 使える記号や書き方の**ヒントが常時画面に出ている**（隠しコマンドにしない。使いながら覚えられる形）

### ゼロヒット ★この面の核
16. 結果がゼロのとき「ありません」で終わらせず、**Claude への依頼に変換される**
17. ゼロヒットの面に、少なくとも「近いもの（あいまい一致）」と「ここから先は muninn の外＝依頼の選択肢」が出る
18. 依頼はクリップボードへ写せ、伝票にも溜められる

### 想起
19. 想起カードが**モード切替なしで**空欄の面に流れてくる（クイズ画面に入るという操作が無い）
20. 問い → めくる → 判定 まで到達でき、判定は画面に反映される
21. **判定の取り消しがある**。トーストが消えたあとも取り消せる手段が残っている
22. **59という総量を画面に出さない**。出してよいのは「今週N件 再読した」型の**増える**カウンタだけ

### 4つのジョブと行き止まり
23. 見渡す（在庫の俯瞰）ができ、**ゴルフが約半分という偏りが見て分かる**
24. すべての詳細画面に「**ここへ来る道**」（被リンク）があり、**リンク元が書いた理由ごと**読める。行き止まりがゼロ
25. 本文中のリンクを、**遷移せずに理由ごと覗ける**

### 越えてはいけない線（`RESEARCH-DIGEST.md` §B）
26. タップ標的は44×44px以上
27. `backdrop-filter` を縦スクロールするカード全部に付けない
28. `prefers-reduced-motion: reduce` で動きが無くなる
29. アニメーションは `transform` と `opacity` のみ。反応は100ms以内
30. `lib/` の localStorage キーを共有している（PBI-01 の受け入れ条件8）

### 戻る
31. **iOS の PWA standalone にはブラウザの戻るが無い**ので、深いところへ入ったときに戻る手段を自前で持つ
    （欄を消せば戻る、という法則で足りるならそれでよい。ただし詳細を開いた状態からの復帰は要確認）

## 設計メモ

### 状態機械

欄の中身から面の状態を決める。**分岐は少なく、法則はひとつ。**

```
空            → 今日差し出されるもの（想起・今日の一本・定点・連載・在庫）
文字          → 全concern横断の絞り込み
記号で始まる  → 別の意味（例: # で在庫を束ねる、> で依頼）
文字＋ゼロヒット → 「ここから先は muninn の外」＝依頼への変換
```

記号の割り当ては実装者が決めてよいが、**ヒントを常時出す**こと（受け入れ条件15）。
コマンド駆動UIの最大の弱点は発見可能性で、隠した瞬間に使われなくなる。

### 検索の実装

**専用インデックスを作らない。** 全データは復号済みでメモリ上にあり、200ノード規模なら
素の総当たりで数ms〜十数ms。`lib/graph.js` の `nodes` をそのまま舐めればよい。
debounce も体感上は不要（入れるなら連続入力時の再描画コストへの保険として）。

### 「上へ積む」という賭け

この面は「欄に近いほど強い」＝**重要度の軸を下向き**にする。
結果として「一番強いもの＝親指のいちばん近く＝ソフトキーボードの直上」が構造的に保証される。

ただし**スクロール位置が下端に固定されるのはチャットやターミナルの文法であって、読み物の文法ではない。**
実地で使って「毎回いちばん上を見失う」と感じるなら、それがこの面の答え（＝負け）だと判断してよい。
オンボーディング1枚で足りるかどうかは、この面が抱える唯一にして最大の賭けである。

### 想起の判定をどう取るか（要判断）

現行実装は「2択＋**一言を書いたか**」で q を 5/4/2 に分岐させている。
**一言を書く行為そのものが定着に効く**（能動的な再構成）ので、これは意味のある仕組みだ。

一方この面は「一本の欄」を主張するので、カードの中に第二の入力欄を置くと骨格が崩れる。
モックでは**自由記述を捨てて「粘った時間」から推定**する形にした（`b-rationale.md` の弱点7）。

**実装時に決めること**: 一言を残すか、粘った時間で代替するか。
残すなら「欄は一本」の主張をどう保つか（例: 判定のときだけ**下の欄そのものが一言の入力欄になる**——
これなら欄は増えない）。**この案を推す**が、実装者の判断でよい。決めたら `DESIGN.md` §6 に反映すること。

## 実装記録（2026-08-01）

### ファイル構成

`web/src/faces/field/` の4ファイル＋CSS。Chakra は使っていない（面のチャンクは JS 39KB / CSS 19KB）。

| ファイル | 役目 |
|---|---|
| `items.js` | `graph.nodes` に「欄から引くための顔」（見出し・添え書き・干し草）を付けた項目空間。総当たり絞り込み・ゼロヒット時の2-gram近傍・見出しの整形（束の和名拾い・`## Links` 節の除去） |
| `views.jsx` | 空欄の面／絞り込み／束ねる／頼む／使い方 の組み立て |
| `detail.jsx` | 記事・定点・人・章・記録・束・観測の詳細と「ここから出ていく道」（理由つき） |
| `index.jsx` | 欄の状態機械・入力（IME・visualViewport）・想起カード・覗き窓／道・伝票・トースト・最初の1枚 |
| `field.css` | 全ルールを `[data-face="field"]` 配下に閉じた。`backdrop-filter` は0箇所 |

`lib/recall.js` に2つだけ足した（面から localStorage を直接いじらないため）:
`undoVerdict(slug, prevShadow)` と `restorePending(list)`。

### 欄の状態機械

**面の状態は欄の中身だけで決まる。** 分岐は7つで、法則はひとつ。

```
こたえ  → めくった直後（下の欄が「一言」の欄になる）※最優先
? 　　  → 使い方
# 　　  → 在庫を束ねて見る（#ゴルフ で単一タグに絞れたら中身へ降りる）
> 　　  → 依頼と伝票
文字    → 全concern横断の絞り込み（ヒット>0）
文字    → ゼロヒット＝依頼への変換（近いもの＋4つのひな形＋依頼行）
空+足跡 → 直前に開いていた詳細
空      → きょう差し出されるもの
```

**並びの法則は「欄に近いものほど強い」の一本だけ。**
これをコメントではなくデータ構造で保証した——`views.jsx` の各ビューは**常に「欄に近い順」の配列**を返し、
描画側が `reverse()` して上へ積む。配列の index 0 が必ず画面のいちばん下＝ソフトキーボードの直上になる。
選択順（↑↓）も同じ配列の順なので、DOM座標を測る必要がない。

### 受け入れ条件31項目の達成状況

**満たした: 30／条件付きで満たした: 1（3番）／未達: 0**

- **1〜2, 4**: タブなし・欄は常駐・法則ひとつ（上記）。
- **3**: **解釈を1つ入れた。** 欄を空にすると「打つ前に見ていた面」に戻る——ホームからならホーム、
  詳細を開いた状態からならその詳細。条件文の括弧は「今日差し出されるもの」だが、
  quasimode の要件（トグル型のモードを作らない／消せば必ず元に戻る）は満たしている。モックも同じ挙動。
- **5〜6**: 空欄の面に 想起カード／きょうの一本／定点のうごき（良い方に動いた一本＋宣言に反したもの）／
  連載のつづき／ゆうべの続き／たな（記録帖・束・見わたす）を積んだ。
- **7**: 起動時に `focus()` しない。PC の実キーボードで打鍵したときだけ欄へ入れる。
- **8**: `pageshow` でも欄と足跡を空に戻す。実機相当の再読込で空欄から始まることを確認済み。
- **9**: 記事・章・人・観測・記録・定点・連載・記録帖・束を横断（`graph.nodes` 総当たり）。
- **10, 13**: `visualViewport` の resize/scroll を購読して面の高さ（`--mn-field-vh`）そのものを合わせる。
  ブラウザで `--mn-field-vh = 844px` かつ面の実高さ 844px になることを確認。隠れる場所には何も置かない。
- **11**: 欄は17px（実測）。 **12**: `isComposing` ＋ `keyCode 229` ＋ composition イベントの三重。
- **14**: 色（アクセント6色）・記号（キャレット `› ! ≡ » i …`）・文言（右端の状態語）の**3チャネル**。
  記号は打った記号の複写にしない（`> >量子…` と二重に見えるため）。
- **15**: `# 束ねる / > 頼む / ? 使い方` を欄の真上に常時表示。`?` に全一覧。
- **16〜18**: ゼロヒットは「近いもの（2-gram）」＋「ここから先は muninn の外」＋4つのひな形＋
  依頼行（強調）。依頼はコピーと伝票（`mn.slips`）の両方へ。伝票は `slipsPrompt` で答え合わせごと1回で渡せる。
- **19〜20**: 想起カードは空欄の面に流れてくる（クイズ画面が無い）。問い→めくる→判定まで画面内で完結。
- **21**: トーストの「↺ 取り消す」（残り猶予が帯で減る）＋**トーストが消えてもカード内に居座る取り消し帯**。
  巻き戻しは `lib/recall.js` の `undoVerdict`（影SRS・伝票・履歴の3つを戻す）。
- **22**: 総量は出さない。出るのは「今週N件 再読した」と在庫数（記事93等＝増える側）だけ。
- **23**: `#` の棒でゴルフ51／サッカー19／肌11…と**偏りが一目で分かる**。
- **24〜25**: 全詳細の下端に「ここへ来る道 N」を常設（0件なら「道をつくるよう頼む」）。
  理由ごと読める（「『これは統一原理の「腕（半径）側の基準」を保つ具体策』と書いてこちらを指している」）。
  本文中の `[[リンク]]`・「出ていく道」・順路の各段は、**遷移せず欄の真上に覗き窓が生える**。
- **26**: 44px以上。ヒント帯の「面のかたち」だけは帯が26pxなので、見た目は小さい札のまま
  当たり判定を上下へ食み出させて44pxにしてある。
- **27**: `backdrop-filter` は0箇所。 **28〜29**: 動きは `ff-in`（100ms・opacity/transform）と
  トーストの帯（transform）のみ。`prefers-reduced-motion: reduce` で両方消える。
- **30**: 新設した localStorage キーは `mn.face.field.intro`（最初の1枚を見たか）**1つだけ**。
  想起・伝票・読了は `lib/recall.js` の共有キーをそのまま使い、面ごとの枝を生やしていない。
- **31**: `◀` が「覗き窓 → こたえ → 欄 → 足跡」の順に1つずつ戻す。Esc も同じ。

### 想起の判定 —— 一言を残した

PBI が推していた**「判定のときだけ下の欄そのものが一言の入力欄になる」**案を採った。決め手は2つ。

1. 一言を書く行為そのものが定着に効く（能動的な再構成）。「一本の欄」を守るためだけに、
   既存実装が持っていた良さを手放す理由が無い。
2. 共有の `lib/recall.js` は `verdictToQ(ok, wroteNote)` で q を 5/4/2 に決めている。
   モックの「粘った時間」で代替すると q を外から注入する必要があり、
   **面ごとに SRS の解釈が食い違う入口**を作ってしまう（`web/DESIGN.md` の「数字の解釈は面で変えない」に反する）。

暗黙のモードにならないよう、色（琥珀）・記号（`…`）・文言（こたえを書いている）・
プレースホルダ（思い出したことを一言）の4つで示し、`◀`／`✕` でいつでも降りられるようにした。
判定中は Enter を無効にしている（変換確定と紛れるため）。

### モックと変えた判断

| 変えたこと | 理由 |
|---|---|
| 「粘った時間」→「一言」 | 上記。判定の情報量と共有ライブラリとの整合 |
| 状態の記号を打鍵記号の複写にしない | `> >量子コンピュータ` と二重に見えてバグに読める |
| 束の見出しを和名側から拾う | `Golf — ゴルフのMOC` が札に「Golf」と出ていた |
| きょうの一本が定点の段と衝突したら復刻へ落とす | 同じ日に同じ札が2枚並んで面が痩せて見えた |
| 「きょうの3枚」を最初に引いた3枚で固定 | 判定すると影SRSが動いてキューから外れ、進捗の点が永久に埋まらない |

### 積み残し・次に触る人への申し送り

1. **「上へ積む」は実機で使ってみないと勝敗が分からない。** これはこの面の唯一にして最大の賭けで、
   実装では変えていない。「毎回いちばん上を見失う」と感じたらこの面の骨格ごと作り直す判断になる。
   最初の1枚（`mn.face.field.intro`）で先に法則を伝える対策だけ入れてある。
2. **iOS 実機での `visualViewport` 追従は未検証。** ブラウザでは `--mn-field-vh` が効くところまで確認したが、
   ソフトキーボードの実挙動（`interactive-widget` 既定値との噛み合わせ、`index.html` の viewport meta）は
   シミュレータで見ておきたい。`web/index.html` の viewport meta には `interactive-widget=resizes-content` を
   足していない（shell と他の面に影響するため。必要なら PBI-01 側の話として起こす）。
3. **こたえの欄はモードである。** カードをめくった直後に「検索しようとして一言欄に打ってしまう」経路は残っている。
   4チャネルで示してはいるが、実運用で事故るなら「一言は書かない（q は 4/2 の2段）」に落とすのが素直な後退案。
4. **`>` の依頼は素の `/mn <打った文字>` で、文脈が薄い。** 詳細から頼むときだけ
   「〈対象〉を読んでいて出た問い:」が付く。実運用の依頼ログを見て、ひな形4つを増減させる前提。
5. **順路（アトラスの `routes`）を面から辿る導線が弱い。** 連載のつづきと詳細内の順路一覧はあるが、
   ルートの切り替え（歴史でたどる／分野でたどる）はまだ出していない。
6. **束（MOC のセクション）を単体で見る面が無い。** `graph.bundles` は使っておらず、束は MOC 詳細の中だけ。
7. `web/DESIGN.md` は触っていない（3面構成の思想は PBI-01 が記録済み。この面固有の判断は本ファイルに残した）。
