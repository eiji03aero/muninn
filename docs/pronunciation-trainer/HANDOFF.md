## 0. このドキュメントの位置づけ

「アメリカ英語の発音を上達させたい」という相談から、**練習の管理と成果の評価を行うアプリ**を作る話に発展した。
その会話で出た結論・判断・そして**判断の根拠**をここに固める。

置き場が muninn なのは、単に**リポジトリを跨いで運ぶための伝送路として一番手軽だから**であって、
muninn の作業項目ではない。新リポジトリを立てたら、このファイルをそちらの `docs/` にコピーして、
以後はそちらを正本にしてよい。

**このファイルだけ読めば着手できる**状態を目指している。読む順は 1 → 5 → 7。
急ぐなら §5（できないこと）と §6（設計上の決定）だけでも読むこと。ここが一番失われやすい情報だから。

## 1. 背景 — 誰のための何か

ユーザーは日本語母語話者で、**仕事で使う程度には英語を話す**。文法や語彙ではなく発音が課題。
本人の自己申告は「もともと口数が多くないのもあって、綺麗に発音できない筋肉っぽい」。

この自己診断はかなり正確で、後述の「調音のベースポジション」の問題を指している。

目標は**ネイティブ同一ではなく「訛りはあるが聞き手に負荷をかけない」**水準。
ここを取り違えると、アプリの評価設計まで狂う（ネイティブとの絶対距離を測る設計にしてしまう）。

## 2. 学習設計 — アプリが支援する対象

アプリの機能を決める前に、**何を練習するのか**が確定していないと機能が決まらない。ここが土台。

### 2.1 診断の3層

日本語話者の「なんか綺麗に聞こえない」の原因は3層に分かれる。**下の層ほど効くが、下の層ほど自覚しにくい**。

| 層 | 内容 | 自覚しやすさ | 効き |
|---|---|---|---|
| 1 | 個別の音素（R/L, θ, æ …） | 高い | **低い** |
| 2 | 調音のベースポジション（oral posture） | 低い | 高い |
| 3 | リズムと母音の弱化（強勢拍 vs モーラ拍） | 最も低い | **最も高い** |

仕事で通じるレベルまで話せている人に残っている違和感の大半は **2と3**。
層1を磨いても頭打ちになる。

**重要な補足**: 層2と層3は独立ではない。英語の母音の弱化（schwa化）とは、
口の構えが「脱力した中間位置」に戻ることそのものなので、
**oral posture を直すと弱化が自然に出て、リズムも直る**。ここが最大のレバレッジ。

### 2.2 フェーズ

| Phase | 内容 | 期間目安 |
|---|---|---|
| **0** | ベースライン録音。標準朗読文（"Comma Gets a Cure" が診断用に設計されていて優秀）＋**自由発話1〜2分** | 1日 |
| **1** | 口の構えを作り直す。顎の開き・舌の後退と奥の盛り上がり・唇の丸め。誇張発音＋鏡＋毎日10分の音読 | 2〜4週 |
| **2** | 母音システム。`/ə/`（最優先）→ `/ɪ/ vs /iː/`、`/æ vs ʌ vs ɑ/` → `/ɜr/` → `/eɪ/ /oʊ/` を二重母音として | 4〜8週 |
| **3** | 子音の急所。**dark L**（語末L、見落とされがちだが訛り信号が強い）、`/r/`、flap T / glottal T、`/v vs b/`、`/θ ð/`、`/s vs ʃ/`、語末 `/n ŋ/` | Phase 2 と並行可 |
| **4** | リズムと連結。語強勢・文強勢、**母音の弱化**、リンキング・脱落・同化、thought group と抑揚 | 8週〜 |
| **5** | 自発発話への転移。練習では出るのに会話で戻る問題への対処 | 継続 |

Phase 0 で**自由発話を必ず録る**こと。朗読だけだと本番で崩れる部分が見えない。

### 2.3 練習法（効果順）

1. **知覚訓練を産出訓練より先に置く**。聞き分けられない音は正確に産出できない（自分の誤りをモニターできないため）。
   ミニマルペアの聞き分けを **複数話者の音声で**やる（HVPT: high-variability phonetic training）。
   1人の声だけで訓練すると汎化しない。地味だが研究的裏付けが最も厚い。
2. **録音して自分で聞く**。頭の中で聞こえている自分の声と実際に出ている音は別物。これなしで進歩する人はいない。
3. **シャドーイングは「短く・多回」**。10〜30秒の同じクリップを、スクリプトあり→なしで何十回も。
   長い素材を1回流すのはリスニング練習であって発音練習ではない。
4. **モデル話者を1人に絞る**。「アメリカ英語」は真似られない。声質の近い**特定の人**をコピーする。
5. **Praat でスペクトログラム／ピッチ曲線を見る**。感覚に頼らず定量的に詰められる。
6. **IPA を覚える**。「なんとなく違う」が「/æ/ が /a/ になってる」に変わる。投資30分、リターン大。

### 2.4 日々の運用

1日15〜20分で回る。配分の目安 —— 調音ウォームアップ3分 / 知覚訓練5分 / シャドーイング7分 / 自由モノローグ録音5分。

**「口数が少ない」問題への対処**: 会話相手を確保しようとしない。音読と独り言モノローグで運動記憶は作れる。
まずソロで量を稼ぎ、会話は転移の確認に使う。**これはアプリ設計にも効く**——
アプリは「1人で完結する練習」を支える前提でよく、対人機能・マッチング機能は不要。

## 3. アプリの要件

### 3.1 練習の管理（技術的論点なし）

課題リスト、フェーズ進行、ストリーク、SRS的な再出題、録音の履歴管理。すべてただの CRUD。
難しいのは技術ではなく設計（**何を管理すると続くか**）だけ。

### 3.2 成果の評価（ここが本体）

評価手段を階層で持つ。上から順に軽い。

#### A. 音響特徴の直接計測（自前・軽い）
- **ピッチ（F0）抽出**: YIN / pYIN で可能。ブラウザ内リアルタイムも可。
  **お手本と自分のピッチ曲線を DTW で時間伸縮して重ねる**のは、実装が軽い割に効果が劇的。抑揚のズレが一目で分かる。**最優先で作る価値がある。**
- **フォルマント（F1/F2）**: LPC 分析で取得可。自分の母音空間を母音四辺形にプロットできる。
  ⚠️ **話者内正規化（Lobanov 等）が必須**。声道長が違うのでネイティブと生の数値を比較しても意味がない。
- **発話速度・ポーズ位置・音量エンベロープ**: 簡単。リズムの粗い指標になる。

#### B. 強制アライメント（サーバー側・中）
課題文が既知なら音声と音素列を時間対応づけできる（MFA / WhisperX / Charsiu）。
**音素ごとの継続長**が取れるので、「機能語の母音がちゃんと短くなっているか＝弱化できているか」を定量化できる。
**Phase 4 の評価はこれが本命**。Python サーバーが要る。

#### C. 音素認識ベースの誤り検出（サーバー側・中）
wav2vec2 の音素出力モデルや Allosaurus で認識音素列を出し、期待音素列と編集距離でアラインして差分を列挙。
「`/θ/` が `/s/` と認識された」のような**具体的な誤りリスト**が出せる。実装しやすさの割にフィードバックの質が高い。
⚠️ モデル自体が訛りに引っ張られるので偽陽性は出る。

#### D. 商用 API（一番現実的）
**Azure Speech の Pronunciation Assessment** が実質デファクト。
accuracy / fluency / completeness / prosody のスコアと、**音素レベルのスコア**まで返る。Speechace API も同種。
個人利用なら費用は誤差レベルのはずだが、**現行の料金体系と API サーフェスは着手時に要確認**（この資料は 2026-08 時点の理解）。

#### E. LLM に音声を直接聞かせる
定性的な所見は出る。ただし**「計測」には使えない**。音素レベルの精密な判定は苦手。
**「コーチのコメント」枠として使い、数値は別系統で取る**という分離を必ず守ること。
ここを混ぜると信用できないアプリになる。

## 4. 天井 — できないこと

**この節がこの資料で最も価値がある。** 楽観的に着手して溶かす時間を防ぐため。

1. **「なぜダメか」の特定ができない。**
   スコアは出せても、舌が前すぎるのか唇の丸めが足りないのかは音響からは一意に決まらない（**調音の逆問題**）。
   ここは人間のコーチか、自分で仮説を立てて試すしかない。アプリで解こうとしないこと。
2. **自由発話は評価できない。**
   スクリプトがないと強制アライメントが使えず、ASR で書き起こすと**誤認識と発音誤りが分離できない**。
   → **評価は必ず既知の課題文で行う**、が現実解。自由発話は「記録して後で自分で聞く」に留める。
3. **「通じるが不自然」レベルの検出ができない。**
   まさにユーザーが直したい帯域だが、商用 API でも取りこぼす。
4. **絶対評価の閾値が存在しない。**
   「スコア78」が良いのか悪いのか誰も定義できない。

## 5. 設計上の決定（と、その理由）

天井 §4-4 への対処が、そのままこのアプリの設計思想になる。

> ### 決定1: 絶対スコアを諦め、「自分の過去との差分」に振り切る
> 閾値問題が消えるうえ、モチベーション設計としても正しい。
> 「ネイティブとの距離」ではなく「3ヶ月前の自分との距離」を主役にする。
> §1 の目標設定（ネイティブ同一を目指さない）とも整合する。

> ### 決定2: 同じ課題文を定期的に再録音する（定点観測）
> 素材が変わると比較できない。課題文は固定資産として管理する。

> ### 決定3: 表示するスコアは1〜2個に絞る
> 数値を並べるほど信用されなくなる。内部で10個計算してもよいが、画面に出すのは絞る。

> ### 決定4: スコアリングエンジンは借りる。自前で作らない
> 自前で作る価値は**学習体験の設計**の側にある。
> §3.2 の B・C を自作するのは、**D（商用 API）で足りないと判明してから**でよい。

> ### 決定5: 評価は既知の課題文でのみ行う
> §4-2 の帰結。自由発話モードを作るなら、それは「記録専用」と明示し、スコアを出さない。

### プラットフォーム: Web (PWA) + サーバー側解析

| | Web (PWA) | Native |
|---|---|---|
| 録音品質 | 十分（getUserMedia） | 十分 |
| iOS の癖 | AudioContext のユーザー操作必須、フォーマット差異でハマる | なし |
| 通知・リマインダー | iOS はホーム画面追加が必要で脱落しやすい | 強い |
| オンデバイス推論 | WASM + WebGPU で可能になりつつあるが重い | Core ML / ONNX で現実的 |
| 実装コスト | **圧倒的に安い** | 高い |

**録音はブラウザ、重い処理はサーバー**でまず作る。
ネイティブに行く理由は実質「毎日開かせるための通知」だけなので、**続かないと分かってから移ればいい**。

## 6. MVP スコープ

### やること
1. フェーズ別の課題文リスト（§2.2 のフェーズに対応）
2. ブラウザで録音 → サーバーへ送信
3. Azure Pronunciation Assessment に投げ、総合＋音素レベルのスコアを保存
4. **お手本と自分のピッチ曲線を DTW で伸縮して重ねて表示**
5. 同じ課題文の過去録音を時系列で並べる＋聞き比べ
6. スコアの低かった音素を SRS 的に再出題

週末2〜3回で動く想定。

### やらないこと（明示）
- 自由発話のスコアリング（§4-2）
- 調音の指示（「舌をもっと後ろに」等）を自動生成すること（§4-1）
- ネイティブとの絶対距離の表示（決定1）
- 対人機能・共有・ランキング（§2.4 —— ソロで完結する前提）
- ネイティブアプリ化（続くと分かるまで）
- HVPT（知覚訓練）の実装 —— **効果は高いが MVP の外**。産出評価が回ってから足す

## 7. 未決事項（次のセッションで決めること）

1. **リポジトリ名とスタック**。フロントの選定（何も決まっていない）。
2. **Azure Pronunciation Assessment の現行仕様と料金の確認**。prosody スコアの粒度が期待通りか、実際に叩いて確かめる。ここが期待外れなら §3.2 の B/C 自作に倒れるので、**着手直後に検証すべき最大のリスク**。
3. **課題文のソース**。"Comma Gets a Cure" 以外に、フェーズごとの短文をどう用意するか。お手本音声をどこから持ってくるか（権利面含む）。
4. **お手本音声とのピッチ比較で、話者の基本周波数差をどう正規化するか**（男女差・個人差）。対数変換＋話者内 z-score あたりが素直。
5. **DTW の実装**。既製ライブラリで足りるか、ピッチ曲線用に調整が要るか。
6. **muninn への書き戻しの形式**（下記 §8）。手動コピペで始めて、必要なら自動化。

## 8. muninn との連携方針

- アプリ＝**計測装置**、muninn＝**記録と理解**、という分担。
- 成果（スコア・所見）だけをテキストで muninn の `follows/` に **goal 型のフォロー**として流し込む。
- **音声ファイル自体はコミットしない**（muninn の CLAUDE.md のルール。follows は写真・動画をコミットしない）。
  計測値と所見だけをテキストで残す。
- 発音学習の体系的な知識（§2 の中身）は、必要になったら muninn 側で `/mn-learn` のアトラスにするとよい。
  この資料の §2 はその素案としても使える。

## 10. 元の会話を辿りたい場合

この資料の出自は muninn の cloud セッション。会話履歴ごと引き継ぐには、
**muninn のローカルチェックアウトから**:

```bash
claude --teleport session_01KAypag8RpyRuDCSP5Rt5xp
```

※ teleport は**同一リポジトリのチェックアウトからしか実行できない**ため、
新リポジトリ側では使えない。だからこの資料がある。
