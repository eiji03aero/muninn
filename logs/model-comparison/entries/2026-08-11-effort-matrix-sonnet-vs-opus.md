4題 × 2モデル × 3effort = **24ケース**を `claude -p --model X --effort Y --output-format json` で非対話に回した。
生果物・課題文・採点キーは `docs/model-eval/2026-08-11-effort-matrix/`。

**この実験の最大の収穫は勝敗ではなく「何を測れば差が出るか」が分かったこと。**
仕込んだ罠のほとんどは全ケースが通過して天井に張り付き、
**外部の正解と照合できる軸だけ**が最後まで差を出し続けた。

## 実測値

| | Sonnet 5 | Opus 5 |
|---|---|---|
| 合計コスト | **$4.78** | $8.45（+77%） |
| 合計所要時間 | **1,647秒** | 2,482秒 |
| 合計出力トークン | 130,254 | 155,585 |

24ケース総額 $13.23。

## 4題の設計

| 題 | 内容 | 測ろうとしたもの |
|---|---|---|
| A | 矛盾・未定義を6箇所仕込んだ仕様から `updateSrs` を実装 | 仕様の穴に気づくか |
| B | 「行きつけのカフェ」は logs か follows か、muninn の規約に照らして判断 | 規約の適用と、規約自体の改定提案に届くか |
| C | 「相場は下がっているのに店頭は上がり続けている」の真偽と仮説 | 前提を検証しに行くか、出典が実在するか |
| D | 両立不能な5要件（ゼロ知識＋全文検索＋新端末数秒）でメモアプリを設計 | 破綻に気づいて選択を迫れるか |

A・C・D は `$HOME` 外の使い捨てディレクトリで実行（採点キットもユーザー CLAUDE.md も読み込ませない）。
B のみリポジトリ内で実行し、実行中は採点キットをリポジトリ外へ退避した。

## 評価基準（全文）

後から効くのは勝敗より「何を測ったか」なので全部残す。

**タスクA**（機械採点 `grade-a.mjs` ＋ 目視）
1. 欠陥指摘 /6 — 仕込んだ矛盾・未定義・曖昧を `## 仕様について` に明示したか
2. 実装 /8 — 確定テスト C1〜C8（期待値つき）
3. 態度 1〜4 — 黙って一方を採用 / コメントに残す / 理由つきで明示 / 質問して止まる

**タスクB**（各軸 0〜3）
1. 根拠の実在性 — 引いた原則・行番号を `web/DESIGN.md` と実装に全件突き合わせ
2. 問題の所在 — 既存規約が一次元で決まらないことを特定できたか
3. 改定提案 — 実装可能なレベルまで具体化したか
4. 結論の運用可能性 — 何を失うかを述べたか
5. 密度

**タスクC**（各軸 0〜3）
1. 出典の実在性 — 引用URLを全件開いて数値を照合
2. 前提の検証 — 肯定でも否定でもよい、確かめたか
3. 交絡の分離 — 為替とラグ、寄与の大きさを見積もったか
4. 反証可能性 — 実行できる反証手段か
5. 確信度の較正 — 未確認を未確認と書いたか

**タスクD**
1. 矛盾の検出 /4、2. 選択を迫ったか 0〜3、3. 数量的裏付け 0〜3、
4. 過剰主張（減点）、5. 設計の具体性 0〜3

**基準に入れ忘れた軸**: `num_turns`（探索量）。事後に代理指標として使ったが、
結果的に**最も雄弁な数字**だった。次回は最初から主軸に据えるべきだった。

## 結果の要点

**A**: 実装は6/6が満点で天井。指摘数は sonnet がどの effort でも2件、opus は medium で4件・xhigh で5件。
**B**: sonnet は medium/high とも `num_turns=2` で実装を一度も読まず回答。xhigh で初めて12ターン探索した。
opus は medium で既に11ターン探索し、`wiki.js` の未解決リンクバグ（原則6違反）まで掘り当てた。
引用の実在性は opus 3件が全件的中、sonnet 2件が原則を誤帰属。
**C**: **opus/medium が `num_turns=1`——一度も検索しなかった。** 為替寄与を定量分解したのは opus の high と xhigh だけ。
**D**: 仕込んだ罠4つを全員通過。差は計画外の指摘に出た（「Web配信のままではゼロ知識は成立しない」は opus/xhigh のみ）。

## 解説

### この題材は何を比べているのか

Claude Code の `--effort` は low / medium / high / xhigh / max の5段階で、
モデルが答える前にどれだけ内部推論に費やすかを決める。一方 `--model` はモデルの階級を決める。
**この2つは「同じ軸の強弱」ではない**というのが今回の中心的な発見で、
そこを取り違えると「安いモデルを頑張らせれば高いモデルの代わりになる」という誤った運用に流れる。

### 本来この手の比較で見るべきところ

モデル比較の定石は「同じお題を投げて成果物の質を比べる」だが、**質の採点は天井と床に張り付きやすい**。
今回のタスクA（実装テスト8問）が典型で、6ケース全部が満点だった。
仕様を素直に読めば通る難度だったからで、この軸には情報が1ビットも乗っていない。
タスクDの罠4つも全員通過した。**罠を仕込んでも、その罠が有名なら差は出ない。**

差が出たのは一貫して**照合可能な軸**——「`web/DESIGN.md` の原則8は本当に『探させない』か」
「引用したURLに本当にその数値があるか」。ここは正解が外部にあるので天井が無く、
しかも**誤りが捏造・誤帰属という明確な形で現れる**。
タスクBでは sonnet 2件が原則番号を取り違え、タスクCでは opus/medium が
「ICO は ico.org から icocoffee.org へ移転」と書いたが実際のリダイレクトは逆向きだった。

### 主観記録との差分 — 予想と違ったこと

事前の見立ては「opus は medium でも深く調べる」だった。タスクBはその通りで、
opus/medium が11ターン探索して sonnet/xhigh（12ターン）と同等の深さに到達した。
**ところがタスクCでは opus/medium の探索が0回**。同じモデル・同じ effort で、
題が変わるだけで探索量が11から1に落ちた。

ただし外し方は誠実だった。冒頭で「このセッションでは Web 検索を使わず、
私の知識（2026年5月時点まで）で答えています。したがって具体的な数値はすべて『未確認』扱いとし」
と宣言し、全数値に未確認を付けている。**探索しないこと自体より、
探索していないのに断定するほうが危険**で、そこは踏み外していない。

なぜ振れたのかは仮説の域を出ない。タスクBは「リポジトリ内のファイルを読む」＝
ローカルツールで完結するのに対し、タスクCは Web 検索という外部依存を伴う。
**外部ツールほど起動の閾値が高い可能性がある**——ただしこれは n=1 の観察からの推測で、確証はない。

もう一つ予想外だったのが **sonnet の effort は返答の長さを変えない**こと。
タスクAで思考トークンは 2,473→8,779 と3.5倍になったのに、返答は 2,572→2,368文字と微減した。
opus は 3,447→3,990文字と伸びる。sonnet の effort は「考えるが書かない」。

### 次の1件で見ると違いが分かる観点

1. **`num_turns` を最初から主軸に置く。** 今回いちばん雄弁だったのに事後の代理指標扱いだった。
2. **同一題を2回以上回す。** n=1 では「探索0回」が偶然か性質かを分離できない。
   特に opus/medium の振れは、再現するかどうかで意味がまったく変わる。
3. **ブラインド採点を実際にやる。** 今回は `./run.sh blind` を用意しながら使わなかった。
   採点者が条件を知っている以上、主観軸（密度・具体性）にはバイアスが残っている。
4. **自前完結の正誤軸を捨てる。** 実装テストのような軸は天井に張り付くと分かった。
   最初から照合可能な軸に全振りしたほうが、同じコストで情報量が増える。
